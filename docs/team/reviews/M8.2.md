## 4. Decisions and deviations

- **Substitute the first word (not prefix the window's `PATH`)** — same three reasons as the PM side (M8.1): the
  binary that starts is exactly the binary the identity check resolves; no directory such as `~/.bun/bin` is put
  at the front of the window `PATH` where it would shadow same-named `node`/`npm` shims; template mode then has
  the same shape as the built-in Pi branch (absolute path in the command). A first word containing `/`, quotes,
  `$` or `{` is left as written, and an explicit `TEAM_AGENT_BIN` naming a *different* binary leaves the template
  alone — both asserted.
- **An immediate non-zero exit is a hard dispatch failure for adapters only.** The brief asks dispatch to
  distinguish "harness started" from "agent started"; for a custom adapter the template *is* the CLI that must do
  the work, so a fast non-zero exit (127 = command not found, 1/2 = rejected flags) can only mean "it never ran".
  The built-in Pi path keeps the M4.3 B3 contract (a short-lived `TEAM_PI_BIN` is allowed and only warned about),
  because tests and users legitimately point `TEAM_PI_BIN` at a placeholder. Exit **0** is success with an honest
  "finished and exited" line: script-style adapters do that.
- **The failed window is kept, not killed.** The older failure path (no spawn proof) kills the window to avoid a
  half-started scene; here the evidence *is* the CLI's own error on screen, and the PM side made the same call in
  M8.1. The next dispatch replaces the window, and the tool says so.
- **The diagnostic is per agent** (`state/dispatch-<agent>-launch-failed.log` + `…-tail.txt`), unlike the
  single `pm-launch-failed.log`: two workers can fail independently.
- **The harness writes the exit code before capturing the pane** (event semantics first: `TEAM_DISPATCH_ALIVE_SEC`
  must not be spent waiting for a screenshot); the diagnostic waits up to ~1s for that capture and only then
  falls back to a fresh `capture-pane`. The stale-tail hazard is closed by removing the tail file at the start of
  every attempt.
- **`team_agent_pane_tail` mirrors `team_pm_pane_tail`** (bounded retry + `team_pane_tail_normalize`) instead of
  parameterising the PM helper: `team_pm_pane_tail` is M8.1's code and lives in the PM area this brief puts out of
  bounds. The normalizer and the blank-content check *are* shared.
- **No `openspec/**` change** — the brief forbids it. See §6: if the new dispatch contract should be normative,
  the PM owns that delta.
- Nothing else in the brief's boundaries was touched: the PM launch path, the meetings code, the doc-invariant
  scanner and `docs/team/**` (except this report and its evidence directory) are unchanged.

## 5. Known risks / not verified

- **Observation window, by design**: an adapter that dies *after* `TEAM_DISPATCH_ALIVE_SEC` (default 1s) is not
  detected and the dispatch reports "agent is still running". The key is documented as the window; the brief's
  fixture is "exits immediately".
- **No real non-Pi worker CLI run.** The live fixtures are fake CLIs; the real `codex` binary is only checked at
  the rendering level. M3.0's opencode run and M8.1's PM-side codex run are the project's real-CLI evidence, but
  neither exercised *this* failure path.
- **A CLI that dies and then lets the container shell clear the screen**: the harness capture is designed for
  that (bounded retry until non-blank) but no fixture simulates it — flip C shows the source assertion is the
  guard, and the fallback re-capture may still succeed.
- **Windows in the `SCRIPT`/`TMUX_PANE`-less case** (e.g. `dispatch` run outside tmux) cannot capture a pane;
  `team_require_cmd tmux` already makes that path unsupported.
- Fast smoke skips 6j's live half (registered in 14c, so it cannot be skipped silently); the non-live rendering
  assertions run in both modes.
