## 一、判定：NEEDS-CHANGES（一条实体 + 一条小项）

提案在**语言层、页面 schema、声明与探针、版式规则、真源划分**这五件上都超出了我的要求，取舍写得清楚（每条决策都带被否决方案）。但**用户提的第一件事没有落进契约**——所以现在还不能接收。

### F1（必修）：分级菜单没有落地，而这正是用户报的第一件事

用户原话是「`--help` 菜单出来的也很乱，不好看」，我给的硬要求是「第 0 级只给『teamsmith 是什么』＋分组清单＋新手上手 3–5 个命令＋下一级怎么进，**目标 ≤30 行且有夹具断言规模**」。

现提案里（`specs/help-surface/spec.md` 第 3–30 行 + `tasks.md` 1.3）**第 0 级仍然是「每个命令一行、48 个命令全列」**：没有任何规模上界、没有上手命令块、没有 `team help <组>` 这一级。这等于把今天那 98 行换成 130+ 行（表驱动、更整齐，但**没有变短**），用户抱怨的「乱」没被解决。

我理解为什么会这样：Walk A（诚实性走查）今天要求「总览里逐条打印 usage 行」才能把每条用法喂给真解析器，于是总览必须列全部命令；而 design §4 又把「页面 usage 与总览行旗标集合相等」作为 Walk A 的替代覆盖——两者都把命令清单钉在了同一个面。

**修法（这不是选择题，是用户要求的形态）**：
1. **第 0 级（`team` / `team help`）**：`teamsmith 是什么`（2–3 句）＋ 8 个组的**一行一句**＋ 新手上手的 3–5 个命令＋「看某组用 `team help <组>`、看某命令用 `team help <命令>`」；**规模 ≤30 行**，并有一条夹具断言这个上界（超了红）与「第 0 级不必列出每个命令的 usage 行」。
2. **第 1 级（`team help <组>`）**：该组每个命令一行（usage + 一句用途）。**这里才是 usage 行所在的面**。未知组 → exit 2 并点名、指回 `team help`。
3. **第 2 级**：命令页（提案已写好，保留）。
4. **Walk A 的重挂（这是 F1 的必然连带，也是我原要求的「覆盖面扩到每一级的所有页」）**：把「每条 usage 行喂真解析器」的判定从第 0 级移到**第 1 级的组页**（每个组页都是被走查的面），并保持既有强度不许降：非空洞控制臂、承诺探针、既有翻转一条不动；design 里给出**改动前后覆盖的命令数**（今天走查覆盖 1 个面；改后覆盖 N 个组页，命令数与 dispatcher 表里的标签数相等）。
5. 第 1 级的每条 usage 行与第 2 级该命令页的旗标集合仍要求**双向相等**（提案已有这条，把锚点从总览行换成组页行）。

### F3（必修，小）：缺「今天 vs 改后」的逐字节样例

我在任务书里要求 design 给一张目标排版样例（同一命令的今天 vs 改后，逐字节对比），让评审一眼能看出层次。现 design §4 只有规则、没有样例（唯一的代码块是文件布局）。加一个 fenced 样例即可。

### F2（我接受这条偏离，记录在案）

「不把 Walk A 改成逐页解析、而用『页面 usage 与所在面 usage 旗标集合相等』替代」——在**分级之前**我不同意；按 F1 改成三级之后，这条等价关系仍然有用（锚点换到组页行），而且比逐页解析稳。**接受**，但前提是 F1 的第 4 点（走查挂在组页上）成立。

## 二、我核过并接受的部分（不必改）

- **新能力 `help-surface`（ADDED ×6）而不给 `dispatch` 写 MODIFIED**：理由成立（帮助面是产品的一层，有独立读者与独立失效模式）。
- **语言只从环境变量读（`TEAM_LANG`，缺省 `en`）**：理由强——`team help` 是「什么都还没配好」时唯一能用的面（今天不加载配置），语言若只能来自配置就切不了；非法值一行告警点名后回退英文且状态不变；缺键打印含键 id 的标记 + 另一语言回退 + 键集比对非零退出。三条都落进了 delta 与 tasks。
- **13 个必定义概念 + 页内复述**（`pm`/`seat`/`worktree`/`task-branch`/`brief`/`category`/`change`/`spec`/`gate`/`ledger`/`pulse`/`knock`/`yes`）：正是用户「对不懂这个项目的人也要讲清」那条；「定义写进每页独立键会漂移」的否决理由也对。
- **12 节页面 schema**（含 `Reads`/`Writes`/`Side effects`/`Authorization`/`Undo`/`Concepts`/`See also`）：深度标准（读完能答「干什么/什么时候用/读什么写什么/副作用/要不要 `--yes`/能不能撤」）与我的要求一致。
- **数据驱动、不引 CLI 框架**：一份结构表 + 两语言表 + bash/awk 渲染器，npm 依赖仍为空；JSON/heredoc/复用面板 `.ts` 三个替代方案的否决理由都成立。
- **版式**：100 显示格（CJK 2 格）、`TEAM_HELP_WIDTH` 显式覆盖、**不做 TTY 自适应**（逐字节稳定）、列 0 组头、2 格条目、悬挂缩进、宽字符不切断——每条都有夹具（`layout` 组）。
- **声明与探针**（封闭词表 + 注册表 + 逐条红侧）：沿用 §51 的精神而更严，`--flag` 出现在散文而 usage 行没有 → 红，这类判据我特别认可。
- **路由与退出码**：`--help` 先于配置解析、无项目也能用、未知 token exit 2 且不执行任何命令/不写状态（今天是打印全局页 exit 0）——这条行为变化是改进，delta 有专门场景。
- **不变量**：命令名、旗标、退出码、机器出口逐字节不变有专门 requirement 守住。

## 裁定点 3（作者请我裁的取舍）：我采纳作者的推荐

**第 0 级的组清单用紧凑清单**（列 0 的 `Groups` 标题 + 每组一行、缩进 2），而不是「每组一个顶格小节标题加一行说明」。理由：你（用户）的要求是菜单要短、要能一眼看完；30 行上限正是这个结果，而「每组两行 + 空行」加上上手命令就必然超过 30 行。层级本身没有丢：第 0 级仍有一个列 0 的标题，`── Start here ──` 那块也照旧用完整小节形态，组页与命令页照旧按四级缩进渲染。请在 delta 里明确「第 0 级的组清单是清单，不是小节标题序列」这一句，以免实现时又长回小节形态。
