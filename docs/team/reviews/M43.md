## 根因（实证，非推断）

**结论：spool 被外部力量原位截断又写回（两次，间隔 6 秒）；扩展的 `size < offset → offset = 0`
静默重置把整份 spool 从 0 重读了两遍。仓内没有任何路径能让 spool 变小。**

证据链（全部可在主树复核）：

1. **单一监视进程、offset 跟踪原本健康**：`inbox-watch.log` 里 PM 最后一次 `started` 是
   `2026-09-19T15:05:59Z baseline=9447`（9447 = 现存 spool 第 32 行末尾的字节偏移，逐行字节数已对账）。
   此后 10 次真实追加 ↔ 10 次 wake（total=1..10）一一对应——例如第 42 行 epoch `1789837182057`
   = 16:59:42.057Z，wake 于 16:59:42.208Z（+151ms = merge window）。注册文件 `pid=186805` 至今仍活，
   其环境无任何 `TEAM_INBOX_WATCH_*` 覆盖。
2. **两次重放读的就是第 1–42 行**：16:59:43.940 与 16:59:49.945 两行 `wake n=42` 的 `kinds=` 序列
   与现存 spool 前 42 行的 kind 列**逐字节等值**（已用脚本比对：`MATCH`）。total 52→94 被灌水 84；
   16:59:53.430 真实追加（第 43 行）→ 16:59:55.250 `wake n=1 total=95` 恢复正常。
3. **是原位截断+重写，不是整文件替换**：spool inode 的 `btime=2026-09-18 12:48:51.782` 与首行 epoch
   （`1789735731784` = 12:48:51.784Z，文件由首次追加创建）吻合 —— inode 从未被 rename 替换。
4. **仓内写路径只有追加**：全部 scripts/extension 里 `.wake` 的唯一写点是 `outbox.sh:761` 的 `>>`；
   扩展自己的 `trimSpool`（唯一的截断点）需要 size > 128KiB（无 env 覆盖=默认 cap，文件才 13KB），
   且裁剪会永久切掉头部 —— 现存文件 44 行历史完整，证明**裁剪从未发生过**。
5. **没有第二个监视者**：两次 n=42 的 total 连续（52→94→95）= 同一个闭包；15:05:59 与 17:02:22 之间
   账本无任何 pm 的 `started`/`stopped`/`skip` 行（14:57:12 那条孤儿 `started` 进程在 15:31 前已死，
   否则 15:31 起每条追加都会有双份 wake 行）。
6. **旧路径的静默性**：`readNewLines` 的 `size < offset → offset = 0` 不写账本 —— 所以两次重置在
   账本里一个字都没有（这本身就是可审计性缺陷，已修）。

修复的目标因此是：无论谁把 spool 弄小，行为都必须有界、去重、可审计 —— 这正是 brief §3 的要求。

## 修复（`skills/teamsmith/extension/team-inbox-watch.ts`）

投递保真三条（也写进了扩展头注释与 agent-adapters §4a.1）：

1. **shrink 必记账本**：`readNewLines` 不再静默 `offset=0`，改为返回 `shrank` 标志（size<offset 或
   文件在跟踪期间消失都算）；`flush()` 收到标志后先写
   `spool shrink: size fell below offset=N … → bounded rescan from 0` 再进 rescan。
2. **去重**：每条已投递行的整行 `(epoch_ms, kind, from, durable, preview)` 元组进去重记忆——
   内存 Set + `state/inbox-watch/<key>.seen` 持久化（tmp+rename，容量 `TEAM_INBOX_WATCH_SEEN_MAX`
   默认 512），session_start 重新加载（跨重启有效）。普通路径与 rescan 路径都过这道过滤；
   普通路径压掉重叠行时记 `dedup: skipped N …`。
3. **有界重放**：rescan 从 0 读，但已投递行一律不投；「真新」行只投最近
   `TEAM_INBOX_WATCH_REPLAY_MAX` 条（默认 20），更早的跳过——唤醒文本写明
   `(spool rescan after external shrink: delivered the last K unseen line(s); skipped D already-delivered + M older)`，
   账本记 `rescan lines=L dup=D skipped=M deliver=K total=T`。全被去重压掉时**不唤醒**（没什么好说的），
   账本 `deliver=0` 行就是审计痕迹。

计数语义：`seen`（账本 `total=`）只在 `wake()` 里随**真实投递**增长；rescan/dedup 的跳过不计数。
事故场景在新实现下的形态：两次 shrink 各记一行 + 两行 `dedup: skipped 42`（或 `rescan … deliver=0`），
**零唤醒**，`total` 停在 10 不动。

兼容性：durable 收件箱格式、outbox 守卫、`team notify` 契约（M17/M24/M30/M40）一行未动；
spool 行格式不变；`.seen` 是新增旁路文件（shutdown 不删——它是跨重启记忆），不影响发送方路由判据
（发送方只认 `.reg`）。裁剪路径（`trimSpool` + offset 对齐）行为不变。
