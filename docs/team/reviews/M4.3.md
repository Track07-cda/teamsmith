## 每个 finding 怎么修的

### A · 小窗口模型复用大会话（D9 事件 A）

- **口径**：派单前若目标 sid 已有会话文件，就用 `stat` 的大小估 token（**字节 ÷ 4**，消息里写明「粗糙」），与选中模型的
  窗口比较；窗口来自 `TEAM_MODEL_WINDOWS` → Pi 的模型目录 → 都拿不到时用保守阈值 `TEAM_SESSION_WARN_TOKENS`
  （默认 200000，消息里明说「解析不到窗口、用的保守阈值」）。
- **默认拒绝**（任务书两选一里选 (a)）：给出两条出路 `--fresh`（推荐）与 `--allow-overflow`（显式放行，改成醒目警告）。
  拒绝发生在 `--print` 之前也是同一套（不会先打印一份注定 wedge 的计划）。**没有会话文件**（首次派单）不受影响。
- **可见性**：`roster` 增加 `模型` + `会话`（`400k/272k ⚠`，无会话 `-`，窗口未知 `400k/?`），`ps` 的模型表加 `WINDOW`
  列并单独列每个 agent 的会话大小。两个命令都**只 stat 字节数，不读会话内容**；实测 `roster`/`ps` 在本仓库仍是 0.2s 级。
- 保守阈值窗口下不会误放行，也不会静默：红的现场（361k tok + 272k 窗口）在真实目录上复算过
  （`team_model_window sub2api/gpt-5.6-sol` → `272000`，`kimi-coding/k3` → `1048576`）。

### A′ · `--model` 在第一次派单时其实是假的（子发现，任务书外但 A 的前提）

- 旧实现里启动命令（与 adapter 模板的 `{model}`/`{provider}`）都**回读 state**，而 state 是在启动**之后**才写的：
  第一次派单 / 换模型时，派单日志印的是本次 `--model`，真正拉起来的是 state 里的旧模型。命令行的对抗验证也解释了
  「小窗口模型为什么照样 wedge」。
- 修法：`team_agent_launch_cmd <agent> <sid> <wt> <prompt_file> [model]` 与 `team_agent_expand … [model]` 接受显式
  模型，dispatch 把本次解析出的 `$model` 传下去；空值仍回读 state（兼容既有调用点）。smoke `6h` A′ + flip A′ 各一条断言。

### B · 派单打进卡死窗口却报成功（D9 事件 B）

- **启动证据**：窗口 harness 拿到可执行文件后、**exec agent 之前**，把 `<本轮 nonce> <pane shell pid>` 写进
  `state/dispatch-<agent>.spawn`；dispatch 只认**本轮** nonce（每轮换一个，旧文件先删）。
  换窗口、打字进旧进程、别的进程占着窗口都不会产生它——这正是现场「命令被卡死进程吞掉、新 session id 从未出现」的形状。
- **失败语义**：等 `TEAM_DISPATCH_VERIFY_SEC`（默认 8s，0.25s 粒度）→ 没证据就杀窗口、重试**一次**；两次都没有 →
  报 `派单已发出但未能确认启动：…`（含「缺的是启动证据」/排查方向/重派命令），**并且真的**再杀一次窗口，让终态已知
  （`roster` 显示「无窗口」）。失败路径不再有「文案说杀了、其实没杀」。
- **额外观察（诚实但不当失败）**：内置 Pi 路径拿到证据后再看 `TEAM_DISPATCH_ALIVE_SEC`（默认 1s）内窗口是否还活着，
  已退出就**明确告警**（`roster` 会显示「pi 已退出」+ 给出 `resume`）。为什么不判失败：`TEAM_PI_BIN` 允许指向短命 CLI
  （smoke 的 11c 正是用「秒退的假 pi」造「窗口在但 pi 已退出」的现场），而 harness 确实跑过（有证据）——
  把这种情况报成失败会误伤既有语义，也会让 `resume`/digest 的「停了的 agent」信号失效。
- **楔死夹具**：smoke `6h` 用一个假 tmux（`new-window` 声称成功但从不跑我们的命令，只留一个忽略 stdin 的 sleep），
  断言 `派单已发出但未能确认启动`、`new-window` 试了 2 次、`kill-window` 真的被调用、终态窗口不存在。

### C · 草稿报告被当成「可以复验」（digest §[3]）

- `team review` 从任务分支的 checkout 里**摘录**报告；还没进 HEAD 的草稿摘不到。现在 digest §[3] 对
  **agent 工作区里的**报告先查「在不在 HEAD、工作区是否与 HEAD 一致」（`team_report_committed`）：
  未提交 → `report 未提交：先等 agent 交付（不指 review：…）`，**仍然列出**（不静默丢）；已提交 → 与今天逐字一致。
- 微妙处（有意为之）：只对 agent 工作树里的报告这么判；主工作树里的报告是 PM 侧副本，review 的候选链本来就会回退到它
  （cmd-review.sh 的 F14 设计），那里「文件存在」就可用——这条边界也是 M6.4 的 F6 夹具（主工作树里的报告）不被搅动的原因。

### D · squash 合并后的分支永远「待收尾」（digest §[4] / roster）

- 判据（**启发式**，文档里写明）：分支 tip 的 tree 等于保护分支最近 `TEAM_SQUASH_LOOKBACK`（默认 200）个提交之一的 tree。
  命中且工作区干净、且没有真未 push 的提交时：digest §[4] 报 `已合并（squash，内容一致）· 无需 push`（不给 `say` 建议），
  roster 的 `领先` 列显示 `已合并`。
- 反例照旧诚实：分支上再落一个无关提交（tree 不同）→ 立刻回到 `领先 main N`；脏工作区 / 真未 push 优先，不会被这条判据盖住。
  窗口外或部分 squash 也只会退回「领先 N」——信号只会**多回来**，不会静默消失。

### E · 回合内的内部生命周期被广播成「交付」（D9 事件 E）

- 旧实现只看「最后一条有文本的 assistant 消息」，于是长工具调用里**本轮开头**那句被当成结论；通知读起来像「agent 停了、
  还有未提交文件」，而 agent 正 mid-turn。
- 现在：`before_agent_start` 划回合边界；`session_start(reload/new/resume/fork)`、`session_before_compact`、
  `session_compact`、`session_compact_failed`、`session_shutdown` 记「本轮内有内部生命周期事件」；settle 时
  - 最后一条 assistant 消息 `stopReason` ∈ `stop|length` → **完成**：照旧一行 + 摘要（`[auto]`）；
  - 未完成 + 本轮内有生命周期事件 → **完全不发**（只写 `TEAM_NOTIFY_LOG`），不敲门；
  - 未完成但没有生命周期事件（Esc / provider 错误）→ 仍然告诉 PM，但标 `[auto·interrupted]` 且**不带摘要**。
- 保留 `⚠ 未提交 N 个文件` 旗标；它再也不会把正在干活的 agent 说成「已交付未提交」。对照 case（同一回合里压缩过但回合
  真的完成 → 照常一行 + 敲门）确保没有过度抑制。

## 决策与偏离

1. **A 选 (a) 拒绝而不是 (b) 警告后继续**：默认拒绝 + 两条显式出路最不容易误解；`--allow-overflow` 仍然保留「我知道它大」
   的表达力。窗口解析不到时**不猜数字**（猜错会误拦合法派单或误放行必然 wedge 的组合），而是用保守阈值并说明。
2. **B 的「agent 秒退」只告警、不判失败**：判失败会破坏既有语义（`TEAM_PI_BIN` 允许指向短命 CLI；smoke 11c 用秒退的假 pi
   造「窗口在但 pi 已退出」的现场），而且 harness 确实跑过（有启动证据）。启动证据仍然是成功判据——它才是现场
   「什么都没跑」的那一格。窗口不杀：它是一个合法的 `pi 已退出` 状态，`resume`/digest 都靠它。
3. **C 只对 agent 工作区里的报告判「未提交」**：主工作树里的报告是 PM 侧副本，review 的候选链本来就会回退到它；
   对那里也改口径会动到 M6.4 的 F6 夹具（别的任务的段落），收益也小。
4. **D 用「一次 tree 比较 + 窗口」的启发式**：任务书明确说不要 patch-id 之类的昂贵推断；窗口外/部分 squash 只退回
   诚实的「领先 N」，方向安全。
5. **E 用 `before_agent_start`（而不是 `agent_start`）当回合边界**：`agent.continue()`（重试/压缩后继续）也会发
   `agent_start`，用它当边界会把本轮的压缩事件清掉，正好漏掉现场。`before_agent_start` 一次用户提交只发一次。
6. **顺手修的 A′ 属于任务边界内**：A 的守卫按「选中模型」判断，而旧代码让这个模型对启动命令不生效——不修就等于守卫在
   撒谎。改动只在 `team_agent_launch_cmd`/`team_agent_expand` 增加一个**可选**参数，adapter 层语义（占位符集合、校验、
   模板形态）逐字节未变，smoke 6f/6g 全绿。
7. **没有 `--fresh` 的会话 id 是 `<session>-<agent>`**：守卫只看这个精确 sid 的会话文件；`--fresh` 生成
   `<session>-<agent>-<timestamp>`，天然不会与旧文件混淆（旧历史留在原文件里）。
