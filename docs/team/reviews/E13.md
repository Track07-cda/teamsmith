## Approach judgment

**Accepted:** task-category policy plus persisted model/SID selection; independent PM model; removal of retired seat/default policy; canonical config writer and CLI/console/template/guidance coverage; no implicit downgrade; unchanged Pi responsibility and authorization/ownership guards. The report identifies the old contracts to modify/remove instead of proposing a parallel specification system.

The proposal brief will apply these PM refinements:

- `routine`, `analysis` and `verify` are the initial project mapping, not a universal hardcoded category vocabulary. Project configuration defines the valid category names; dispatch checks the brief against that mapping. This keeps future project-specific task types a configuration decision rather than an engine change. No classifier or natural-language difficulty judgment enters the tool.
- Model/SID restrictions concern calls launched or resumed through Teamsmith. Do not detect, rewrite or forbid Pi-internal manual model selection, reasoning blocks or message conversion. A launch record is a record of Teamsmith's selection, not proof of every later inference inside that conversation.
- Keep PM launch model handling within existing launch/continue paths; do not create a new PM recovery subsystem. Preserve the fact that existing model concurrency limits count workers, not a subscription-wide PM-plus-worker budget.
- Keep legacy diagnosis and a usable canonical config-editing front door. Choose the smallest safe editing/upgrade transaction in the design; do not maintain old routing semantics, generalize into a bash parser, or repair the unrelated init identity/force and blocker-recipient defects.
- Split by explicit file and delta ownership. Shared fixture/helper edits must be serialized or have one owner; apparent directory-level parallelism must not create concurrent writers to the same scripts/spec deltas.
- Full model identities and launch parameters remain observable; preview/refusal/assignment transaction tests must inspect effects and recorded arguments, not just a green exit code. Document any conservative fresh requirement for a changed thinking suffix without inventing an API compatibility rule.

The report's human-day estimate is an unmeasured engineering estimate, not an agent delivery schedule or proof of cost. Proposal work must name execution slices and acceptance evidence; it must not start implementation because the exploratory recommendation was accepted.
