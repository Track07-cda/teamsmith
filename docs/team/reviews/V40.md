### F1 · `references/migration.md:255-256`：「拒绝时会给一条从你项目自己的配置推导出来的命令」——对三类被点名的拒绝都不成立

文档原文（§6 Step 2，第 255–256 行）：

> If it **refuses**, it names the obstacle (a shape it cannot locate unambiguously, a fallback category name that
> collides, an invalid model value) and prints a **pastable command derived from your own configuration**.

我把这三类障碍逐个造出来（`/tmp/v40-cand` 上的三个一次性项目，只跑 `--print`，未写盘），工具实际打印的手工路线是**带占位符的模板**，不是从该项目配置推导出的值：

| 障碍形状（触发方式） | 工具实际打印的手工路线 | 有推导值吗 |
|---|---|---|
| `shape-not-locatable`（`export TEAM_AGENT_MODELS=…`） | `team config upgrade-models --task-models '<完整映射>' --pm-model '<独立模型>' --dry-run` | 无 |
| `fallback-name-collision`（席位名 `default` 与兜底 `default` 撞名） | 同上（逐字同一行） | 无 |
| `invalid-model-value`（`dev=vendor//bad`，前面已有一对合法） | `--task-models 'verify=vendor/strong:high <非法那一对用占位符>'` + `--pm-model '<独立模型>'` | 半条（带占位符） |

原始输出在 `../pm-skills-ledger/team/reports/V40-verify/refusal-shapes.txt`（三个形状各一份完整 stderr/stdout，含下面这条规范化后再粘贴的对照）。把打印出来的那条命令逐字粘回去有两层证据：

1. **原样粘贴**（export 行还没规范化）：`rc=5`，工具仍卡在「unsupported relevant source shape；请手工规范为顶层唯一 `KEY='literal'` 后重试」。
2. **按它自己的指示把那行规范化之后再逐字粘贴**：`rc=4`，`category token 不合法：<完整映射>；接受 category=provider/model`；同一形状、换成真实推导值的同一条命令是 `rc=0`（dry-run，`no config/audit mutation`）。这一层单独就能证明 `<完整映射>`/`<独立模型>` 是字面量而不是值。

**这不是整个「两条路线」都错了**：`team up --no-migrate` 那一支（文档 231–232 行）确实打印从项目配置推导出来的完整映射，我把它端到端跑通（`c1 --no-migrate` rc=1 → 取出的 map/pm → `c2 --dry-run` rc=0 不写盘 → `c3 --yes` rc=0 → `c4 config list` rc=0 无 `migration_required` → `c6 team up` rc=0 起 PM）。缺陷在**文档把「`--no-migrate` 的推导命令」与「形状判不出来的拒绝」写成了同一句话**：后者（正是它列举的那三类）只能给模板，其中两类连半条推导值都没有。

夹具为什么没抓住：`upgrade-recipe.sh:348` 的 `promise nomigrate-pastable` 只对着 `--no-migrate` 的输出文件断言（`UP_NOMIGRATE`），`promise` 探针的 want 也只是 `config upgrade-models` 这一小段字面量，拒绝分支的文案没有任何断言覆盖。

**建议修法**：把 255–256 行拆成两种拒绝——「形状定位不了/兜底名撞车/值不合法」时它给的是**模板 + 要你手工填的值**；只有 `--no-migrate` 与形状可推导时才给**可粘贴的推导命令**。夹具相应加一条：对三类拒绝，断言打印里含 `'<完整映射>'`（或含占位符）且**不含**推导出的那对值——即把这条承诺两侧都钉住。

### F2 · `references/migration.md:315-316`：「`team up` rebuilds the pulse window」——`team up` 不建巡检窗口

文档原文（§6 Step 4，第 315–316 行）：

> Text already read into a running session does not change under it: restart each project's own agent sessions (or
> `/reload` the PM in Pi) so they read the new `SKILL.md` and `references/**`. `team up` rebuilds the pulse window;
> `team pulse status` shows it.

实测（§4 的 PROJECT F，私有 tmux，逐窗口名取证）：

| 状态 | `tmux list-windows` |
|---|---|
| `team up`（迁移 + 起 PM）之后 | `pm`（**没有** `pulse`） |
| 紧接着 `team pulse status` | `巡检 未起 → team pulse up`；`tmux 重建 不接管（session/窗口没了只告警）` |
| 先 `team pulse up` | `pm pulse`（巡检确实起来了，rc=0） |
| 把 `pulse` 窗口杀掉，再跑一次 `team up` | `pm`（**没有重建** `pulse`） |

也就是说：巡检窗口是 `team pulse up` 建的，不是 `team up`。P255 的这次改写**把原本正确的一步改错了**——`git diff main...91b40abe` 显示旧 §6 第 7 步写的是 `team pulse up` + `team pulse status`，新 §6 第 4 节换成了「`team up` rebuilds the pulse window」。夹具的 `DOC_LITERALS` 不含这条承诺，`walk` 组也不检查窗口列表，所以两面都没牙。

**建议修法**：316 行改回 `team pulse up`（可写「`team pulse up` 重建巡检窗口，`team pulse status` 看它」），并把这条承诺写进夹具（走查里断言 `team up` 后窗口集合只含 `pm`、`team pulse up` 后含 `pulse`）。
