## 唯一的 ❌，而且它是**真缺陷**，不是文本问题

契约（`boundary#Destructive tmux calls that resolve to the shared default socket are refused`）承诺：
**窗口里的破坏性调用 MUST NOT execute（exit 64）**。实际：**这条守卫在真实窗口里默认是"放行"**。

**PM 独立复现（只读 + 私有 server，未碰真 server）**：

```
$ env | grep ^TEAM_ALLOW_DESTRUCTIVE_TMUX=          # 我自己的 PM 窗口
TEAM_ALLOW_DESTRUCTIVE_TMUX=1
$ tmux show-environment -g TEAM_ALLOW_DESTRUCTIVE_TMUX
TEAM_ALLOW_DESTRUCTIVE_TMUX=1                        # tmux 全局环境里也有
$ 私有 server 复现：env TEAM_ALLOW_DESTRUCTIVE_TMUX=1 tmux new-session …
$ tr '\0' '\n' < /proc/<pane_pid>/environ | grep ^TEAM_ALLOW_DESTRUCTIVE_TMUX=
TEAM_ALLOW_DESTRUCTIVE_TMUX=1                        # 新 pane 继承（tmux 行为）
```

**根因（两处，都在我们自己的代码里）**：

1. `skills/teamsmith/scripts/team:19` —— `export TEAM_ALLOW_DESTRUCTIVE_TMUX="${TEAM_ALLOW_DESTRUCTIVE_TMUX:-1}"`：
   **导出**且**默认 1**。注释原文说"窗口侧不受影响：这个变量不进 update-environment，agent 窗口里它不会被继承"，
   但 `update-environment` 管的是反方向；**泄漏路径是 tmux server 的全局环境**：
   任何带着这个变量的进程**启动/重启 tmux server** → server 环境带它 → 全局环境带它 → **之后每个新 pane 都继承**。
   （M62 的证据还指出：当前 server 进程自己的 environ 里就有它，cwd 是另一个项目。）
2. `cmd-config.sh` 的 schema 里 `TEAM_ALLOW_DESTRUCTIVE_TMUX` 默认 **0**（= 守卫开），而 `scripts/team` 默认 **1**（= 守卫关）
   —— **文档与实现的默认值相反**，于是我们以为有保护，实际没有。

**影响**：M36/M41 建这道闸门的目的正是"不要再发生默认 server 被误杀"（已经发生过 6 次）。
现在它在窗口里**默认放行**（`act=override`），唯一剩下的保护是"调用方自觉"。
