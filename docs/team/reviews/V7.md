### F1（高 · 必须处理）检测器有第二个可达的漏检：草稿在光标行下方 → 判 EMPTY → 真实 Pi 上直接复现原始事故

- **现象**：`team_input_box_state` 只看「光标行及以上」的内容行。人的草稿如果**从空白行开始**（粘贴/输入以换行开头很常见），
  再把光标往上移（`Up`），光标就停在空白行、草稿文字全部在光标行下方 → 判定 EMPTY → 守卫直接往框里打字并按 Enter：
  提交出来的用户消息 = 自动通知 + 人的草稿，草稿离开输入框，**队列 0 条**（守卫从没打算排队）。
- **真实 Pi 复现（§90.C，pi v0.85.1，私有 socket 的独立 session）**：

  ```sh
  # 起真实 pi（--no-session --offline --provider deepseek --model deepseek-flash）
  printf '\nBODY-1\nBODY-2\n' > lead.txt
  tmux load-buffer -b b lead.txt && tmux paste-buffer -p -b b -d -t <session>:dev   # 草稿含前导空行
  tmux send-keys -t <session>:dev Up; … Up; … Up                                      # 光标移到草稿上方的空行
  # → cursor=0,20，第 22/23 行是 BODY-1/BODY-2（文字严格在光标行下方）
  # 生产判定函数（在沙盒仓库里 source 库后调用；这就是包 §90.C 跑的那一行）
  bash -c '. <skill>/scripts/lib/common.sh; team_input_box_state <session>:dev'   # → EMPTY   ← 漏检
  team say dev "V7-REALPI-BELOWCURSOR"                                          # → 打字 + Enter
  ```

  现场（pane 里的真实提交，`User` 气泡）：`V7-REALPI-BELOWCURSOR` / `BODY-1` / `BODY-2`；队列 0 条。
- **合成状态同样可证伪**：§20.1 第 11 态（光标在空白行、下方有文字）→ EMPTY；而 §20.1 第 4 态（纯空白草稿）→ EMPTY。
- **与文档/规格冲突**：`references/troubleshooting.md` §3 写「**A whitespace-only draft is the one known miss** … Nothing
  else in the detector has this hole」，delta 规格 R1 也只把纯空白草稿称作「the one known miss」；而 E3 §1.6 自己就把
  「a draft whose only text lies strictly below the cursor row」列为 v2 的漏检（reasoned，未实测）——我的测量把它变成实测。
- **影响**：不是竞态，是**稳定可达**的状态；后果与 D20 事故完全相同（人的半截草稿被自动消息带走并提交）。守卫在这里
  既不排队、也不警告。
- **选项（PM 决定）**：(a) 判据升级为 E3 的 v3（基线：校准后某偏移从空变非空即 BUSY）或直接「框内任意可见行非空即 BUSY」；
  (b) 至少把这条洞写进 `troubleshooting §3` + delta 规格（把「唯一」改成「两条」），并与 E3 §1.6 对齐；(c) 接受风险 + 明说。
  (a)(b) 都需要 PM 改实现/规格（`scripts/**`、`references/**`、`openspec/**` 都不归 agent）。

### F2（中）Enter 前的复检是「可见非空白字符数 ≤ payload 长度」；大 payload 被 TUI 折叠后它必然放行

- **真实 Pi 的形状（§90.D）**：14 行粘贴在真实 Pi 上被折叠成一行占位符 —— 框里是 `HI-[paste #1 +15 lines]`（23 个非空白字符），
  而 payload 是 98 个字符。生产复检函数 `team_box_holds_only <target> "$(cat payload)"` 返回 **0（only-ours）** ——
  即「框里只有我们这段」，于是会按 Enter。人的草稿 `HI-` 就在这一行里。
- **夹具端到端（§70.3）**：marker 模式下同一条消息路径**真的提交了**：`SUBMIT:HI-[paste #1 +14 lines]`——
  竞态窗口里 payload 被贴进框、复检放行、Enter 送出（D20 的粘连在窗口内复现）。
- **同一段还量到另一半（§70.1a/§70.2）**：判定（EMPTY）之后、复检之前，payload 已经**打进人的框里**。三行 payload 的变体里
  现场是 `HUMAN_alpha line one …`（交付自带的真 pane 测试 12b-h ⑨ 断言的正是这一串），而 delta 规格 R1 的场景写
  「the fixture's draft is unchanged」、正文写「when the box holds text, MUST send no key at all … neither the payload nor
  an Enter」。**规格场景与实现行为不一致**（payload 进了框；只是没按 Enter）。
- **影响**：竞态窗口是毫秒级（一条命令宽，§70.1b 已证）。窗口内人的草稿会被污染（可能连同自动消息一起被提交），
  且复检的判据可被「TUI 折叠/裁剪」欺骗 —— 长 payload + 正在打字的人就是它的失效条件。

### F3（中）被污染的草稿之后还会被**再投一次**：同一 payload 到两次

- **复现（§70.2）**：粘贴瞬间注入草稿 → 没有提交、条目进 `held/`（`draft-raced`）；人的框里现在是 `HUMAN_alpha line one …`。
  人按 Enter（他本来就要发送自己的草稿）→ 提交 = 草稿 + payload；随后 `team outbox flush` 把 held 条目正常投递 →
  第二次提交 = 同一条 payload。真实 agent 看到两遍。
- **与规格的关系**：R3 要求「claim 之后再打字，一条只投一次」，R4 要求未确认时「至多补一次 Enter，然后进 held/，**绝不把
  payload 再贴一次**」——`draft-raced` 这条路径里 payload 先被贴进了框（未计数），又被当作全新消息投了一遍。
- **影响**：重复通知 + 人的草稿被污染；draft-raced 的 held 条目没有「已经部分到达」的概念。

### F4（中）投递确认只看 pane **尾部 400 字节**：成功投递被判「未确认」→ 留在队列 → 下一拍再贴一遍

- **复现（§70.4）**：页脚静态的 TUI（我的夹具，`MTUI_STATIC_FOOTER=1`）：第一次排水**确实提交了**（提交 1 次），
  但 `team_pane_snapshot`（`capture-pane -p | tail -c 400 | cksum`）没变 → 输出「投递未确认」→ 条目**留在活动队列**（没进 held/，
  因为 TTL 未到）→ 第二次排水把同一条 payload 又贴了一遍（提交 2 次，内容相同）。
- **与规格冲突**：R4 的场景「An unconfirmed delivery is held, not duplicated」写「the payload was pasted once …, the entry is
  under `outbox/held/`, and no second copy of it exists in the queue」；交付自带 smoke 的 12b-e 靠 `TEAM_DEFER_TTL=1` + `sleep 2`
  才走到 held/，即**只在 TTL 过期后**成立。
- **真实 Pi 上不易触发**：§90.B 在真实 Pi 上投递被正常确认（页脚的 ↑↓/spinner 会变），所以这是**脆弱点**而不是必然事故；
  但只要 TUI 的尾部 400 字节不随投递变化（静态页脚、框被滚出窗口、pane 很高而内容很短），它就会变成重复投递。

### F5（中 · 行为变更）一次成功的 `say` 也会写收件人收件箱（tag 固定 `queued`），并且把 PM 的巡检待办抬起来

- **复现（§50.4/§50.5）**：干净框、确认送达的一次 `team say dev "…"` 之后：

  ```console
  $ wc -l docs/team/inbox/dev.md
  1        →  - 2026-09-15T17:57:48Z [queued] agent:dev · V7PROBE-PENDING     # 已送达却记 [queued]
  $ team_pending_counts
  say 之前: 1 0 0 0 0 0 0    say 之后: 2 0 0 0 0 0 0      # inbox 未读 +1
  $ team digest          →   待办   未读通知 2
  $ TEAM_WATCH_NUDGE_GAP=0 team watch --once
  ✓ watchdog: 有待办（未读通知 3）→ 已提醒 PM                # 下一拍真的叫醒了 PM
  ```

- **机制**：`team_cmd_say` 无条件传 `--inbox <agent>` → `team_outbox_enqueue` 调 `team_inbox_append`（tag 固定 `queued`），
  条目投递后收件箱那一行**不会**被改写；`team_pending_counts` 的 `inbox` 项按收件人算未读，于是「PM 对 agent 说了一句话」
  变成「有未读通知」的待办，watchdog 因此叫醒 PM。
- **与规格的关系**：delta 规格里 `notify-and-inbox` 的兜底收件箱是「**agent 不在跑时**」的通道（"MUST be appended … instead"）；
  delivery-guard 的 TTL 条款要求 payload 在过期前 durable（实现用收件箱满足它），但**投递成功后仍留一行 `[queued]`**、
  且把它算成未读通知，这两点既没被规格要求、也没有测试覆盖（交付自带夹具完全没看这一面）。
- **影响**：PM 的每一次 `say` 都会给下一拍巡检制造一条自造待办（并可能叫醒自己）；收件箱的 tag 与真实结果不符（诚实性）。

### F6（低-中 · 门禁自洽性）smoke 的 §12b-h ⑤/⑥ 依赖 `TMUX` 非空：非 tmux 环境里整套门禁变红

- **差分（§95.4，同一 revision、同一套 smoke）**：`TMUX` 非空 → `✓ 1449 ✗ 0`（rc=0，198s）；`env -u TMUX -u TMUX_PANE`
