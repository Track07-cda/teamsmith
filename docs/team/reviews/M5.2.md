## 2. `config.yaml` 的决定

- **`context`**：一段话说清 teamsmith 是什么（PM 拥有 brief/派单/独立复验/合并/账本，worker 各在自己的
  worktree+窗口里并行），并把规范文档指出来（`SKILL.md`、`references/philosophy.md`、`protocol.md`、
  `workflows.md`、`openspec.md`），明确「原因去 references 读，别抄进 spec」+「账本在 docs/team，OpenSpec 拥有
  规范与变更，不要再长第二套 spec 系统」+「artifact 一律英文」。
- **`rules.specs`**：一条 requirement = 一句可证伪的话（SHALL/MUST）+ ≥1 个可观测场景；场景必须是命令/退出码/
  文件内容；**不允许不能失败的场景**（做不到就留在 references 当散文）；引用文档而不是复述。
- **`rules.proposal`**：验收命令必须逐字可复制可跑（PM 原样执行）；边界必填（什么不做、哪些路径不许碰）；
  **缺陷修复必须写 flip**（修复前红 → 修复后绿，或「破坏实现→守门测试必须失败」）；结尾写清报告必须带的证据；
  提案 ≤500 词，长期理由进 `DECISIONS.md`。
- **`rules.tasks`**：一条 = 一个可验证步骤（有能失败的命令，不许写「改进 X」）；每条 requirement 至少被一条
  覆盖且点名 capability；需要真进程（tmux / 模型调用）的条目要标注，且不能是唯一证据；按依赖排序。
- **`operations.apply` / `archive`**：小步提交 + `Agent:` trailer；证据优于文字（跑过 + 贴输出尾部）；
  只改 brief 允许的路径，需要别人的文件就 `BLOCKED:`；archive 只在「review 记录存在 + 代码已落地」之后，
  并且**同一提交里更新受影响的能力 spec**，账本（brief/report/review）才是证据，归档只是摘要。
- **踩到的坑（值得记）**：`rules:`/`guidance:` 的值必须是**带引号的字符串**——YAML 里未加引号的标量只要含
  `": "`（例如我写的 `Agent: <name>`、`no "TODO: ..."`）就会被解析成 mapping，OpenSpec 会把**整条列表**丢掉
  并警告 `Rules for 'proposal' must be an array of strings, ignoring ...`。已改成全部双引号，并用
  `openspec instructions <artifact> --json` 验证 context/rules 真的被注入（proposal/specs/tasks 各自命中）。
