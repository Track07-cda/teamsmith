## F1（我裁定：**必须修**）—— "框只会变大"对**混宽度帧**是假的

它自造的帧（`f1-mixed-width-disjoint-box.txt`）：

```
row1 ────────(100)        光标框的上边框
row2  HUMAN DRAFT LINE    ← 光标行
row3 ────────(100)        光标框的下边框
row5 ────────(120)        下方另一对（宽度不同、自成一对）的上边框
row7 ────────(120)        该对的下边框
```

| 规则 | 判定 |
|---|---|
| 旧（最近候选） | `geometry=[1 3]` → **NOT-EMPTY / BUSY** |
| 新（最低候选） | `geometry=[5 7]` → **EMPTY / 生产路径 EMPTY** ← **框落在光标下方、与光标框不相交** |
| 影子成旧顺序 | 回到 BUSY（证明是候选顺序造成的） |

**后果**：这正是本 change 要防的那类事故（**就绪门放行 → payload 打进人的草稿**），而它**由本 change 引入** ——
requirement 里那句 *"relative to the nearest-candidate rule the box can only grow … no frame's verdict may move
from BUSY to EMPTY"* 在混宽度帧上**是假的**（我写的判据太乐观）。

**根因**：规格只说"顶边框是**下边框之上**最高的合格行"——旧顺序下（下边框紧贴光标下方）它**隐含**了"框含光标"；
改成最低候选后，配对可以**整个落在光标下方**。**定位的前提本来就是"框从光标行长出来"**。

**裁定（修法，写进 P86）**：下边框候选**必须**满足"配到的顶边框**严格在光标行之上**"（即**定位出的框必须包含光标行**）；
不满足的候选**跳过**，继续在更近的候选里找。这样：要么顶边框与旧框相同（新框=旧框向下扩展的**超集** → BUSY 不变）、
要么该候选被拒（回落到更近的候选），**单调性因而重新成立**。
并同步修 requirement/design 里那句假话（改为"在框含光标的前提下"或直接以"框必须含光标"为约束）。

**结论**：`bottom-border-candidate-selection` **不能带着 F1 归档**；P86 修完并重新验证后再谈。
