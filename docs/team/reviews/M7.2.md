## Diagnosis（deliverable 1）：根因 + 原始采样

**结论：不是「两拍之间存活闪了一下」，而是「启动在飞行中」这个状态根本不存在。**

`team_pm_start` 的时序是 `respawn-pane` →（等证据）→ 写 `state/pm.pid`。在写盘之前，PM 窗口里是
一个**正在跑启动命令的 shell**（cwd 在本项目里、命令行里带 agent 路径、还没 exec 完成）——对
`team_pm_state` 来说它既不是 `running`（没有证据），也不是空提示符，只能落到 `unknown:<cmd>`。
于是**另一拍**（同一个 watchdog 窗口的下一拍、并发的 `watch --once`、人跑的 `team up`）把它当成
「没有 PM」，再做一次 `respawn-pane`：**pane 被换掉 = 刚起来的那个 PM 被杀**，`pm-restarts.log`
把一次启动记成两次；冒出 quota 告警的假象，以及 smoke §11b 里 `拉起计数已记录（期望 [1] 实际 [2]）`
这条老 flake。

复现方式（`tests/flip-m7.2.sh`，确定性）：wrapper 假 agent（先睡 3s 再 exec 真 agent，所以证据不会在
顷刻间就绪）→ 第一拍在后台启动 → **pane 一换进程就立刻打第二拍**，正好落进那个窗口。

**修复前（base `cad3229`）逐拍采样**（每 0.2s 一拍；`rec=` 记录的 pid，`spawn=` spawn 文件里的 pid，`mark=` 启动标记）：

**同时发现的第二个同族缺陷**：`team_proc_is_agent_bin`（M6.5 的 argv 证据）按「命令行里出现配置

## What changed（deliverable 2）

规则（`team_watch_once`，一拍一次 `team_pm_state` 读完再决策）：

| 状态 | 这一拍做什么 |
|---|---|
| `running:<pid\|cmd>` | 有待办 → 提醒（沿用 `TEAM_WATCH_NUDGE_GAP` 限流） |
| `starting:<age>` | **不提醒、不拉起、不计数**：日志写「PM 正在启动（证据：…）→ 不重复拉起」 |
| `idle:*` / `unknown:*` | 有待办 → 配额检查 → 记账尝试 → `team_pm_start` |
| `foreign:*` / `missing` | 不碰（`TEAM_WATCH_REBUILD_TMUX=1` 才重建 tmux） |

- **启动在飞行中 = 一个状态**：`state/pm.pid.starting`（epoch / 发起者 pid / 目标窗口），
  新鲜窗口 = `TEAM_PM_START_WAIT + 5s`；`team_pm_state` 报 `starting:<age>`（既不是 running，
  也不是「没有 PM」）；`team_pm_start` 见到新鲜标记直接返回「不重复拉起」；成功、respawn 失败、
  超时三条出口都会撤标记；过期标记只是证据过期（读命令不改状态，也不会锁死）。
- **一拍一次读取**：`running` 判断不再和后面的 `team_pm_state` 读两次；`digest` / `ps` / 面板 /
  `watchdog-status` 的 PM 行与待办行都由同一次读取推导，不会在同一份输出里既说「在跑」又说
  「会拉起」。
- **配额诚实**：`pm-restarts.log` 只记**真的重启**（成功之后写，行尾带决策证据
  `state=… evidence=…`）；失败的尝试写 `state/pm-start-attempts.log`，不冒充实重启；
  限流同时看两份日志（成功 + 失败都算一次尝试），所以「每次都拉不起来」的循环仍然有上限。
- **拉起决策带证据**：`team_pm_evidence()` 把凭据写进 `watchdog.log`、`pm-restarts.log`、
  `watchdog-status`（`state/pm.pid=<pid>（proof=spawn）`、`state/pm.pid.starting（…s 前由 pid … 发起）`、
  `PM 窗口是空提示符（cmd=zsh）`、`PM 窗口里是项目内非 agent 进程（cmd=sleep，cwd=…）`）。

## Decisions and deviations

- **没有让 smoke 的 §11b3 ① 去断言「真实启动窗口里一定看到 starting」**：真实窗口有多宽取决于
  spawn 文件何时落盘（实测 ~30ms 到 ~1s 之间抖动）。所以 ① 只钉与时间无关的结果（不重复拉起、
  不计数、不动 pane、只起一个 PM），「starting 这个状态本身」由 ③ 用真实函数
  `team_pm_starting_begin` 造的确定性现场钉死；真实路径在宽窗口下的表现由 `tests/flip-m7.2.sh`
  的采样表作证。**没有重试、没有放宽断言**。
- **两份日志而不是一份**：`pm-restarts.log` 保持「一行 = 一次真重启」（老的 smoke/V4.0 断言、
  `wc -l` 语义都不变），失败尝试另记 `pm-start-attempts.log` 并纳入限流。这样既满足「重启次数是
  事实」又保住规范里「1 小时最多 N 次」的上限（否则失败的 respawn 循环可以无上限）。
- **反向守卫没有做成「指纹一变即 FAIL」**：门禁每跑一次都可能与真实团队的正常写入并发
  （watchdog 每 15 分钟写 capacity/watchdog.log），那样会造成假红。改为「签名出现即 FAIL」+
  「指纹变化如实打印 diff」，并在报告与脚本注释里写明这个取舍；PM 若坚持严格相等，我可以再加上
  一个 `TEAM_FLIP_STRICT_LEDGER=1` 开关。
- 未改 `cmd-project.sh` / `cmd-agents.sh` / meetings / `openspec/**` / `docs/team/**`（除本报告目录）；
  没有新配置项。
