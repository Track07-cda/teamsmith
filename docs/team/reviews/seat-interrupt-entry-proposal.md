## 判定

这是我在任务书里点名的那个缺口的正解，而且**比我要的更严谨**：

- **两条要求的十个场景**覆盖了我担心的每一面，其中三条是我没写但必须有的：**「对象不再是那个被证明的进程 → 拒绝，不发信号」**（pid 复用防线，与门禁锁那套同源）、**「正在写盘的席位被拒绝，且拒绝点名证据」**（不误杀正在交付的人）、**「读命令永不结束回合」**（别把 `status` 当长回合）。
- **判据两侧**：**新近的窗口**（证据是活的）+ **审计里读到的打断前读数**（`session_last`、`uncommitted`）——事后能回答「这次打断是否必要」，这正是我当天手动杀进程时**没有的东西**。
- **审计一行一打断**、字段逐个可核（对象、信号序列、结果、`guard=clear|forced`、一句话理由）；**被拒绝的打断不写审计**（「没有动作就没有证据」✓，与 `reap` 同口径）；**actor 解析不出来就拒绝**（身份不许猜 ✓）。
- **理由投递到席位的阅读顺序**（写进它的收件箱/线程 ✓）——我当天手动做的正是这件事（写线程再续跑），现在成了工具行为。
- **§8 已知边界写得诚实且具体**（我逐条读过）：陈旧窗口拦不住「反复跑命令却从不落盘的席位」（正是 D188 的形状，代价明说）、只对一个 pid 发信号（不整组不按名字）、窗口留下的是**活着的 shell 而不是遗体**（`resume` 走既有替换路径，权威记录是 `interrupt.log`）、**被打断席位的后台作业不受影响**（续跑后按 `long-job-suspend` 的纪律先查 `bg.log`）、死因分类**不认**这次停止（会显示 `unknown`，原因由审计行回答）、**进程级**（当前回答丢了、工作树逐字节还在）、**不做批量**（与「每次都要一句话理由」冲突）。
- 与 `long-job-suspend` 的关系按要求写清：**长作业有记录有叫醒，长回合两者都没有**；本变更补的是后者。
