## 5 门禁只有两类（存在性 + 行为），没有顺手锁措辞

逐行读 `key-replies.sh` 的 `guide` 组 diff，本变更新增的断言只有：

- **存在性**：`guide_spec()` 三行各加 token `written for the user`（命令表那行是 `row:written for the user`）—— 正是
  P264 裁定「没有机器面、而那串字是某个要紧行为的唯一证据 → 留一条稳定 token（不是整句）」的那一类；
- **存在性（失败形状）**：`guide_flip_names_criterion()` 要求红文案里出现 `[written for the user]`，即「缺了什么」要能被
  读成缺了那条判据，而不是要求某种措辞；

## 7 未验到项与观察

### 7.1 本轮没验到的产品行为

- **「某条回复是不是写给用户的」不可机判**：门禁只证「判据在场上 + 示例命令能用」，没有任何断言能判一条真实回复
  该不该发布；规格自己也写了这条诚实边界（`No tool can verify`）。**PM 是否真的照做、发布的正文与答复是否一致，无工具可证。**
- **选段不是全套门禁**：我按任务书跑了相关段与两组夹具（`smoke --select 26,28,62`、`key-replies.sh --all`、pty、ui），

### 7.2 观察（不改判定，供 PM 处置）

1. **判据 token 是文件级存在性检查，段落之外也能命中；救回它的是翻转断言。** 把 token 从承载义务的段落里拿走、
   改在文末附录写一句带 token 的话（m6/m6b），三面的主检查照旧全绿，红的是翻转断言
   `guide-flip/①②：红文案没有点名缺失的判据 [written for the user]`（`✓23 ✗1` rc=1）。好处：这种形状**不会静默通过**；
   代价：红文案读起来是「翻转断言失败」，而不是「这个面丢了判据」。
2. **协议代码块与命令表行里的示例命令从不被真解析器执行**（m5c 绿、m5d2 红）：行为腿只对模板那行生效；协议/命令表的
   `--stdin`、`team reply post` 只是**子串**锚点（`--stdinX` 也能满足字面锚点，m5d 因此被我作废重做成 m5d2）。
3. **文字层面的段落不进断言**：协议 §4b 的边界段（排除项/兜底/自测题）整段删掉全绿（m2b），模板里的内容要求与反向句
   删掉也全绿（m8）。这是 D170 与冻结规格的明确选择（门禁不得断言措辞与判据两极的举例），代价是「这几段确实印在
   每个面上」只由人读差异把关。
4. **SKILL.md 的两份副本只钉了一份**（m3b 绿）：命令表行被 `row:` 锚点钉住，Non-negotiable 条目那一份删掉不会红；
   任务书 1.3 的「两处不许一个有一个没有」靠人读，不是门禁。
5. **`spec-refs.sh --check` 的既有红**（§0 第 8 条，rc=1）：唯一一条 undeclared 是
   `openspec/specs/extension-slash/spec.md:47 docs/team/tasks/P1.md`（来自 `86c7ada9` 的归档），与提案基线、作者报告
   口径一致，不在本变更写集里 —— 我按任务书 4.2「未授权则如实记录」处置，没有去修。
6. **`openspec validate --all --strict` 的条数**：我实测 `22 passed, 0 failed (22 items)`，作者报告写 `23/0` —— 同一棵树、
   同一命令，差异只在计数口径，两者都 rc=0，不影响判定。
