## 判定

我 brief 里要的两侧代价都写了，而且**结论有事实支撑**：设计引用了 loadavg 20+ 出现在**排队正常**的那一轮——也就是说**一套全量门禁自己就能把 32 核机器压满**。由此两条都成立：① 锁要留（两套并发更糟）；② 嵌套运行**不能没有预算**（一台机器已被压满再叠一个无期限的夹具，就是 §36 那次超时的形状）。

**决定 D1：嵌套运行不排队。** 理由与我的直觉一致但更严谨：机器锁的契约是「串行化**顶层**运行」，而嵌套运行按定义在某个顶层运行内部，**让夹具去抢机器唯一的共享资源，还会和它自己的祖辈死锁**。

**另一侧（我点名必须交代的那条）它给了三条，没有用「不会发生」打发**：① **放行是有条件的**——必须能**证明祖辈持有锁**（沿进程树走到记录的持有者 pid，且该 pid 的 starttime 仍是那一次，防 pid 复用；**不成立就按顶层排队**，所以不是自由通行证）；② **一次只放一个顶层运行**，跨席位的嵌套重叠因此只剩同一顶层内部；③ 残余窗口**做成可见**（`no_lock=1` 标进记录 + 写进纪律），而不是假装没有。

另外三处我认可的设计：
- **嵌套运行受生它的那一段的预算约束**（读祖辈已武装的段预算心跳，取不到就退回自己的表预算），到期由**自己的**看门狗点名段号与预算并停掉、离开现场——这正好治住今天那次「嵌套运行无期限地占了一小时十六分」。
- **持有者记录要写 kind / 席位 / 工作树 / 已跑多久 / 上限**，等待者据此能归因（今天那条只写「持有者：smoke.sh」，等于没说）。
- **夹具留下的已注册嵌套运行要一行可见地点名，且只允许对夹具自己注册过的 pid 发信号**——这条与今天那次「按名字选进程」的事故正对上。
