## 2. What changed

| Path | What |
|---|---|

| `scripts/lib/cmd-status.sh` | The pending-verification detector: board gate, candidate/ownership model (`team_report_candidates`, `team_report_copy_rank`, `team_report_primary_candidates`), phase-aware action (`team_report_pending_action`), the explain-the-skip list (`team_reports_skipped_by_board`), the digest `[3]` rendering, and the `team status <ID>` note. |

| `docs/team/reports/M9.4-dev2/pkg/run.sh` | Independent flip package for this task (own sandbox, 23 checks, two "break the implementation" directions). |

The rules, in order:

1. **A board row the PM has adjudicated is never listed.** `done`/`closed` → the report is skipped; the
   evidence was enforced where the transition happened (`team_done_evidence`, M9.2), so the list does not
   second-guess it.
2. **In-progress rows keep the M6.2 rules byte for byte** (`todo`/`wip`/`review`/…: listed when the record is
   missing, stale, or gates-less). A phase task in progress is *still listed*; what changes is its **action**:
   `explore`/`propose`/`archive` print the phase's own next step (M9.2's `team_done_phase_evidence`, e.g.
   "阶段证据已就绪（提案审查记录 …（判定 ACCEPTED））→ 等 PM 把看板移入 done"), never a generic
   `team review <ID>` that would send the PM at the wrong artifact. `apply`/`verify` keep `→ team review <ID>`
   exactly as before.
3. **Skipping is never silent.** The digest prints one line naming the reports it skipped because of the
   board (`已按看板跳过 N 份报告（任务已 done/closed）：… · 证据在 board set 时核对（M9.2），这里不重复质疑`),
   and `team status <ID>` says the same for that task:
   `待复验：**不列**（看板是 done；报告的证据在看板转变时核对，见 docs/team/reviews/P1-done.md）`.
   Only reports that would *otherwise* have been listed are named — a task with a valid review record adds
   no noise.
4. **Copies are attributed, not inherited silently.** An agent worktree copy belongs to its task when
   (a) the report's author suffix is that worktree's name (`<ID>-<agent>.md` in `.worktrees/<agent>/`),
   (b) the agent's recorded task is this one, or (c) its HEAD is exactly `task/<ID>`. Otherwise it is an
   inherited copy from a stacked branch (D16): it never outranks the owning copy, the id is listed once, and
   the digest no longer claims it lives "on <someone else's> branch" (it prints
   `（副本：在 m94a 的工作树里，本任务自己的工作树里没有它）` instead).

`team_status`, digest `[1]`, and the watchdog's pending count all read the same function, so the fix reaches
the wake-up path, not just the display: the real ledger's `待办` went `待复验 2` → `待复验 1`.

## 6. Decisions, deviations, and things worth the PM's attention

1. **How I read requirement 2.** The brief says the phase-aware evidence decides "reviewed" for phase tasks,
   *and* its fixture control says the same propose/ACCEPTED fixture with board `wip` must **stay in the list**.
   I implemented: the board decides what is *listed*, the phase evidence decides what the entry *says* (its
   next step). A `wip` propose task with an accepted proposal is therefore still visible — the PM's remaining
   action is the board transition, which is exactly what the ROADMAP line ("证据以看板转变时为准") and the
   brief's own rationale ("the transition itself is where evidence is enforced") ask for. If the intent was
   instead "an accepted proposal clears a non-done row", say so and I will change the listing rule (one line).
2. **`closed` is not a board status in this version** (`board set` accepts `todo|wip|review|done|blocked|dropped`).
   I still treat `closed` as adjudicated so a hand-edited BOARD cannot produce the same false positive.
   **`dropped` is deliberately left listed** for now: it is not `done`, and the brief did not name it. It is
   the same class of false positive, so it may deserve the same skip — the PM's call.
3. **The spec now understates the rule — needs a PM-owned delta.** `openspec/specs/board-and-status/spec.md`
   ("Requirement: Delivered-but-unverified work is detected") says a task report without a review record
   *is* pending, with no board exception. The brief told me not to touch `openspec/**`, so I did not: the
   behavior change needs a MODIFIED delta (proposal → apply → verify) or the C0 spec-delta gate that P2/P2.1
   is landing will correctly flag this commit. Everything else in the gate is green.
4. **A latent bug was fixed on the way**: the old detector registered the id *before* checking
   `team_report_is_task`, so a milestone note (`<ID>-closure.md`) sorting first could hide the real report for
   the same id. The rewritten candidate scan filters first, then de-duplicates.
5. **Cost**: the digest needed the candidate set twice (listed + skipped). Sharing one pass took it from
   `12.8s` back to `10.1s` against a `9.6s` pre-change baseline on the real ledger (the remaining cost is the
   pre-existing per-report analysis); the watchdog runs this every tick, so I did not leave the doubling in.
6. **Ownership heuristic limits**: (4) above keys on the report author / recorded task / exact branch. A
   report whose name does not match its owning worktree (not the convention here) is only *labelled* a copy —
   it is still listed once, never dropped, and never attributed to a foreign branch.
