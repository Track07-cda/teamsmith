## 6 · 观察（不构成 FAIL，但值得在下一轮处理）

**O1 · 探针不校验退出码，「第二次跑 rc≠0 但一字不写」会被判成绿。** 这是我为看边界造的第三棵变异树 m3（`mutants/m3.diff`：「无变化」分支 `return 0` → `return 1`）。我自己的仪器先测：

```
review   第一次 rc=0（文件 none→957b25958e82） 第二次 rc=0（文件 957b25958e82→957b25958e82）未变
m3       第一次 rc=0（文件 none→1049b238beff） 第二次 rc=1（文件 1049b238beff→1049b238beff）未变
```

m3 的第二次跑打印的是**成功文案**（`✓ 本会话 skill 版本未变化…`）却以 rc=1 退出；同一棵树上夹具的判定是 `rc=0  == 结果 ==  ✓ 64  ✗ 0`——**绿**。规范原文是「probes assert effects, never exit codes alone」（是「不能只看退出码」，不是「不许看退出码」），所以这不是违反规范，而是一个判据盲区：任何「第二次跑命令失败但不写盘」的退化都躲在这条绿后面（F1 就是它的近亲：静默失败）。加一条 rc 断言（第二次跑 rc=0）就把这一类收进去。

**O2 · 哨兵值可以被实现「写回原值」骗过，而这一点是有意设计。** 若某实现的第二次跑把具名字段改写回**它读到的那个值**，哨兵自然存活，探针仍绿。从「逐字节不变」这个声明看这是正确的（文件真的没变），这里只是记下它的边界：吊住的是文件字节，不是「有没有调用写盘路径」。

**O3 · 容器与宿主的 `INSTALL=` 不同（与作者报告 Finding 1 一致，我独立测过）。** 我各造一个临时项目跑 `init` + `mark-loaded`，读同一条记录：宿主 `INSTALL=git`、容器（同一棵树挂载为 `/work`）`INSTALL=copy`。原因是 `team_skill_install_kind()` 走 `git -C "$TEAM_SKILL_DIR" rev-parse`，而容器里只挂了 worktree（`.git` 文件指向挂载外）。两个环境各自内部一致，幂等判定不受影响（容器 5 次的哨兵行与宿主逐字相同）。若哪天要跨环境比对 `pm-loaded.env`，先看这一行。
