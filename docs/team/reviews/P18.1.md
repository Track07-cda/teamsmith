## 机制与修复

`layout.ts` 的两栏放置 pass 里的记账是**两列共享**的：

```diff
         for (const { b, slot } of ordered) {
           const colW = slot === 0 ? leftW : rightW
-          const used = Math.max(columns[0].length, columns[1].length)
+          // The body budget is **per column** (P18.1): the two columns stack side by side, so a tall
+          // left card (the board's B1 growth fills the whole body height) used to consume the right
+          // column's budget as well — its cards got `remaining = 0` and vanished, although the frame
+          // had a full column of empty width. `pickChrome` keeps every column within `bodyBudget`, so
+          // the flush below still ends both columns on the same row.
+          const used = columns[slot].length
           const chunk = place(b, bodyBudget - used, colW)
           for (const l of chunk) columns[slot].push(l)
         }
```

链条：B1 把 board 养满整个 body（`target = max(col0, col1, bodyBudget)` ≡ `bodyBudget`）→ 共享记账下
`used` 被那一列直接吃满（`used = bodyBudget`）→ 右栏三卡（p11/13/14）`remaining = 0` → `pickChrome`
返回 `null` → 整块不渲染（不是降级 `—`）。每列独立记账后右栏拿到自己的 `bodyBudget`；`pickChrome` 保证
`chunk ≤ remaining`，所以每列仍 ≤ `bodyBudget`，flush 依旧把两列收在同一行。

B1 的展开量没有改（bug 不在它身上——它在旧记账下只是**受害者之一**）：board 依旧把余高花在折叠历史上
（夹具实测 270x66：显示 `其余 40 条` vs 未封顶自然值 `其余 91 条`；120x40：`66` vs `91`）。

## 附带问题：height=300 时 decisions 仍缺席 —— **不是同一族，是另一个坑**

结论：**当前代码（修复前也一样）在 height=300 时右栏三卡齐全**；「decisions 仍缺」是**管道短写**
造成的观感。证据（真实数据）：

```
# 1) 直接重定向：完整帧
$ node panel.js --snapshot --root . … --page 2 --width 270 --height 300 > f.txt
rows=300 bytes=59873 | ╭─ 活动变更/规格/最近决策 = 1/1/1
#     pre bundle 同样 = 1/1/1（所以这不是两栏预算那族）

# 2) 接管道：同一个命令只出来 8192 字节 = 15 行
$ node panel.js --snapshot --root . … --page 2 --width 270 --height 300 | wc -c
8192
#    那 15 行里：活动变更=1、规格=1、最近决策=0  ← 与 PM 的观察逐字吻合
```

根因（最小复现，与 panel 无关的通用形状）：

```
$ node -e 'process.stdout.columns; const{writeSync}=require("fs"); writeSync(1,"x".repeat(100000))' | wc -c
8192
$ node -e 'process.stdout.columns; const{writeSync}=require("fs"); const n=writeSync(1,"x".repeat(100000)); process.stderr.write("returned="+n+"\n")' | wc -c
returned=8192
8192
$ node -e 'const{writeSync}=require("fs"); writeSync(1,"x".repeat(100000))' | wc -c     # 不碰 process.stdout
100000
```

即：`main.tsx` 启动时读了 `process.stdout.columns`（`const stdoutColumns = process.stdout.columns || 0`），
fd 1 因此进了 non-blocking 模式；随后 `out()` 的 `fs.writeSync(1, text)` 对管道只写进 8192 字节并**返回
8192**，而 `out()` 丢弃返回值 → `--snapshot`/`--json`/`--palette`（以及大输出时的 `--print`）在**接管道**时
静默截断（重定向到文件是 blocking fd，不截断）。**这条不在本任务范围（brief：发现别的坑写 finding 别顺手修），
只记录为 F-P18.1-A。**

## Findings

- **F-P18.1-A（本任务发现，未修）**：`panel.js` 的机读出口（`main.tsx` 的 `out()`）用单次
  `writeSync(1, text)` 且不看返回值；stdout 是管道时会短写（本机实测每次都是 8192 B），帧/JSON 被静默截断。

  `panel.js --print|--json|--snapshot … | grep/jq/…` 的调用方；本任务验收里所有帧证据都用 `>` 重定向

  （如 `while (off < buf.length) off += writeSync(1, buf, off)`），或按返回值重写/等待。
