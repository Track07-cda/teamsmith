## 判定

这份提案把我给的两条要求（**归属**与**察觉**）做成了一个我没想到但更对的结构：

- **互斥搬到了「伴生锁」**：真互斥是同一目录下**点开头**的 `<published>.machine`（`…/.teamsmith-smoke.lock.machine`），因此**那条 `rm -rf /tmp/teamsmith-smoke.*` 够不着它**；而**发布路径保留为兼容声明**（先取发布路径、再取伴生——顺序写进合同，于是 P287 之前的写入者仍与本运行互斥）。它还明写「**持有者不得删除或改名自己持有的锁文件**」——这正是今天那半条静默并发的根因（`flock` 锁 inode，文件被删后新运行会新建文件、在另一个 inode 上拿到「锁」）。
- **察觉有落地**：运行时按有界节奏核对两个前提（工作根还活着、伴生锁还是它），一旦不成立就**一行点名 + 安全点停跑**（复用既有的哨兵退出码 **2**，**不新增判定 token 也不新增退出码**），把证据写到工作根之外并**保留现场**；**丢锁不许报 PASS**。
- **入场检查**：拿到锁后核对活登记的身份，**不同就拒绝起跑并点名**（新来者侧唯一的保护，与旧持有者的守卫互补）。
- **等待者**：排队期间重新解析，文件被 unlink/替换时**带两侧身份打印**；读取持有者记录时对旧版本记录用 `?` 标注（不假装知道）。
- **同一件事顺手做实**：性能套件那把锁（同一平铺家族）一并走同一实现——它分裂的后果是**静默的错误测量**，比门禁那次更糟。
- **诚实边界**：`TMPDIR` 覆盖造成的互斥分裂（P255 的残留）**明写在界外**，不新增第二个解析规则；历史平铺残留不由本变更清理。
