## 2 · 兼容声明（发布路径）双向

```
$ 正向：一个旧版写入者（bash -c 'exec 7>>$PUB; flock -x 7; sleep 12'）先持发布路径，
        并写一条旧形状记录（<ISO> pid=<pid> cmd=legacy-writer）
  另一套全量 smoke 正在跑（kind=? pid=3083658 cmd=legacy-writer agent=? worktree=? 已跑 ?s
     expected=? bound=? version=legacy）；本套排队，最多等 6s（算式：remaining=-s + 60s → cap=6s …）
  排队超限：等满 6s 仍拿不到门禁锁 …（持锁者：kind=? pid=3083658 cmd=legacy-writer … version=legacy）
     → 本套**没有运行**（这不是对代码的判定）          rc=2
$ 反向：新版运行持有两把锁时
  旧版写入者 flock -n 发布路径 = 拿不到（与旧版写入者仍互斥）
  伴生锁对任何人不放行
  rc=0 ｜ 运行结束后两把锁都还在：发布=yes 伴生=yes（永不 unlink）
```

读数：升级窗口里**没有静默并发**（正向：旧版持锁 → 新版排队、缺字段写 `?`、标 `version=legacy`、
到上限大声失败且「本套没有运行」；反向：新版持锁 → 旧版拿不到发布路径）。两把锁文件跑完都还在。

## 7 · 发现

### F1（必修）· `flip-p287-name.sh` 的「平铺家族」判据过宽，把带命名空间的合法根判成平铺名

- 位置：`skills/teamsmith/tests/flip-p287-name.sh:48` 的
  `FLAT_RE='^(teamsmith|review)-[a-z0-9-]*\.[A-Za-z0-9]{6}$'`（同文件 `leg0` 判定「命中平铺家族模式」）。
- 机制：`ns = <slug>-<hash8>`，`slug` 是**项目名**过滤 `[A-Za-z0-9_]`（`scripts/lib/common.sh:96`）——
  项目名里没有 `-` 时 slug 就不含 `_`，于是 `teamsmith-smoke-<slug>-<hash8>.<rand>` 落进上面那条
  「`-` 随便吃」的正则里，被当成平铺名。这条假设没有写进规格，规格说的是契约点名的**改动前平铺形状**
  （34c 段用的就是事故那条 `teamsmith-smoke.*`，它对新根零命中）。
- 我在**同一棵树**上只改目录名做 A/B（`env -u TEAM_PROJECT`，`TMPDIR` 各自私有）：

```
[cand]   ns=cand-237fcf6e    rc=1  ✗ leg0：有条目不合规（1 条）
                                   BAD teamsmith-smoke-cand-237fcf6e.MoabMr ← 命中平铺家族模式
[can-d]  ns=can_d-921d6da3   rc=0  ✓ leg0：全部条目点开头或带 ns，且平铺家族模式零命中（13 条）
```

- 第二种暴露方式（同一个 leg0）：调用者环境里 `TEAM_PROJECT` 与检出目录推出来的 slug 不一致时，
  夹具算的 NS 与嵌套运行实际用的 ns 不同，leg0 报「既不点开头、也没有 ns」并 rc=1：

```
$ TEAM_PROJECT=foo TMPDIR=/tmp/x/fliptp bash cand/skills/teamsmith/tests/flip-p287-name.sh --self-test
   ✗ leg0：有条目不合规（3 条）
       BAD teamsmith-smoke-cand-237fcf6e.Q7Xzde ← 既不点开头、也没有 ns ← 命中平铺家族模式
       BAD teamsmith-select.cand-237fcf6e.1172706.sh ← 既不点开头、也没有 ns
       BAD teamsmith-smoke-queue.cand-237fcf6e.94tpnc ← 既不点开头、也没有 ns
   ✗ leg0：没有收到带 ns 的根（名字里找不到 -foo-237fcf6e.）          rc=1
```

- 为什么算必修：这是**变更自己列的验收命令**（proposal 的 Acceptance 与 apply 任务书都有它），
  在一个独立树上 rc=1；它是随变更一起交付的翻转夹具，判据分辨不出「带 ns 的合法根」与「平铺名」，
  而同一变更的 34c 段用的是正确的那条模式 —— **同一交付物里两条判据互相矛盾**。本仓（主检出名
  `pm-skills` → slug `pm_skills`）因为 slug 含 `_` 恰好绿，所以作者与 PM 都没看见。
- 修法方向（留给 apply）：leg0 的「平铺家族」用**事故那条家族形状**（如 34c 的 `teamsmith-smoke.*`）
  或显式排除「名字里带本项目 ns」的条目；同时让夹具的 NS 与嵌套运行实际用的 ns **同源**
  （不要在子进程里 `-u TEAM_PROJECT` 而父进程还在用它），或直接从运行自己写的标记/台账里读 ns。

### F2（记录，不阻塞）· `34b⑫` 是既有的计时类脆弱断言，两棵树同样红

- 候选树：`--select 34,34b` 两次批量都红在这一条（`✓100 ✗1`），单独跑 `--select 34b` 一次全绿（`✓101 ✗0`）。
- 改动前的 main（`/var/tmp/v53/main` @ `3d92bb20`，同一环境、同一命令形状）：**2/2 次都红在同一条**——
  `✗ 34b⑫ 收尾：登记随它退出消失（只删自己那条）（期望 [1]，实际 [0]）`，`✓117 ✗1 rc=1`。
- 机制（我自己的探针，`ev/probe-34b12b.sh`）：夹具先 `grep -l | head -1` 挑一条 `no_lock=1` 登记，
  再对**那一条记的 pid** 发 TERM，然后只等 8s（40×0.2s）要 `.runs/` 空。选段运行是双重 fork，
  **select 副本的登记用的是副本 shell 的 `$$`**：TERM 只打掉副本父进程时，另一个同 `$$` 的进程会
  重新登记同一条文件，登记于是活到那个进程结束（我的现场里 `509089.run` 在 TERM 后 ≥20s 仍在）——
  8s 窗口因此时灵时不灵。按 D192，两棵树同红 + 机制在夹具侧 ⇒ **不是本变更引入的回退**，
  记成既有 flake（谁在门禁里遇到它，别当成 P287 的账）。

### O2（记录）· 发布路径丢失的那条点名行不带证据文件路径，其诊断节也不带运行身份

- console 行（§1.2）：`! 哨兵：发布锁路径（兼容声明）丢失 —— <路径> <状态>（互斥仍在伴生锁上，只记录不停跑）`

  没有伴生锁那一节里的 `本套：pid=… ns=… 工作树=… 席位=…`。
- 影响：任务书 ① 的「哪次运行」在发布路径这一现场只能从**诊断文件名里的 pid** 与运行自己的日志推。
