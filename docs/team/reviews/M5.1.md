## 为什么有些地方"required"没法硬起来（如实说明，不装作能）

1. **dispatch 只告警、不拒绝**：这是任务书本身的要求（"warn loudly (do not refuse)"）。理由也成立——worker 干活
   本身不需要这两个依赖，缺的是**证据层与规格层**；硬拒绝会让一个能交付的任务卡住。所以这里的强制力来自
   `doctor` 失败 + 每次派单的可见告警，不来自拦截。
2. **magic-context 的"检测到"≠"运行时会加载"**：doctor 沿用轻量探测（settings.json 里提到这个包 + 包自己的
   `package.json` 能读出版本），没有真的把扩展加载一遍（那需要起 Pi）。装了但加载失败的场景仍会显示 `✓`。
3. **包路径跟着 settings 文件走是个行为变化**：默认路径下与旧实现完全等价；但如果有人把 `TEAM_PI_SETTINGS_FILE`
   指到别处、而包仍在 `$HOME/.pi/agent/...`，现在会被报成缺失（假阴性）。这是为了测试可确定性所做的取舍，已写进
   `config.md`。
4. **`openspec --version` 没在真 CLI 上验证过**（本机没装 openspec）：夹具只覆盖"能打印版本"与"命令不存在"两种；
   一个不认识 `--version` 的真 CLI 会被显示为"已解析"（不会误报失败）。
5. **spec 目录只检查"存在"**：里面有没有合法 spec、能不能 `openspec validate --all --strict` 通过，是 OpenSpec
   自己的事（M2.1 已把 validate 放进验收入口），本任务不重复实现。
6. **两个预检都不安装东西**（不联网、不写项目外的路径）：只打印确切命令，装不装由 PM/用户决定。
7. **`doctor` 现在会真的失败**：本仓库当前 `openspec` CLI 未安装、`openspec/` 目录还不存在（M5.2 才建）
   → 本分支上 `team doctor` 是 `✗ 3 项失败`（含容器内既有的 `pi 缺`）。临时逃生口是
   `TEAM_REQUIRE_OPENSPEC=0`（只警告），或者按提示装 CLI + `openspec init --tools none`。
   注意：项目自己的 `.pi/team/config.sh` 里**没有**这些键（我核对过），所以走的就是新默认值。

3. **`TEAM_REQUIRE_*` 的降级是显式键**，不是"检测不到就放过"：默认失败、显式降级才警告，这样"没检测到"永远不会被
