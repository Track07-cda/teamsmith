# 候选提案收件箱

**用途**：把「值得做但还没决定做」的产品需求集中到一处，任何来源都可以往里写候选（PM、工人席位、用户、外部使用者反馈）。它**不是**看板、**不是** OpenSpec 变更、也不复制规格：只有越过采纳线（见下）的条目才会变成任务书或 OpenSpec 变更。

**每条的固定字段**

| 字段 | 含义 |
|---|---|
| ID | `C-<序号>`，PM 分配，不复用 |
| 来源 | 谁提出的：`user` / `pm` / `worker:<席位>` / `feedback:<出处>`（例如公开仓 issue、跨项目会议） |
| 观察（事实） | 谁在什么场景下遇到什么。可复现的给出命令/截图/日志出处；不可复现的明确写「未经复现」 |
| 影响 | 影响哪些使用者、多频繁、堵住什么 |
| 我们不知道什么 | 未验证的假设、缺的证据 |
| 粗成本 | 小 / 中 / 大 + 一句话依据（是否动契约、是否要迁移） |
| 状态 | `候选` / `待决策` / `采纳` / `驳回` / `搁置`，每次变更都记日期与理由 |
| 推荐 | 有则写；PM 的意见与提案者的意见分开写，PM 不得改写提案者的原文 |

**规则**

1. 提案者只写事实与影响，**不得**把它写成已批准的需求；「事实 / 推测 / 建议」三类必须分开写。
2. PM 负责去重、判断证据质量、把值得决策的少数条目移到 `待决策`；PM **不能**独自把条目改成 `采纳`。
3. 采纳权归用户：产品方向与优先级的采纳线由用户批；工程内部缺陷（回归、隐私、可复现事故）走既有授权，不占本表额度。
4. 每期（按里程碑计）最多 3 条进入 `待决策`，避免堆成待办垃圾场。
5. 驳回与搁置必须写理由，下次可以补证据重提，但不许换标题反复问同一件事。
