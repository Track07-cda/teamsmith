# M9.2 · `done` evidence must understand the OpenSpec pipeline phases

```
task:   M9.2
agent:  dev
deps:   v1.27.0 (M9.1 merged; the pipeline is documented)
note:   P1 (dev2) is writing `openspec/changes/spec-delta-gate/**` in parallel — do not touch `openspec/**`,
        and keep `tests/smoke.sh` additions in your own section.
```

> The F1 guard (`board set <ID> done`) requires evidence: a review record whose verdict is PASS/UNKNOWN/SKIPPED, or the
> task branch's tip already an ancestor of the protected branch. That model assumes **code tasks** — and the OpenSpec
> pipeline (M9.1) introduced phase tasks that legitimately produce no code:
>
> - `phase: explore` — the deliverable is a report and the PM's gate is *accepting the approach* (recorded in
>   `docs/team/DECISIONS.md`); today the PM has to reach for `TEAM_BOARD_DONE_FORCE=1` with a free-text reason
>   (done for E1, see its board row).
> - `phase: propose` — the deliverable is `openspec/changes/<change>/` and the gate is the PM's **proposal review**
>   (`docs/team/reviews/<change>-proposal.md`, verdict ACCEPTED).
> - `phase: verify` / `archive` — these do produce review records / ledger changes, so the current model mostly fits,
>   but `archive` is a PM action with no branch at all.
>
> Forcing with a free-text reason every time is exactly the kind of habit that erodes a guard. Make the evidence model
> phase-aware instead, so a phase task's `done` is provable in the same way a code task's is.

## Required behaviour

1. `done` (via `team board set <ID> done` and `team close <ID> --status done`) accepts, **in addition to** today's
   evidence, the phase-specific evidence of the task's brief:
   - `phase: explore` → a PM acceptance recorded for that task: a `DECISIONS.md` entry that names the task id, **or**
     `docs/team/reviews/<ID>.md`; the tool must print which one it found;
   - `phase: propose` → `docs/team/reviews/<change>-proposal.md` with verdict `ACCEPTED` (the change id comes from the
     brief's `change:` line); a `NEEDS-CHANGES` record must refuse, and say so;
   - `phase: apply` → unchanged (today's rule: PASS review record or merged branch tip);
   - `phase: verify` → a review record for the task id;
   - `phase: archive` → the change id appears under `openspec/changes/archive/` (a directory match is enough).
   Absent/unknown `phase:` keeps today's behaviour exactly (a code task with no phase must not become easier to mark
   done) — this is the invariant that matters most: **do not widen the guard for tasks that do not declare a phase**.
2. The refusal message keeps naming what to do next (the two existing options plus, when a phase is declared, the
   phase-specific route) and, when the phase is declared but its evidence is missing, says which artifact it looked
   for and where.
3. `team status <ID>` / the digest keep showing the same vocabulary; if you add a word, keep it consistent with the
   review-verdict words already used.
4. Smoke coverage: one fixture per phase showing acceptance with its evidence and refusal without it, plus the
   control that an un-phased task's rule did not change. Use the pipeline docs (`references/openspec.md`) as the
   source of truth for what each phase's evidence is; if the doc and your reading of the brief's `phase:` disagree,
   that is a finding — report it instead of widening the guard.
