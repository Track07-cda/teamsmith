# M4.3 · Make two operational failures visible (stuck dispatch paths)

```
task:   M4.3
agent:  dev
deps:   v1.18.0
note:   QUEUED — the PM will dispatch this after V4.0 (the core-lifecycle adversarial pass) lands, because this
        task changes the dispatch path that V4.0 is currently attacking. Do not start before the PM says so.
```

> Both findings came from real incidents on 2026-09-14 while the PM was running the team. Neither is exotic: they are
> the two ways a worker can become "silently dead", and in both cases the tool kept claiming everything was fine.

## Finding A — resuming a long session with a smaller-window model wedges the worker

**What happened**: `verify`'s session held ~361k tokens (1.6 MB of JSONL) from an earlier task. The PM re-dispatched
it with a model whose context window is 272k (`sub2api/gpt-5.6-sol`). The agent started, immediately printed
`Context full — /ctx-flush or /clear to continue.`, then looped on `Error: Connection error.` with `↑0 ↓0` tokens.
`team roster` still showed `pi 在跑`; the only reason the PM noticed was reading the pane.

**Required outcome**: make this visible *before* it burns a dispatch, and make the fix obvious.

- `dispatch` should detect that it is about to **resume** a session whose history is large relative to the selected
  model's window and either (a) refuse with a clear message offering `--fresh`, or (b) warn loudly and continue only
  with an explicit flag. Either is fine — pick one, document it, and cover it with tests. If a model window cannot be
  resolved reliably, use a conservative threshold (e.g. > ~200k tokens) and say so in the message.
  Token estimates may be crude (bytes/4 from the session JSONL) — say so.
- `team ps` / `team roster` should surface the agent session's size next to the model (e.g. `361k tok / 272k window`),
  so the PM can see the mismatch at a glance. Keep it cheap: this must not read full session files every render.
- `team dispatch --fresh` behaviour should be documented in `references/workflows.md` (when to use it: new task on a
  long-lived session, model change, or a wedged session).

## Finding B — dispatch into a wedged pane silently does nothing

**What happened**: after the wedge above, the PM re-dispatched twice. `team dispatch` printed
`! 窗口 pm-skills:verify 已存在 → 替换（旧回合会被打断）` and reported success, but the command was only typed into
the *stuck* `pi` process's input buffer: the new session id never appeared and nothing ran. Only killing the window
and dispatching again worked. (`team say` already verifies delivery with a pane fingerprint; `dispatch` does not.)

**Required outcome**: a dispatch must not report success unless the new process actually started.

- After launching, verify the launch (e.g. wait for the pane's foreground process to change / for the new session
  id or prompt marker to appear). On failure: kill the window, retry once, and if that also fails, say exactly what
  happened and what the PM should do (leaving the window in a known state).
- Report honestly: `✓ dispatched …（含启动校验）` vs `! 派单已发出但未能确认启动：…`.
- Add a test with a wedged fake agent (a process that ignores stdin) asserting the tool detects it and ends in a
  documented state instead of a false success.


## Finding C (revised) — a draft report is announced as "ready to review"

**What happened**: `team digest` listed `待复验 V4.0-verify → team review V4.0` while the report existed only in the
agent's working tree (not in HEAD). The PM cannot review an uncommitted report — `team review`摘录 the report from a
checkout of the branch — so the signal arrives before it is actionable.

**Correction after review**: in that specific incident the *task* genuinely had no review record, so the flag was
right about the task; only its "ready to review" framing was premature. Do not over-fix this: the display should
distinguish "report not committed yet (nothing to review)" from "report committed, awaiting PM review" — nothing more.

**Required outcome**: when the only matching report is untracked/uncommitted, say so (`report 未提交：先等 agent
交付`) instead of pointing the PM at `team review`; keep listing it (never silently drop) and keep the committed case
exactly as it is today. One test: an untracked report draft in a fake agent worktree → digest says "not committed
yet"; commit it → digest says "awaiting review".

## Finding D — a squash-merged branch is flagged as "pending wrap-up" forever

**What happened**: after the PM squash-merges a task branch (the normal path in local mode), the agent's branch
still holds its original commits, so `team roster`/digest keep showing `领先 N` and the "待收尾 → 收尾：提交并
push" hint — for a branch whose content is already in the protected branch. Every finished task leaves this noise
(visible right now for `verify` and `task/V4.0-core-lifecycle`).

**Required outcome**: tell the two situations apart.

- Cheap, exact signal: if the branch tip's **tree** equals the tree of a commit on the protected branch (squash
  merges produce exactly this when nothing else changed), report it as `已合并（squash，内容一致）` and stop
  suggesting "收尾：提交并 push". Fall back to today's wording when the tree differs (the honest "ahead" case).
- Do not try to detect arbitrary partial squash merges by patch-id unless it is cheap — one tree comparison plus a
  note that the signal is a heuristic is enough, and say so in `references/workflows.md`.
- Test both ways: an unrelated commit on the branch → still "待收尾"; the squash-merged case → no push hint.

## Finding E — a mid-task lifecycle restart looks exactly like "the agent stopped"

**What happened** (PM, live): the PM received

```
⚠ 未提交 3 个文件 · [auto] agent:dev · M6.3 · branch=task/M6.3-… · uncommitted=3 · unpushed=2(no-upstream)
   :: I'll start by reading the required files in order.
```

and spent a cycle diagnosing a "stopped agent with unfinished work" — `resume` refused ("在跑 1 个"), and the pane
then showed the truth: the agent was **mid-turn** ("Alchemizing… · bash · 4m42s") with its todo list open. The
notification had fired on an internal lifecycle event (a compaction/session restart inside the turn) and used the
*new* turn's opening line as the "last message", so the summary read like a stop notice.

**Required outcome**: a notification means "this agent's turn ended and it is waiting for the PM" — nothing else.

- Do not emit (or explicitly mark and do not count) settle notifications caused by internal lifecycle events
  (compaction, session restart, reload) while the agent is still working on the same task.
- Never use text from the *current, unfinished* turn as the reported last message; if no completed turn exists,
  omit the summary rather than fabricating one from a beginning.
- Keep the useful part: the `⚠ 未提交 N 个文件` flag stays, but it must not turn a working agent into a "delivered,
  uncommitted" story.
- Test with a fixture that triggers a mid-turn restart (or simulate one) → no inbox line, no wake-up; a genuine
  turn end → one line, as today.
