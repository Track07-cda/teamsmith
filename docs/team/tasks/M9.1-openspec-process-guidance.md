# M9.1 · OpenSpec guidance = process management (who runs which phase, in what order, behind which gate)

```
task:   M9.1
agent:  dev
deps:   v1.26.0
```

> **Direction from the user (verbatim, 2026-09-14):** the OpenSpec guidance must not restate what OpenSpec's own
> skills already contain. It must say **how to run and manage the OpenSpec *process*** — for example: a change
> request goes to an agent that runs **openspec-explore** and produces a rough plan; the PM reviews that plan; the
> same agent then runs **openspec-propose** to create the change; a **dev** agent implements it; an **independent
> verify** agent runs **openspec-verify**; and only when verification passes does anyone ask the user (or confirm as
> the user's proxy) whether to **archive**.
>
> The phases are real, per-tool commands: `openspec init --tools pi` (or `openspec update --tools pi`) generates
> `.pi/prompts/opsx-{explore,propose,apply,verify,archive,...}.md` and `.pi/skills/openspec-*/SKILL.md`. This repo
> was initialized with `--tools none`, so **they do not exist here yet**.

## Deliverable 1 — rewrite `skills/teamsmith/references/openspec.md` as a process guide

**Remove** the parts that duplicate OpenSpec's own documentation (artifact anatomy, requirement/scenario syntax,
the `openspec` command list, `validate` output format, the lint rule table). Keep at most a short "where the
authoritative docs are" pointer.

**Write instead** the pipeline, its owners and its gates — the part OpenSpec cannot know because it is teamsmith's
territory. Concretely:

| # | Phase (command) | Owner | Hand-in | Hand-out (artifact) | Gate before the next phase |
|---|---|---|---|---|---|
| 1 | `opsx-explore` | an **explorer** agent (a worker; the verify agent or a dedicated one — never the eventual implementer) | the user's request / problem statement, existing specs and code | exploration report: options, risks, recommended approach, effort; written as the task's report | **PM**: accepts the approach, records the decision (`docs/team/DECISIONS.md`), and writes the propose brief |
| 2 | `opsx-propose` | the **explorer** (same agent, it holds the context) | the accepted approach | `openspec/changes/<id>/` (proposal, delta specs, design, tasks) — **planning only, no code** (OpenSpec's own `opsx-propose` states this boundary) | **PM change-artifact review — a recorded gate, the same standing as `team review`**: `openspec validate --all --strict` + `spec-lint` green, and the PM's verdict is written to `docs/team/reviews/<change>-proposal.md` (ACCEPTED / NEEDS-CHANGES with per-item findings and the commands the PM actually ran). **No apply task may be dispatched before it is ACCEPTED**; a revised proposal is re-reviewed, never waved through verbally. |
| 3 | `opsx-apply` | a **dev** agent, different from 1 and 4 | the change + the brief | code committed on its task branch + report | **Independent verification** is dispatched to a different agent |
| 4 | `opsx-verify` | an **independent verify** agent (never the implementer) | the change, the landed code, the report | verification record (`docs/team/reviews/<ID>.md`) + findings; each scenario of the change exercised, with red/green evidence | **PM**: re-runs the gate on the merged tree, decides `done`, and only then proposes archiving |
| 5 | `opsx-archive` | **PM** (it changes the ledger) | the verified change | `openspec/changes/archive/<date>-<id>/` + updated capability specs | **the user** confirms; the PM may confirm as the user's proxy only when it states that plainly and records why (small, reversible, already covered by the approved approach) |

Also state, in prose and briefly:

- **One phase = one task = one owner.** Phases are never merged into a single task, and no agent verifies its own
  work (that is the same rule as `team review`, applied to the OpenSpec phases).
- **How it maps onto teamsmith**: every phase is a normal brief (task id, `agent:`, `deps:`), the change id goes in
  the brief, and the phase name goes in a `phase:` header line (see Deliverable 2). The board carries the tasks; the
  change carries the requirements; the ledger carries the evidence. Nothing here replaces `reports/`+`reviews/`.
- **The PM's proposal review checklist (eight points, written into the guide so it can be followed literally)**:
  1. it matches the approved exploration (scope creep *and* scope cuts are called out);
  2. the delta specs describe only externally observable behavior (commands, exit codes, files on disk) and every
     scenario can fail;
  3. coverage is closed both ways: every affected requirement has at least one task item, and every task item points
     at a requirement/scenario (no orphan tasks);
  4. boundaries are explicit (what is out of scope, who may not touch which paths);
  5. the acceptance commands are copy-pasteable and exist (the PM runs `validate`/`spec-lint` and spot-checks them);
  6. defect fixes state the flip (red → green, or "break the implementation → the guard must fail → restore it");
  7. no conflict with existing specs: duplicates/supersessions are MODIFIED/REMOVED deltas, not a parallel statement
     (grep the specs);
  8. granularity: can one apply task finish it? If not, name the split and the order (several tasks under the same
     change, applied and verified one by one).
- **What the PM does at each gate** — a short checklist per phase (what to read, what must be true, what to write
  down). This is the core of the guidance: the PM is the only role that owns a gate.
- **Preconditions**: the project must have OpenSpec's agent commands generated for the agents' tool
  (`openspec update --tools pi`, or the equivalent for another CLI), and `TEAM_OPENSPEC_BIN`/`TEAM_SPEC_DIR` resolved
  (`team paths`, `team doctor`). Say what breaks without them (the phase cannot be invoked as a command; the
  fallback is doing the same steps by hand per OpenSpec's docs — and then the PM cannot check that the phase really
  ran, so prefer generating them).
- **Escalation**: when an exploration concludes "not worth doing", or a verification fails twice, the PM stops the
  change (leave it in `openspec/changes/` with a note) instead of pushing it through.
