> M8.1 fixed the PM launch path and, being explicitly out of its brief's scope, *measured* the same defect on the
> worker side instead of fixing it. The PM reproduced it independently — this task closes it.

## The defect (PM-verified, deterministic)

Window harnesses run `bash -lc`, and on this machine the login-shell PATH does **not** contain `~/.bun/bin` (measured:
`bash -lc 'command -v codex'` → not found; the caller's PATH does contain it). So for a worker CLI that is only
visible in the caller's PATH:

```sh
# fixture: /tmp/…/extra/worker-bare (a script), PATH=/tmp/…/extra:$PATH
TEAM_AGENT_CMD='worker-bare --pf {prompt_file} --ask {prompt}'
TEAM_AGENT_BIN='worker-bare'
team dispatch dev T1.1 <brief> --fresh
  ✓ dispatched T1.1 → <session>:dev（含启动校验：proof=spawn pid=…）     ← success line
# the CLI never ran (its log file was never created), and the window is gone
```

Two distinct problems, both worth fixing:

1. **The bare name is not resolved**: the PM side now substitutes the first word with the resolved absolute binary
   (`team_pm_subst_first_word`, generic); the worker side does not. The rendered worker command should get the same
   treatment (or, if you prefer, prepend the resolved binary's directory to the window PATH — say which you chose
   and why; consistency with the PM side is worth something).
2. **The success line is not evidence that the CLI started**: `proof=spawn` proves the *harness* shell started, not
   that it exec'd the agent. When the CLI cannot be found the harness exits 127 and dispatch still reports success —
   the worst kind of signal. Make dispatch distinguish "harness started" from "agent started": reuse the M7.5 exit
   event (`state/dispatch-<agent>.exit` with the nonce) and/or surface `exit=127` in the report line, and preserve a
   diagnostic (window tail + rendered command + resolved binary) the way the PM path now does
   (`state/pm-launch-failed.log` is the sibling).
