## User's final product direction

The user does **not** want PM to default to `team reply post`. The desired normal flow is:

1. The agent writes its normal Pi response.
2. A special marker in that response means “this is a key reply”.
3. A Teamsmith Pi extension captures the assistant message and publishes the complete body to the existing key-reply page/history.
4. The marker is control metadata, not user content: it must be removed from the **Pulse reply page/history and from the Pi response shown to the user**.
5. Unmarked ordinary Pi replies stay ordinary and are not published. The CLI may remain for manual/backfill/recovery, but is not the default reply path.

This supersedes the temporary P391 heredoc correction and the current default explicit-post instruction. Do not reopen that choice. P391 is paused for the key-reply portion until this exploration settles a compatible design.

## Questions the exploration must resolve

### A. Exact marker and message semantics

Recommend one small, explainable marker syntax and placement that the model can reliably emit in a normal response, with title derivation or a minimal title form that needs no CLI. Avoid collision with Magic Context's required `§N§` reply tags, Markdown/code blocks/quoted examples, arbitrary marker text inside a longer paragraph, and internal tool messages. Define whether only a final assistant response qualifies, how assistant messages with tool calls/intermediate text are treated, and how multiple marked messages in one run are handled. Full body formatting and content must survive without truncation.

### B. Capture, identity and deduplication

Choose the actual Pi public events and payload fields that identify a real assistant response, its session/run/message position and content. Show how to distinguish assistant messages from user/custom/tool results, avoid capturing quoted marker examples, and bind publication to the verified project/seat rather than message-supplied identity. Use the existing reply store/page writer or a single shared authority, with atomic persistence and audit. A visible Pi response must not be withheld merely because reply-page persistence failed; failure and later recovery must be honest and must not cause duplicate posts.

### C. Removing the marker everywhere the user reads

This is a hard product requirement, not optional polish. Separately prove the design for:

- the stored key-reply body and Pulse current page/history/CLI readers;
- Pi's finalized assistant message/transcript;
- Pi's actual streamed/rendered frames, including whether a marker can flash before `message_end`.

Investigate `message_update`/`message_end` transformations and available renderer hooks. If the public API cannot remove an already streamed marker, compare concrete alternatives: a marker form Pi never renders, a display-time renderer/filter if supported, placing the marker at a defensible boundary, or requiring a minimal upstream Pi API. Do not call storage-only stripping a complete solution and do not patch Pi internals in this exploration. Preserve the rest of the message byte-for-byte apart from the control marker.
