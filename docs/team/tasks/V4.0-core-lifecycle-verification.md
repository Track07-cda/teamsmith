# V4.0 · Adversarial verification: the core lifecycle (not the adapter)

```

```

> The adapter layer got a dedicated adversarial pass (V3.0) which produced a blocker. The **core lifecycle** has
> only had partial adversarial attention (V1.1). This task attacks the claims the whole tool rests on.
> **Mission: falsify them.** Findings beat agreement; a "could not break it" section is only credible if it shows
> the exact commands that tried.

## Claims to attack (each must end as "broken (finding)" or "attempted, held — here is the command")

### 1. "Status is a promise"
- `team board set <ID> done` / `team close <ID>`: can you get a task marked `done` without the code actually being
  on the protected branch, or without a review record? What does the tool *claim* at that moment?
- `team digest` "pending wrap-up" detection: dirty worktrees, unpushed branches, branches ahead of main — try to
  make it miss something real or report something that does not exist (false positive).
- Recovery paths: what happens when the merge/push failed halfway, when the branch is already merged, when the
  review record is stale (record exists for an older commit of the same task id)?

### 2. Review evidence integrity (`team review --dir …`)
- Refusals: dirty checkout, checkout on a different branch/commit than the task branch, missing report, missing
  task file, `--dir` pointing at the main worktree or at a worktree of another task.
- Does the review record truthfully describe **which revision** was verified (compare what it prints with what the
  checkout actually contained — e.g. move the branch between checkout and review, or add an untracked-but-ignored
  file that changes the gates' outcome).
- Hard timeout (`TEAM_REVIEW_TIMEOUT`): does a hanging gate really end as `TIMEOUT` → FAIL, or can it be reported
  as PASS/UNKNOWN? Try a gate that prints a lot then hangs, and one that traps signals.
- `--strong`: can you make it claim flip/independent evidence that is not there (e.g. report text that merely
  *mentions* the words), or fail a report that genuinely has it?
- `--no-gates`: what is recorded, and can it be mistaken for evidence later (digest/roster/board)?

### 3. Dispatch guards
- Dirty worktree belonging to a **different** task must be refused; the same task must be allowed to resume.
- Protected-branch checkout, missing worktree, unknown agent, missing task file, task file outside the project.
- Model limits (`TEAM_MODEL_LIMITS`, including wildcards like `openai-codex/*`): can you exceed a limit, or get a
  false refusal? Does the counter survive a crashed agent (`team ps`)?
- Capacity floor: with `TEAM_MEMINFO_FILE` fixtures, can a dispatch slip past the swap floor, or be refused while
  swap is actually fine (zram must not count as disk swap)?

### 4. Notification and knock delivery
- `team notify` (argv) vs `--from-file`: byte-exactness, newlines, empty summaries, very long summaries,
  `TEAM_INBOX_MAX_CHARS` truncation honesty.
- Dedup (`TEAM_NOTIFY_DEDUP_SEC`): can a genuine second notification be swallowed, or a duplicate slip through?
- Offline agent: `team say` must fall back to the inbox and say so — try with no window, a dead window, a busy pane.
- Cross-session typing must be refused (except a registered meeting knock); try to find any path that types into
  another project's/session's window.
- Knock: refusal without `TEAM_MEETING_KNOCK=1` / without a registered peer session; does a failed knock leave a
  false "delivered" claim anywhere?

### 5. Meeting protocol guards
- `intent` allow-list (no command/order), command-like text rejection, `--as-user` requiring a human terminal plus
  the flag, per-side message caps and TTL, consensus requiring both sides, and **zero writes into the other
  project** (verify with a file-level before/after diff of the peer mock).
- Can an `agree` be forged for the other side? Can a closed meeting be reopened or mutated?

### 6. Bootstrap / init idempotence
- Re-running `bootstrap`/`init`: no silent overwrite of existing files, `AGENTS.md` section stays single, the legacy
  `<!-- pi-team:begin -->` marker migrates exactly once, `.gitignore` does not accumulate junk.
- `--print` must change nothing (prove it with checksums).

### 7. Version / reload distribution
- `team mark-loaded` + `team version --check` honesty (stale session, missing marker, version mismatch across
  `common.sh`/`SKILL.md`/CHANGELOG), `team changelog --since`, and the `state/reload-requested` marker path.
- Can the check report "in sync" while the loaded skill is older (or vice versa)?

### 8. Watchdog semantics
- "No pending work ⇒ no wake-up" (including board `todo`/`wip` with `TEAM_WATCH_PENDING_BOARD=0`), standby
  suppression, restart quota (`TEAM_WATCH_MAX_RESTARTS`), capacity logging, and the single-backend state reporting.
- Can you make it wake a PM that should sleep, or stay silent with real pending work?

### 9. Boundary guards
- The "must be running inside this project" guard on destructive tmux operations: try to reach another session or
  an unrelated window; try empty/relative targets (this class of bug killed a PM twice, so test the guard hard).
- Anything that reads or writes outside the project root (other projects' repos, session files, credentials).
