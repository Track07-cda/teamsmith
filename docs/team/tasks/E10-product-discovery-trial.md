## 授权来源与定位

使用者的目标（原意）：Teamsmith 安装者希望高效管理项目开发，项目有完善文档与规格、有足够自主性，自己不用一直盯着详细进度和方案，可以专注高层产品、需求和架构；使用者希望 agent **主动辅助提出产品需求并补足细节**，而不是要求自己先写详细需求。背景记录见 `docs/team/DECISIONS.md` D99。

本任务是**独立产品探索能力试跑**，不是 PM 提出的产品解决方案，也不是已经建立平级产品角色的宣告。你现在在普通 agent 席位运行，工具权限仍受当前协议约束；E9 正由另一席位检查如何实现真正的平级关系。不要参考 E9 的草稿或与它对齐意见，避免独立性失效。PM 不应预先指定你建议哪项功能。

## 研究范围

1. 从上述产品目标出发，独立阅读当前公开 README、SKILL、关键操作文档与相关规格；核对 GitHub 公开 issues/PR 或项目内经处理的使用反馈（只读即可，如没有可信来源请如实说明）。可以在隔离的临时项目里亲自尝试一段真实使用流程，但不要修改这个项目的产品文件、共享配置或外部环境。
2. 找出使用者目标与产品现状间**最值得关注的一处落差**，并提出 1–2 个候选产品需求。每个候选分开写清：目标使用者要完成什么、可复核的观察、你的推断（含不确定度）、用户可感知的行为要求和不做的范围；列至少两种解决方向和主要取舍，推荐一种并说明为什么值得现在讨论。候选可以是功能更新，但不要为了迎合 0.2 版本号硬凑功能；当前材料不足时给出待验证假设和补证办法，不得伪造用户访谈、下载数据或优先级。
3. 评估「使用者是否仍需盯任务细节」：按你建议的行为，指出用户只需做哪项**高层决定**，以及后续什么细节由 PM/团队自行承担。列出一条反向验收：若功能实现了但使用者仍需要亲自追进度或补细节，它应被判未达到目标。
4. 同时做一次自我反驳：如果不做你的推荐需求，只修文档或用已有能力配置/训练 PM，能否同样解决问题？哪些现有证据可能推翻你的建议？必要时诚实结论为「现在还不值得开发」。

## 交付与边界

只在 `docs/team/reports/E10-dev-bob.md` 写报告并提交任务分支。报告是**你的原始产品判断**，PM 会另外写可行性意见，不修改你的结论；使用者能看到完整原件。不要创建 OpenSpec change、开发任务、规格或第二套需求文档；不要修改产品代码/配置/其他席位目录；不要对外联系或向 GitHub 发写请求，不推任何远端，不读 token。项目账本公开，证据里不得出现本机路径、其他项目名、内网地址或隐私资料。

开工先按 `AGENTS.md` 读自己的 `docs/team/threads/dev-bob.md` 与本任务书，再读相关 capability specs 和 `skills/teamsmith/references/openspec.md`。这是一个只读 explore，不得擅自进入 propose/apply。被阻塞时从你的席位工作树执行 `bash skills/teamsmith/scripts/team notify pm "<一句话>"` 并交 PARTIAL 报告；若生成的通用提示写成 `team notify dev-bob`，以这里的 PM 收件人为准。

## 验收

- 每项事实附文件位置或公开 URL；「观察 / 推断 / 建议」明确区分，不把没有用户证据的假设说成已证实的痛点。
- 至少一项完整候选（或证据不足的明确结论），含行为要求、替代路线、自我反驳、高层人类决策点和用户仍需盯细节的反向验收。
- `openspec validate --all --strict && bash skills/teamsmith/tests/smoke.sh`：真实运行并记录输出尾部；如环境未能跑，按事实报告，不能声称通过。
- 报告提交后保持分支干净；PM 独立核实事实，再把原件与自己意见分别呈给使用者。本报告通过也不等于产品需求自动获批。
