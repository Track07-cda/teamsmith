> `team doctor` already reports whether magic-context is installed, the skill mentions it in three places, and
> `templates/memory-seed.md.tmpl` exists — but there is no single place that explains **how a long-lived PM should
> actually use memory**: what belongs in project memory, what must land on disk instead, how it interacts with
> compaction, restarts, `/reload`, and how to work without it. Write that guide.

## Deliverable: `skills/teamsmith/references/memory.md` (English, ~120–180 lines)

Cover, concretely:

1. **Why a PM needs memory at all** — it is the only role that spans tasks/restarts; an agent is a short session.
   Include the failure it prevents: decisions that get re-litigated, constraints that silently disappear, the
   "context says X but disk says Y" drift (we hit exactly that: an old skill copy living in a compacted context).
2. **The three layers, and who owns what**:
   - session memory (magic-context: search/expand/notes) — the PM's shortcut;
   - **disk evidence** (`reports/`, `reviews/`, `BOARD`, `threads/`, `DECISIONS.md`) — the only thing other people
     and other tools trust;
   - skill version state (`mark-loaded`, `version --check`, `/reload`) — memory *about the tool itself*.
   State the rule plainly: **conclusions must land on disk; "I remember" is never evidence** (creed #6, #1).
3. **What belongs in project memory** (one standalone fact per entry): project facts (session/window, roster, gates,
   protected branch, worktree paths), the creed's working rules, and project-specific traps ("the e2e gate needs a
   build first", "this test is flaky, re-run once"). Point at `templates/memory-seed.md.tmpl` as the starting set.
   What does **not** belong: anything that will be stale in a day (current task state — that is BOARD), secrets,
   long logs, or anything that is evidence on disk.
4. **When to read / when to write** — the two moments from the PM prompt (session start: search before re-deriving;
   wrap-up: record cross-task rules, park "do later" items), plus what to do when memory and disk disagree
   (**disk wins; fix the memory**).
5. **Lifecycles**: what survives `/compact`, a restart (`pi -c`), `/reload`, or moving the worktree (sessions are
   keyed by cwd — the PM's own memory is tied to its session, which is why "keep the worktree path stable" matters).
   Explain honestly what magic-context does *not* do (it does not make you stateless-safe, it does not sync across
   machines, it is not shared with other agents).
6. **Working without it** — `team doctor` says "not detected"; the fallback routine (read `DECISIONS.md`, the
   roadmap's leftovers, the newest thread entries) and what you lose (search over compacted history).
7. **Optional: keeping another PM (or a human) in sync** — memory is per-session/per-machine, so anything another
   PM needs must be on disk or in a `team meeting`; say that explicitly.
