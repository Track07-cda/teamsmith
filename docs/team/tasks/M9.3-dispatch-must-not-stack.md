# M9.3 · `dispatch` must not silently stack a second task on one agent

```
task:   M9.3
agent:  (unassigned — dispatch when an agent is free)
deps:   M9.2 (phase-aware `done`), M9.4 (pending list vs board)
```

> This is the tool-side half of DECISIONS **D16**. The PM's half is a rule ("check for an unfinished task before
> dispatching"); the rule failed once already — P2 was dispatched to `dev` while M9.2 was still in flight, the new
> dispatch replaced its window, and M9.2 had to be handed to another agent. The tool knew the agent's task and branch
> the whole time (`state/<agent>.env`, the board, the worktree) and said nothing.

## Required behaviour

1. `dispatch <agent> <ID> …` inspects the agent's current state before launching:
   - the task recorded for that agent (`state/<agent>.env` / the board row) is **not** finished (no review record, not
     merged, not `done`) **and** its worktree has the task's branch checked out → **refuse by default**, printing:
     the task it found, its status, the branch, and the two ways forward — finish it (`team resume <agent>`), or
     override explicitly.
   - `--force` (name it what fits the existing conventions) is the explicit override, and the override is **printed**
     in the dispatch output so it lands in the transcript (no silent takeover).
   - When the agent is idle and its previous task is finished (review record / merged / board `done`), behaviour is
     unchanged — a plain dispatch, exactly as today.
2. The refusal must not fire on the **same** task: re-dispatching the task the agent already has is how
   `team resume` and recovery work today; that path stays as it is (it is the "continue" case, not the "stack" case).
3. If the agent's state cannot be determined (no `state/<agent>.env`, unknown worktree), do not guess: proceed as
   today, but print the one line saying which signal was missing.
4. `team resume <agent>` and `team up` keep their current semantics; if either of them would stack a *different*
   task than the agent currently has, apply the same refusal (they are the other two doors into the same room).

## Fixtures (smoke)

- agent with a delivered-but-unreviewed task → plain dispatch refuses, the message names task/branch/status and the
  override; with the override → dispatch proceeds and the output shows the override;
- agent with a finished task (`done`) → plain dispatch succeeds, unchanged output;
- re-dispatch of the agent's **own** current task → unchanged (this is the recovery path);
- unknown agent state → dispatch proceeds and says which signal was missing;
- `--dry-run`/`--print` variants stay side-effect free.

5. **Ambiguous task ids**: a task id that matches **more than one** brief (`docs/team/tasks/<ID>-*.md`, e.g. an old
   `V1.1-review-dir.md` and a new `V1.1-reverify-…md`) must be refused with both paths listed — today the slug of the

   a worse case could dispatch the wrong task's scope. Deterministic resolution: refuse on ambiguity, never guess.
