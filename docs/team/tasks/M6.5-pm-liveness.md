# M6.5 · False PM liveness (breaks `team up` and the project's own gate) + honest TIMEOUT attribution

```
task:   M6.5
agent:  dev
deps:   M6.1 (state helpers), M6.2 (review verdicts) — both merged
```

> After the environment restarted (new tmux server), the project's own smoke suite went from green to **7 failures**,
> identical on `main` and on every task branch. Root cause found by the PM: **a freshly created, empty session window
> is reported as "the PM is running"**, so `team up` skips starting the PM while claiming success. This is the
> "status is a promise" class — it hides the very failure the tool exists to surface.

## Finding 1 (high) — `team up` claims a PM is running when nothing was started

**Deterministic reproduction** (PM-built, `/tmp/pm-freeze-repro`):

```sh
# temp repo + teamsmith init, TEAM_PI_BIN → a fake pi that logs its argv, TEAM_SESSION=<nonexistent>
team up
  ! tmux session 'repo' 不存在：重建
  ✓ PM 在运行（tmux）          ← FALSE: the session was just created and is empty
# fake pi was never called; no window has any process that could be a PM
```

Why: `team_tmux_ensure_session` creates the session with `-n "$TEAM_PM_WINDOW"`, so `team_pm_window_exists` is true
immediately; `team_pm_state` then looks at the pane's **front process** and classifies *any* non-shell process as
`running:*`. In this environment a freshly created pane's front process is not a shell name (observed: `tmux`,
likely a shell hook/auto-attach), so the state becomes `running:tmux` → `team up` reports "PM 在运行" and skips
starting it. The same false liveness makes `team watchdog-status` claim the PM is alive, and it is what breaks the
smoke assertions (`up 报告了 PM 启动`, `PM 的 pi 真的被拉起`, `PM 用 -c 延续会话`, `PM 用 @文件 传开场提示词`,
`watchdog-status 看到 PM 在跑`, `up 不会重复启动已跑的 PM`, `PM 没有被拉起`).

**Required outcome** — liveness must be proven, not inferred from "not a shell":

- `team_pm_start` records the PM pid (e.g. `state/pm.pid`). Liveness = that pid is alive **and** its cwd is inside
  this project (the existing `team_proc_cwd`/ownership helpers apply). Manual case (PM started by hand in the pane):
  treat the pane as a running PM only when its front process is **our configured agent binary** (resolve the same way
  `dispatch` resolves `TEAM_AGENT_BIN`/`TEAM_PI_BIN`) *and* its cwd is in this project.
- Anything else (a `tmux`/`sleep`/editor/unknown process, or a fresh empty pane) must be reported as
  `foreign:<cmd>` / `unknown:<cmd>` (+ cwd) and must **not** suppress starting the PM — `team up` should create/start
  in that window (or refuse with `TEAM_REPLACE_FOREIGN_PM` semantics — your choice, but state it and make it loud).
- `team watchdog-status`, `roster`, `ps` must use the same proof; never print "PM 在运行" without it.
- Tests with fixtures, no reliance on the developer's shell:
  1. fresh session, empty pane whose front process is a non-agent (spin up `sleep`/`tmux` in the fixture window) →
     `team up` **starts** the PM (assert the fake agent's argv log), `watchdog-status` does not claim a PM beforehand;
  2. recorded-pid path: start a fake agent, kill it → liveness false again; alive → true;
  3. a foreign agent in the PM window (different cwd) → `foreign:*`, still not "running";
  4. the 7 smoke assertions above must pass **in this environment** (that is the actual acceptance test here).

## Finding 2 (medium) — a TIMEOUT verdict can be attributed to the gate's own exit code

`cmd-review.sh` decides `TIMEOUT` from the wrapper's exit status (124/137). A gate script that exits 124 **by
itself** — or a suite whose internal test propagates 124 — is then recorded as "the gate was killed at the
deadline", which is a different fact. (Observed live: the same smoke run was recorded `TIMEOUT` in one review and
`FAIL` in another, with the gate itself finishing in ~50 s.)

**Required outcome**: attribute a timeout only when the wrapper actually hit the deadline — require *both* the
wrapper's exit status and an elapsed time close to `TEAM_REVIEW_TIMEOUT` (e.g. ≥ timeout − a small grace), or use
`timeout --verbose` output. Otherwise the verdict is `FAIL` (or `KILLED:<signal>` if it was signal-terminated) and
the record states the elapsed time. Add a test: a gate that exits 124 immediately → **FAIL**, not TIMEOUT; a gate
that sleeps past the deadline → TIMEOUT.
