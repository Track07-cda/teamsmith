## 现场（PM 实测 + 收件方报告）

1. **收件方报告**：dev2 在 2026-09-22T14:44:48Z 的消息里写「**同样是旧消息的重复投递**（14:09 那条）」——
   它收到的正是 PM 在 **14:09:56Z** 发出、并且**已经进过它收件箱**的那一条
   （收件箱文件里那条在同一位置，没有第二份；`docs/team/inbox/dev2.md:82`）。
2. **PM 实测的状态**（`state/inbox-watch/teamsmith_dev2-e88859f1.*`）：
   - `.wake`（该席位的唤醒 spool）**9 行**，最后一行就是 14:09 那条（`1790086196029`）；
   - `.seen`（去重记忆）**8 行**——**缺的就是最后这一行**。
   即"**投递了但没记进去重记忆**"的形状。
3. **重启历史**（`state/inbox-watch.log`，该席位当天）：
   `14:52:40 stopped` → `15:05:56 TEAM_IDENTITY_CONFLICT + started` → `16:53:32 stopped` → `16:54:21 … + started`；
   每次重启都伴随一次 `TEAM_IDENTITY_CONFLICT`（新进程继承了旧 env 里的 `TEAM_ROOT`，M40 的守卫纠正它）。
4. **一条可疑的日志**：`14:33:07 wake n=1 total=1 inbox=dev kinds=say`——`total=1` 说明某个 spool 被**从头**读了一遍，
   而它周围的日志是 dev3 的 watcher；这行的 `inbox=dev` 与上下文不符（**要么标签写错，要么读错了 spool**）。

## 要裁决的设计问题

1. **投递必须幂等**：跨进程重启时，"已投递但未记录"的那一条**不得**再投递一次；
   两个方向都可选，但要论证：① **先记后备**（send 之前把该条写进 `.seen`/in-flight 标记；崩了也只是丢掉一次唤醒，
   消息仍在 durab​le 收件箱里）；② **in-flight 标记 + 重启时的三态判定**（未开始/进行中/已完成），
   进行中的按"至多一次"处理并在账本里记一行。
2. **账本要能看出重放**（P28 已有的口径）：任何重复投递事件都要能在 `inbox-watch.log` 与 `deliver=` 计数里看出来
   （"重复"与"新消息"必须可区分）。
3. **收件方要能自证**：一条消息在收件方看来"是重复"时，它应能从**落盘的记录**判断（例如 spool 与 `.seen` 的关系），
   而不是靠记忆——本条正是靠这一点被发现的。
4. **那条 `total=1` 的日志要解释清楚**：标签/读数错就是缺陷；真的从头读过就是"重放"（要按 ①② 收口）。
5. **可证伪**：夹具模拟"投递后立刻被杀（未记 `.seen`）→ 重启" → **不得**出现第二次投递；
   反向：真的新消息仍要唤醒；`SIGKILL` 掉 watcher 后重启 → 不重放已投递的旧行。

## 追加现场（PM，2026-09-22 17:5x）：**PM 自己被一条 2 小时前的 nudge 叫醒了**

- 我收到的唤醒文本是 `[nudge] from pulse :: [pulse] 待办：未读通知 7 · 待复验 4 → …`，
  而该文本在 `state/nudges.log` 里对应 **16:13:56Z / 16:28:56Z** 两条（最新一条是 16:43:56Z 的 `9 · 4`）
  —— **即 2 小时前的旧 nudge 被重新投递**。
- 核对当前状态：`inbox_lines` 与文件行数**六个席位全部 0 未读**；`digest`/`pending` 都是 0；
  **`watchdog.log` 最近一拍是 `16:58:56Z 无待办：不叫醒 PM`** → 巡逻**没有**再生成新 nudge。
- PM 的唤醒 spool：`teamsmith_pm-d59ea631.wake` **247 行**、`.seen` **313 行**；
  该 nudge 文本在 spool 的 **240/241 行**（16:13/16:28），而 watcher 日志里那两条**当时已经投递过**
  （`16:13:57 wake n=1 total=85 kinds=nudge`、`16:28:57 … total=86 …`）。
- **结论**：这与 dev2 报的"旧消息重复投递"是**同一个缺陷**（投递跨重启不幂等 / 旧行被当新行唤醒），
  而且受害者是 **PM 自己**——它让人去处理一件早已完成的事。提案必须覆盖这一例：
  **比 `TEAM_INBOX_WATCH_STALE_SEC`（默认 900s）更旧的行，只进 durable 收件箱、绝不唤醒**（P28 已定的口径），
  以及"投递过的不再投递"（幂等）。

## 追加现场二（PM，2026-09-22 18:0x）：**同一条旧 nudge 在 10 分钟内被投递两次**

- 第二次收到**同样文本**的 `[nudge] from pulse :: … 未读通知 7 · 待复验 4 …`（第一次见上一节）。
- **`.seen` 里明明有它**：`grep -c "待复验 4" .seen` = **3**（含 `1790094537381 nudge pulse -`），
  即去重记忆认为**已投递**。
- 巡逻侧没再生成：`watchdog.log` 最后是 `16:58:56Z 无待办：不叫醒 PM`；
  outbox 的 `delivered.log` 最后一条是 `1790095437`（= 16:43:57 那条 `9 · 4`），**之后没有发送**。
- 收件侧日志 `inbox-watch.log` 自 16:43 之后只有 `kinds=knock` 的投递（90/91/92），**没有新的 `kinds=nudge`**。
- **推断（要由提案实现方证实/证伪）**：唤醒路径在**读完 spool 之后没有把偏移持久化**（或读到了旧段），
  于是同一条旧行每一轮都被重新读出并投递，而**去重记忆 `.seen` 在这一路上没有被咨询**（否则它会被跳过）。
- **要求**：① 去重必须在**所有**投递路径上生效（含重读/重放）；② 偏移的持久化与投递必须**原子化或可自愈**
  （投递前记 in-flight、投递后落偏移；重启后不重复投递）；③ **旧行（> `TEAM_INBOX_WATCH_STALE_SEC`）
  只进 durable 收件箱、绝不唤醒**；④ 账本要能区分"新消息唤醒"与"重放唤醒"（P28 已有此口径，落实到这里）。

## 追加现场三（PM，2026-09-22 18:1x）：spool 已截断、rescan 投递 0，**旧文本仍在后续回合边界上再次出现**

- PM 已把 spool 截断（证据留档 `/var/tmp/P71-pm-wake-spool-1746.bak`），watcher 走了
  `spool shrink → bounded rescan from 0`，并记 **`deliver=0`**；
- 之后 PM **又**在下一个回合边界收到了 `未读通知 9 · 待复验 4`（= 16:43 那条）的 nudge 文本；
- 与此同时：`nudges.log` 最新仍是 **16:43:56Z**（未再生成）、`watchdog.tick.log` 末尾是
  **"pulse: 无待办（PM 在跑：不打扰）"**、outbox 的 `delivered.log` 之后没有新发送、
  `.seen` 里已有该文本。
- **推断（要证伪/证实）**：这条文本可能已被**投递进 Pi 会话的自身队列**若干份，
  于是它会在**之后的每个回合边界**被重新呈现一次——即"**投递侧的重复**"与
  "**会话侧排队副本**"叠加。提案必须覆盖：**投递确认必须落到唯一的 durable 记录上**
  （同一条消息在会话队列里也不得多份），以及**已投递文本不得在任何后续路径重现**。
