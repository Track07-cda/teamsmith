## 用户的原话（这是本变更的唯一需求来源）

> 我看 `team --help` 里描述的语言风格太难懂了，而且需要默认是英文，且支持多语言。`--help` 菜单出来的也很乱，不好看。
>
> 你要确保的是对这个项目的实际内容和原理不懂的用户能够通过 `--help` 了解各种功能的作用和含义，避免过于简化的描述。

## 现状（PM 2026-10-14 实测，你复核一遍）

- `team help` 是一段 98 行的中文 heredoc（`scripts/lib/cmd-project.sh` 的 `team_cmd_help`），风格是**源头压缩式**的：用 `→` 串起一长串动作、把前置条件塞进括号、概念不解释（例如 bootstrap 那段：「一条命令把项目初始化到可派单状态：写配置 + 文档骨架 + AGENTS 段落 + 把 skill 装进项目 .pi/skills/ → 建 agent worktree → 起巡检窗口 → 打印下一步清单；幂等，可反复跑」）。对不懂本项目的人，读完不知道 **PM/席位/worktree/brief/change/门禁/账本/pulse/knock** 各是什么、为什么要它们。
- **没有任何按命令的帮助页**：`team <cmd> --help` 会退回全局那 98 行（`team reply --help` 的这条 nit 在 V27 复验里记过）。用户想查「`team config` 到底有哪些子命令、每个参数什么意思」只能滚全局页。
- **没有语言层**：CLI 全是中文硬编码（`scripts/lib` 里 5477 行含中文），而 README 与 `references/**` 是英文——同一项目两种语言没有机制区分。面板早就有先例：`scripts/panel/src/strings/{en,zh}.ts`。
- **布局**：组标题用 `── xxx ───…`，选项说明换行顶到第 19 列、没有悬挂缩进，长段落与选项混排；`--help` 里同一命令的参数说明与行为说明没有分开。
- **已有的诚实性守卫（你要保住它）**：`tests/routes.sh` 的 Walk A 会把 `team help` 里的**每一条用法行**喂给解析器（必须被接受），Walk B 校验 schema 注释点名的命令都有承诺探针，还有一条「把树改坏必须红」的翻转；门禁段 `§51 · 用法诚实性` 跑它。**改帮助文本必须让 §51 继续绿**，不许用删用法行/放宽解析器的方式。

## 实现方式（PM 的倾向，你可以反驳但要给依据）

现状：帮助**没有任何框架**——入口是纯 bash（`scripts/team` 的 `case` 分发，48 个命令），帮助本体是 `cmd-project.sh:5` 的一个 `cat <<'EOF'` 哈拉文档（98 行中文散文），npm 包的 `dependencies` 是**空的**；产品里唯一用框架的是面板（ink + react，那份因此早就有 `strings/{en,zh}.ts`）。

所以本变更**不要**引入 CLI 框架（那会给一个只靠 bash 的 CLI 拉进 Node 运行时，或者引入生成器/buld 步骤），而是把帮助改成**数据驱动**：

- 一份**机器可读的命令清单**（单一真源：命令名 / 所属组 / 用法行 / 参数与说明 key / 一句用途 / 例子 / 触碰的文件与状态 / 傻作用与 `--yes` 需求），放在 `scripts/lib/` 下（TSV 或 bash 数组都行，你选并给理由）；
- 一个**渲染器**把清单渲染成三级页面（第 0 级只渲染组清单 + 入门命令，第 1 级渲染一组的行，第 2 级渲染一页）；**布局规则变成渲染器的不变量**（宽度/折行/悬挂缩进/禁 `→` 链），只在一处实现、只在一处测；
- **语言表**与文本 key 平级（`en`/`zh`），缺键由渲染器点名；
- `tests/routes.sh` 的 Walk A 改为**读同一份清单**（而不是正则哈拉文档）——覆盖度变成「清单里每个命令 × 每个有用法行的页」而不是「那一坨文本里能抓到什么」，这是本变更把诚实性守卫拧紧的地方；;要写进 design：改写前后 Walk A 覆盖了多少个命令（数字对比）。
- 帮助**不进**机器出口（`--print`/`--json`）——渲染器只在人类入口跑。

若你认为数据驱动不合适（例如预算/复杂度不划算），在 design 里给出替代方案与它的代价，并说明三级菜单、语言表、缺键可见、布局不变量这四件怎么各自被钉住。

## 你要产出的东西

一个 OpenSpec change（新能力 `help-surface`，或按你的判断落在既有能力上——但要在 proposal 里说明理由）：`openspec/changes/cli-help/{proposal.md,design.md,tasks.md}` + `specs/help-surface/spec.md`。至少覆盖：

1. **分级菜单（用户第二条要求，2026-10-14 追加）**：帮助**不许一次把所有命令都吐出来**（今天 `team`/`team help` 是 98 行、48 个命令一次铺开）。要三级：
   - **第 0 级** `team`（无参）与 `team help`：只给「teamsmith 是什么」（两三句人话）＋**分组清单**（今天那 8 组，每组一句用途）＋「新手上手的 3–5 个命令」＋下一级怎么进（`team help <组>` / `team help <命令>`）。**目标 ≤ 30 行**，并且要有一条款式的夹具断言它的规模（超了就红）。
   - **第 1 级** `team help <组>`：该组每个命令**一行**（命令 + 一句用途 + 最必要的旗标提示），并说明「看某一页用 `team help <命令>`」。
   - **第 2 级** `team help <命令>` 与 `team <命令> --help`：该命令自己的页（用途 / 何时用 / 参数逐个解释 / 例子 / 触碰哪些文件与状态 / 副作用 / 是否要 `--yes`）。两条入口**行为必须一致**（这条写进 delta 并配夹具）。
   - **未知组/未知命令**：报错并点名，指向 `team help`（不许静默退回第 0 级或全局页）；`team <命令> --help` **不得**再退回全局那 98 行（V27 复验记过这条 nit）。
2. **读者与深度**（用户要求的核心）：帮助文本的**目标读者**是「知道要管一个项目、但不懂 teamsmith 内部模型的人」。要为以下概念各给一句**可读的定义**（不是行话）：PM 与 worker 席位、工作树（worktree）与任务分支、任务书（brief）与它的 `category:`、变更（change）与规格（spec/OpenSpec）、门禁（gate）与「为什么绿是证据」、账本（ledger）与「谁写的」、pulse 巡检与 knock 叫醒、`--yes` 与授权边界。**深度**要能回答「这命令是干什么用的、什么时候用它、它读什么写什么、有什么副作用、能不能撤」，而不是只列旗标。
3. **默认英文 + 多语言**：默认语言 = **en**；语言选择机制（建议 `TEAM_LANG`，值 `en`/`zh`，落在 `.pi/team/config.sh` 或环境变量——你评估两者并给理由）；**缺键必须可见**（某个语言缺一条键 → 打印时点名缺失的键并以可读回退，另有一条可跑的检查：把语言表里删一条键 → 红并点名）；帮助文本与 `references/**`、README 的语言关系要写清（哪些是英文、哪些可翻译、谁是谁的真源）。
4. **布局规范（含用户 2026-10-14 追加的第三条：「缩进也很糟糕，全都是同一级」）**：今天组标题、命令、说明、参数、散文全部挤在同一个 2 空格缩进上（只有长段落的换行跑到 19 列、没有悬挂缩进），所以看不出层次。要求给出**显式的层级**并由渲染器强制执行：组标题**列 0**（唯一顶格的文字）且与前一组空一行；**命令**缩进 2，用法行与说明**分行**；**说明**自成悬挂缩进块（后续行对齐到说明首列）；**参数/旗标**再进一级（例如 +4），一行一个；**例子**单独成块且缩进一致。宽度默认 100 列、超宽自动折行且**折行只用悬挂缩进**（不许出现「后半句顶到左边」）。每一条都要能被**夹具**查（行宽、层级只有那几档、组标题顶格、空组、第 0 级规模、禁止 `→` 链），不是靠人看；design 里要给一张**目标排版样例**（同一命令的今天 vs 改后，逐字节对比）。
5. **诚实性沿用**：每条用法行仍必须被解析器接受（`routes.sh` Walk A）；帮助里的**每条承诺**要么有夹具兑现（§51 的既有口径），要么从文本里去掉——不许出现「文档说能、实际没做」的句子。**分级之后 Walk A 的覆盖面必须扩到每一级的所有页**（今天只读 `team help` 那一处；改成读第 1/2 级各页 = 更强，不是更弱——design 里要写清这一点）。新增/改写的承诺要在 proposal 里列成清单（哪几条进了 §51 的探针清单）。
6. **红侧**：至少给① `--help` 缺一条命令 → 红；② 中文表缺一条键 → 红并点名；③ 帮助里写一条解析器不接受的形式 → §51 红；④ 帮助里写一条没有夹具兑现的承诺 → §51 红；⑤ 布局规则（行宽/缩进/禁止 `→` 链）被违反 → 红；⑥ **第 0 级超规模**（例如超过 30 行或一次列出超过 N 个命令）→ 红。
7. **不变量**：命令名、旗标名、退出码、机器出口（`--print`/`--json`）**一个字节都不改**；本变更只动帮助文本、语言层、分级路由与它们的夹具。

## 边界

- 只写提案（proposal/design/tasks/delta）；apply 与 verify 另行换人。
- 现有 `§51`/`routes.sh` 的**强度不许降**（可以为了新文本更新清单，但要在 design 里逐条说明为什么不是削弱）。
- 别在本批试图把 `scripts/lib` 里 5477 行中文全部翻译（那是另一个量级的工程）：**本变更的范围就是帮助面**（`team help`、每个命令的页、以及帮助里用到的概念词）。其余消息的迁移写成 design 的「未决/后续」一节，给一条能分步推进的路线（例如先错误信息里最常被读到的少数几条）。
