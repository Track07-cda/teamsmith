## 现状（今天实测，不要重新测量）

- **地板 = 产品全套**：那张映射表只声明 7 段「门禁自己的机制」，其余默认都进地板 → `--floor` 实测 **121 段、88.7 分钟**。
- 最贵的段：设置选项 **767 s**（接线后地板里跳过写信面夹具是 332 s）、窗格留存 368 s、临时根纪律 229 s、身份面 160 s、npm 安装 152 s、门禁锁排队守卫 40 s。
- 门禁自检那 7 段（段落自述、选段器、元变异、指纹等）已不在普通推送里；探针 11 分钟那次也不再每次付。
- GitHub 作业上限 1 小时；0.3.0 的公开 CI 就是在一小时上限处被取消的。

## 要回答的

**A · 地板切片并行**（PM 倾向）：把地板按**确定性规则**切成 N 片（N=4 建议），每个 CI 作业跑一片，覆盖一点不减。

要点：切片键怎么选（段号？段 key 的稳定哈希？必须**不随行的增删漂移**，否则新增一段会让某些片重复/漏跑）；「N 片的并集恰好等于地板」怎么写一条断言（这条是本方案的承重，不许只写在文档里）；单片的门禁锁、私有临时根、真终端依赖（有些段需要 tmux）在独立机器上是否成立；某一片失败时读者能不能直接看出是哪几段（作业名/注释行）。

**B · 地板瘦身**：只留「契约面 + 事故墓碑」的若干段，其余靠改动路径选中 + 发布时全量。

要点：哪些段属于契约面/墓碑（按 `DECISIONS`/`reviews` 里点名过的事故逐条对，不许凭感觉）；瘦身后「推送时不跑什么」要显式写清；失效面（例如一个只在下游才暴露的问题会在发布前才被抓到）。

**C · 两者组合**：瘦身后的地板再切片，各片多少分钟。

每条给出：预计 CI 时长（用今天的分段实测相加，标明算式）、实现代价（改哪几个文件）、失效面（最坏情况下什么会被漏到发布前才发现）、以及「怎么验证它没丢覆盖」的具体判据。
