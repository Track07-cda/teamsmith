# T1.1 · smoke 快慢分层：给门禁一个 60 秒内的快模式

```
task:   T1.1
agent:  dev
issue:  -
依赖:   -
状态:   todo
预计:   <1 个工作块；超时先交 PARTIAL 报告，不要静默卡死>
```

> 任务书写给「没有上下文的弱模型」看：范围、边界、验收命令、报告格式都要自包含。
> PM 派单：`team dispatch dev T1.1 docs/team/tasks/T1.1-smoke-60.md`

## 验证证据要求

本任务属于**工程改造**（不是缺陷修复），翻转证据按下面第二条形式给：

- **「破坏实现 → 守门测试必须失败」**：临时把快模式的选择条件改坏（例如让 `TEAM_SMOKE_FAST=1` 仍跑全部），
  证明新加的断言真的会失败，然后还原；把两段输出都贴进报告。

## 背景

`skills/pi-team/tests/smoke.sh` 是这套 skill 的门禁：它在临时仓库里端到端跑完整流程
（含真实 tmux / 真实 `pi` 拉起、看门狗、容器 dry-run 等），**全量约 3~5 分钟**。

问题：派单/复验的基本门禁只需要"逻辑正确"，不需要每次拉起真 pi。每次 review 都跑 5 分钟太慢，
会让人想跳过门禁。

## 交付物

1. `skills/pi-team/tests/smoke.sh`（可另建 `skills/pi-team/tests/smoke-fast.sh` 由它调用）
   — 支持 `TEAM_SMOKE_FAST=1 bash skills/pi-team/tests/smoke.sh`：
   只跑**不依赖 tmux / 不依赖真实 pi 进程 / 不依赖 podman** 的部分（纯逻辑、渲染、坐标、容量、
   文档契约、meeting 等），跳过需要真进程的段落（派单真拉起、watchdog 拉起 PM、容器、真实续跑等）。
   - 跳过的段落必须**明确打印** `SKIP（FAST 模式）`，不能静默少跑。
   - 退出码语义不变：有失败 → 非 0；全绿 → 0。
   - 默认（不设环境变量）行为**完全不变**：断言数量、顺序、退出码与今天一致。
2. `skills/pi-team/SKILL.md` — 在「排障 / 测试」处补一句：快模式怎么用、它不覆盖什么。
3. `CHANGELOG.md` — 加一条条目（**不要改版本号**，版本由 PM 决定）。

## 边界（不要做）

- 不要改 `skills/pi-team/scripts/**`（实现归 PM）。
- 不要删/弱化任何既有断言；只做"分类 + 跳过 + 打印 SKIP"，全量模式必须一条不少。
- 不要改 `TEAM_*` 的语义或默认值。
- 不要引入新依赖（只用 bash/git/tmux 已有能力）。
- 不要动 `docs/team/**` 里 PM 的文件（除你自己的报告 `docs/team/reports/T1.1-dev.md`）。

## 验收（必须真实执行，输出写进报告）

```sh
# ① 快模式：目标 < 60 秒，0 失败（请把 `time` 的输出贴进报告）
time TEAM_SMOKE_FAST=1 bash skills/pi-team/tests/smoke.sh

# ② 全量模式：必须仍然全绿，断言数不少于改造前（改造前请自己先跑一次记录基线）
time bash skills/pi-team/tests/smoke.sh

# ③ 翻转证据：把快模式的选择条件临时改坏，证明新断言会失败
#    （例如把"跳过"改回"照跑"，或用一个小 patch 让 FAST 模式仍跑 tmux 段）
```

## 报告

写入 `docs/team/reports/T1.1-dev.md`，必须包含：

- 交付物清单（文件 + 一句话说明）
- ① 快模式实测耗时与断言计数（含 `time` 输出尾部）
- ② 全量模式基线 vs 改造后（断言数：`✓ N / ✗ 0`），说明"一条不少"如何保证
- ③ 翻转证据两段输出
- 快模式**覆盖不到**什么（明确列出跳过的段落）
- 未验证部分 / 风险 / 偏离任务书之处 / 下一步建议
