## 已确定的目标，不再向使用者重新确认

Teamsmith 安装者希望把项目开发交给一个能持续负责的人与 agent 团队：文档与规格完整，有足够自主性，自己不必盯详细进度和实现方案，可以专注高层产品、需求、架构。使用者明确希望 agent 主动辅助提出需求、补足细节；不能假定详细需求仍由人全部给出。产品/交付分工见 `docs/team/DECISIONS.md` D99：PM 保持日常入口，产品判断与 PM 的工程意见分开保存，使用者决定重要产品方向。

使用者在 D100 同意：收录并关闭 E9/E10，继续一次聚焦具体使用过程的产品探索。这是普通席位上的能力试跑，不是平级角色已经上线；未授权新产品功能、候选队列、新面板或 OpenSpec 提案。

## 为什么再试一次

E9 研究了平级角色的机制，E10 建议候选流转和待决读面。PM 的异议是它主要设计了需求管理流程，尚未充分证明能从使用事实发现使用者未详细指定的产品需求。你不是来证实或推翻 E10 的结论，也不用为上轮方案寻找支持。先独立看使用事实，再在报告末尾说明与 E10 的关系；原建议与 PM 异议仍分开保留。

本次只追一段具体过程，例如“负责人给一个高层目标，PM/团队补齐细节并交付”，或者“负责人隔一段时间回来，只做关键判断并继续交给团队”。由你依据证据选哪一段，不由 PM 指定功能答案。调查对象是人实际要完成的事，不是新增角色或提案管理机制。

## 可用材料与调查方式

- 已处理的真实反馈：`docs/team/DECISIONS.md` D59（四轮看板反馈）、D65（延迟读取的三条反馈）、D66（另一个实际使用 Teamsmith 的 PM 的八条答复）。从引用继续追原记录、相关任务/报告/复验；公开仓 issue/PR 为零不等于没有使用反馈。
- 本项目已公开的任务书、规格、报告、评审和线程，可追一条完整交付链。主仓内的这些文件是只读材料，不修改它们。历史记录受历史改写影响，不能解析的旧哈希不算今天的可执行证据；优先用现有文件、当前代码和复验记录交叉核对。
- 当前使用入口：`README.md`、`skills/teamsmith/SKILL.md`、`skills/teamsmith/references/{protocol,workflows,troubleshooting}.md` 及选中过程触及的 capability spec。你可以亲自运行有关 CLI 入口，验证当前实现是否已有解决办法，但不能把静态扫描当作使用体验。
- 先按 `AGENTS.md` 读 `docs/team/threads/dev2.md`、本任务、`skills/teamsmith/references/openspec.md` 和相关规格；不参考其他席位未交付的草稿。

先把这段过程的事实串起来：使用者想完成什么，实际采取了哪些步骤，哪里需要再补细节/做判断/等别人，结果如何。随后核对历史摩擦今天是否仍存在：是否已经被现有命令、文档、授权方式或 PM 的正常职责覆盖？“当时出过问题”不能直接推出“今天应开发功能”。

可以做一个隔离的受控流程实验补当前行为证据。它是实验，不是真人访谈或新客户反馈，报告分别标明。禁止编造用户语句、点击、优先级、耗时和使用频次。

## 交付内容

仅提交 `docs/team/reports/E11-dev2.md`，作为你的原始产品判断；不要创建第二份产品文档或产品规格。

报告先讲选中过程与证据，再讲结论。把“观察 / 推断 / 建议”分开，每项事实标注文件位置、真实命令结果或只读公开来源。若提出候选，最多一项：解释它帮谁完成什么、今天具体哪里不够、希望人的工作怎样变化、至少两个替代方向及主要取舍、粗成本与未知项、最值得使用者作出的高层选择。它是供讨论的建议，不是已经生效的行为要求。

同时给出最强的反对理由：用现有能力、改一处说明或调整 PM 的执行方式，能否解决同一个问题？什么证据会推翻你？如果加了功能但使用者仍要盯同一类细节，如何识别“功能做了但目标没实现”？没有足够新证据就明确交零项，并说缺什么，不凑需求，也不反复请求使用者确认 D99 已定的目标。

PM 的可行性评审将另写在 `docs/team/reviews/E11.md`，不改写你的原始结论；事实错误由你追加勘误。报告接收和关单都不代表候选自动获批。

## 执行边界与隔离

- 只修改自己的上述报告文件；产品代码、测试、规格、配置、主仓账本、其他席位目录全只读。不开 OpenSpec change，不进入 propose/apply，不派开发任务。
- 不向远端推送、不发 API 写请求、不联系其他项目或外部使用者、不读凭据文件。不得把私有项目信息、家目录绝对路径、内网地址写进公开报告。无需认证的公开只读资料可引用，没有访问条件就标明未知。
- 实验在私有 scratch 仓库或无宿主 tmux socket 的门禁容器里完成，不能直接挂 worktree 的 `.git` 指针作为容器仓库；使用干净 clone 或独立 `git init`。清除继承的项目/席位/会话环境，不复制真实 `.pi/team` 配置或 state。调用写盘入口前先核对 `team paths` 的 main_root 是 scratch；不能证明隔离就不要执行，记录限制即可。
- 不启动/重启真实项目、共享 tmux 会话、其他 agent 或用户会用的预览环境；不使用全局进程匹配、裸 tmux 破坏命令、共享 socket 或 host PID 命名空间。若实验必须越过该边界，交 PARTIAL 与所需权限，不自行扩大授权。
- 原始实验日志留在仓外私有 scratch，报告只给必要的脱敏片段、复现方式与指纹；不把证据包提交进仓。长命令按工具规则用后台任务且全部收割后再交付。开跑前检查 /tmp 余量，别把容量拒绝说成产品缺陷。
- 硬阻塞时从席位工作树执行 `bash skills/teamsmith/scripts/team notify pm "<一句话>"` 并交 PARTIAL；生成的通用提示若写成 `notify dev2`，以本行的 PM 收件人为准。
