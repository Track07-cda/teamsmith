> The smoke suite's watchdog section (§11b) has been "fixed" twice by making fixtures more explicit, but the
> underlying race was never pinned: `make_pm_idle` and `team_pane_busy` disagree about an idle PM pane for a tick, so
> the watchdog sometimes decides "PM 没在跑" and tries to start a second PM (quota warnings), or misses a real
> pending item. Retries hide it. This task finds the actual cause and removes it, or proves the jitter is inherent and
> makes the tool handle it deterministically.

## What is already known (do not re-derive)

- The watchdog is a single tick: read state (capacity, backlog, PM liveness) → decide (nudge / start / nothing).
- The PM liveness signal is derived from the pane's front process + cwd ownership (`team_pm_state`), with the
  recorded pid from M6.5 (`proof=spawn`) as the strong signal.
- Two smoke flakes have been observed historically around this section: `超过配额时拒绝继续拉起（告警）` and
  `拉起计数已记录（期望 [1] 实际 [2]）`. Both look like "liveness flickered between two ticks".
- A pane whose shell just started can transiently look like something else (`pane_current_command` = the shell, or a
  shell hook's child), and a pane that just received `respawn-pane` can briefly report `tmux` as its command. Use
  `state/pm.pid` + `team_proc_cwd` as the source of truth where possible.

## Deliverable 1 — a diagnosis, with evidence

Write a small harness (under `docs/team/reports/M7.2-dev2/` or `tests/`) that runs the liveness/start logic in a tight
loop against a controlled pane and records what each layer reports tick by tick:

- start a fixture PM (fake agent, `proof=spawn`), let it settle, then sample `team_pm_state`, `team_pm_alive`,
  `team_pane_busy`, the recorded pid's liveness and cwd, and the pane's `pane_current_command` every ~200 ms for a
  few seconds — including immediately after `respawn-pane`, after the fake agent exits, and while it is starting;
- publish the raw samples in your report (a table or a log excerpt). If the jitter reproduces, the table shows where;
  if it does not reproduce in 10 minutes of sampling, say so and prove the deterministic path instead (next item).

## Deliverable 2 — remove the race, or make the decision deterministic

Whichever the diagnosis supports, the tick must be **idempotent and honest**:

- if the PM is starting (spawned pid alive but the agent not yet identifiable), the tick must treat it as "starting"
  and neither count a restart nor start a second PM; a later tick sees it running;
- if the recorded pid is dead, the tick may start a PM (quota applies) — and must say which evidence it used;
- `team watchdog-status` / `digest` must never report "PM 在跑" and "PM 没在跑" in the same output for the same tick
  (today's reports can be read that way), and the capacity/restart log must record the decision plus its evidence.

Cover it with smoke assertions: a fixture that samples a starting PM (fake agent with a slow start, e.g. sleeps 2 s
before exec'ing) must produce exactly **one** start attempt and **zero** quota complaints across several ticks, and
after the agent exits the next tick must see a stopped PM exactly once.

## Deliverable 3 — document the decision rule

`references/protocol.md` (watchdog section) and `references/troubleshooting.md`: the liveness/stating rules, what each
state means (`running` / `starting` / `busy` / `idle` / `foreign` / `unknown`), and what the PM should do for each.
`references/config.md` if a new knob appears (keep such knobs to a minimum).
