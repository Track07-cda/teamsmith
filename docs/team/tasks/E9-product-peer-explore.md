## 背景与目标

用户确认的产品目标和已同意的工作方式见 `docs/team/DECISIONS.md` D99。使用者给出高层产品、需求与架构目标，团队负责补细节和自主交付；产品探索要能**主动提出产品需求**，不是只审计文档。PM 仍是人的日常入口，但产品角色与 PM 在判断上独立，原始产品意见与分歧可直接让人看见。先试按需 B，价值证实后才考虑常设 C。

**你的身份只是前期独立研究员，不是已经建立的平级产品席位。** 现有席位由 PM 派任务、PM 控制看板；绝不能把这项研究的交付冒称为新角色上线。本任务不写 OpenSpec 提案，不更改协议、代码或运行配置，不建任何新席位。

## 要回答的问题（文件位置与实测证据优先于推理）

1. **真实用户与需求输入**：从当前公开说明、规格、经处理的项目内使用反馈及公开 GitHub issues/PR（只读；如无则注明）找出一条与 D99 目标有关、值得继续调查的**产品问题**。用一条需求候选示例展示「观察 → 推断 → 方案」三者的界线；若证据不足，明确标为假设并说明还缺哪种使用者证据，不能编造访谈、使用量或需求优先级。不要复用 D99 已否定的关键词计数。
2. **现有项目内权限与渠道**：核实 roster、`team dispatch`、任务书、`notify`/`thread`/inbox、pulse、看板/OWNERSHIP 和跨项目 `meeting` 的具体归属。列出为什么一个普通 worker 即使叫 `product` 也不是 PM 的平级；用户能否看到产品判断的原件、PM 能否静默截留，以及何时会误打扰用户。按事实区分已有能力与新机制。
3. **B 的最小诚实试点**：比较至少两种实现路线（PM 派 product worker 但原件可见；产品角色有独立调查授权和可直达使用者的异议通道），也可分析跨项目 PM 方案是否合理。分别写出谁发起调查、谁改产品候选记录、PM 如何附可行性意见、谁能否决/搁置、意见冲突如何送到人面前，以及双写账本如何避免。明确你推荐哪条、代价和不能保证的地方。
4. **一条可证伪的演示路径**：在**本地纸面/临时副本**模拟产品角色提案、PM 不同意以及使用者看到双方原文的全过程；标清哪些步骤今天可运行、哪些只能等机制改变。再给出反向例：PM 静默删除或改写意见应怎样被发现。不要向真实用户窗口投递测试消息。
5. **升级为常设 C 的条件**：怎样评估「主动提出了使用者没写明却有价值的需求」，且不靠提案数量或虚构采纳率；包括试点停止条件、预算/频率界限与当前不可测之处。文档与规格如何在之后的正式变更流程里保持单一来源，而不是在候选记录里另造规格。

## 交付与界限

只提交 `docs/team/reports/E9-verify.md`（含选项/推荐/证据索引/不确定项）和必要的同名报告证据文件。报告给 PM 评审，原件也直接留给使用者查看，PM 的意见须另记，不改写你的结论。除本席位报告路径，不改任何受跟踪文件；不建新 seat、不修改 `.pi/team/config.sh`、不开新会、不写 API 请求、不 push、不触发 CI、不与外部项目/用户联系。只读 GitHub API 可用，但结果须说明是否真的读过；切勿读取或打印 token。

遵守 `AGENTS.md`、自己的 `docs/team/threads/verify.md` 与本任务书的阅读顺序。现有协议要求开工先读相关 `openspec/specs/notify-and-inbox/spec.md`、`openspec/specs/dispatch/spec.md` 和 `skills/teamsmith/references/openspec.md`。如果当前规则与平级角色构想冲突，记录冲突，**不要**绕过它或假装已实现。
