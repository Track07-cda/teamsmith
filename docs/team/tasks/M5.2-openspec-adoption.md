```
task:   M5.2
```

> Decision (PM, 2026-09-14): OpenSpec is a **required dependency** and owns spec management and the change
> workflow — "no need to reinvent the wheel". teamsmith keeps its own evidence layer (task briefs, reports, reviews,
> decisions) but **must not grow a parallel requirements/spec system**. This task sets that up in **this repo** and
> wires it into the PM workflow.

## Verified facts about the tool (measured on this machine, do not re-derive)

- `openspec init --tools none [path]` creates `openspec/config.yaml` (with `schema: spec-driven`) plus
  `openspec/specs/` and `openspec/changes/archive/`. Nothing else.
- `config.yaml` supports: `context:` (project context shown to the AI when creating artifacts), `rules:` (per
  artifact: proposal/tasks/…), `operations:` (advisory `apply:` / `archive:` guidance).
- Commands: `openspec list [--specs]`, `openspec change show`, `openspec spec`, `openspec validate --all --strict`,
  `openspec archive -y [--skip-specs]`, `openspec context [--json]`, `openspec doctor`, `openspec update`.

## Deliverables

### 1. Initialize OpenSpec in this repo

- Run `openspec init --tools none` **in the repo root** (this project is the tool's own home; the specs come with it).
- Fill `openspec/config.yaml` so that artifacts created later automatically follow our standards:
  - `context:` — what teamsmith is (one paragraph), where the normative docs live
    (`skills/teamsmith/SKILL.md`, `references/philosophy.md`, `references/protocol.md`), and that English is the
    language of all artifacts.
  - `rules:` — proposal/tasks rules that encode our working rules: acceptance commands must be copy-pasteable and
    runnable by the PM; each requirement needs a falsifiable scenario; a change that fixes a defect must state the
    flip (red before → green after); boundaries (what is explicitly out of scope) are mandatory.
  - `operations:` — `apply:` guidance (small steps, commits carry the task id + `Agent:` trailer, evidence over
    prose) and `archive:` guidance (only after the PM's review record exists and the code landed).

### 2. Write the first capability specs (this is the substance)

Convert what today lives only in prose + test assertions into `openspec/specs/<capability>/spec.md` with proper
requirements + scenarios. Suggested capabilities (pick or split as you see fit, but cover the promises that matter):

| capability | must capture |
|---|---|
| `dispatch` | self-contained briefs, worktree/branch guards (dirty worktree of another task refused, same task resumable), model limits, capacity floor (swap, zram excluded), the adapter template contract (placeholders, unknown placeholder fails, `{summary_file}` data channel) |
| `verification` | independent checkout required, dirty checkout refused, hard timeout → FAIL, the review record states the verified revision, `--strong` requires flip + independent evidence, reports are claims and reviews are evidence |
| `board-and-status` | `done` only after the code landed on the protected branch and was pushed, status restored on failure paths, digest's pending-review / pending-wrap-up detection, what the board columns mean |
| `watchdog` | one backend (tmux window), pending-work definition, no wake without work, standby suppresses, restart quota, capacity logging |
| `notify-and-inbox` | turn-end notification, `--from-file` byte-exact delivery, dedup window, offline fallback, cross-session typing refused, knock requires registration |
| `meeting` | intents are informational only, no command/order, `--as-user` requires a human terminal, consensus needs both sides, zero writes into the peer project |
| `memory-and-deps` | magic-context + OpenSpec are required (doctor fails without them), disk wins over memory, spec management belongs to OpenSpec |
| `boundary` | actions must run inside the project, empty/relative tmux targets refused, no reading/writing other projects or credentials |

Rules for the specs: one requirement = one falsifiable statement; scenarios in Given/When/Then form with concrete
commands or observable outcomes; **no scenario that cannot fail** (a scenario we cannot test is a smell — either make
it testable or leave it as prose in `references/`, not as a requirement). Cross-reference the doc that explains the
*reason* instead of copying it.

### 3. Wire it into this project's workflow

- `.pi/team/config.sh`: add `openspec validate --all --strict` to `TEAM_GATES` (before the smoke suite, since it is
  fast) — the review checkout must fail when specs are invalid. Verify the combined gate really runs both and that a
  broken spec turns the gate red (flip evidence!).
- `references/openspec.md` (new, English, ~80–120 lines): **how teamsmith uses OpenSpec** — the division of labour
  (specs = what must hold; task brief = one work slice referencing the change; report/review = the evidence; archive =
  closing the change), the rule "do not create a parallel spec system", the day-to-day commands
  (`openspec list`, `openspec change show`, `openspec validate --all --strict`, `openspec archive -y`,
  `openspec context`), and what a PM does when a change is bigger than one task.
- `references/workflows.md`: add the spec step to the runbook (idea → change proposal → tasks → dispatch → verify →
  archive) with the concrete commands.
- `templates/task.md.tmpl`: a brief must name the change id it implements and the spec delta/scenarios it must
  satisfy.
- `templates/pm-prompt.md.tmpl`: one line in the PM loop — specs live in OpenSpec; check `openspec list`/`validate`
  before dispatching and archive when the change is done.
- `SKILL.md`: add a short "Specs (OpenSpec)" section + a row in the deeper-reading table pointing at
  `references/openspec.md`. **Do not rewrite the Requirements section** — a parallel task (M5.1) owns that.

### 4. Evidence for the report

- `openspec validate --all --strict` output (must pass) and `openspec list --specs` output.
- The flip: temporarily break one requirement (e.g. remove a scenario's `THEN`) in a **scratch copy** and show the
  gate/validate failing; restore. Do not leave a broken spec behind.
- The combined `TEAM_GATES` run in a review-like checkout (specs + smoke).
