# P425 · 过度防御审计（只出报告，不改代码）

用户 2026-11-06 的判断：这个产品是**本地单用户工具**，防事故是对的，但代码里有一批判断是在防**假想的对手**或**不会发生的输入**，代价由正常使用来付。已发生的实证：一天内两次把核心功能打掉（目录权限 775、Pi 会话文件 664 被判不安全；详情页对项目内软链直接拒绝）。

## 要产出的东西

一份按**代价**排序的清单，而不是按代码行数。每条至少包含：

1. **位置**（文件:行）与它挡的东西；
2. **这个场景真实发生过吗**：给出证据——事故记录、issue、日志，或「没有证据」；
3. **代价**：用户必须多做什么、或哪种正常布局被拒、或多跑多少次；
4. **判定**：`删`（没有任何真实故障对应）、`收窄`（真有故障，但判据比问题大）、`留`（对应真实故障，如并发写坏、崩溃写半个、两个任务抢同一工作树）；
5. **若删/收窄**：受影响的面（夹具、规格、文档）与大致工作量。

## 建议覆盖的范围（可增删，每处说明理由）

- 输入校验：时间解析、ID/编号格式、路径与字符白名单、长度上限、"必须是正规文件/目录"这类形状断言。
- 数值与容量：并发上限、重试上限、超时、历史修剪、队列上限——哪些是防真实耗尽，哪些只是让人多跑一步。
- 静默兜底：`|| true`、`2>/dev/null`、`catch {}`、失败即当空值继续的地方。列出总行数与分布，并指出**哪些掩盖了真实故障**（用户明确讨厌"吞掉错误"）。
- 双份状态与自证：同一事实存在两处（例如 loaded 记录 vs mtime、outbox vs 投递日志），以及"证明自己没被篡改"的机制（锁文件 mark、pid proof、tmux 证据、generation 计数）。哪些是必要的并发保护，哪些是自证循环。
- 门禁与夹具里的过度验证：为了证明"测试有牙齿"而复制产品的判定、为每个变异重跑整组、同一事实断言多次。
- 文档/提示词里的重复约束：同一个规则在 AGENTS、PM 提示词、席位提示词、SKILL、references 各写一遍的地方（给出计数与建议归属）。

## 方法要求

- **只读**：不改任何产品文件，不跑全量 smoke。可以用 `rg`、读代码、读事故记录（`docs/team/DECISIONS.md`、`docs/team/reviews/`）与现有日志。
- 至少抽查 5 条给出**反例或现场**：证明"这条拒绝对正确使用也生效"或"这条限制从没被触发过"。
- 结论里必须回答一句：**如果只能改三处，是哪三处，为什么**。
