## Context（用户实机发现，PM 已定位到机制，证据如下）

用户在 pulse 实机看 work 页：「怎么只有左侧的 board 模块了？」——270x66 的 pane 上 board 卡（左栏 147 宽）
独占，右栏 changes/specs/decisions 三卡**整块消失**（不是降级 `—`，是不渲染）。数据层无罪（page-1 进度行
「specs 13 · decisions 27」、16 个块读取器并发全 rc=0）。

**机制（layout.ts，两栏放置 + B1 折叠展开，约 1528-1562 行）**：

1. `placeColumns` 的预算记账是 `used = max(columns[0].length, columns[1].length)`——**两列共享同一个
   bodyBudget**，放进任何一列都消耗另一列的预算。
2. B1 的折叠展开 `target = max(columns[0].length, columns[1].length, bodyBudget)` 恒等于 bodyBudget
   → board 被养满整个 body 高度（我们的 BOARD.md 有 92 条 done，折叠池巨大）。
3. pass 2 重排：养大的 board（61 行，priority 10 先放）→ `used=61` → 右栏三卡（p11/13/14）
   `remaining = 61-61 = 0` → `pickChrome` 返回 null → 整块丢弃。

**实证**（真实数据、--snapshot 忠实复现）：

```sh
node skills/teamsmith/scripts/panel/panel.js --root . --snapshot --page 2 --width 270 --height 66
# 现状：右栏空（无 specs/decisions 卡）；height=40 同样全饿死；height=300 specs 复活（decisions 仍缺）
```

判别实验已证明饥饿随预算变化。**修复方向**（你定具体实现，两个候选）：

- **每列独立记账**：`remaining = bodyBudget - columns[slot].length`（而不是 max 两列）——保留 B1
  「board 展开填满 body 底」的意图（左列 61 + 右列 26 合法共存，帧体 = 61）;
- 或把展开量改成真实空隙：`extra = min(folded, bodyBudget - max(两列自然高))`（pass 1 之后的 slack）。

**必须回答的附带问题**：height=300 时 decisions 仍缺席——同一族还是另一个坑，报告里说明。

**为什么 V18 没拦住**：它的夹具板子 done 少、折叠池小，自然高度装得下，饿不出来。**回归夹具必须用
大折叠池**（done ≥ 90 的板子，270x66 与 120x40 两档）。
