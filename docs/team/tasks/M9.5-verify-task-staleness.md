# M9.5 · A verify task's record is bound to the *reviewed* revision, not to the verifier's own branch

```
task:   M9.5
agent:  (unassigned)
deps:   M9.4 (pending list vs board), M9.2 (phase-aware evidence)
```

> Third instance of the same class, found the same way (watching the real digest while running the pipeline): after V2
> wrote its record for P2.1's revision, the digest says
>
> ```
> V2-verify [stale: verified 398716887, branch now 44788f09b]（在 verify 分支上）→ team review V2
> ```
>
> `3987168` **is** the revision V2 verified (P2.1's tip, bound explicitly with `team review V2 --dir … --branch …`), and
> `44788f0` is V2's **own** branch tip (the report commit). Nothing is stale — the verifier's branch is where its
> evidence lives, while the record is about someone else's revision. The staleness rule ("the record only speaks for
> the revision it saw", M6.2/F3) is right for an **apply** task and wrong for a **verify** task.

## Required behaviour

1. Staleness is judged against the revision the record is **bound to** (the record already carries it: the `--branch`
   / checkout revision the review ran on). For `phase: verify` tasks, the task's own branch tip is not the subject and
   must not make the record stale.
2. The pending list must still flag a genuine case: a `verify` task whose **reviewed revision** has moved on (a new
   commit landed *after* the record was written) → stale, listed, with both revisions named.
3. Keep the apply-task behaviour exactly as it is today (record vs branch tip), including the existing message.
4. Fixtures: (a) verify task whose record is bound to X and whose own branch is Y ≠ X → **not** stale, nothing listed;
   (b) verify task whose record is bound to X, and X is no longer the tip of the reviewed branch → stale, listed with
   both revisions; (c) apply task whose branch moved after the record → stale (unchanged control).

## Boundaries

- Files: `scripts/lib/cmd-status.sh` (the pending/staleness computation), `scripts/lib/common.sh` if a shared helper is
  needed, `tests/smoke.sh` (your own section), `references/openspec.md` (one sentence: what "stale" means per phase).
- Do not change the review record format or M9.2/M9.4 behaviour; compose with them.
