# M9.4 · Pending verification must not outlive the board's decision

```
task:   M9.4
agent:  (unassigned — dispatch after M9.2 lands; same file area)
deps:   M9.2 (phase-aware `done` evidence), v1.27.0
```

> Found as a real false positive while running the pipeline: **P1** (`phase: propose`) was reviewed, its verdict
> recorded in `docs/team/reviews/spec-delta-gate-proposal.md`, marked `done` on the board — and the digest still lists
> it as `待复验（在 dev 分支上）→ team review P1`, every tick, forever.
>
> Two causes, both worth fixing:
> 1. the pending-review detector equates *"reviewed"* with *"`docs/team/reviews/<task id>.md` exists"*; a phase task's
>    evidence is `reviews/<change>-proposal.md` (propose) or a DECISIONS acceptance (explore), so it never clears;
> 2. it does not consider the **board status**: a row the PM has already moved to `done` cannot also be "waiting for
>    the PM" — otherwise the signal punishes the PM for having adjudicated.
>
> The second cause is the more serious one: the digest is the PM's wake-up source. A list that can never be emptied
> trains the PM to ignore it (the same failure mode as a guard that cannot fail).

## Required behaviour

1. Tasks whose board status is `done` (or `closed`, if that state exists) are **never** listed as pending
   verification; the transition itself is where evidence is enforced (M9.2's job), so the list must not second-guess it.
2. When a task's board row **is** in progress (`wip`/`todo`/`review`/…) and its report exists, the current rules keep
   applying; the phase-aware evidence from M9.2 decides "reviewed" for phase tasks.
3. The stale entry must be explainable: when the detector skips a report because its task is done, a one-line note in
   the digest (or in `team status <ID>`) says so — silent skipping is how a false negative hides.
4. Fix the *other* direction too if it is cheap: the detector currently searches the agent worktrees, so a stacked
   branch (an apply branch based on a propose branch, per DECISIONS D16) makes the propose phase's report visible a
   second time. If that produces a duplicate or an attribution to the wrong task, name it and fix it.

## Fixtures worth having (smoke)

- a phase-`propose` task with `reviews/<change>-proposal.md` ACCEPTED and board `done` → **not** in the pending list;
- the same task with board `wip` → **is** in the list (the control: the skip must come from the board, not from the
  filename);
- a plain code task with board `done` and no review record → not in the list, and the digest says why;
- a plain code task with board `wip` and no review record → still listed (unchanged behaviour).
