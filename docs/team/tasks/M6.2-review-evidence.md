# M6.2 · Review evidence integrity: the record must describe what was really verified

```
task:   M6.2
agent:  dev2
deps:   V4.0 (merged: docs/team/reports/V4.0-verify.md has the reproductions)
```

> The review record is the PM's licence to merge. V4.0 found several ways it can describe something other than what
> happened. Fix them so that "what the record says" and "what was verified" cannot diverge silently.

## Findings to fix

### F7 (high) — a review can be stamped with a branch that does not exist
PM-verified: `team review P1 --dir <clean checkout> --branch no-such-branch` exits 0, prints PASS, and the record
reads `分支: no-such-branch · HEAD: <sha>`. When the branch cannot be resolved in the main worktree, the
checkout-consistency guard is skipped entirely.
Required: **fail closed**. If `--branch` is given and cannot be resolved, or the checkout's HEAD is not that
branch's tip, refuse and say which refs were expected/found. The PM may always fall back to an explicit
`--allow-unresolved-branch` (recorded in the record) if a legitimate case exists — but the default must be refusal.

### F8 (medium) — `TEAM_REVIEW_ALLOW_DIRTY=1` still claims "clean"
With the documented override the review runs but the record still says `（分支 …, 干净）`.
Required: the record must state the truth (`dirty: 3 files (override)` and the file list head) so that later
readers — including the digest — can tell an overridden review from a normal one.

### F9 (medium) — ignored files are invisible to the clean check
`git status --porcelain` shows nothing for ignored files, so gates can read a build artefact that is not in the
commit while the record says PASS. Reproduction in F9.
Required: either run the gates from a checkout that cannot contain untracked/ignored artefacts (`git clean -xdf`
equivalent on a *detached scratch* copy is acceptable if documented and safe), or detect and record the presence of
ignored files before/after the gates. Do not silently trust `status --porcelain`.

### F10 + F11 (medium+low) — timeout detection and verdict labels
`TEAM_REVIEW_TIMEOUT` kills the gate (rc 124) but the record says **FAIL** with no timeout line, because the
detector greps the gate's own output for the word `timeout` (GNU `timeout` prints nothing without `--verbose`).
Conversely a gate that merely *prints* "using timeout 5" and exits 3 is recorded as **TIMEOUT**.
Required: base the verdict on the wrapper's exit code (124/137) and/or `--verbose` output, never on a substring of
the gate's own logs; keep `TIMEOUT` distinct from `FAIL` in the record and in `team status`.

### F12 (medium) — `--no-gates` can be mistaken for evidence
The record says `SKIPPED`, but because `reviews/<ID>.md` now exists the digest drops the task and `team status`
shows the record path without a verdict. A "no gates ever ran" review is therefore indistinguishable from PASS in
the places the PM actually looks.
Required: `--no-gates` reviews must stay visibly unverified in digest (e.g. listed as pending with a
`gates: none` marker) and `team status` must print the verdict next to the record path. Add tests.

### F13 + F14 (medium) — `--strong` is a keyword grep, wrong in both directions
A report that says "there is no 翻转 evidence and no 独立验证包 — those words merely appear here" is judged
**满足**; a genuine report written in the post-english-first style is judged **不满足** (`independent verification
package` does not match the list, and the flip half matches only because the prompt's phrase "guard test" appears).
Required: define `--strong` structurally and honestly. Accept at least: a heading/section that states the flip
outcome with a command and its red/green result, and a path to an independent package; reject mere prose mentions.
Make the check explain itself ("what it looked for, what it found, which file/line"). Update
`references/workflows.md`/`SKILL.md` wording to match what the check really does.

### F3 (medium) — a review record suppresses pending work forever
`reviews/P1.md` records HEAD A; the branch later moves to B; digest stops listing the task because a record exists.
Required: bind the record to the revision it verified (`HEAD` already in the header) and let digest/status flag
"verified A, branch now at B" as pending again. Coordinate: `cmd-status.sh`'s pending logic is yours to change here
(M6.4 will not touch it).
