# P432 · 全仓测试改造：先研究，不实施

## 目标

把 D 的单一样本扩展成一份**全仓测试改造地图**：哪些测试可以确定性化、哪些重复执行可以退休、哪些真实接口必须保留，以及按什么顺序分批做。不是再写一份“测试很重要”的综述，也不是设计新测试框架。

用户明确授权研究全仓改造；这不等于授权全仓实施。

## 必须使用的证据

- `skills/teamsmith/tests/`、`section-paths.tsv`、`section-select.sh`、`smoke.sh`、`meta-suite.sh`、公开 CI 配置；
- 已有完整日志，优先 `/var/tmp/rel46-full-2.log`、`/var/tmp/ci-meta-42365002327/2026-11-07T10-42-26Z.log` 及现有夜间记录；
- D 样本：`openspec/changes/route-page-check-determinism/`、P428–P430、V130–V132；
- P398 的反例和 P410 的一阶/二阶分层；不要把已否决的“再收窄 61b 故障用例”重新包装成主方案。

本轮不跑全量、完整夜间、61b 或新增长实验。缺数据就标注，不把估算写成实测。

## 要回答的七个问题

1. **全仓清单**：按功能域列出测试文件、所属段、当前执行频率和大致成本；指出真实成本集中在哪，不只列文件数。
2. **行为分类**：每类主要判据是在验证产品行为、测试夹具自身、还是部署/选择机制；哪些输入与输出可确定复现，哪些必须真实 Pi、tmux、进程、窗口、锁或外部命令。
3. **重复模式**：找出跨段重复准备、重复全组重跑、相同判据多份实现、只有计数没有行为的检查。每条给具体文件/函数/执行路径，不能只凭名称猜。
4. **迁移单元**：提出少量可独立交付的批次。每批必须写明保留什么行为、删除哪条旧执行、如何证明改坏仍红；只新增快速路径而保留旧路径的不算改造。
5. **真实验证底线**：明确不得确定性替代的区域，以及每批至少需要保留的真实端到端样本。
6. **目标运行形态**：日常选段、合并检查、夜间自检、发布前检查各自承担什么；不新增调度服务、数据库或第二套测试平台。
7. **总账与顺序**：给可证明的结构减少量、已有实测和未知项；按收益/风险排序，说明第一批做什么、哪些不值得做。

## 约束

- 每批遵守守卫净零：替代或退休旧检查，不在旧检查旁边叠加新层。
- 不引入 mock 平台、统一事件系统、插件框架、run id 账本或新的全仓状态中心。
- 不用降低断言、删除真实接口测试、增加跳过或延长超时来制造提速。
- 性能只作参考，不设性能门禁；行为可证伪优先于数字好看。
- 不修改产品、测试、正式规格、CI 或 OpenSpec change；只写研究报告。

小步提交报告，通知 PM。PM 审阅后决定是否需要独立复核和首个提案；本任务不直接派实施。
