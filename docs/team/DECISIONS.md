2. **危险的一半**：**锁文件被删会静默破坏互斥**。`flock` 锁的是 inode；文件被删后，正在跑的持有者仍握着那个**已被 unlink 的** inode，而新起的运行会**新建一个锁文件**、在**另一个 inode** 上获得「锁」——于是两套「顶层」运行可以并发，而双方都以为自己独占。今天没造成实际冲突，但这是**真缺陷面**。

**为什么这条对我们重要**：夹具根与锁文件用的是**全机共用的前缀**（`teamsmith-smoke.*`），而任何装了 teamsmith 的项目都会看到同一前缀，于是「清理自己的残留」很容易误伤别人的**活**运行——这次正是如此。这与「按名字杀进程」是同一族：**共享机器资源缺归属**。

**处置**：
- 立 **P287**（`gate-lock-external-deletion`，propose）交下一批：① 夹具根与锁文件的名字带**项目身份**（或放进项目自己的状态目录），使一个项目的清理不可能命中另一个项目的运行；② 持有者要能**察觉锁文件被替换/删除**（持有者记录里已有 `start=` 与心跳路径，可比对 inode 或续期失败即点名），并在这种情况下**响亮地停**而不是继续以为自己独占；两条都要红侧。
- **不塞进 P281**（门禁锁卫生）的返修——那份规格没有这个场景，按纪律新场景走新变更，不夹带。
- dev3 已用私有 `TMPDIR` 复跑同一条验收，并把这件事写进 P281 报告（那股「现场被抽走」的哨兵行为正是它要验的东西之一）。

### D189 · 容器里指定 `TMPDIR` 必须**先建目录**（我自己的调用错误，2026-10-15）

**现象**：`smoke.sh --select …` 在容器里立刻以 rc=2 结束，原文：`section-select.sh: line 390: /var/tmp/p281g/teamsmith-select.<pid>.sh: No such file or directory` → 「写副本失败 → 选段被拒 → 什么都没跑」。

**根因**：我在 `podman run` 里传了 `TMPDIR=/var/tmp/p281g`，但**没有先建这个目录**；选段器要先在 `TMPDIR` 下写一个运行副本，父目录不存在就直接拒跑（**这是正确的 fail-closed**：宁可不跑也不跑一半）。我先前几次 `TMPDIR=/var/tmp/p29Xg` 之所以成功，是因为**那些目录已经被更早的一次运行创建过**——属于「碰巧」，不是「对」。

**规矩**：容器里改用非默认 `TMPDIR` 时，**同一条命令里先 `mkdir -p`**（例如 `mkdir -p /var/tmp/p281g; TMPDIR=/var/tmp/p281g bash …`）；另外注意 `-e HOME=/tmp` **不会**把宿主 `/tmp` 带进容器（没有对应 bind），所以宿主 `/tmp` 紧张时容器里用默认 `/tmp` 往往就够了。

**报错质量**：这次的原文把「写副本失败」与「父目录」摆在第一行，**一眼能定位**——比「选段为空」那种含糊说法好得多，值得当作「响亮失败」的样本。

### D190 · 席位自己的夹具会挂死，而「挂死」在窗口里长得和「在算」一样（2026-10-15）

### D191 · **已撤回**：我误报了一条「门禁锁记录陈旧」的缺陷（解析错误，2026-10-16）

> 撤回理由（写在前面，原文保留在下方）：**记录并不陈旧**。持有它的席位**先取证后实现**，指出 `pid=599698` 与 `/proc/599698/stat` 的 `starttime=25584249` **与记录里的 `start=` 完全一致**，而 599698 就是那次运行本身（`ps -p 599698` → 活着的 `bash …/tests/smoke.sh`）。我**自己复核后确认它是对的**：那两个 pid 是**同一次运行的两层**（`flock` 包装层持内核锁、记录写的是 runner）。
> **我的错误来源**：我用 `awk -F'[= ]' '/pid=/{print $2}'` 去解析一份 **TAB 分隔**的记录，取到的是字符串 `pid`（不是数字），于是 `ps -p pid` 报「不在」——我把**自己的解析 bug** 当成了产品的陈旧记录，还据此发了任务书与关键回复页。教训：**要判「记录是否陈旧」，就用记录自己提供的判据**（`start` 与 `/proc/<pid>/stat` 的 starttime 比对——这正是我在那条变更的 brief 里自己写下的判据，却没有用它），不要用自造的旁路检查。



**现场**（我查的是内核事实，不是记录）：`/proc/locks` 显示锁文件（inode 33995889）由 **pid 160298 持有**、pid 2247100 在等；而**记录** `/tmp/teamsmith-smoke.lock.holder` 写的是 `pid=599698`（**已不存在**）与 `started=…`、`agent=dev3`、`expected=9581`。

**影响**：等待者（dev-bob 的 `-w 7200`）看记录**看不到真正的持有者是谁/还要多久**——而这正是 P281 那条变更的核心目的（可归因）。锁本身没坏（内核锁把两个运行正确串起来 ✓），坏的是**记录的准确性**：新持有者接手时（无论是正常排队接手，还是走「原持有者已死 → 可接管」那条路径）**没有重写记录**。

**处置**：这属于 `gate-lock-hygiene` 已合并代码的**缺陷**（该变更已归档 → 按规矩**新开变更**修，不在归档目录里改）。任务书已排队（P294）：接手时**必须**重写记录（含 `kind/agent/worktree/started/expected/heartbeat`），并加红侧——「陈旧记录 + 新持有者」的现场里，记录必须指向**当前**持有者；同时把「记录指向死 pid」的读数**可见地**标出来（不许让等待者读到已死的持有者还以为那就是当前）。

**另一条观察（不是缺陷，是成本）**：那次持锁运行是全量 `smoke.sh`（budget≈2.7 h），而按纪律「按改动跑选段、全量留给合并/归档」——**一个席位的全量运行会让别人的选段排队两小时**（dev-bob 的等待就是这个形状）。下次派单我在 brief 里把这条写得更硬：**交付验收用闭包选段，全量只在我说的时候跑**。
