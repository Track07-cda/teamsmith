**三次真回归（自己或门禁发现的红 → 绿，都留了断言）**：

1. **IFS 吞字段**（第一版读取器，自查）：`team_death_scan_text` 用 tab 分隔、字段可能为空，`IFS=$'\t' read`
   把连续分隔符吞掉 —— 一条**没有分类**的现场行被当成了分类名（夹具 ②/⑥ 立刻红：`provider said: …` 成了分类）。
   改为「扫描结果走**全局** `TD_SCAN_*`、四段表面用 `-` 占位保证字段不空」后绿。
2. **`TEAM_AGENT_SCENE_LINES=0` 泄漏现场内容**（smoke §49 红，自查在完整门禁）：死因行默认带原始证据行，
   而 P94 的契约是「旋钮为 0 = 按配置不打印画面内容」。修法：旋钮为 0 时死因行保留分类与来源、原文改印
   `（按 TEAM_AGENT_SCENE_LINES=0：不打印原文）` —— 既有断言一个字没改，绿。
3. **干净退出被尾屏散文误判成死亡**（smoke §12b-e 红，**完整门禁套出来的真缺陷**）：该夹具的 fake agent
   会把 prompt 回显进 harness 尾屏，进程 exit 0；第一版只在「没有任何可读证据」时才认干净退出，于是
   prompt 的尾句把一次干净退出报成了 `unknown` 死亡 —— 巡检记了一条、入队一个 knock，§12b-e 的
   「队列恰好一条」因此变成两条。修法（`fb28bca5`，`cmd-death.sh` 的干净退出判据）：
   - **当前启动的 `.exit 0` / `pane_dead_status=0` 是正证据**，pane 侧「可读但没有帧」的散文
     （prompt 回显、装订文本）**不是**死亡证据 → 不报、不记录、不 knock；
   - 例外一：任何来源**分类过**的帧仍然赢过 exit 0（供应商报错后干净退出正是 D46 的现场）；
   - 例外二：会话侧 `stopReason=error` 自身就是一种帧 —— 即使措辞不认识也报 `unknown`，不被 exit 0 抹掉
     （否则「供应商换措辞」这类死亡又回到用户看不见原因的状态）。

   三条新增断言把它钉住：`② 干净退出 + 无帧尾屏 → normal（不报，不记录）`、`② 非零退出 + 无帧尾屏 → unknown`、
   `③ session 侧不可分类的 errorMessage → unknown + 来源 session`；红侧 ④ 证明旧写法必红。

2. **`unknown` 的分类来源**：`cause_source` 的闭集是 `pane|session|recorded`；**没有可读来源**的 `unknown`
   （design D6 的边缘）在面板 JSON 里**不带** cause 键（不给 `cause_source` 造第四个值），但 `team status`/
   digest 仍然点名 `unknown`（「死因无法判定 / 来源：无」）。这是我对 D6「named unknown」的落地方式。
3. **巡检不 knock 无来源的 `unknown`**（D6/D7 的字面组合）：可读来源都没有时无法在正文里给出证据行，故
   不入队（避免噪声），pending 行仍点名。standby 时两者都顺延。
4. **`state/deaths.log` 的 500 行上限**：design 说「只增、有界」，我取 500 行（超出裁掉最老的，保留最新
   500）。参数写在函数里（无旋钮），需要改时一行。
5. **knock 的投递**：走既有 `team_outbox_enqueue --kind knock`（不是 `team notify --from-file`）—— 它带着
   M62 的投递守卫与 `--dedup`；`kind=knock` 是 M6.5 起「没用正文的敲门」的既有形状，正文由我填。
6. **性能**：`team_stopped_deaths_text` 只对「有任务且没在跑」的席位做读取（最多 64 KiB 会话尾 + 有界现场尾），
   面板 pending 9s TTL、巡检 15 分钟一拍 —— 比 design D9 关心的情况更省；没引入新的逐拍 git 调用。
7. **三处平局判定的落点**（design 没逐字写，我按 D2/D4 的意图定，夹具逐条钉住，供复验时挑战）：
   pane/会话**分类过**的因 > exit 0；会话侧 `stopReason=error`（未分类）> exit 0；pane 侧无帧散文 < exit 0。
   取舍理由：exit 0 是「这次启动干净收场」的正证据，但一条**显式错误记录**不能被它抹掉，否则 D46 那类
   「报错后干净退出」的死亡又会被藏起来；反之 prompt 回显之类的散文不是错误证据，不能凭空造出死亡。

## 5. 已知边界（不是缺陷，写在明处）

- `normal`（干净退出）**不**进任何表面（design D4/D7）：状态段不印原因行、巡检不记录不 knock、pending 退回裸计数。
- tmux 直接给出 `pane_dead_status` 的场景仍按既有 `dead:status=N` 词表；`pane_dead_signal=9` 且现场无帧 → `unknown`。
- 会话侧只读**最新**一个 JSONL（按 mtime）；多个会话文件并存时旧文件里的错误不会被读（当前启动守卫本来也会挡住）。
- `dispatch-<agent>-tail.txt` 的证据时间取文件 mtime：文件被后续启动覆盖后仍靠 mtime ≥ started 守卫，
  极端情况下（重启发生在同一秒内且文件被覆盖）可能读到新启动的尾屏并分类 —— 与现场/会话两侧同一时间粒度，
  design D2 的取舍；夹具 ② 覆盖了「重启 → 空」的正常路径。
