## 4 · 最小展示候选及不采纳理由

**唯一考虑的改动区域是首页“最近交付”**：把按时间排列的“报告名 / 作者 / 时刻”，换成“对象 / 当前证据 / 负责核对的人 / 原记录入口”。其它首页区域、工作页、设置页、叫醒规则均不动，不设第二份任务清单，不引入 run id、事件总线或新状态文件。

以下是本次样本的表达草图，**不是已实现界面、事实字段或新规格**；它们不应被当作可直接执行的命令：

```text
P431  负责人记录不一致       PM 核对任务书与派单
P388  无窗口，报告记有阻塞   PM 核对原报告
P430  验收通过，收尾授权未核实 PM 核对验收记录
```

“原记录入口”只复用现有任务详情里的任务书/报告/评审，不另建 dashboard。若采用，它应删除原“最近交付”的三行重复摘要，而不是旁边再加一块。预计能替代的只是“看报告名字 → 去工作页找同一任务 → 打开详情”的定位步骤；**本轮没有操作原型，未实测这个跳转节省**。

否决依据有三条：

1. 原“最近交付”只扫描主检出报告文件；P431 当前无报告、P388 报告在作者 worktree。要画上面三行，已经不只是重排这一个区域的数据，需扩大任务选取与跨来源合并。
2. 即使扩大读取，三行仍要求 PM 回原文作决定。它没有消除表中为了确认负责人、验收阶段和用户授权而发生的阅读；只把“需要核对”搬到更前面。
3. 若改成确定动作，P430 会被陈旧报告再列为待复验，P388 会被通用 review 建议推进，用户确认条件也会被误当成未回答的问题。减少一次定位不足以证明值得引入这些判定。

因此本轮不建议为这个草图写提案。保留现有详情阅读路径；只有后续实际交接里能找到“已有同源事实足够，只缺首页入口”的更窄样本，才值得重新比较。本报告没有为找这个样本扩展调查或建议新建待办系统。

## 5 · 新鲜度与三个反例

`cmd-watch.sh:1147` 的“最近交付”按文件 mtime 选三个主检出报告，时间不是模型完成、提交、通知或验收时间。P430 作者报告自记 03:57:31，落到主检出的 mtime 是 04:25:53，且与 V132 报告同秒；`git diff a5ed228e:docs/team/reports/P430-dev.md HEAD:docs/team/reports/P430-dev.md` 为空。复制相同正文使它看起来新近，不能改变报告所说的阶段。

`panel/src/data.ts:174–201` 中 frame 的缓存期是 500ms，pending/agents/board 是 15s，changes 是 180s；刷新还需等待各子读取结束。`build()` 成功才更新该块的时间，失败标为不可用。它们不是同一事务快照；首页时钟前进不说明这些来源同刻更新。以上是源码边界，不是本轮测得的延迟上界。

| 必须考虑的反例 | 本次真实依据 | 展示应如何说；不能如何说 |
|---|---|---|
| 状态陈旧或来源互相矛盾 | P430 正文未变但 mtime 更新；P431 的 BOARD dev 与派单/任务书 dev2 不同 | 分别注明“看板记录 / 派单记录”及来源；不能按较晚 mtime 选赢家，也不能以首页时钟保证全行最新。读失败为不可用，不保留一个看似最新的确定动作。 |
| 席位已经不在但记录仍在 | 04:29 首页 dev-bob 无窗口；04:31 `tmux list-panes -t teamsmith:dev-bob` 返回 `can't find window: dev-bob`；`dev-bob.env` 仍记录 P388、started=10-28 13:05:18 | “无窗口；保留派单 P388；进程状态未在本轮另查”。不能叫“正在执行”，也不能只凭窗口不存在断言所有后台进程已死；恢复/关闭由 PM 核对。没有故意杀席位。 |
| 报告存在但没有被接受 | `a5ed228e` 的 P430 作者 DONE，与 `56d5dc68` 的 review 状态、V132 明确未完成职责并存 | 当时应说“作者已交付；独立复验待完成（任务书指派 dev3）”，不是“任务完成”。到 34d96364/963ead4a 已有新验收/关闭记录后，不能继续用旧结论。 |

不为新鲜度加未经授权的硬时限：过了若干分钟不自动视为失效，文件最近改过也不自动视为事实正确。安全的降级是说清“哪份记录如此说 / 本轮观察到什么 / 尚不能确定什么”，不是猜下一步。
