## 结论与待复核的边界

建议采用 **一个项目级持久状态 + 既有 Pulse 轻量到期检查 + PM inbox-watch 直接通过 Pi 投递**。单条或多条 Reminder 合成一个批次，先持久化意图，再发送完整自定义消息；只有匹配批次/nonce/成员和 PM 会话的 `message_start` 才算实际唤醒，不代表模型成功或任务完成。Standby 代际与提醒状态放在同一原子快照中，唤醒时只退出发送意图中绑定且当前仍有效的代际，每批只能退出一次；不确定发送不自动重投。

提案已写齐并做静态检查、隔离 Pi/锁探针和试归档，**没有实现产品功能**。有两项必须由 PM 正式评审，不可被包装成已证明的完全兼容：

1. **D204 的不可判顺序边界。** G1 已绑定发送意图后出现 G2，而 Pi 事件与 G2 的先后在公开回调中不可证明时，提案保留 G2、明确报告不确定。无论事件实际上发生在 G2 前还是后，回调看到的持久事实相同；后一种真实唤醒未自动退出 G2。正常 G1 在意图和观察时一致、或 G2 在意图前已生效的情况仍自动退出。`design.md` 的交错表和 delta 场景给出反例；这是安全边界，不能声称无条件满足「每次实际唤醒都自动退出」。
2. **旧环境兼容成本。** 保证 Bash/Node 和所有 Standby 写入口使用同一个跨进程崩溃安全锁，提案采用现有其他组件也使用的 OS `flock`。过去没有 `flock` 的系统也可改 Standby；提案要求它们先安装可用的 `flock`，否则即便没有 Reminder，Standby 变更也明确失败。常规有 `flock` 的环境非 Reminder 行为不变；本轮没有证明该依赖在所有受支持环境可用。`memory-and-deps` delta、诊断、升级/回退均披露此成本。不能把「无需第三方调度器」混说成「完全没有新增环境要求」。

OpenSpec 指令输出中的 `ready` 只表示规划工件完备，不是 PM 接受、Apply 授权或验证结论。下一步是 PM 的 `docs/team/reviews/agent-self-reminder-proposal.md` 正式评审，接受前不得派 Apply；后续还需要非作者独立验证和授权后的真实模型自主行为检查。

## 探针复现材料

以下是本轮 `cold-probe.mjs` 的完整模板：将 `__PI_AI__` 替换为 `$HOME/.bun/install/global/node_modules/@earendil-works/pi-ai/dist/index.js` 的展开绝对路径，即还原本机实际脚本及上述 SHA-256。`P387_TRACE` 指向隔离夹具文件，扩展通过 `P387_SEND=1` 仅在恢复进程注入。它不依赖产品实现。

```javascript
import { appendFileSync } from 'node:fs';
import { fauxProvider, fauxAssistantMessage } from '__PI_AI__';

export default function (pi) {
  const log = (type, data = {}) => appendFileSync(process.env.P387_TRACE, JSON.stringify({ type, time: Date.now(), ...data }) + '\n');
  const fake = fauxProvider({ provider: 'p387-faux', models: [{ id: 'controlled', name: 'controlled' }] });
  fake.setResponses([async (context) => { log('controlled-request', {messages: context.messages}); return fauxAssistantMessage('controlled response'); }]);
  pi.registerProvider(fake.provider);
  for (const name of ['session_start', 'before_agent_start', 'agent_start', 'message_start', 'message_end', 'session_shutdown']) {
    pi.on(name, async (event, ctx) => {
      log(name, {event, isIdle: ctx.isIdle(), sid: ctx.sessionManager.getSessionId()});
      if (name === 'session_start' && process.env.P387_SEND === '1') {
        setTimeout(() => {
          log('api-enter');
          const result = pi.sendMessage({customType:'p387-reminder', content:'REMINDER-P387-COLD-01 full text', display:true, details:{batchId:'P387-COLD-01'}}, {triggerTurn:true, deliverAs:'followUp'});
          log('api-return', {resultType:typeof result});
        }, 1000);
      }
    });
  }
}
```

Node 锁探针完整内容（`lock-probe.mjs`）：

```javascript
import { spawn, spawnSync } from 'node:child_process';
import { appendFileSync } from 'node:fs';
const [mode, lock, log] = process.argv.slice(2);
if (mode === 'worker') {
  appendFileSync(log, `node enter ${Date.now()}\n`);
  await new Promise(r => setTimeout(r, 250));
  appendFileSync(log, `node exit ${Date.now()}\n`);
} else if (mode === 'node') {
  const child = spawnSync('flock', ['-x', '-w', '3', lock, process.execPath, import.meta.filename, 'worker', lock, log], {stdio:'inherit', env:{...process.env, TMPDIR:'/var/tmp/node-probe'}});
  if (child.error) throw child.error;
  process.exit(child.status ?? 1);
} else throw new Error('mode');
```

以文中相同 `flock -x -w 3` Bash 命令与 `node lock-probe.mjs node "$L" "$LOG"` 并发，检查四行必须是某一进程的 enter/exit 连续后另一进程 enter/exit；持锁子进程自停并 SIGKILL 后以 `flock -n -x "$L"` 验证可重新取得。
