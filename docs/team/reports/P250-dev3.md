## Decisions and deviations

- **多余的三处，均由提案显式记名**（都在 `notify-and-inbox` 的写入面内，请在提案评审时裁定）：
  1. **尾行锚 + per-recipient 锁**：合并只重写收件箱**最后一行**（被别的行插开就结束 run）。理由与替代方案
     见 design 决策 4；若 PM 裁定「穿行合并」，要补原子重写协议与新红侧。
  2. **明细写失败的行带 `detail=unavailable` 且不做后续锚**：否则下一条成功的事件会把失败标记从行上抹掉，
     缺口不可见；这是「`×N` = 记录数」不变量的兜底（design 决策 8）。
  3. **写盘失败不叫醒**：扩展今天在收件箱写失败时仍会入队 knock；提案把它对齐到手工路径既有的
     「写失败不得授权唤醒」（`notify-and-inbox` 的手工通知要求）—— 属行为收紧，已在 proposal 的 What Changes
     与 design 决策 6 点名。
- **待裁的三点**（proposal「需要 PM 裁定的点」，提案按推荐版本落笔）：① 尾行锚；② 一代轮转 + 默认 2048 事件；
  ③ 新读面 `team inbox <agent> --detail` 与它的非零退出。
- **字段拼写**：合并装饰取 `×N first=<ISO> last=<ISO>`（`×N` 就是用户口径的显示；`first`/`last` 给机器解析），
  放在 ` :: ` 前的字段区；行首时间戳保持 **run 首事件**时间（行身份/knock 去重身份稳定），所以
  `uncommitted`/`unpushed`/`tip`/`branch` 自动是最后一条的值。
- **夹具落点**：沿用 `tests/bg-ledger.sh` + `bg-ledger-harness.mjs`（通知面的现成入口），新增
  `merge`/`detail`/`wake` 三组；两个前提写进了 tasks：① `awaiting` 由真实作业记录产生；② 临界区可用
  sentinel 暂停以证明并发追加不丢行。翻转时变异文件必须与真扩展同深度（或 harness 显式拿到 `scripts/team`
  路径），否则 knock 断言会因找不到 CLI 假红 —— 这条列为 apply 的前提检查。
- **无偏离**：任务书头字段 `specs: notify-and-inbox` / `deltas: notify-and-inbox` 与 delta 落点一致，
  没有碰 `dispatch`/`delivery-guard`/`panel`/`watchdog`。
