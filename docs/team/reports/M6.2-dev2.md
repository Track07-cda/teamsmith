## 每个 finding 怎么修的

### F7（high）`--branch` 解析不到时守卫被整段跳过 → 默认 fail closed

`want_head` 为空时旧代码不报错也不校验；现在：`--branch` 无法在主工作树解析 → 直接拒绝，报错里给出
期望的 ref（`` `$branch^{commit}` ``）、`--dir` 的 HEAD、名字里带该 ID 的候选分支，以及两条出路
（换真实分支 / `--allow-unresolved-branch`）。覆盖开关用了就在记录抬头写 `branch-unresolved (override)`，
正文再写一行说明"checkout 一致性无法自动校验"。被拒时**不写记录**。

### F8（medium）`TEAM_REVIEW_ALLOW_DIRTY=1` 仍说"干净"

输出与记录都改成真话：CLI 打 `dirty: N 处未提交改动（TEAM_REVIEW_ALLOW_DIRTY=1 覆盖）`（不再出现"干净"），
记录里 `checkout dirty: N files (override TEAM_REVIEW_ALLOW_DIRTY=1)` + `git status --short` 头部 10 行，
抬头也挂 `· checkout: dirty N file(s) (override)`。

### F9（medium）ignored 产物对 `status --porcelain` 不可见

两件事都做了（任务书给的是二选一）：
1. **检出并记录**：`team_review_ignored_paths` 用 `git status --porcelain --ignored=matching`（老 git 退回
   `--ignored`）在门禁**前后**各扫一次，记录里写 `ignored artifacts: N` + 路径头部 + 门禁跑完后**新增**的
   未跟踪/忽略产物清单（"门禁确实在 checkout 里写了东西"）；
2. **默认拒绝**：复验开始时 checkout 里已有 ignored 产物 → 拒绝，给 `TEAM_REVIEW_ALLOW_IGNORED=1` 覆盖；
   覆盖时记录里明确"override … 门禁可能读到了它们"。
没有选 scratch copy 方案：skill 的设计约束是**不执行 git 写操作**（`--dir` 只读），`git clean -xdf` 会越界。

### F10 + F11（medium+low）超时判定与 verdict 标签

`timeout --verbose --signal=TERM --kill-after=60`，判定只看 **包装器退出码**：`0`→PASS，否则 FAIL，
`124`（TERM 生效）/`137`（TERM 被忽略后 KILL）→ TIMEOUT，并往门禁日志追加一句
`[teamsmith] 门禁在 Ns 未结束，被硬超时终止（timeout 包装器退出码 124…）`。不再 grep 门禁自己的日志，
所以「日志里恰好有 timeout 字样」的普通失败是 FAIL；TIMEOUT 在记录、`PM 结论`、digest 里都与 FAIL 区分。

### F12（medium）`--no-gates` 不能被误当证据

记录抬头写 `判定: **SKIPPED** · gates: none`，正文写 `- 门禁：**none（--no-gates：没有跑过任何门禁）**
—— 本记录不是 PASS 证据`；`team status <ID>` 在记录路径旁打印 `（判定: SKIPPED · HEAD <sha> · gates: none）`。
digest 的待复验清单继续列这个任务，显示名后带 `[gates: none]` 标记（`UNKNOWN` 同理标 `gates: unconfigured`）。

### F13 + F14（medium）`--strong` 从关键词 grep 改成结构化判定

`team_strong_scan`（记录里 `## 强复验（结构化判定：翻转证据 + 独立验证包）`）：

- **翻转** = 有一个标题命中「`flip` / `flip evidence` / `red before … green after` / `break the implementation` /
  `翻转` / `破坏` / `回归` / `guard test`」的**小节**（大小写不敏感），且该小节里同时出现失败侧
  （`red|fail|before|✗|红|失败|退出码 1|rc=1|exit 1`）与通过侧
  （`green|pass|after|restore|✓|绿|通过|恢复|退出码 0|rc=0|exit 0`）结果；
- **独立包** = 报告里有一条**路径**（不是词，也不是“独立”这种声明）：`…/pkg/run.sh`、`docs/team/reports/<ID>-<agent>/pkg/…`、
  脚本后缀（`.sh|.mjs|.js|.ts|.py`）、或**任何真实存在的脚本/目录**；路径按 4 个基准解析
  （checkout 根 → 报告所在目录 → 报告同名的包目录 → 主工作树根），并存不存在都记为提示项；
- **报告来源** = 先看被验 checkout 里的报告，再看记录实际摘录的那份（主工作树 / agent worktree），取“证据最全”的一份
  （并列时 checkout 优先），记录里列出候选清单、采用哪份、那份是否在 checkout 里；
- 记录里逐条写「看了什么（判定规则）、在哪一行看到（`文件:行` + 命中文本）、哪条缺」；命令行、独立性声明、
  路径是否存在都只作提示项（不参与判定）。"只提到关键词"的报告 → 没有路径 → `独立包 | 缺` → 不满足；
  M4.1 之后的英文写法与模板写法（`## Flip evidence` + red/green 结果 + 真实存在的 pkg 路径）→ 满足。

## Decisions and deviations

1. **F9 默认拒绝 ignored 产物**（任务书二选一里选的第二条的加强版）。风险：复验目录**复用**时，上一次门禁
   留下的产物（或 PM 手工放进 checkout 的东西）会让下一次复验直接拒绝。这是有意的：那种情况下的证据本来
   就不可复现；错误信息给了干净重建命令和 `TEAM_REVIEW_ALLOW_IGNORED=1`。已写进 `references/config.md`。
2. **pending 逻辑用覆盖而不是改 `common.sh`**：任务书把 pending 划给 M6.2、同时要求不动 `common.sh` 的状态/
   看板函数。覆盖点写在 `cmd-status.sh`（source 顺序在 `common.sh` 之后），注释里说明了原因与归属，方便 M6.1/PM 判读。
3. **`--strong` 里“路径是否存在”“有没有独立性声明”“有没有命令行”都只作提示项**（PM 返工时的验收口径：
   模板形状 + red/green 结果 + 真实存在的 pkg 路径即"满足"，独立性声明不在必需要求里）。代价是结构化检查判不了
   "意图"：一份报告完全可以故意造一个 flip 小节 + 一个包路径；而"关键词汤"这类**没有路径**的报告仍会被拒
   （F13 的拒绝行为未变，有双向测试）。这一层边界写在这里，供 PM 决定是否收紧。
   另外报告来源优先 checkout，但没有时也认主工作树/agent worktree 的那份（并在记录里注明"不在 checkout 里"），
   因为 PM 的现场就是"报告已交、checkout 是干净分支"。
4. **同一个 `stale` 判定对 FAIL/TIMEOUT 记录不适用**：跑过门禁但失败的记录不算"待复验"（PM 已经知道结论，
   `team status` 里看得到判定），只有"没跑过门禁"和"记录过期"才重新进待办清单。
5. **`cmd-project.sh` 只改了 `team help` 的一行**（review 新旗标/拒绝行为）——按任务书它属于"仅当需要状态行"，
   这里认为是新旗标可发现性的最小必要改动，实现逻辑未动。
6. **没有动 `openspec/**`**（任务书要求修好后另行更新）。现有 spec 与新实现兼容（例如 verification 的
   "A dirty or mismatched checkout is refused"、"Gates run under a hard timeout"、"Verdicts are explicit"），
   但以下新行为还没有对应的 requirement，建议下一条 spec 变更补上：
   （a）ignored 产物/无法解析的 `--branch` 默认拒绝 + 三个覆盖开关写进记录；
   （b）TIMEOUT 判定来自包装器退出码（不是日志字样）；
   （c）`--strong` 的结构化规则（小节标题 + red/green 两侧 + 包路径 + 独立性声明 + 记录里的 `文件:行` 依据）；
   （d）digest "待复验"包含"记录已过期 / 门禁没跑过"，`team status` 打印判定与 stale 标记。
