## 1 · A · 地板切片并行

### 1.1 切片键：段 key 的稳定哈希，不是段号

brief 的两个候选里，**段号（或任何按位置轮转）不能用**：位置随行的增删漂移 —— 表里插一行，它之后每一段的片号
都变，于是「第 2 片」在这次推送和下次推送里指不同的东西，重跑一次失败的分片就可能在跑另一批段。

规则：`shard(key) = cksum(key) % N`（POSIX `cksum`，纯 ASCII 输入，跨机器一致；`md5sum` 首字节也可，效果同类）。
`N` **只有一个来源**：workflow 矩阵的长度。GitHub 的 `strategy.job-total` 就是矩阵作业数，于是命令行写
`--slice ${{ matrix.slice }}/${{ strategy.job-total }}`，改矩阵只在矩阵里改一处。
（`strategy.job-total` 与下面的并发组规则都是 GitHub 的文档行为；本仓没跑过矩阵，所以这两条是文档事实，不是本仓实测 ——
第一次真跑要看作业数是否为 4。）

三条性质，都是规则本身给的、不需要维护：

1. **新增一段自动落在恰好一片**，已有段的片号不动（不漂移）；
2. **各片 own 的并集恒等于这次决策的 key 集合**（floor ∪ 改动路径，或 FULL 的全集），因为规则是对 key 的纯函数；
3. **平衡不是保证**。哈希按段数均分、不按成本；实测估算见 §1.4，把「平衡」当测量而不是契约对待。

### 1.2 承重断言（三层，全部可执行）

brief 说「N 片的并集恰好等于地板」这条是本方案的承重、不许只写在文档里。分三层落：

**① 选择器内（每次运行都在跑，纯逻辑）** —— 新开关 `--slice k/N`，与现有决策**正交**：
`--floor`（地板 ∪ 改动路径）、`--paths`（NONE/RUN/FULL）、以及不带决策（全套）都能加它。同一个进程里按规则算出全部分片，
断言 `1 ≤ k ≤ N`、本片非空，并把清单分成「本片自己的段」与「为了 needs 从别的片借来的段」两类打印。
和今天一样，前导段（0, 0b, 0c, 0d）在每一片都跑，needs 闭包按片各自补齐。

**② `--check ⑨`（静态，`section-select.sh --check` 的一部分）** —— 对 `N ∈ {2,3,4,5,6,8,12}` 断言：
分片是对地板的**精确划分**（无重复、无遗漏、无空片）。这条抓的是「哈希实现退化了（比如全落一片）」这类错误，
与具体 N 无关；顺带把「表里每行 key 都能被哈希到」也钉住。

**③ CI 的 coverage 作业（真正承重的那一层）** —— `needs: [gates]`、`if: always()`、无 `continue-on-error`：

1. 下载 N 份 `shard-<k>.keys`（每片在 host 侧由选择器写出，`if: always()` 上传）；
2. 断言 N 份都在；
3. 断言每份与**自己对选择器的重算**逐字相同 —— 防止某片静默收窄；
4. 断言各片 own 的并集 **==** `--floor` 的 key 集合，缺的段逐个进 `::error::` annotation；
5. 任一片作业失败或被取消 → 本作业红（所以「取消了 1/4」永远不会读成通过）。

**为什么必须是独立作业**：①②都只能证明「规则今天没坏」，证明不了「N 片真的都跑了」。矩阵作业会因 fail-fast、
并发组、配额、取消而少片，那才是这套方案真正会丢覆盖的唯一入口。

### 1.3 workflow 必须同时改的四件小事（否则方案会静默失效）

| 项 | 现状 / 风险 | 改法 |
|---|---|---|
| `fail-fast` | 矩阵默认 true：一片红会取消兄弟片，读者看不到全貌，coverage 作业也会红（但它红得对） | `strategy.fail-fast: false` |
| `concurrency.group` | 现在是 `gates-${{ github.ref }}`。矩阵 4 个作业进同一个组，GitHub 的规则是**同一组只留 1 个 running + 1 个 pending，新 pending 取消旧 pending** → 另外两片会被**静默丢掉** | `gates-${{ github.ref }}-${{ matrix.slice }}` |
| 临时根 / 容器名 / 锁 | 现在是单一 `TEAM_CI_TMP_ROOT` + 固定容器名；锁默认在 `${TMPDIR}/teamsmith-smoke.lock`（`scripts/lib/gate-lock.sh:74`） | 每片一份：`TMPDIR=$TEAM_CI_TMP_ROOT/s<k>`、`--name teamsmith-gates-run-s<k>`、`collect-scene.sh --tmp-root` 同一个值 → 锁与临时根自动每片一份 |
| 产物命名 | 现场 artifact 现在是 `gate-failure-scene` 一个名字 | 每片 `gate-failure-scene-s<k>` + `shard-<k>.keys` |

**一片失败时读者怎么看出是哪几段**（brief 点名要答的一条）：三个信号叠加，不需要打开日志去数 ——

1. **作业名**：`gates (shard 2/4)`（矩阵作业标题），读者先在运行页面看到是哪一片；
2. **注释行**：该片开跑前打印 `::notice::shard 2/4 — 43 段：38 41 40 …`（本片清单逐段点名），失败时这份清单直接
   出现在该作业的注释区；每段的结果行本来就逐段打印段头，与这份清单对照就能定位；
3. **产物**：`shard-<k>.keys`（本片 own 清单）与 `gate-failure-scene-s<k>`（现场）在失败时也上传（`if: always()`），
   coverage 作业把 N 份清单排成一张表打印出来，并点名缺的那一片负责的段。

代价说清：一段挂住时，读者面对的是「这 43 段里的某一段」；今天则是整批取消、上限之后的段一条都没跑、且日志到
段头为止不再前进。所以这是改善而不是损失。

单片的门禁锁 / 私有临时根 / 真终端（tmux）在独立机器上**成立**，依据：

- **锁**：默认路径在 `${TMPDIR}` 下（上面那行），每片一份根就每片一把锁，互相不排队；而 §34/34b/34c/34d 自己的夹具
  是**显式传 `TEAM_SMOKE_LOCK`** 造两把锁来验证排队语义的（`smoke.sh:16444,16474`），所以「锁的语义」不依赖机器上
  恰好有几个作业 —— 那 200 s 的成本只由拿到 `34`/`34d` 的那一片付。
- **临时根**：§40 判的是「本套只用自己拥有的根 + 泄漏断言」，根的来源是 `TMPDIR → TEAM_TMP_ROOT → 磁盘默认`；
  每片一份根后它依旧只碰自己那份。`--keep` 留下的现场也落在自己那份根里，收集步照自己的根拷。
- **tmux**：§0h 先把隔离钉成三条件（私有 socket + 私有 `TMUX_TMPDIR`），套件所有 tmux 调用都走那套壳；hosted
  runner 是一作业一 VM，本来就不共享 server。§10c 需要 `--pid=host` 复现 SIGTTIN，四片各在自己的 VM 上
  `--pid=host`，语义与今天单作业逐字相同。
- **唯一需要提前说清的条件**：以上成立的前提是 **hosted runner（一作业一 VM）**。如果哪天换 self-hosted 共享主机，
  两片同机时会出现「另一片的活进程被本片的孤儿普查（§51b）/ 信号闸门（§58）看见」这类跨片可见性 —— 它们按记录的 pid
  判断而不是按名字，所以判定逻辑本身不坏，但「本项目的孤儿」这个集合会短暂变大。换 self-hosted 前必须单独复验这一条，
  别把它当免费的。

### 1.4 预计 CI 时长（算式）

算式：`单片墙钟 ≈ Σ 本片 own 段的成本 + Σ 为 needs 借来的段 + 前导段 + 构建 59 s + checkout/openspec ≈ 2 分`。
成本取值：6 条实测（§0 表）+ 其余每段 33 s。两种读数的差别只在 `38` 是按地板里的 332 s 还是按独立的 767 s：

| N | 每片 own 段数 | 每片 run 段数（含闭包） | 片墙钟（38=332 s 读数） | 片墙钟（38=767 s 读数） | 各片合计 |
|---|---|---|---|---|---|
| 2 | 66 / 62 | 78 / 73 | 51 / 49 分 | 46 / 52 分 | 6066 s / 5921 s |
| 3 | 45 / 43 / 40 | 51 / 63 / 54 | 33 / 39 / 42 分 | 30 / 42 / 46 分 | 6926 s / 7152 s |
| **4** | **35 / 31 / 31 / 31** | **43 / 48 / 40 / 42** | **32 / 33 / 22 / 30 分** | **29 / 37 / 19 / 34 分** | **7091 s / 7297 s** |

对 N 的读法：

- **N=2 不行**：46–52 分的墙钟加 2 分固定开销就是 48–54 分，60 分上限下没有余量，任一段慢一倍就撞上限。
- **N=3 勉强**：30–46 分。它比 N=4 更差不是笔误 —— 哈希落在 3 片时闭包重复反而更不平（一片借 20 段），
  说明「平衡是运气，不是保证」。
- **N=4 是建议值**：19–37 分，而且地板还在长 —— 映射表的数据行数在 `main` 上 10-01 是 115、10-10 是 125、10-17 是 135
  （`git show <commit>:skills/teamsmith/tests/section-paths.tsv`，约每周 +10 段）。片数是最便宜的旋钮：改矩阵一行，
  别的一个字都不用动。

**计费分钟 +33%**：各片合计 7091 s（38=332 读数）对 5322 s，增量来自两处 —— needs 闭包重复（本片需要前置段，
哪怕前置段归别片）与前导段 ×4。若 Actions 配额重新变成约束，N=3 是 +30%，N=2 是 +14%。

### 1.6 怎么验证它没丢覆盖

1. `--check ⑨` 绿：`N ∈ {2,3,4,5,6,8,12}` 时各自精确划分地板（无重、无漏、无空片）。
2. `slice-coverage.sh` 的四条行为用例（**翻转证据**在这里）：
   - 真表 + 4 份真清单 → 绿，并打印每片段数与秒数；
   - 删掉第 3 片 → **红**，并逐个点名第 3 片负责的段；
   - 把第 2 片的清单收窄一段 → **红**（点名「规则算 43 段，清单给 42」）；
   - 同一段出现在两片的 own 里 → **红**（重复是覆盖的超集，但不许静默）。
   破掉规则必须红 —— 这是可执行判据，与「文档写了并集等于地板」无关。
3. 第一次真跑看三件事：运行页面出现 **4 个门禁作业 + 1 个 coverage 作业**；coverage 作业打印每片段数/秒数；它的
   `union == --floor` 计数相等（这条比任何预算表都硬）。

### 1.7 失效面

- **片挂了 = 信息丢 1/4，诊断变粗**：一片崩掉时，读者看到的是「这 43 段里的某一段」，而不是今天那一条完整的段头。
  日志里最后一个段头 + 选段披露行能缩小范围，但比单作业时费力。这是并行换来的、绕不开的代价。
- **单片成本失控**：像 §51 那次 1018 s 的 SIGPIPE 空转（P343 归因）落进某一片，该片撞 60 分上限被取消，coverage 作业
  红并点名该片的段。**比今天好**：今天是整套取消、一条段头都不剩（0.3.0 的公开 CI 就是这样死在 #110）。
- **FULL 兜底仍会超上限**：基点不可解析或未声明路径时走全套，含 `61b`（记录在案 4946 s ≈ 82 分）——分片后仍会有一片
  扛着它超上限。今天更差（也一样被取消），所以这不是回归；要根治得另立一条「CI 的 FULL 也排除 gate-self-check」
  的决定（一行改动，但是个新裁定，不塞进本方案）。
- **跨片可见性**：只在 self-hosted 共享主机上出现（§1.3 最后一条）。
- **计算量 +33%**，wall clock −65%。

## 2 · B · 地板瘦身

### 2.1 判据（两条，都可以逐段反驳）

只留满足**任一**条件的段，其余靠改动路径选中 + 合入/里程碑/发布跑全量：

- **R1 契约面**：这个段判的是**别的项目或操作系统能观察到**的东西 —— CLI 与退出码、JSON 形状、看板/账本文件格式、
  安装与升级路径、门禁锁、tmux 边界。
- **R2 事故墓碑**：这个段是**一次付过代价、复发时没人会立刻发现**的事故的墓碑 —— 静默类：账本被写坏、凭据/家目录泄漏、
  挂住、配额烧掉、假绿。

不合这两条的段不是「不重要」，而是**失败会被人当场看见**（用工具的下一次就发现），代价有界在项目自己身上。

### 2.2 保留清单（69 段）与丢弃清单（59 段）

完整枚举，每段恰好出现在一侧（`0e 0f 0g 0h 0i 36 61b` 是两边的外面：它们已经在门禁自检行里）。

**保留 · 69 段**

|---|---|---|
| 前导 | `0 0b 0c 0d` | 任何选集都先跑；不是判定，是运行前提 |

### 2.3 预计 CI 时长（算式）

`Σ 保留段的成本 = 1281 s（6 条实测）+ 63 段 × 33 s = 3360 s = 56 分`，加构建 59 s 与 checkout/openspec ≈ 2 分 →
**约 58 分，顶到 60 分上限**。这不是估算误差的事，是结构性的：**成本集中在留下来的那几段**上（38/41/40/34d/39 合计
1281 s 占瘦身后的 38%），丢掉的 59 段全是 33 s 量级的尾巴（合计 1947 s）。

要把瘦身后的地板压到 40 分（2400 s），还得再从保留清单里丢 29 段 —— 也就是**合计丢 88/128 = 69% 的地板**，
而按 R1/R2 那些段都是契约面或墓碑。两难是算出来的，不是口味：

| 目标 | 需要丢多少段 | 丢的时候会丢到什么 |
|---|---|---|
| 60 分上限（含构建/openspec） | 59 段（本表） | 尾巴；落地即顶格，零余量 |
| 40 分 | 88 段 | 开始丢契约面（例如 §38 配置一致性走查、§34d 锁身份面） |
| 30 分 | 96 段 | 只剩安装/初始化/部分派单/门禁锁 |

### 2.4 失效面

- **被丢的段回归要等一次「改到它声明路径」的推送**。窗口是天到周 —— 这段区间里，一个静默回归（例如某条账本写入
  悄悄不生效）不会被任何推送抓到。
- **路径声明比「这个段的行为不受影响」窄得多**：`section-select.sh --check ⑥` 只核段里点名的**字面**路径 token，
  不核传递依赖。地板是唯一不依赖这份声明正确性的东西 —— B 换掉的正是它。
- **B 会让「镜像钉的版本变了」这一类彻底无覆盖**：今天 `ci/Containerfile` 被 `14b` 一行声明着
  （`--paths ci/Containerfile` → `keys=5`：只有前导段 + 14b），普通推送因为有地板才不至于无覆盖；B 之后 14b 在丢弃侧，
  于是**换 tmux/pi/bun 版本只会跑前导段**。这正是 M47 那一类（CI 环境漂移）静默回来的路。修法是一行（把 `ci/Containerfile`
  从 14b 的 patterns 里去掉，让它落到 FULL），但那是一条独立的裁定，谁做 A 还是 B 都得先修。
- **保留清单是一份要长期维护的判定账本**：每加一段判一次，规格变一次复核一批。这是「控制面自己长出一套系统」的形状，
  与本项目「净零守卫」的纪律直接冲突。
- **B 的省下来的时间是会缩水的**：今天的分段实测里含两个夹具缺陷的成本（§41 的 368 s 里约 300 s 是等待上界设错，
  P343/P344；§51 那一族在修掉前是 1018 s）。缺陷修好后 §41 会掉到几十秒 —— 而 B 的天花板由**保留的重段**决定，
  省掉的时间恰恰不在那儿。

### 2.5 怎么验证它没丢覆盖

B 能验证的只有「机制还在」，验不了「行为没坏」，这点必须写清：

1. **逐条路径选择**：对 59 个丢弃段，取它声明的每条路径跑一次 `--paths <path>`，断言该段被选中（59 行清单）。
   任何一行选不中 → 该段实际变成「只在发布时跑」，必须显式声明而不是假装被路径覆盖。
2. **发布清单**：把「推送时不跑的 59 段」写进发布清单，并断言发布全量运行的收口行覆盖 135 段（无遗漏）。
3. **无法验证的那一半**：路径没变但行为坏了（例如共享工具函数改了、上游依赖变了），B 无处可抓 —— 只能等发布前的
   全量。这正是 A 不必付的代价。

## 3 · C · 瘦身后再切片

| N | 每片墙钟 | 备注 |
|---|---|---|
| 2 | 32–36 分 | 闭包重复后仍两片 |
| 3 | 17–33 分 | 不平（哈希运气） |
| 4 | 10–24 分 | 余量最大 |

**实现代价**：A 与 B 的写集相加（A 的五个文件 + B 的六个文件），外加一条交互规则 —— 切片作用在**瘦地板**上而不是
地板上，于是 `--slice` 必须与 `--push-floor` 同用；任何一边改语义都要两边一起改。这也是「两个机制」的真正价格。

C 的数字漂亮，但它是**两个机制的成本相加**：A 的 +33% 计费分钟与诊断变粗，B 的 69 段覆盖损失与永久判定账本。
A 已经把 CI 压到 19–37 分、离上限留 20 分以上，C 多买的那 10 分钟没有对应的需求。

## 4 · 为什么推荐 A（四句，都可核对）

1. **唯一不拿覆盖换时间**的路：覆盖是 coverage 作业断言出来的（并集 == 地板，缺一段就红），不是承诺的。
2. **达到目标还有余额**：19–37 分 vs 60 分上限；B 单独 56 分已顶格，C 才有多余余额但要多付 B 的全部代价。
3. **不需要维护任何新清单**：新段按规则自动进一片，N 只有一个来源（矩阵长度），`section-paths.tsv` 一个字不改。
4. **代价都是可接受的**：+33% 计费分钟、诊断粒度从「整套」变成「1/4 套」；两者都不涉及交付物正确性。

## 5 · 假设与误差（诚实边界）

- **122 段按均值 33 s 估**是唯一的估算假设。误差方向：如果地板里还有未被 brief 点名的中段（100–150 s 量级），
  每片估算会被低估；上界可按「一片 ≤ 最重 own_sum + 闭包」估，今天最重的一片是 2261 s ≈ 38 分（§1.4 右上栏）。
- **`61` 在地板里的成本我核不到**：brief 的 6 条没含它，而 V28 记录 live 495 s、FAST 121 s。若它在地板里按 live 跑，
  拿到它的那一片 +495 s（19–37 → 27–45 分），结论不变。
- **容器与宿主的速度差没有实测**：88.7 分是宿主上的数，CI 是钉死镜像里的数；本仓库已知同一套在容器里会因非 FAST 档
  略慢（`design.md` §3.4 的两条界限）。这也是「第一次真跑必须记录实测」的原因。
- **4 个容器并发对宿主的负载影响**：hosted runner 一作业一 VM，不存在；本机复现（4 个容器同跑）会互相抢 CPU，
  不能拿本机 4 并行的时间当 CI 的读数。

## Decisions and deviations

- **`--slice` 与三种决策正交**（`--floor` / `--paths` / 无决策的全套），而不是只给 `--floor` 加一个分片开关：FULL 兜底
  （基点不可解析）那条路也需要分片，否则它永远是「一条作业跑 11.7k 秒然后被取消」。
- **N 的来源取 `strategy.job-total`**，不新增表头声明行、不写第二个字面量 —— 这是「一个数一个来源」的具体做法。
- **没有把切片键做成表里的 `slice` 列**：那会让「新增一段」变成「必须有人记得给它填片号」，而漏填的默认方向是
  少跑（不安全）。哈希的默认方向是多跑（新段自动进恰好一片）。
- **没有为 B 单独做逐段核对到段正文**：B 的 59 条丢弃项是按**段的主题与它自己点名的 P/M 编号**分的组，属于第一轮
  判定；真要落地，每条都要对段正文复核一遍 —— 这条成本本身已经写进 §2.4，也是我不推荐 B 的理由之一。
- **`ci/Containerfile` 的声明问题**（§2.4 第三条）是路上发现的既有事实，我没改（不在写集内）。它对 A 无害
  （普通推送有地板兜着），对 B 是硬伤；无论裁哪条，建议单独立一行小任务把它挪出 `14b` 的 patterns。
