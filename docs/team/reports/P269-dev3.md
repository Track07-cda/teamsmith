## Decisions and deviations

1. **`deltas:` 头部必须改（裁定点 1）**：任务书写 `deltas: -`，但本提案必须改 `board-and-status` 的**一条
   既有 requirement**（实时字段表），并把 `team reap` 的破坏性纪律落在 `boundary`。推荐改成
   `deltas: seat-visibility,boundary,board-and-status`，apply 按 delta 切两个任务
   （apply-1 `seat-visibility,board-and-status`；apply-2 `boundary`——两组不相交，满足 dispatch 的 delta
   单写者守卫）。**这是我没有自行改任务书、而是写进裁定点的原因**：任务书是 PM 的只读文件。
2. **能力落点与任务书的「新能力，名字你定」有一处扩张**：任务书只要求一个新能力；实现上有三份 delta——
   新能力 `seat-visibility` 加 `boundary`（`team reap`）与 `board-and-status`（实时字段表）各一条。
   理由写在 proposal 的「为什么落点是这三处」：`team status` 的实时字段表住在 `board-and-status` 那条缓存
   等价性 requirement 里，`team reap` 是破坏性动作而 `boundary` 正是这条纪律的家；写进新能力会制造两份
   互相矛盾的规格。若 PM 裁定「只许一个新能力」，请明说——那要么放弃 `team status` 的完整读数（只留容量行
   提示），要么让新规格与 `boundary`/`board-and-status` 重复。
3. **digest 的提示挂在容量行行尾（裁定点 2）**：这样 M50 的 digest 归一化（`grep -v 'RAM 可用'`）一个字
   都不用改；`team status` 的读数则**必须**改那条 requirement 的实时字段枚举并让闸门按新表过滤——这是
   本变更唯一一条被改的既有 requirement，改动只有一处枚举。
4. **三个新契约键（裁定点 3）**：`TEAM_ORPHAN_WARN_MB`（阈值）、`TEAM_ORPHAN_SCAN`（关掉普查的接缝）、
   `TEAM_ORPHAN_PROC_ROOT`（`fixture-only:` 夹具接缝，用来确定性地造「读不到 / 中途消失 / 空环境」三种
   边界）。都进既有 `delivery` 组，不新增 group。加面板文案必须用钉住的工具链重建 `panel.js`（写进 tasks 7.3）。
5. **`team reap` 而不是 `team resume --adopt-orphans`**：进程的 TUI 已经不在任何 pane 里，没有「收编回窗口」
   的可行路径（`respawn-pane` 会杀掉它 = 清理）。一个叫 adopt 的旗标却只能 kill 是误导，所以命令名就说它
   做的事。默认态（无 `--yes`）**退 0**（与 `--print`/`--dry-run` 的既有惯例一致），复验不过的目标退非 0。
6. **不自动清理、不定时清理**：没有 pulse/watchdog 自动 reap 的路径——「不可逆动作自动发生」与既有纪律相反。
7. **不进面板数据面**：面板按帧预算刷新，一次全主机 `/proc` 普查会把预算打穿；`__panel-data` 与面板输出
   保持不变（写进规格的 ADDED requirement 与 tasks 4.4/4.5）。
8. **普查的代价**：先用一次 `ps -eo pid=,args=` 筛候选再读 `/proc`（同 `team_pm_other_sessions_in_dir` 的
   既有做法），避免每个 pid 都 fork；写进 design §7 与 tasks 1.1。
9. **`signal-lint.pl` 的调用口径**：见「已知前提」——裸调用今天是既有红（过期豁免清单），验收行按闸门 §58
   的既有做法写成 `--legacy /dev/null`。没有去修那条清单（不在本任务范围，且属于别人的账）。
10. **没有偏离任务书的范围**：五条要求逐条落成 requirement 与任务，没有加「自动清理」「按名字找孤儿」
    「跨项目动手」这类扩张；跨项目只报总量、不点名、不清理。
