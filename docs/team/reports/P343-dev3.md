## 51：明细是 `C2/tmp-root-mkdir`，触发条件是环境里的 `TMPDIR`

段里的红行只说「有失败」，明细在段临时根里（`--keep` 留下来了）。`$TMP/routes.log` 里**只有一条** finding：

```
$ grep -aF -e $'\033[31m✗' /var/tmp/p343-dev3/tmp/teamsmith-smoke-clean_main-eca8311f.HGw5IC/routes.log
  ✗ C2/tmp-root-mkdir：拒绝命令没有拒绝（rc=0）
$ grep -a '== 结果 ==' …/routes.log
== 结果 ==  ✓ 252  ✗ 1  SKIP 0
```

这个走查名字的期望（`tests/routes.sh` ⑲，P309 的“拒绝 + 可粘路线”族）：在夹具里把 `TEAM_TMP_ROOT` 指到一个
**不存在**的目录、跑 `dispatch … --print`，期望它**拒绝**、输出里点名「临时根不可用」、并打印一条
`修法：mkdir -p <根>`；把那条路线原样粘回去之后再跑，阻塞项必须消失。实际拿到 rc=0（派单直接放行了），
所以第一条断言就红。

原因在产品里是**文档化的**，不是缺陷：临时根的来源优先级是 `TMPDIR` > `TEAM_TMP_ROOT` > 平台默认，

```
$ sed -n '/^team_tmp_root_source()/,/^}/p' skills/teamsmith/scripts/lib/common.sh
team_tmp_root_source() { # → tmpdir | config | default（顺序只在这里实现）
  if [ -n "${TMPDIR:-}" ]; then printf 'tmpdir\n'
  elif [ -n "${TEAM_TMP_ROOT:-}" ]; then printf 'config\n'
  else printf 'default\n'; fi
}
```

产品自己还会把这件事说出来（`team_tmp_root_note` 的 `source=tmpdir（项目配置 TEAM_TMP_ROOT=… 未生效：环境里的
TMPDIR 赢了）`）。于是当 `TMPDIR` 被导出时，夹具设的那个不存在的 `TEAM_TMP_ROOT` **根本没被用**，真正生效的是
`TMPDIR` 下的根（存在、可写），派单当然不会拒绝。

决定性对照：同一棵干净树、同一个夹具族（`routes.sh refusals`，只跑 Walk C），只改 `TMPDIR` 一个输入：

```

  ✗ C2/tmp-root-mkdir：拒绝命令没有拒绝（rc=0）
  == 结果 ==  ✓ 27  ✗ 1  SKIP 0
$ env -u TMPDIR TEAM_ROUTES_TREE=…/clean-main bash …/routes.sh refusals
rc=0  wall=47s
  == 结果 ==  ✓ 28  ✗ 0  SKIP 0
```

第二臂里 ⑲ 那条 **绿**，而且是走完整条契约的绿（拒绝 → 点名 → 粘路线 → 阻塞项消失），说明产品侧没有坏，
坏的是夹具的前提：它假设「临时根的唯一来源是 `TEAM_TMP_ROOT`」。**建议：修夹具** —— 那个 case 的
`rc_team` 里加 `-u TMPDIR`（与它已经在用的 `-u TMUX -u TMUX_PANE` 同一手法），或干脆把 `TMPDIR` 设成同一个
`$d/explicit-root`，这样它测的才是它声称的那条路线。断言本身要留：它是 P309「显式根不可用就具名失败」的唯一牙齿。

## 41：不是「roster 看不见活窗口」，是「读之前窗口已经被等掉了」

段里的两条红（机器面红带出了原因，一并贴）：

```
  ✗ P55 ④：roster 四态 ① running（证明成立）（…/p55-roster.log 中没有匹配 [^p55live +● .*在跑]）
  ✓ P55 ④：roster 四态 ② exited（窗口/pane 活着，没有 agent）
  ✓ P55 ④：roster 四态 ③ dead（行内带退出证据）
  ✓ P55 ④：roster 四态 ④ absent
  ✓ P55 ④：图例说全四态（含死 pane 的含义与现场入口）
  ✗ P55 ④：机器面断言失败
    机器面断言失败：p55live 不是 running+live：{'name': 'p55live', 'state': 'absent', 'task': 'T9.56', …}
```

`p55-roster.log` 全文（四态都在，唯独 p55live 是「无窗口」而不是「在跑」）：

```
p55live    · 无窗口 -                             -        -       -  ·unavailable
p55exit    ○ p55-agent 已退出 -                             -        -       -  ·unavailable
p55w       ▲ 已死 signal=9 task/T9.55-t9-55              0        0       -  deepseek/deepseek-flash·policy
p55none    · 无窗口 -                             -        -       -  ·unavailable
```

关键在**位置**：④ 的断言之前，段的看门狗在这一段里连打了 60/120/180/240/300 秒五次心跳，也就是那 300 秒
全花在 ④ 开头的那个等待循环上。那循环是（`smoke.sh` §41 ④，P55 原样，P316 只改了上界）：

```
  P55_W=0
  while [ "$P55_W" -lt 1000 ]; do
    P55_RENV bash "$SKILL_DIR/scripts/team" roster 2>/dev/null | grep -q '在跑' && break
    sleep 0.3; P55_W=$((P55_W + 1))
  done
```

`smoke.sh` 顶部是 `set -uo pipefail`。`grep -q` 一命中就退出，而 roster 在命中行（p55live 那行）之后还要打印
图例与四行说明（整份输出 1597 字节），于是 roster 吃到 SIGPIPE、管道状态变 141 —— `&& break` 永远不成立。
这不是罕见竞态，是每次都发生：

```
== 同一行管道（带 pipefail）跑 8 次 ==
  run1 pipeline_rc=141   run2 141   run3 141   run4 141   run5 141   run6 141   run7 141   run8 141
== set +o pipefail（只在本子 shell 里）==
  run1 pipeline_rc=0     run2 0     run3 0
== 落文件再 grep（routes.sh 头注推荐的口径）==
  run1 roster_rc=0 grep_rc=0   run2 同   run3 同
== grep -c（把输出读完，不早退）==
  run1 pipeline_rc=0     run2 0     run3 0
```

循环于是每次跑满 1000×0.3s = 300 秒，而夹具那个假 agent 的寿命正好是 300 秒（`echo P55-MARK-1…5; sleep 300`），
手工窗口又没有 `remain-on-exit`：

```
t=0s  windows: [tmux p55livefast]
t=4s  windows: [zsh]        ← 用快版假 agent（sleep 2）演示：pane 里的命令一退出，窗口自己就没了
```

所以 300 秒一满，p55live 的窗口已经关闭，最后那次 roster 读到的是「无窗口」（机器面于是 `state: absent`，
不是 `exited`）——两条红是同一个原因的两个面。

**产品侧是好的**：用那一次运行的同一个临时根（repo + 状态文件 + 配置里的 session 名）、同一台机器的私有 socket，
逐字照抄夹具那两条 `tmux new-window`，同形的 `team roster` 给出

```
p55live    ● p55-agent 在跑 -                             -   …   T9.56
p55exit    ○ p55-agent 已退出 …
$ team_seat_condition p55live   →  running
$ team __panel-data --block agents → p55live state='running' pane='live'；p55exit state='exited' pane='live'；p55none state='absent'
```

也就是：只要在窗口还活着的时候读，断言要的东西就在 —— 包括那第二条也一并变绿的**机器面**（面板数据）。

**为什么今天才红**：这一行是 P55（`26738856`，2026-09-22）写下的，但当时上界是 `-lt 20`（6 秒）—— 6 秒后
循环照样退出，窗口还活着，断言是绿的（假绿：等的那件事从来没被等到）。P316（`d92f0a17`，2026-10-20，合在
main 上）把这些夹具的等待统一抬到 300 秒（`-lt 20` → `-lt 1000`），正好压到假 agent 的寿命上，假绿就翻成了
稳定的红。**建议：修夹具** —— 把读面落到文件再 `grep`（或 `grep -c`）并且让上界明显小于假 agent 的寿命；
断言本身要留（它守的是「活座位必须是 ●」和「遗体绝不能是 running」，两条都是点名事故的墓碑）。不动它的话，
这一段每次白等 300 秒，且永远红。
