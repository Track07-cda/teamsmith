# P446 · 修复关键回复两个 command reload 看门狗超时

branch: `task/P446-reply-reload-timeout`   PR/MR: -

## 根因

不是关键回复的 `ctx.reload()` 或 90 秒等待有问题，而是提醒能力记录删除时泄漏了锁：

1. `updateRemindCapability()` 在判断写入还是删除之前就生成 `temp = .current-<uuid>`。
2. 删除分支只删 `current.json`，不会创建这个临时文件；`finally` 却无条件删除 `temp`，因此得到 `ENOENT`。
3. 这个异常发生在 `closeSync(lock)` 之前，导致 `capability.lock` 和目录描述符留在 PM 进程里。重载清理已经删除旧记录，但锁仍由旧描述符持有；新会话启动时再次取锁，于是在 `locks_lock_inode_wait` 自等，最终表现为 `command reload` 的 90 秒 fixture watchdog 超时。

最小修复只在真正创建临时文件的写入分支里设置 `temp`。删除分支没有临时文件可清理，正常执行到锁和目录关闭。没有提高 90 秒上限、删除场景、改 SKIP，也没有用静态检查替代真实 reload。

改动前基线 `61d3ae19` 与改动前当前提交 `0f72bd48` 都在私有真实 Pi/tmux 中复现两次超时；修复后同两场景在 12.3 秒内通过。直接产品函数对照也在改前得到 `.current-<uuid>` 的 `ENOENT`，改后完成删除并立即重新注册。
