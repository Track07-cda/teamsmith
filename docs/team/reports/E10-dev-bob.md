> 这份报告是**探索者的原始产品判断**，不是 PM 的方案，也不是已批准的产品方向。事实、推断、建议分开写；
> 每项事实带文件位置或公开 URL。PM 会另写可行性意见，不修改本结论。

## 摘要

- **落差（一处）**：teamsmith 的自主性从「拿到目标」开始，往后的拆解、派单、复验、合并都很自主；但**目标本身
  只有使用者一个人能提供**。产品里没有这样一层：团队自己观察到一个产品级问题，把它连同证据与选项放到一个
  固定的地方，使用者只对方向做一次决定，之后确认结果能回链到真正实现的改动。
- **候选 1（推荐）**：把决策日志里已经写好的三种状态变成**真机制**。新增/明确「提议（等待使用者）」状态：
  ≥1 个带证据、选项、推荐与不确定度的候选；任何席位的报告都可以提出，PM 只能记下或**带理由**拒绝，
  不能静默丢弃；使用者一次只做一个方向决定；确认后的条目必须回链到承载它的 OpenSpec change，并有检查。
- **候选 2（可独立、也可作为 1 的读面）**：使用者的「只需看我」一屏：等待我决定的条目 + 已确认需求在飞的
  进度。它回答「不必一直盯着详细进度」的那一半。
- **使用者只需做的高层决定**：每个候选一次「做 / 选哪个方向 / 缓一缓 / 不做」，外加本就要保留的共享状态授权
  （merge / push）。需求的行为细节、场景、实现选择与验收都由 PM 与团队承担。
- **反向验收**：若功能做出来了，使用者却仍要写需求正文、读任务书或设计、或追问「我确认的那件事做了吗」，
  候选 1 判为没有达到目标。
- **自我反驳的诚实结论**：如果使用者真正想要的是「我口述目标，agent 补齐细节并问我」，那么当前流程加一条
  PM 行为规则就够，不需要新对象；本建议多出来的价值只在「团队主动发起」与「可检查、可追踪」两点。这个取舍
  需要使用者本人拍板，本报告的工作是把它摆清楚。

## 3. 落差判断

**观察**（上文 O1–O8）：产品的模型是「使用者给目标 → PM 拆成任务 → 团队自主交付与验证」。
所有自主性都在目标**下游**；需求本身没有入口、没有候选、没有使用者确认的落点，也没有回链。
决策日志的模板里预留了「已确认（用户确认）」这一状态，但账本不用它、工具不读它。

**推断**（含不确定度）：

1. 团队目前**无法发起**一个产品级需求。席位能在报告里写 finding（缺陷类确实会变成后续任务），
   但一个「产品该新增什么」的候选没有可去之处；是否让使用者看见，取决于 PM 当时是否愿意转述。
2. 使用者要「不必一直盯着详细进度」，那么他需要的是**方向决定**这一层；产品的读面（digest、面板四页）
   全是 PM 运维视角，没有任何地方回答「有什么在等我」。
3. 这两点合起来意味着：目前产品更接近「一个执行力很强的交付团队」，而不是「一个能自己盯住产品方向的
   项目负责人」。D99 明确要后者。

**不确定度**：我无法证实使用者想要一个**清单**（他可能更愿意在对话里被问）。也无法证实团队提出的候选
会有足够质量（目前样本只有本次探索这一例）。这两点是本报告建议先做「最小可检查版本」、而不是做完整
子系统的原因。

## 4. 候选需求 1 · 产品级「提议 → 使用者一次定方向 → 回链」闭环

**目标使用者要完成什么**：使用者在不写需求正文的前提下，收到团队从产品高度提出的需要，每次只需要做一个
方向决定；确认之后不需要再盯，交付结果能反向追溯到这次确认。

### 4.1 可复核的观察（支撑本候选的事实）

- O1、O2、O3：需求层不存在；任务与 OpenSpec change 都接不上「为什么做」。
- O4：需求变成行为要求的整段过程由 PM 独占，使用者只在开端（聊天）与末端（archive 确认）出现。
- O5：模板已经定义「已确认（用户确认）」这个状态，实际 0 次使用，工具也不解析它。
- O6：待决策的候选已经在 PM 的自由文本里出现过，说明这条链有人需要，只是没有机制。

### 4.2 推断与不确定度

推断：把 O5 里已经写在模板上的状态变成真机制，比新建一套「需求库」代价小，也不会与
「只有一个规格系统」的规则冲突（`references/openspec.md` §3：承诺进规格，不要在任何地方长出第二份
需求清单）。不确定度：新增的「等待使用者」状态是否会变成 PM 的流程负担，取决于候选的粒度；
我建议把粒度限制在**每次只有一个方向问题**。

### 4.3 用户可感知的行为要求（建议以规格场景形式落地）

1. **候选有固定形状**。一条候选至少含：一句话标题、问题观察（可复核的证据指针：文件/命令/URL）、
   推断与不确定度、提议的**使用者可感知行为**、明确不做的范围、≥1 条替代路线、一条推荐、
   提出者与时间。
2. **谁都能提，PM 不能静默丢**。任何席位的报告都可以提出产品级候选（经由报告，不需要新命令）；
   PM 要么把它记成一条「提议」条目，要么在**同一个地方**记下拒绝/缓办的理由。使用者随时能看到
   「被提过但没做」的清单。
3. **状态是闭集且被工具读**。条目状态取自固定集合（如：`提议（待用户）`、`用户已确认`、
   `PM 已定（用户可否决）`、`废弃`），「待用户」的清单可以由工具一条命令读出。
4. **使用者的决定是一次选择**。每个候选用一个紧凑的块呈给使用者：证据 + 选项（含推荐）+ 需要他回答的
   那一个问题（做 / 选哪个方向 / 缓 / 不做）。**不要求使用者写行为细节**。
5. **确认必须回链**。`用户已确认` 的条目必须指向承载它的 OpenSpec change（或 brief 锚点）；反过来，
   由候选产生的 change 必须回指该条目。检查是双向的：确认了却没有 change → 红；有 change 却没有
   任何确认记录 → 红。
6. **不打扰**。使用者的「需要我」读面只列 `提议（待用户）` 的条目；确认或拒绝后它立即离开这个读面。

### 4.4 不做的范围

- 不是第二套规格系统：条目里**不放**场景、验收标准或行为正文；能成立的行为文字只在 OpenSpec 里。
- 不是任务板、不是排期工具、不是优先级系统（不做分数、估时、截止日期、自动排序）。
- 不改变现有派单 / 复验 / 合并门禁；不新增外部服务或依赖；不让候选绕过 PM 直接开 change。
- 不在没有证据时生成候选（宁缺毋滥），不使用虚假的「用户访谈」。

### 4.5 至少两种解决方向与取舍

| 方向 | 做法 | 优点 | 代价 / 风险 |
|---|---|---|---|
| **A（推荐）** 复活决策日志的状态 | 在 `DECISIONS.md` 里启用「提议（待用户）」等状态；PM 维护条目；`team digest`（或一条只读命令）列出待决条目；门禁加一条「确认 ⇄ change」双向检查 | 复用已有对象与模板，不新增文件、不撞「一个规格系统」；账本本来就在公开面；检查可证伪 | `DECISIONS.md` 从「append-only 的记录」变成「有可变状态的队列」——历史条目更新必须保留原状（如追加状态变更行），否则审计性受损 |
| **B** 新建 `docs/team/REQUIREMENTS.md` 候选清单 | 独立文件、独立 schema、独立命令 `team req …` | 队列语义最清晰；可以被使用者单独打开 | 与 `openspec.md` §3「不要在 `docs/team/**` 里长需求清单」正面冲突：要么放宽规则（削弱既有保证），要么让两处文字漂移；新增的命令面与门禁也要长期维护 |
| **C** 把候选做进 OpenSpec | 允许在 `opsx-propose` 之前存在「候选 change」，使用者先确认它 | 只有一个规格系统，回链天然存在 | 使用者要读 pipeline 的产物（proposal/design 形态），与「不读方案」的目标相反；同时把 PM 的 proposal review 门与使用者的方向门混在一起，谁负责哪道门变模糊 |

**推荐 A**。理由：它把「团队主动提出」「使用者一次定方向」「确认可追踪」三件事接在**已经存在的对象**上，
不需要新的概念体系；而且它天然符合「规格只在一个地方」的硬规则。B 的清晰度代价太高，C 的altitude不对。

### 4.6 为什么值得现在讨论

- 使用者刚刚明确提出这个目标（D99），而产品发布 0.1.1、尚无外部使用者——现在是定义「产品负责人如何
  获取需求」最便宜的时刻，之后每加一个能力都会被这条缺口拖住。
- 具体成本小：复用模板状态 + 一个读面 + 一条双向检查。它不是新引擎，不碰交付门禁。
- 现在不做的话，缺口会以两种方式复利：每个新能力都等使用者口述需求；账本里「为什么做」的确认记录
  继续缺失（今天状态词使用次数为 0）。

## 5. 候选需求 2 · 使用者的「只需看我」一屏（可独立，也可作为候选 1 的读面）

**目标使用者要完成什么**：一次 30 秒的查看，只看到「需要我决定的」与「已确认的需求在飞到哪里」，
不用读任务、报告或方案。

### 5.1 观察与推断

观察：`team digest` 的三段是容量/存活、待处理通知、待复验报告（`skills/teamsmith/scripts/lib/cmd-status.sh`），
是**给 PM 的待办摘要**；面板四页（总览/工作/消息与日志/看板）按 PM 的运维需要组织；总览的「最近决策」是
最近三条灰字标题，不区分状态（O5）。推断：使用者的现状是「要问 PM 才知道」或者「不看」——两种都不满足
「不必一直盯着」。不确定度：使用者可能更想被**推送**一条消息，而不是打开一个界面。

### 5.2 行为要求（建议）

1. 存在一个只读读面（命令或面板页），列出等待使用者的条目：问题、选项、推荐、证据指针、需要他回答的
   那一个问题。
2. PM 只允许用这个读面上的条目打断使用者；不在读面上的事情由团队自己处理。
3. 条目被回答后离开读面；被 PM 自行决定（用户可否决）的条目与等待用户的条目视觉上可区分。
4. 同一读面回答「已确认的需求在哪个阶段」（不需要进度百分比，只需要：在提方案 / 在实现 / 在复验 / 已交付）。
5. 推送是可选方向：一个里程碑一次产品高度摘要，而不是每次任务变动。

### 5.3 方向与取舍

- **A（推荐）** 作为候选 1 的读面：从决策状态 + 已确认条目推导，复用 digest/面板，不加新文件。
- **B** 独立的「产品页」+ 周期推送：体验最好，但要新增面板页、文案与推送通道，成本明显更高，
  而且使用者尚未表达要推送。
- **C** 不做，保持现状：使用者继续靠对话询问。这是最诚实、但直接违背 D99 的选项。

## 6. 使用者还需要盯什么（按本建议的行为）

**使用者只需要做的高层决定**：对每个候选做一次方向选择（做 / 选哪个方向 / 缓 / 不做），以及保留本就需要
使用者授权的共享状态动作（合并、推送、生产类操作）。除此之外不需要写需求正文、不需要读任务书或设计。

**由 PM / 团队自行承担的细节**：把方向决定展开成可验证的行为要求与场景（OpenSpec delta）；选实现路线与
取舍；拆任务、派单、复验、合并；候选的证据收集与不确定度标注；被拒绝/缓办条目的理由记录；进度与风险的
整理。团队只在出现**新的方向级选择**或需要授权时回到使用者。

**反向验收**（若功能实现后仍出现下列任一情形，判为未达到目标）：

1. 使用者为了推进一个已确认的需求，仍然要写行为细节（例如回答「这个按钮具体应该怎么工作」）。
2. 使用者要读任务书、设计或 spec 才能知道将要发生什么。
3. 使用者要追问「我确认的那件事做了吗 / 卡在哪」才能知道结果。
4. 某个席位提出的产品级候选被 PM 拒绝，而使用者从未见过它（静默丢弃）。

## 7. 自我反驳

**7.1 不新增对象，只改文档或训练 PM，能否等效？**

能覆盖一半：在 PM 的提示词里加一条「在开 proposal 之前，把问题、证据、选项、推荐摆给使用者，并把回答写进
决策日志」，确实能让「问使用者」这件事规矩起来。但覆盖不了三件事：

- **磁盘取代记忆**（`references/philosophy.md` §6）：只活在对话里的询问，下一次 PM 会话重启就找不回；
  而「建议使用者做决定」恰恰是最需要跨会话保真的东西。
- **不能静默丢**：席位的 finding 是否被转述，完全取决于 PM 当时的判断，没有可检查的痕迹。
- **确认要能追踪**：使用者确认过什么、后来做成了没有，今天没有对象可以回答。

另外，产品自己的信条写了「重复出现的问题要变成机制，而不是『下次小心』」和「每一个承诺都要有对应的断言」
（`references/philosophy.md` §5）。所以我的建议是**最小的可检查版本**：状态 + 一个读面 + 一条双向检查；
不是新引擎。它和「只改提示词」的差别，正是产品自己划的那条线。

**7.2 现有的什么证据会推翻我这个建议？**

1. 使用者说「需求我会在对话里提，我只要 agent 把细节补齐」→ 那候选 1 的「发起」那一半不必要，
   只保留「细节补齐 + 提问规矩」即可。
2. 试运行一段时间后发现使用者从不看「待我决定」读面，只接受对话询问 → 候选 2 不必要，候选 1 只留
   账本 + 转述规则。
3. 实际上 PM 已经在转述每一条产品级 finding、使用者每次都在对话里确认方向，且账本完整记下了每次确认
   → 那缺的只是「把确认写进日志」（最小切片），不需要读面与双向检查。
4. 反向的证据：如果外部使用者开始提需求（公开仓有 issue），需求来源不再稀缺，这条缺口的优先级自然下降。

**7.3 诚实结论**

- **值得现在讨论**：候选 1 的最小版本（复活状态 + 不允许静默丢 + 确认回链 + 一个待决读面）。
  它直接对应使用者的原话目标，成本小，且能用可证伪的检查守住边界。
- **不值得现在做**：新建需求库/新命令体系/自动排序（候选 1 的方向 B）、独立的推送面板（候选 2 的方向 B）、
  任何形式的「假装有用户研究」。
- **需要使用者本人裁决的**：他想要的是「团队主动发起需求」还是「只补齐细节」。这两种答案对应两种不同的
  产品，本报告不能替他选。

### 待验证的假设与补证办法

| 假设 | 怎么补证 |
|---|---|
| 使用者要的是「团队主动提出」，不只是「补齐细节」 | 让使用者读本报告后直接选一次（一句话即可）；无需任何访谈或统计 |
| 待决读面不会变成新的盯梢负担 | 试运行一个里程碑，记录使用者被请求决定的次数与每次耗时；超出约定预算就缩小粒度或改为推送 |
| PM/团队能提出有证据、有不确定度的候选 | 从一个真实的小目标跑一次「观察 → 候选 → 使用者确认 → change」并留下记录（本次 E10 只提供了一个样本） |
