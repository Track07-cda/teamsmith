## 结论

**PARTIAL。** 用户裁定的**主体已经落地**：性能套件不再判定（只测量、只打印、`exit 0`；阈值、负载前提、
可见 SKIP 全删），实测 4065 ms 首帧的机器上 `perf.sh --host` rc=0；CI 那一步本来就是
`continue-on-error: true`，所以「性能不阻塞」在产品面和流水线面都成立。三条必要行为（锁的排队/运行边界与
归属、没等到真实 UI 状态、不终止进程的停跑与现场）都还在，且锁那一条的判据从「等了几秒」换成了账本自己的
`排队等满上限` + rc，比原来更硬。

但报告里三句结论按字面不成立，且改动删掉两条**活契约**的守卫：

1. **「门禁里不再有任何墙钟判据的红」不成立。** `smoke.sh` 的三处首帧等待仍写死 **20 s**（`12062`、`12076`、
   `12175`），到点就 `bad`「没等到…渲染」——这正是「帧时间换个名字当正确性失败」。`gate-guard.sh` 的第 ① 条
   （只按 `$elapsed` 这类变量比较做正则）看不见它，所以守卫绿着、判据还在。
2. **「慢 ≠ 挂住」在实现里不成立。** 1800 s 上限的触发条件是**本段武装后经过的时间**（`lib/section-guard.sh:429`
   `[ "$(( now - armed ))" -ge "$cap" ]`），不是「多久没有进度」。我用现有旋钮造了一个**每 0.2 s 都在 tick**
   的段落：它照旧在 3 s 被判定「挂住」并 `exit 2`（见 §二）。作者报告 §4 那个 1800 s 实例就是真实尺度上的同
   一件事——六个用例各等 300 s 后依次报错，段落一直在推进，却按耗时被定性成「挂住」。
3. **「覆盖率没减少」不成立（总数相同 ≠ 覆盖相同）。** 两处删掉的不是机器速度，而是**产品契约**：
   `key-replies` 的等锁区间 1500–6000 ms（`openspec/specs/key-replies/spec.md` 仍承诺「contention 最多等
   2000 ms 后返回 5」，`scripts/replies.mjs:53` 就是 `LOCK_WAIT_SEC = 2`）与 `routes` 的宽限 0/2 两档差别
   （删完之后两腿断言的是同一个可观察量）。前者今天没有任何断言在守，改 `LOCK_WAIT_SEC` 为 30 也不会红。

另外交付物自身有一个可复现的缺陷：`perf.sh` 的参考汇总表把**已经测到**的首帧与窗格 CPU 打成 `?ms` / `无读数`
（`perf.sh:445-446` 的正则双写反斜杠），并把 `· 参考` 行的真实数字藏在上面的散行里。这是两处反斜杠、
外加一处重复单位的小修。

两棵树的产品/测试字节我核过：`8ff3ac1b..3bb414ba` 只有 `docs/team/reports/P316-dev.md` 一个路径变化，所以

## 二 · 仍然存在的墙钟判定（不成立的部分）

### F1 · 1800 s 上限按「经过多久」触发，不是「多久没动」

`skills/teamsmith/tests/lib/section-guard.sh:429`（看门狗）：

```
if [ "$(( now - armed ))" -ge "$cap" ]; then
```

心跳行里本来就有 `ticks`，但触发条件不看它；`_sg_trip` 打印的「最后状态 Ns」是 `last_seen`（最后一次 tick
时的**武装后秒数**），也不是「距上次进度多久」。于是「正在推进」和「卡死」在上限面前没有区别。

用现有旋钮（`TEAM_SMOKE_FIXTURE=1 TEAM_SMOKE_SECTION_HANG_CAP=3` + 每轮 `section_guard_check`，即
`ok()`/等待循环的真实路径）造的最小现场（scratch，不提交）：

```
$ bash /tmp/v61-probe-567137/progress-probe.sh <8ff3ac1b 导出树> <scratch tmp>
== #1 probe-progressing == 2026-10-19T12:19:24+00:00
TICK … ticks=1
…                     # 每 0.2s 一轮，心跳被重写，ticks 一直涨
TICK … ticks=16

  ✗ 段落 #1（probe-progressing）挂住：已 3s 没有结束（挂住上限 3s，最后状态 3s）→ 停跑（exit 2），现场 …
SUBSHELL_RC=2
```

**影响**：一个合法的慢段落（例如 `panel-b3` 里连续几个各 300 s 的等待）会被定性成「挂住」并停跑，后面所有段
的覆盖丢失，且归因是错的（它把「慢」写成「没动」）。作者报告 §4 的 1800 s 实例就是这个形状，作者自己把
`TEAM_DISPATCH_VERIFY_SEC` 抬到 300 s 后六个用例各等满 300 s——六个用例在依次完成，不是挂住。

**最小建议**（不新增看门狗/状态系统）：把触发条件从「武装后经过 cap」改成「**心跳/ticks 在 cap 窗口内没有
变过**」——心跳文件每次 `section_guard_check` 都会被重写，长等待引擎（`pty_wait_frame`）每轮调一次现成的
`section_guard_check` 即可；自检的四个卡死形状（`stuck`/`stubborn`/`spin`/`deadspin`）本来就不 tick，0f 的
注入段落也不 tick，所以现有红侧一条都不用改。「慢但在动」与「没动」到这里才真的分开。

退一步的最小改法（如果不想动触发条件）：停跑行不要写「挂住」、不要给 `✗`，并让停跑用一个「未跑完」的退出码
（`3` 已被「建不出临时根」占用，需要挑一个）——但那只是**换措辞**，仍然是时间在阻塞，我不推荐。

## 五 · 交付物自身的缺陷

### D1 · perf 汇总表把已测到的两条读数打成 `?` / 无读数

```
$ TMPDIR=/tmp/v61-perf bash skills/teamsmith/tests/perf.sh --host   # 原样 8ff3ac1b
  · 参考 首帧：3930 3936 3819 -> 中位 3930        # 散行：测到了
  · 参考 首帧：3930ms（3 次独立 spawn 的中位）｜ 窗格 CPU：0.50%（三等分中位）｜ …
  ① 交互首帧               | ?ms          | 无读数     # 汇总表：没读到
  ③ 稳态窗格 CPU           | ?%           | 无读数
== 结果 ==  · 参考…；没有红/绿/SKIP 结论        $? = 0
```

根因（`perf.sh:445-446`，单引号里又双写了反斜杠）：模式 `\\(` `\\)` 与替换 `\\1` 在 BRE 里都是字面反斜杠，
永远匹配不到；改成单个反斜杠后立刻读出数字（scratch 里改完再跑）：

```
  ① 交互首帧               | 4065msms     | 4065ms
  ③ 稳态窗格 CPU           | 0.50%        | 0.50
```

第二行的 `msms` 是同一个匆忙的痕迹：捕获组已带单位，`printf '%s' "${J_FIRST_MEDIAN}ms"` 又加了一次。
最小修法：两行各去掉一个反斜杠（4 个转义点），并把单位只留一处。影响：不是绿红，而是参考报告器的
**门面**（人读的那张表）把两条读数丢成「无读数」——正好是这次改动要保的东西。
