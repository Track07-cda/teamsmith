## 现场复核的结论：第 ① 条的缺陷判断与代码/设备不符

任务书写「发送成功后没有清空草稿」，复核不成立：

1. `scripts/panel/src/App.tsx` 的 send 结算里已有

   ```ts
   if (r.state !== 'error') { updateDraft('', false); setPoint(0); api.clearDraft() }
   ```

   `src/main.tsx` 提供 `clearDraft: () => writeDraft('')`；`src/compose.ts` 的 `mapReceipt` 决定回执类。
   `tests/panel-b2.sh:894` 早就断言 `queued` 之后 `state/draft.md` 为 0 字节（B3 组，本轮实跑 ✓）。
2. 本轮实跑（上面第三条证据）三种回执各一次真发送，跑完后保留现场的 `draft.md` 是 0 字节 —— 即
   `held`（`unconfirmed`）今天也是清空的。任务书说的「没清空」在这个树上复现不出来。
3. 真正可复现的缺口是**反方向**的：`writeDraft` 吞掉写盘错误、`clearDraft` 不回报结果，所以「磁盘没清掉、内存已经
   空了」时，下一次 `m` 会把已发出的正文带回来（幽灵草稿）。提案把这条修成合同（先写盘、成功才清内存、失败点名
   文件），并给失败侧与结算侧各补一条现在完全没有夹具的红侧。

## Decisions and deviations

1. **第 ① 条的定性改了**：从「没有清空（缺陷）」改为「结算规则没进规格、失败侧没有红侧、写盘失败会留幽灵草稿」。
   证据见上一节。若 PM 仍认为存在「清不掉」的现场，请把复现步骤（哪个回执、哪个窗口、哪个版本）给回来，我按它
   另开一条缺陷支线。
2. **两处与任务书字面不同，已写成待裁定项**（`proposal.md`「需要 PM 裁定的两点」，design §2 的判定表按推荐版本落笔）：
   `queued` + `TEAM_OUTBOX_RESULT=busy` 按**清空**（= 今天的绿灯行为，条目已 durable；改成保留会因草稿不去重而重复
   投递）、`held`（含 `unconfirmed`，rc=0）按**清空**（= 今天的实际行为；`unconfirmed` 的 payload 可能已在 PM 框里，
   保留草稿会让用户再按 Enter 而守卫没有去重）。两处各只影响判定表一行 + 一条场景，PM 裁定后改的是文字不是结构。
3. **入口选了「既有页里开详情」（design §3 的方案 B）**：工作页三块的行加入该页的绘制序焦点行走，复用同一个详情
   视图与 `FocusRef`；否决第六页与「引用跳转」。代价写在 design 里：既有一条场景
   `An empty or degraded board has no dead item` 必须按新语义重述（空板 + 预览块无行 → 仍无死项；空板 + 有预览行
   → 首个 ↓ 聚焦它），delta 保留该场景名、只改 GIVEN/THEN，`panel-b3` 的对应夹具已在 tasks 4.3 点名。
4. **没有承诺「任意决策号」的键盘入口**：读取面接受任意合法 id，但面板能打开的是三块真正画出的行（规格 6 条、
   决策最近 3 条、变更全部）。这条缺口写进 design §3 与报告，不在规格里承诺；补它只需在方案 B 上加一个输入模式。
5. 没有触碰 `team reply`、路由/派单/账本写入、配置键、依赖与机器出口；delta 只有 3 条 MODIFIED，无 ADDED/REMOVED。
