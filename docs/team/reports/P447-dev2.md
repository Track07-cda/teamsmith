## 结论与推荐

**V153 已交付；最后一次自动通知有落盘、没有产生新的 PM 唤醒。停点在通知写入后的合并分支，不在 watcher 的接收或去重。** 19:51 的事件把 `tip=4f0f6d1dff31` 写进席位记录及 PM 收件箱，但结果明确为 `skipped:merged`；PM 的 wake 文件及投递 journal 都没有该 tip。对照 P446 与 V152，手工通知均有收件箱、wake、journal `sent` 三层记录（下文 A–C）。

原因分四层：

1. **没有独立的手工交付通知，但这不是已证明的 worker 违约。** V153 的三个消息存储面均无 `[manual]` 交付记录；内置 Pi 的派单代码默认依赖自动通知，只有自定义 adapter 配置满足条件才生成手工通知步骤。P446/V152 的手工通知绕开了本次自动合并，但不应倒过来规定人人再发一遍来掩盖自动路径的问题（B、D1）。
2. **19:33 的自动事件错误地没有标成等待后台任务。** 同时刻 `bg.log` 明确记录 `v153-select-39-51:running`，而通知是 `[auto]`、没有 `awaiting=`。该作业执行目录是 `/var/tmp/v153/checkout`；当前归属判断却把执行目录当成发起会话目录，要求与 `.worktrees/dev3` 相等，因此漏认了本席位在独立 clone 中运行的作业（A、D2）。这让“进行中”和“报告已提交”都进入 `delivered` 类别。
3. **跨提交合并按现有实现和规格执行，暴露了通知语义缺口。** 合并键不含 tip；同席位、类别、任务和等待集合即可合并。19:51 是新报告提交，但与 19:33 共用行身份，扩展对 `state=extended` 直接记 `skipped:merged`，不创建唤醒条目。不是 20 秒内的去重，也不是下游把消息丢了（A、D3）。
4. **PM 的日常步骤缺少“没有新通知时也核对文件”的触发条件。** 模板写“Wait for notifications”并承诺回合结束会提醒，但只明确禁止读屏；磁盘核对散在启动步骤、SKILL 与 workflows §D。任务书记录的持续等待，与这个缺口吻合；本调查未读 PM 会话记录，不把它推断成模型当时实际读过或遵循过哪一句（E）。

**推荐先修 PM 等待指引与作业归属，不增加通知系统、定时服务或人工双发步骤。** 修正归属后，本现场应变成 `suspended → delivered`，最后一条自然成为新行并唤醒。另请 PM 在提案时明确裁定：是否要求“同类事件的新 tip 也必须再次提醒”；它涉及现有规格中“跨 tip 仍合并”的明确约定，不能只改扩展偷偷反转（F）。

## C. CLI、投递与 watcher 的停点

```text
手工成功路径（P446 / V152）
team notify pm → PM 收件箱 [manual] → team_send_guarded / outbox
              → PM .wake → watcher read / intent → pi.sendMessage → sent

V153 最终自动路径
settle → __inbox-write → 席位行 extended + notify.log 明细
       → skipped:merged → __notify-settle → PM 指针 + notify-knock.log
       → return（没有新的 outbox 项，没有 .wake 项，没有 watcher read）
```

来源：`scripts/lib/cmd-agents.sh:2238–2328` 的 `team_cmd_notify` 先写收件箱，成功后才调用投递；`extension/team-notify.ts:636–671` 消费 `__inbox-write` 的结果；`cmd-agents.sh:2131–2184` 的 `__notify-settle` 写 PM 指针和结果账。

watcher 的 `sendWake`（`extension/team-inbox-watch.ts:1090–1147`）先写 read/intent，调用 `pi.sendMessage`，成功返回后写 sent；`notify/knock` 使用 `followUp`，不是 `steer`。因此 journal `sent` 只能证明会话 API 接受，不证明 PM 已读懂或已行动；本次最终事件连 read 都不存在，应修上游而非改变 watcher 的投递优先级。

## D. 两处产品行为与一个指引前提

### D1. 默认并没有“交付必须另发一次手工通知”

- `scripts/lib/cmd-agents.sh:103–124`：只有 `TEAM_AGENT_NOTIFY_CMD` 与自定义 `TEAM_AGENT_CMD` 都非空，才生成手工步骤；注释明确内置 Pi 再塞命令会诱导重复通知。
- `templates/AGENTS.section.md.tmpl:96–98`：收件箱与 PM 提醒在回合结束自动发生；显式 `notify` 放在阻塞场景。

所以本现场应修自动路径与 PM 核对方式，不以缺少手工通知为唯一归责。P446/V152 展示手工路径当前可用，不能证明它是默认交付前提。

### D2. 作业执行位置被误当作发起者身份

- `state/bg/v153-select-39-51.job`：`cwd=/var/tmp/v153/checkout`，pid 与 `bg.log` 启动作业一致。
- `extension/team-bg.ts:294–313`：root 从会话 cwd 解析，作业 cwd 则允许 `params.cwd` 覆盖；`:197–198` 把**作业 cwd** 写进 `.job`。
- `extension/team-notify.ts:194–214, 254–255, 570–575`：归属集合只有会话 cwd 与席位工作树；记录里的 cwd 必须等于集合某项才计为自己的作业。

这不是目录缺权限或 PID 被复用的证据：独立 clone 路径与席位路径本就不同；后台账还在 19:33:50 记录作业 running。现有判据挡住了其他席位作业误入本席位，却遗漏了“本席位在另一目录运行自己的作业”。`notify-and-inbox/spec.md:104–112` 也把两种 cwd 等同，提案需一起修正这个前提。

### D3. 新提交不能逃出同类事件合并

`cmd-agents.sh:1766–1820` 的 `team_notify_line_key` 只输出 `seat|class|task|awaiting`；注释明确 branch/tip/uncommitted 不进键。`team-notify.ts:625–671` 的短时间去重键虽包含 `revStamp`，但后面的**合并键不包含**。两事件相隔 17 分 11 秒，结果账也点名 `merged` 而非 `dedup`，所以调小 `TEAM_NOTIFY_DEDUP_SEC` 无效。

这部分不是偏离规格：`notify-and-inbox/spec.md` 的 “The merged line carries the last event's values” 明写三种 tip 合成一行；“Count churn does not wake” 明写延长同类行不再入队。现有 `tests/bg-ledger-harness.mjs` 的 `groupMerge` 也在两事件之间提交文件，断言仍为一行、取最后 tip。新提交应不应该再提醒，是需改既有约定的产品决定。

## F. 最小落地范围与可证伪验收建议

以下是给下一阶段的建议，不是本轮已实施或已验证的承诺；产品要求仍只写入 OpenSpec。

### F1. 推荐范围

1. **指引：三处同步。** 只改 `templates/pm-prompt.md.tmpl`、`SKILL.md` §3、`references/workflows.md` §D；复用现有巡检，区分不读屏与读文件。无新配置、定时器、服务或自动重发。
2. **确定的产品缺口：作业归属与执行目录分开。** 在既有 `.job` 记录保留执行 cwd，同时记录发起会话的目录身份；`team-notify.ts` 用后者确认归属，继续验证 pid/starttime，不能把共享状态目录内所有作业都算成自己的。最小实现面为 `extension/team-bg.ts` 的记录写入与 `extension/team-notify.ts` 的读取；旧记录行为须在提案说明，不能无依据把其他席位作业接过来。对应修正 `notify-and-inbox` 的 cwd 前提，必要的记录约定落 `background-jobs`，不在任务书复制规格。
3. **需要单独裁定的跨 tip 语义。** 若 PM 决定新 tip 必须再次提醒，最小位置是 `cmd-agents.sh` 的合并边界及 `notify-and-inbox` 既有场景，让不同 tip 新起一行、同 tip 重复仍合并；不能只在扩展对所有 `extended` 强制敲门，原行身份还会被投递去重。代价是任意提交都可能多一次提醒，不仅报告提交。若不作该决定，保留当前合并语义，但不能再声称所有最终报告都会自动产生独立唤醒。

### F2. 行为验收与反向证明

复用 `tests/bg-ledger-harness.mjs` 既有 `owner-scope / merge / wake` 组和它们在 `section-paths.tsv` 已登记的 §13c，不新建检测服务或门禁段。替换/扩充原“执行 cwd 必定等于席位目录”的用例，减少重复断言而不是堆第二套守卫。

| 场景 | 可观察结果 | 故意改回旧行为应怎样失败 |
|---|---|---|
| 本席位在独立 clone 用 `team_bg_run(cwd=clone)` 跑一个作业并结束回合 | 本席位记录为 suspended，awaiting 命名该 job；其他席位不受影响；作业在跑时不唤醒 PM | 归属仍读执行 cwd 时，得到本现场的普通 `[auto]`，断言失败。 |
| 上一作业完成、收取结果、提交报告后结束回合 | 与 suspended 分开成为 delivered 新行；PM 收件箱有新 tip；只有一次对应唤醒，journal 有 read/intent/sent | 恢复旧归属后，先前事件错归 delivered，最终事件 merged、没有第二次唤醒。 |
| 其他席位有活作业；本席位没有 | 本席位不出现对方 job，也不被标 suspended；死 PID/错误 starttime 不算在跑 | 删除发起者区分或 PID 验证，现有 owner-scope / 身份反例应失败。 |
| 手工通知与已有 watcher 路径 | PM durable 行、wake 身份、read/intent/sent 对齐；不向真实团队重放 | 在隔离目录破坏上游写入，不能声称通知已送；复用既有 §12b-pi 覆盖，不另加一套实现。 |
| 若批准跨 tip 新提醒：无后台作业，先报进度，提交报告后再报结论 | 不同 tip 为新行、各提醒一次；同 tip 的重复保持一行、一次提醒 | 去掉 tip 边界后，恢复当前 merged 且少一次提醒，断言失败；替换现有跨 tip 合并用例，不能两套相反约定共存。 |

**提示词验收不能只 grep。** 在隔离的一次性真实 PM 中放一个 BOARD 仍 wip、任务分支报告已提交、最终唤醒缺失的现场；给一次既有巡检唤醒，观察它读取 digest/BOARD/report/git 并识别交付，不捕获席位屏幕、不跑验证、不仅说“继续等通知”。另一条现场报告未提交或作业仍活着，应仍等待或续跑而非假报完成。恢复旧提示后应可观察到原等待缺口；若旧版也能正确处理，就不能把这次试验写成提示修正的反向证明。该人工/真实会话验证不新增自动门禁。
