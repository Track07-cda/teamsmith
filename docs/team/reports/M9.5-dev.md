## 1. What changed, and where

`team_review_record_note` judged a record against `team_review_branch_tip <ID>` = the tip of the branch
`team_resolve_branch` returns for that task. For a `phase: verify` task that is the **verifier's own branch**
(the one its report commit lives on), not the branch the record was bound to — hence the reported
`V2-verify [stale: verified 398716887, branch now 44788f09b]` while the record itself spoke about
`task/P2.1-apply-rework-close-v1-findin` @ `398716887`, which had not moved.

| Path | What |
|---|---|
| `scripts/lib/cmd-review.sh` | `team_review_record_branch` (reads the reviewed branch from the record's stable header `时间: … · 分支: \`x\``, header-line shape only) + `team_review_subject_tip` (the judged subject **per phase**: `verify` → the recorded reviewed branch, everything else → `team_review_branch_tip` unchanged); `team_review_record_note` now compares against the subject tip instead of `team_review_branch_tip`. |
| `tests/smoke.sh` | §23: 20 assertions (pure logic, runs in both smoke modes), fixtures ①/②/②c/③ below. |
| `references/openspec.md` | §5: one sentence saying what "stale" means per phase. |
| `docs/team/reports/M9.5-dev/pkg/run.sh` | Independent flip package (own sandbox, 18 checks, a broken-copy direction — see §5). |

Rule as implemented:

1. **`verify`** — the subject is the branch named in the record's header; the verifier's own branch tip is never
   consulted. A report commit on the verifier's branch therefore cannot expire the record.
2. **Genuine movement is still flagged** — a commit landing on the reviewed branch after the record makes the
   record stale again, listed with both revisions (`stale: verified A, branch now B`, message shape unchanged).
3. **Unresolvable = unjudgeable, not stale** — a deleted/merged reviewed branch, a record bound to a bare sha or
   to `HEAD`, or a header the tool did not write → no verdict; this is the same rule that already keeps a merged
   task from staying pending forever.
4. **Everything else is byte-for-byte M6.2** — `apply` and tasks without a `phase:` line keep
   `team_review_branch_tip`.

**Boundary note (for the PM).** The brief named `scripts/lib/cmd-status.sh` for "the pending/staleness
computation". The computation itself (record reader + subject tip) lives in `scripts/lib/cmd-review.sh`;
`cmd-status.sh` only consumes `team_review_record_note` in the pending list / digest / `team status`. I changed
the two functions where they live rather than adding a third silent override in `cmd-status.sh` (the file
already overrides one `common.sh` function, M6.2) — no other `scripts/lib` file was touched. The record header
format and M9.2/M9.4 behaviour are untouched.

## 6. Decisions, deviations, and notes

1. **The brief's file list vs the code's location** — see §1 "Boundary note". Happy to move the logic if the PM
   wants the override-in-`cmd-status.sh` shape instead; it is a small, mechanical change.
2. **A record bound to the verifier's own branch** (e.g. `team review V2 --dir <checkout> --branch <own-branch>`
   with `TEAM_REVIEW_ANY_DIR=1`) is still judged against that branch: the record then speaks for it, so a later
   commit there is genuine staleness. Requirement 1's "own branch must not make it stale" is honoured for the
   reported shape — a record bound elsewhere.
3. **Malformed headers**: if a record has `HEAD:`/`判定:` but no header line in the tool's shape, the subject is
   unknown → not stale (the old rule would have used the task branch tip). The tool always writes the header
   (`scripts/lib/cmd-review.sh`), so this only affects hand-written records.
4. **No spec change**: `openspec/specs/**` is PM-exclusive and the brief did not grant it. I checked the
   `verification` and `board-and-status` specs: neither pins the staleness rule ("the record names the verified
   revision and the branch" is the closest, and this fix makes the reader use exactly those two fields). The
   behaviour is documented in `references/openspec.md` §5 (one sentence, as the brief asked) and
   `references/workflows.md` already says "a record is bound to the revision it verified".
5. **M9.2/M9.4 untouched**: the note feeds `team_report_unverified`, `team_reports_pending_list`,
   `team_reports_skipped_by_board` and `team status` unchanged; their smoke sections (§20 M9.2, §21 M9.4)
   stay green.
