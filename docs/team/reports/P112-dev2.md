## 5 · findings（3 条）

### 5.1 V1（机制层，严重，本次 change 引入）：过滤副本可能**语法就不能解析** —— 选段跑会白跑一场然后 exit 2

**结论**：smoke 生成选段副本的 awk 把**任何** `^[[:space:]]*section[[:space:]]+"` 都当段边界；而 `tests/smoke.sh:7714`
那行就是 14c 的真身，它缩进着、且坐在 FAST 守卫里面：

```
7713: if [ "$FAST_REQ" = "1" ]; then
7714:   section "14c · 快模式自检（跳过必须是显式的、且没有偷偷跑真进程）"
```

于是「保留 14、不选 14c」的选集把这行当边界 → 丢掉它后面的全部内容（**包括那个 `fi`**）→ 副本里
出现一个永不闭合的 `if` → bash 读到 EOF 才报 `syntax error: unexpected end of file`，整个选段运行在
**跑完所有选中段之后**以 `exit 2` 收场：没有结果行、没有解释。反方向同样坏：只选 `14c` 不选 `14`
→ 那个 `fi` **落单**（`unexpected token 'fi'`）。

| 复现（都是秒级 `bash -n`，本包 `55` 分节自动跑） | 结果 |
|---|---|
| `--select 14`（键 `0 0b 0c 0d 14`）的副本 | `line 1003: syntax error: unexpected end of file from \`if' command on line 977` → rc≠0 |
| 同一副本 + 一个键（`14,14c`） | rc=0（**只差这一个键** —— 机制就在这） |
| `--select 14c`（键 `0 0b 0c 0d 14c`）的副本 | `line 995: syntax error near unexpected token \`fi'` → rc≠0 |
| `--paths skills/teamsmith/scripts/lib/cmd-agents.sh` | 副本 rc≠0（同一个 `if`，副本 line 9780）；**端到端原件** `logs/exp-paths-agents-full.log`：真跑也撞同一行，且没有结果行（exit 2） |
| `--paths skills/teamsmith/scripts/team` | 该选集 90 段，含 14、不含 14c → 同一形状 |
| `--paths skills/teamsmith/tests/smoke.sh` | 该选集 24 段，含 14c、不含 14 → 反方向（孤儿 `fi`） |
| 翻面（break→fix）：在 scratch 树里把 14c 的段头提到守卫**外面** | 同一选集的副本 rc=0（`55⑤`） |

**影响**：`scripts/team` 与 `lib/cmd-agents.sh` 是本仓库最常被改的两个文件，`tests/smoke.sh` 自己也是
—— 也就是「按路径选段」这条功能在**最常用的三个入口上直接不可用**（跑完一大堆段落，拿到一堆 `✓`，
然后一个裸 bash 错误，没有结果行）。而且它不会在普通整跑里出现（整跑不生成副本），所以 P98 的 §36
夹具（只测过 `0b`/`17`/`14d` 一类小选集）没碰到。
**建议修法**（任一，二选一都行，但**必须**加回归）：① 把 14c 的段头提到 `if` 守卫外面（让
「段头在其它段之外、`if…fi` 全在同一段体内」这个前提真的成立 —— 本包 `55⑤` 已把这一修法翻转成绿）；
② 或者把边界正则收成列 0-only 并且**生成后跑一次 `bash -n` 校验副本**，不通过就响亮报错并退回全集。
回归夹具：把 `--select 14` 与 `--select 14c` 两个选集的副本 `bash -n` 钉住即可（`55` 就是现成的）。

### 5.2 V2（数据层，实质）：选出来的那一片**不自足** —— 表里的 `needs` 少声明了建夹具的前提段

**结论**：「路径 → 段 + 声明的 `needs` 闭包」这个**机制**是对的（键、闭包、头尾、`--check` 都成立），
但**数据不够**：若干行的 `needs` 漏了它们真正依赖的夹具段，于是「按路径选出一片、跑绿它」在一个真实
产品路径上**不成立** —— 调用者只改了自己的文件，却在一堆不相干的段上拿到红。

**最短因果链（我自己跑出来的，可重跑）**：`5 · add-agent` 用 `$TEAM add-agent dev --create --no-install` 建成
`$REPO/.worktrees/dev` 工作树（`tests/smoke.sh:1614-1616`，含改动文件），而 `3b`（`needs=4`）和 `6`（`needs=4,3b`）
都靠它（3b 在它上面切任务分支，6 在它上面派单，10 从它算复验记录的改动文件）：

**这为什么算 finding 而不是「本来就该跑全套」**：change 的 requirement 就写着
*A product path selects the sections that cover it, **and their prerequisites*** 与
*A section's prerequisites run with it **instead of being assumed***（`specs/verification/spec.md`），
P98 报告也把「其他行的 needs 没逐条跑过对比」列成**已知余量**。本包把这条余量变成了实测：

后果是：一个开发者按这套功能的本意「只跑我改的文件影响到的段」时，会在与改动无关的段上拿到红；
自然的反应是加 `--force`、忽略红，或者干脆每次跑全套 —— 功能等于白做。

### 5.3 V3（轻微，可诊断性）：§36 的嵌套跑对**调用者 TMPDIR 深度**敏感，且外层日志不说原因

`section-guard` 的 tmux 私有 socket = `<TMPDIR>/tmux/tmux-<uid>/default`，而 §36 的嵌套跑会把 TMPDIR 再嵌两层；
最深的是 **§36⑤**：`<TMPDIR>/teamsmith-smoke.XXXXXX/p98-locksel/tmp/teamsmith-smoke.XXXXXX/…`，于是

```
最深 socket 路径 = len(TMPDIR) + 85        实测（tmux -S）：107 ✓ / 108 ✗（sun_path 上限）
⟹ 预算：len(TMPDIR) ≤ 22
```

超过就会让 §36 的嵌套套件里 `0c` 的 `tmux 隔离：私有 socket 没生效` 变红 → 那个嵌套套件 rc=1 →
外层 **1~5 条**「选段嵌套跑退出 0（期望 [0]，实际 [1]）」的红，而**嵌套日志里的红行不会打在外层日志里**
（排查成本很高）。本包第一轮正是踩在这里（根 `/tmp/p112-pkg.<pid>/full-fast`，长 31 → 最深 socket 116 →
5 条红），两条原始红日志留在 `logs/30-full-fast.longtmpdir-red.log`、`logs/80-fast.longtmpdir-red.log`；
对照实验（长→红 / 短→绿）在 `logs/30-socket-limit.log`。P98 的报告只把它当作「探针」的注意事项，
**门禁自己跑的 §36 夹具没有绕开**。建议（同样交回 owner）：① §36 给嵌套跑固定一个短 TMPDIR；
② 嵌套跑非零时把嵌套日志里的 `✗` 行回显到外层（可诊断）；③ 门禁启动时对最深 socket 路径做一次前置断言并点名。

本包侧的处理：包自己的根取短路径 `/tmp/p112p.<pid>` 并且**不继承**调用者的 `TMPDIR`，
`30 §0` 留了一条限度守卫（短→绿 / 包式长→红的对照）。
