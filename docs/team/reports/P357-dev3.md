## 1. `51c` 打断入口夹具：两个独立缺陷

### 复现（改前，宿主，私有 `TMPDIR=/var/tmp/p357-dev3`）

```
$ TMPDIR=/var/tmp/p357-dev3 timeout 900 bash skills/teamsmith/tests/seat-interrupt.sh
  ✗ 隔离前置不成立（拒绝执行）：目标 socket 不在本轮自有目录
    /var/tmp/p357-dev3/teamsmith-seat-interrupt-pm_skills-deb708fe.fRLMPs 之下
    （/var/tmp/p357-dev3/.t-1000.hdIxJe/tmux-1000/default）（段 seat-interrupt；实际 socket …）
  SKIP 隔离前置不成立（私有 socket 没证明）——真回合那一段跳过（绝不碰非私有 server）
== 结果 ==  ✓ 162  ✗ 0  SKIP 1
```

发布形态（门禁是带 `--keep` 跑的）：

```
$ TMPDIR=… timeout 900 bash skills/teamsmith/tests/smoke.sh --select 51c --keep
  ✗ 51c 打断入口夹具有失败（rc=1）
      …/seat-interrupt.log: ✗ 绿：被跑的那一轮自己退 0（它自己的收尾自检也过了）：期望 [0] 实际 [1]
      …/seat-interrupt.log: ✗ 绿：隔离基里没有留下任何根：期望 [0] 实际 [1]
      …/seat-interrupt.log: ✗ 绿：它的 run 台账 / pid 记录也撤了：期望 [0] 实际 [1]
      …/seat-interrupt.log: ✗ 红：库的泄漏旋钮确实生效（静默不回收）：文本里没有 [FLIP(leak)]
      …/seat-interrupt.log: ✗ 隔离前置不成立（拒绝执行）：目标 socket 不在本轮自有目录 …
      …/seat-interrupt.log: == 结果 ==  ✓ 158  ✗ 4  SKIP 1
```

与发布日志里那一段**逐字同形**（`✓ 158 ✗ 4 SKIP 1` + 同一条隔离前置红线）。

### 缺陷 ①：live 组自 P309 起从没跑过（`SKIP` 被当成通过）

`9453e9e3`（P309）把本夹具的私有 socket 目录改成 `tmp_root_socket_dir`——它**在临时根之外**，同时给
`task-model-routing.sh` / `upgrade-recipe.sh` 的隔离前置加了第二个 `--own-root "$TMUX_TMPDIR"`，**漏了本
夹具的两处**（`live` 组与 `cleanup`）。`tmux_iso_prove` 的判据是「目标 socket 必须在声明的自有目录之下」，
只声明 `$TMP` 时它永远不成立 → 真回合那一半每次都走 `skip`。

而门禁那一段只看夹具的**退出码**（`smoke.sh:21563-21572`），夹具 SKIP 后照旧退 0 → 段是绿的。
这就是 spec anchor `verification#…never reports a skip as a pass` 的失效形状：跳过的是一整组端到端断言，
账本上一个字都没有。修前 `--select plan` 之外的 12 个组里，`live` 是唯一一组实际不跑的。

修后同一命令 `== 结果 == ✓ 168 ✗ 0 SKIP 0`——**多出来的 6 条断言是那三天多里从来没跑过的真回合断言**
（执行态退 0 / 点名 pid / 审计 +1 / 审计 pid 就是 pane 里那个进程 / 进程已退出 / 信号是 SIGTERM）。

### 缺陷 ②：外层 `--keep` 把收尾自检顶成红

`cleanup` 的自检是「根还在 = 泄漏 = 退 1」，但门禁的 `--keep` 是**明确要求保留现场**（`TEAM_TMP_KEEP=1`）。
同一个开关还被 hygiene 组的两个嵌套运行继承：那两个基是**用完就扔**的隔离基，继承保留开关后
「绿侧退 0」「绿侧不留根」「泄漏旋钮打印 `FLIP(leak)`」三条一起反转——这就是发布日志里的 3 条 ✗。

### 最小修法（已提交 `9333e025`）

| 位置 | 改动 | 为什么最小 |
|---|---|---|
| `live` 组与 `cleanup` 的 `tmux_iso_*` | 加 `--own-root "$TMUX_TMPDIR"`（第二自有目录，与 `task-model-routing.sh:326`、`upgrade-recipe.sh:354` 同形） | 判据与前置实现一字不改；只是把 P309 漏声明的那个目录补上 |
| `cleanup` 的收尾自检 | `TEAM_TMP_KEEP=1` 时不算泄漏（保留的是**现场**，不是泄漏） | 不弱化自检：泄漏旋钮那条红侧仍然要求退非 0 |
| hygiene 组两个嵌套运行 | `env -u TEAM_TMP_KEEP` | P324 的原话：保留开关属于发起它的那一层；这两个基是夹具自己的 |

红侧（改前 → 改后，两条都实测）：

- live 组：改前 `SKIP 1`（前置不成立）→ 改后真跑，6 条端到端断言全绿；
- 保留开关：改前 `TEAM_TMP_KEEP=1` 下 `rc=1` + 「收尾：临时根没有回收」→ 改后 `rc=0`；
  不带 keep 侧不受影响（`✓168 ✗0 SKIP0`，根照旧被收走）。

## 2. `62` key-replies：`skip-path` 的子进程继承了 `--keep`

### 复现（改前，宿主）

```
$ TMPDIR=/var/tmp/p357-dev3 TEAM_TMP_KEEP=1 bash skills/teamsmith/tests/key-replies.sh --select skip-path
  ✗ skip-path：子进程没跑完整轮（末行=[保留临时根：…/teamsmith-key-replies-pm_skills-deb708fe.61Ht2L（TEAM_TMP_KEEP=1）]，
      rc=0，子进程日志长度=3517）
== P234 key-replies 结果 == ✓7 ✗1 SKIP0

$ env -u TEAM_TMP_KEEP TMPDIR=/var/tmp/p357-dev3 bash …/key-replies.sh --select skip-path
  ✓ skip-path：缺观测器时子进程跑完整轮且 ✗0（末行：== P234 key-replies 结果 == ✓19 ✗0 SKIP3）
== P234 key-replies 结果 == ✓8 ✗0 SKIP0
```

两行的差别只有那一个环境变量 ⇒ 红是**保留开关外泄**，不是观测器缺失路径、也不是产品行为。

### 定性

`skip-path` 组用子进程的**末行**当「跑完整轮」的判据（`key-replies.sh:1040`），而那个子进程是夹具自己的
隔离基。继承了 `TEAM_TMP_KEEP=1` 后，`tmp_root_reap_all` 按契约打印「保留临时根：…」并把它放在末行——
断言从此永远不成立，无论被测的跳过路径对不对。这和 `51c` 的缺陷 ② 是同一个根因。

### 最小修法（已提交 `8a3192d2`）

两个调用点（正式跑与失败取证时的 `bash -x` 重跑）加 `env -u TEAM_TMP_KEEP`。**没有**放宽断言（末行判据
原样保留）——放宽它会把「子进程真的没跑完」也放过去。

改后：`TEAM_TMP_KEEP=1` 下 `== P234 key-replies 结果 == ✓8 ✗0 SKIP0`，子进程末行回到结果行
（`✓19 ✗0 SKIP3`）。

## 3. `61b` 路由翻转变异：臂自己超预算，变异并没有漏抓

按边界只跑了**一次**，而且不是整套（82–105 分钟），而是把日志点名的那条臂单独造出来跑：
`flip_run` 对每条臂执行的就是 `TEAM_ROUTING_TREE=<变异树> task-model-routing.sh --select <组>`，
`template-shadow` 的组是 `boundary`。

```
### ① 变异确实落了盘（tests/lib/model-routing-flips.py）
$ python3 skills/teamsmith/tests/lib/model-routing-flips.py /var/tmp/p357-dev3/mut-ts template-shadow
{"mutation": "template-shadow", "changes": [{"file": "…/scripts/lib/common.sh", "matched": 1,
  "before": "7abcc32d…", "after": "3ed95685…"}]}
# 变异后的函数：
team_template_identity_guard() {
  return 0 # hardcoded template identity accepted
}

### ② 绿基线（未变异树，同一命令）
$ TMPDIR=… TEAM_ROUTING_TREE=<worktree> bash skills/teamsmith/tests/task-model-routing.sh --select boundary
RESULT pass=2434 fail=0 selected=boundary            # rc=0，作业时间戳 18:46:01→18:52:52 = 411s

### ③ 变异树（同一条命令，只换 tree）
$ TMPDIR=… TEAM_ROUTING_TREE=/var/tmp/p357-dev3/mut-ts bash …/task-model-routing.sh --select boundary

```

### 逐条判（日志里那三条名字）

| 名字 | 判定 | 依据 |
|---|---|---|
| `monitor-missing-A-unavailable` | **内层 check 名**，不是臂的控制行 | `flip_run` 每条臂都会 `tail -4` 回显内层日志；这个名字在 `sid-readers` 组里（属于 `monitor-record-drift` / `latest-monitor` 那几条臂），它出现说明那条臂**按预期红了** |
| `pm-publication-failure-stops-uncommitted` | 同上（`pm` 组，属于 `pm-fallback` / `pm-publication` 臂） | 同上；整轮 `RESULT … fail=1` 说明这些回显行不是失败项 |
| `flip-template-shadow-red` | **唯一那条真失败的控制行** | `check "flip-$mutation-red" eq "$FLIP_RC" 1`：它要求该臂**退 1**；③ 证明变异树确实会退 1（631 条命名 FAIL），所以剩下的可能是 `flip_run` 的 `timeout 900`（`task-model-routing.sh:1396`）先到，rc=124 |

**结论：不是覆盖洞**（若真是漏抓，③ 会给 `rc=0` 或 `fail=0`，实际是 `fail=631`、`rc=1`），**也不是产品缺陷**。
它是**臂预算不足**：这条臂把 `team_template_identity_guard` 整个拆掉，于是 boundary 组 29 类故障模板
× 4 种模式**全部**走到真派单（绿基线 0 条红 → 变异树 631 条红、411s → 842s），而 `flip_run` 给这条臂的
是 `timeout 900`（`task-model-routing.sh:1396`）——**只剩 6% 余量（842/900）**，发布那一轮整机在跑 134 段，
超时几乎必然。这也解释了这个数字为什么在两次整套里不一样（`fail=2` → `fail=1`）：它取决于哪几条臂撞上时限。

**修法（按边界只写不修）**：`flip_run` 的 `timeout 900` 改成覆盖该臂实测运行时间（例如 1800s，与整段
7200s 的同一套「实测 × 2」口径一致），或给每条臂按实测单列预算。风险为零：臂本身会红，红得还非常充分。
**不建议**的方向：调大整段的上限、或给这条臂改 mutation——那会把真红也一起放宽。

另：`61b` 在 D198 里已被记为「既有红（未改动 main 副本 `pass=199 fail=2`）」。本次的定点复现说明这一族红
里至少 `template-shadow` 这条与产品无关，后续治理（D198 说的「一次把整批既有红做成一件」）可以直接用
这里的读数，不必再跑 82 分钟。

即：整段两次、queue 组五次，**七次全绿**，包括发布形态（`--keep`）。发布那一轮的现场是
`== 4 queue 结果 == ✓ 75 ✗ 1 ==` / `✗ team status 没有阻碍计数`，而同一组里 `outbox list` 那条（读的是
**同一份 held 条目**）是绿的。

### 能指出的唯一机理（未证明，不修）

`team status` 的整段阻碍文字挂在 `team_outbox_status_line`（`scripts/lib/outbox.sh:1006-1030`）上，而那个
函数**先数条目**：

```
n="$(team_outbox_count)"; case "${n:-0}" in ''|*[!0-9]*) n=0 ;; esac
[ "$n" -gt 0 ] || return 1          # ← 数不出来就一个字都不打印，也不报错
```

`team_outbox_count` 是一次 `find … | grep -c .`。**任何**一次读空/读失败都被静默归一成 0，于是整行消失、
退出码照旧 0 —— 这是唯一能让「同一份阻碍事实，`outbox list` 绿而 `status` 红」而其余 7 段不受影响的路径。
按 D192 的对照法它应当对机器负载敏感，而我这边负载低、连续六次都读得出来。

**要定性至少需要一条**：在容器里按发布形态连跑 `--section queue`（或 `--select 57`）若干次，或者造一个
「数不出条目」的场景看 status 是否静默消失。前者我没法在这里做（容器现场没保住），后者是**新夹具**，
在边界之外（不新增夹具）。所以：**不修**，把它记成「静默失效面」的候选，治理时优先做的是让这个计数
**失败即响**（一行红 + 点名哪一次读空了），而不是继续守这条断言。
