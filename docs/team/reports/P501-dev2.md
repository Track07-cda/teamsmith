### 为什么现有记录不够

- `scripts/lib/cmd-watch.sh:team_panel_board_json` 按 Markdown 物理顺序发 `id/title/agent/branch/deps/state/phase`；`phase` 从任务书读，并非行更新。`team_panel_deliveries_json` 取最近三份报告的文件 mtime，`team_panel_recent_json` 读巡检日志，`common.sh:team_done_record` 只记录办结证据。这三处既不覆盖新增、非办结状态及换负责人，也区分不了同 ID 的不同记录。重复 `assign` 即可换整份文件 mtime，不能把这个时间赋给任一行。
- Git 历史（`git log`、`git blame`）记的是入库提交，不是现场操作。基线 `12b153de` 的 `git show --format='' HEAD -- docs/team/BOARD.md` 只证明提交中新增 P501 行；不能证明此行的实际新增时间，更不覆盖未提交操作、合并多次修改或同 ID 行的对应关系。编号、刷新时间也没有这层事实。故不做历史回溯、不在每次刷新跑 Git 或逐行启动进程。

### 首选：任务表可选时间列，同一笔写入

1. **不做迁移。** 老表不预填时间；第一次有效新增或表内有效字段修改时，如还没有专用列，由原写入顺手在任务表最右追加该列的表头与分隔格。识别明确归团队管理的列名，不把项目的自定义日期列当来源；不用改其它行、列或表，旧行缺末格即未知。已有表不满足可识别边界时仍按原方式读取，不给推不清身份的行补时间。时间列是源码元数据，不上工作页或卡片。`team board ls` 是原表查看，仍按原顺序、保留警告，不另做投影；已写入的时间列会随 Markdown 原文可见，这不是命令行默认改排序。如另要求原文连列形状都不变，需要先裁定存储方式，不承诺该方案能同时做到。
2. **一个写入、一个事实。** 在 `team_board_add`、`team_board_write_col` 的读—改—替换中给每条真正变化的任务行同批记一次 UTC 时间；每次操作取一次时钟，同批同秒允许并列。每条同 ID 行独立比较旧值：已是目标值的不动时间，实际改了的才一起记。时间与字段在同一份临时文件中一次替换后才可读到，保留 `team_scan_invalidate board`。当前 `write_col` 用固定 `.tmp`，未见覆盖 `add` 与 `write_col` 的共同锁；同文件替换不等于并发不丢改动。若需要覆盖并发写入，沿用 `team_with_lock` 将两条现有入口的整笔读改写串起来，不另开服务；手改不经过该入口。按位置读有效的时间，空、缺或无效值当作无时间，不改写它们。
3. **只排序页面使用的行引用。** `cmd-watch.sh:team_panel_board_json` 在现有批量扫描里随每条原始行带出时间，保持 `rows`、计数、工作页的数据物理顺序。建议仅现有交互看板数据读取路径取可选字段，保留 `data.ts:MACHINE_BLOCKS` 的 JSON 键和 `--print` 的原顺序；不为排序加一条读取进程或定时任务。`data.ts` 的 `board` TTL 是 15 秒，`App.tsx` 的 `r` 强制刷新；时间来自行，不来自这两个刷新时点。分栏后一次性排序供绘制和操作共用，不对原数组就地排序。备选用独立索引文件虽不增加 Markdown 列，但必须解两份文件哪次更新有效、旧行如何可靠寻址、复制/合并后如何对齐；以 ID 或行号做键都会误配。尾部未命名 Markdown 单元格或注释也让读写器推断保留边界，且格式化时是否保留未验证，不优于明确的可选列。

### 页面排序、滚动与寻址

- **示例。** `A` 先建，`B` 后建；同栏初始 `B, A`。随后 A 改负责人（或 A 从进行中变成与 B 同栏的待复验），A 的实际更新时间晚于 B，显示 `A, B`，文件不动行。再对 A 提交相同负责人或状态，时间与次序不变。有有效时间的在无时间行之前；同时间按物理顺序。无时间行保持确定顺序：普通栏按文件顺序；完成、已放弃栏按文件尾往前，使从未记过时间的历史仍先露出原来最后一批。后者是缺时间的显示规则，不宣称文件尾真是历史上最近更新。
- **窗口不能把新次序倒回去。** 目前 `layout.ts:laneCards` 只筛状态；并排 `laneWindow` 对 `done/dropped` 从 `maxStart` 起，窄屏 `kanbanGrouped` 则用整页窗口。倒序后并排历史应从首屏开始，先见较新的行；窄屏在同一分组窗口内也先画该栏新行。上下隐藏提示跟实际窗口走。该栏重排时，把原在屏幕内的已选行保留在可见窗口；其余栏不动。未重排的刷新不清空轮滚位置，用户有意滚离光标时也不把整页拽回去。折合与六栏的固定位置不变。
- **先找原行，再用新顺序做交互。** `layout.ts:dupOrdinals/focusRow` 目前以原始文件中 `ID + 第几次出现` 寻址；`App.tsx:moveFocus` 另按原 `boardRows()` 找相邻卡，`cardAction` 给非焦点点击带原始 `nth`，焦点点击与 Enter 目前再解析焦点。只改绘图会让键盘走另一个顺序。建议每帧用原始行计算身份，再生成一份看板顺序给并排/分组视图、鼠标目标、窗口计算、方向键和 Enter 共用；鼠标带该帧行引用，打开后保持原 `entry` 文件发现规则。当前 `App.tsx:openDetail` 和 `cmd-watch.sh:team_panel_detail_records_entry` 的文件按 ID 查，同 ID 的两行可各自选中但仍共享任务文件，不应承诺两套文件。显示层重排、状态换栏、负责人变化不改变原始出现序号；对手工交换同 ID 的物理行、在前面插入同 ID 表外行等，没有永久行标识可证明仍是原行，不把本次页面排序承诺扩到那里。工作页继续用 `layout.ts:boardBlock`、`App.tsx:moveBoardFocus/openWorkFocused` 的绘制次序。
- **标签衔接只留一个排序分支。** 未接收的 `4cbc5bc7` 中，`layout.ts:projectBoard` 已先从原行取重复序号，再过滤、按优先级或文件顺序投影；`App.tsx:moveFocus/openKanbanFocused` 用同一结果，详情保留打开时的 `taskTable` 资格。如果以后经批准接入标签，在这一处把默认分支和两个语言里的 `boardFileOrder` 改为「最近更新 / Recently updated」，选择列表与当前值一起改，按优先级的比较器和文件序同分不动；标签不可用时仍回到最近更新而非旧文件顺序。候选 App 的 `ranking` 只看 `id/state/labels`，接入时须识别默认排序确有变化（同状态换负责人也可能移动）。不改标签数据、筛选、分数、按键处理或 P497/V196 的暂停结论；`openspec/changes/task-labels/BLOCKED.md` 的快速上键失败在本单未重现、未诊断。
