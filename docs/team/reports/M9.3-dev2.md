# M9.3 · dispatch must not silently stack a second task on one agent

```
task:   M9.3                     phase:  -               deps: M9.2, M9.4 (both done)
agent:  dev2                     status: DELIVERED
branch: `task/M9.3-dispatch-must-not-stack-a-se`          PR/MR: - (local mode)
time:   2026-09-15T07:45:00Z
```

D16's tool half: the PM's rule ("check for an unfinished task before dispatching") failed once — P2 was dispatched to
`dev` while M9.2 was still in flight, the new dispatch replaced its window and M9.2 had to be handed to another
agent. The tool knew the agent's task and branch the whole time (`state/<agent>.env`, the board, the worktree) and
said nothing. This change makes dispatch say it — and refuse.

## 2. What the guard does

Before launching — and for `--print` too, so a printed plan can never show something the real run would
refuse — dispatch reads the agent's recorded task (`state/<agent>.env: task=`), the board row of that task and the branch the worktree is on. It refuses with
`--force` being the only way past when **all three** hold:

1. the recorded task X is a **different** id than the one being dispatched;
2. X is **not finished** — no non-`FAIL`/`TIMEOUT` review record, its branch tip is not in the protected branch, no
   phase evidence, and the board is not `done`/`closed`/`dropped` (the judgement is `team_task_open_reason`, which
   reuses `team_done_evidence` — M9.2 — so the two cannot drift apart);
3. the worktree can be located and it sits on a **task branch** (not the protected branch, not detached).

Deliberately **not** refused:

| Situation | Why |
|---|---|
| the dispatched id **is** X (dispatch of the agent's own task) | that is `resume` / the recovery path — "continue", not "stack" |
| X is finished (review record, merged tip, board verdict) | behaviour and output are exactly as before |
| no `state/<agent>.env`, empty `task=`, no worktree, unreadable branch | the state cannot be determined: dispatch proceeds and prints **one line naming the missing signal** (it does not guess) |
| the worktree sits on the protected branch | the regular branch guard already refuses that with the git command to run; the guard only notes that X is still open |

One id that matches **more than one** brief (`docs/team/tasks/<ID>-*.md`, e.g. after a title change) is a hard
refusal listing every path; `--force` does not bypass it (picking a task's scope is not a judgement call — rename or
drop the stale brief first). This replaces the old behaviour where the first glob hit silently won and produced
`fatal: a branch named … already exists` or, worse, the wrong scope.

`--force` prints the override in the dispatch output and appends a line to `state/watchdog.log` once the launch is
proven, so an intentional takeover is auditable. It covers **only** this refusal: a worktree parked on the old task's
branch is still refused by the branch-identity guard (M6.3 F16) — that is a different problem (the worker would do
the new task in the old checkout), and the message tells the PM to move the worktree first.

### One judgement call worth recording

The brief's condition was "the worktree has the task's branch checked out". The actual D16 accident shows **two**
shapes and the tool was blind to the one that mattered: before dispatching P2 the PM had already switched `dev`'s
worktree onto P2's new branch (accident #2, same episode), so a guard keyed only on "the worktree still has X's
branch" would have stayed silent exactly where the damage happened. The guard therefore refuses in both shapes —
X unfinished while the worktree is on X's branch **and** X unfinished while the worktree has already been prepared
for the new task (fixture ①). It deliberately does *not* refuse when the worktree sits on the protected branch
(nothing has been prepared; the normal branch guard refuses only after the PM creates the branch) and it does not
refuse when the state cannot be read at all. Fixture ①b records the boundary between the two guards.

## 8. Decisions, deviations
One judgement call, above. Everything else follows the brief: the exit-evidence logic (M7.5) and the phase-evidence
logic (M9.2) are untouched — the new helper *calls* `team_done_evidence` instead of duplicating it. `team resume` and
`team up --agents` keep their current semantics by construction (they dispatch the agent's own recorded task, which
short-circuits on "same task"); the only change in `cmd-watch.sh` is a comment saying so.

## 9. Suggested next steps

- **Spec (PM-owned)**: `openspec/specs/dispatch/spec.md` has "A dispatch never mixes two tasks in one worktree";
  this change adds a second, distinct rule ("a dispatch never stacks a second unfinished task onto one agent" +
  "an ambiguous task id is refused, never resolved by glob order"). `openspec/**` is PM-exclusive and the brief did
  not grant it, so I did not write a delta. Suggested scenarios if the PM wants them: refuse on an unfinished other
  task (naming task/status/branch/both ways out), proceed on the agent's own task, proceed on a finished task,
  `--force` prints the override, undeterminable state proceeds with the missing signal, ambiguous id refuses with
  both paths — the smoke §22 fixtures are written to be quotable as the WHEN/THEN shape.
- `dispatch --force` currently writes its audit line to `state/watchdog.log`. If the PM wants takeovers in a
  longer-lived ledger, `docs/team/DECISIONS.md` (PM-owned) is the better home; the message is already stable
  (`dispatch <agent>: 显式覆盖叠任务（<old> 让位给 <new>）`).
- Two docs rows now name the guard; if the PM prefers the rule stated in `references/protocol.md` (the safety-model
  doc) rather than only in `workflows.md`/`troubleshooting.md`, that is a one-paragraph PM edit.
