## 结论

如果只能改三处，按对正常工作的影响排序是：

1. **详情读取的项目内软链拒绝**（`cmd-watch.sh`）：已有真实用户现场，整个详情面不可用；按真实落点是否仍在项目内判断即可，P424 已有明确修法。
2. **后台作业记录写失败被吞掉**（`team-bg.ts`）：作业已经启动并返回成功，但 `bg list` 可能显示“没有作业”，`bg stop` 也无法按身份停止它；应让调用者当场知道记录没写上。
3. **任何未知席位都卡住有限模型的派单**（`common.sh`）：即使该席位的完整记录明确是另一种模型，也会阻断目标模型派单；应只让真正无法分类的席位阻断，而不是让所有证据缺口共享同一个拒绝。

其次值得处理的是：唤醒读失败静默当成“没有新消息”、通知记录 64 KiB 后永久丢原文、详情 128 KiB 后无法继续阅读，以及性能套件针对“调用者故意挂载公开标记”的自证。

P415 的 775 目录与 P418 的 664 会话文件已经按 D231/D232 修正，本报告不把旧缺陷重复列为待改。自己的 journal/runtime/lock 继续保留严格保护。

- **正常代价**：一种实际存在的账本布局使整个详情面不可用，用户只能绕开面板自行找文件。保护“不得读到项目外”的真实需求被扩大成了“项目内也不许有软链”。

### 2. 作业记录写不进去仍返回“启动成功” — **收窄**

- **位置与所挡内容**：`skills/teamsmith/extension/team-bg.ts:191-201` 的 `writeJobRecord` 把 mkdir/write 的所有异常吞掉；`:293-335` 随后照常返回 `job <id> started`。`scripts/lib/cmd-bg.sh:182-207` 又只枚举 `.job` 文件，没有记录时打印“还没有作业记录”。
- **真实证据**：**代码反例；没有找到该写失败已发生的记录**。日志文件已创建后，若磁盘在写 `.job` 前写满，`writeJobRecord` 返回空，调用者得到成功回执；下一次 `team bg list` 因为没有 `.job` 而显示空表。`team-bg.ts:200` 注释所称“`team bg list` 里可见”在这条读路径上不成立。
- **正常代价**：一个正在运行的作业从管理面消失，不能凭记录安全停止，也不知道为什么会消失；恢复只能人工找 PID，正是身份机制要避免的动作。
- **判定与影响面**：**收窄**“通知不得打断会话”为“作业可以继续，但结果必须带 `recorded:false` 和具体错误”，同时在作业日志与 `bg.log` 留原因；不要假称 `bg list` 可见。影响 `team-bg.ts`、`team-bg-harness.mjs` 的现有记录断言和后台作业规格；复用现有故障夹具，预计 **0.5 天**。

### 3. 一个证据不全的席位阻断所有有限模型派单 — **收窄**

- **位置与所挡内容**：`skills/teamsmith/scripts/lib/common.sh:4779-4815` 在读取模型之前先检查每个活席位的启动证明与模型交付；任何一个失败就加入 `TEAM_MODEL_UNKNOWN`。`:4834-4852` 只要这个集合非空，就拒绝当前有限模型的派单。
- **真实证据**：**真实相邻事故 + 当前代码反例**。D120（`docs/team/DECISIONS.md:971-975`）实测 Pi 会话内回落后，记录模型仍占着一个实际不存在的强模型名额，证明“记录不等于实际”。当前反例：目标为 `kimi-coding/k3`，另一席位完整记录为 `openai-codex/...`、但缺少当前 spawn 证明；代码在能读取这个不同模型之前就把派单判为不可判。`openspec/specs/dispatch/spec.md:239` 还把这一扩大拒绝写成了合同。
- **正常代价**：一个与目标模型无关的席位证据缺口，会让所有有上限模型的预览和真实派单停下；用户必须逐个 fresh 接管或 teardown 席位，即使已知它运行的是别的模型。
- **判定与影响面**：**收窄**。完整且形状合法的“明确不属于目标组”的记录可先排除；缺模型、模型畸形或无法判定归属才阻断。D120 同时说明这不是实际模型的完整观测，诊断不应再暗示它能证明 Pi 后续没有切换。影响 `common.sh`、dispatch 规格及 `task-model-routing.sh` 的 unknown-peer 组，预计 **1 天**。若产品选择“名额只是估算”，也可改为警告而不拒绝，但那是另一项用户决策。

### 4. 唤醒读失败被当成“没有新行” — **收窄**

- **位置与所挡内容**：`skills/teamsmith/extension/team-inbox-watch.ts:602-635` 在打开或读取 spool 失败时返回空数组、原 offset、`shrank:false`；`:316-323` 的账本写入也吞掉所有异常。`:1254-1257`、`:1286-1291`、`:1437-1438` 对重试、恢复、心跳的异常统一 `ignore`。
- **真实证据**：**代码反例；没有证据表明这个 catch 已造成事故**。stat 成功后权限变为不可读，`readNewLines` 走 `:633-635`；调用方看到的就是“没有新消息”，没有降级记录。M43（`docs/team/reports/M43-dev.md:8-40`）证明 spool 异常确实发生且静默处理曾造成 42 行双投，但它不是当前 catch 已触发的事故证据。
- **正常代价**：权限、磁盘或短暂 I/O 故障期间，唤醒可以一直不来，用户只看到“没有工作”，恢复重试也没有可排查原因。
- **判定与影响面**：**收窄**空结果语义：只把明确的“没有新增字节”当空；打开/读取失败记为 degraded，保留 offset，并让既有降级记录带错误原因。清理最外层 `ignore` 时逐个点名允许失败的操作，不能换成让扩展崩溃。影响 `team-inbox-watch.ts`、现有 watcher harness 与 agent-adapters 规格，预计 **1 天**。

### 5. 通知“记录全文”在 64 KiB 后永久截断 — **删**

### 7. 关键回复超过 128 KiB 直接拒绝收录 — **删**

- **位置与所挡内容**：`skills/teamsmith/scripts/replies.mjs:49-52` 固定正文上限；`:448-469` 读取 stdin 时拒绝超限，`:406-408`、`:748` 对既有正文也拒绝。
- **真实证据**：**既有边界实测，没有真实超限事故**。现有测试接受恰好 131,072 B、拒绝多 1 B；设计评审明确说“128 KiB 是本轮工程选择，不是新增用户需求”（`docs/team/reviews/pulse-key-replies-proposal.md:14`）。
- **正常代价**：一条合法长回答不能进入关键回复存储，用户必须手工缩短或放弃收录；正文本来就是独立文件，这个数值不是固定 4 KiB 元数据槽所必需的限制。
- **判定与影响面**：**删固定正文上限**，不是删资源意识：写入改为流式落盘与哈希，读取沿用分页/按需窗口，避免把“删掉检查”变成无界缓冲。影响 `replies.mjs`、key-replies 规格、`key-replies.sh`、`reply-capture.mjs` 测试与长正文 UI 测试，预计 **1–2 天**。

### 8. 面板把命令失败/目录不可读显示成空数据 — **收窄**

- **位置与所挡内容**：`skills/teamsmith/scripts/lib/cmd-watch.sh:1261-1264` 和 `:1304-1309` 把 `openspec list` 的任何失败都变成目录扫描；`:1283-1284`、`:1316` 把 grep 失败变成 0。`scripts/monitor.mjs:471-483` 把 outbox 目录读取失败变成空数组。
- **真实证据**：**真实 CLI 故障 + 代码反例**。`docs/team/DECISIONS.md:2106` 记录 OpenSpec 1.16 在本仓产生大量 strict 错误，证明“命令存在但执行失败”不是假想输入。当前面板此时仍可回退成 `available:true, source:dir`；outbox 目录 EACCES 时也与真空队列同形。未找到用户已看到这张假空面板的记录。
- **正常代价**：规格已经坏了、队列实际存在但不可读时，界面仍像一切正常；用户失去最需要处理的信号。
- **判定与影响面**：**收窄**兜底条件：只有“命令不存在”才允许目录扫描；命令执行失败、目录不可读应显示 unavailable + 原因，不能变成 0/空。影响 `cmd-watch.sh`、`monitor.mjs` 及现有 panel/outbox 数据断言，预计 **0.5–1 天**。

### 9. 性能套件防“调用者故意挂载公开标记” — **删**

- **位置与所挡内容**：`skills/teamsmith/tests/perf.sh:105-116` 解析 `/proc/self/mounts`，`:133-140` 发现 `/etc/teamsmith-gate-image` 是挂载点就 exit 3。ENV 与镜像内标记文件是另外两层，不要求删除。
- **真实证据**：**只有故意构造的对抗实验，没有事故**。M64 第三轮专门用“foreign image + bind-mount 同样的公开 token + ENV=1”证明会误自称参考环境（`docs/team/reports/M64-verify.md:176-199`）。代码注释同时承认：调用者若把同一公开 token 烘进自建镜像或伪造 mounts 表，仍然挡不住。
- **正常代价**：合法调试时把标记挂载进容器会被拒绝，必须重建镜像或改用不作为验收的 `--host`；却仍未建立对主动伪造者的可靠证明。
- **判定与影响面**：**删第三层挂载点判据**，保留防普通误用的 ENV + rootfs 标记与结果里的实际环境自述；验收可信度由冻结输入和独立复验承担，不由不可验证的“镜像自我声明”承担。影响 `perf.sh` 自检、M64 对应断言、`ci/Containerfile` 注释和 `references/troubleshooting.md`，预计 **0.5 天**，是净删除。
