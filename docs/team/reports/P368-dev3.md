## 1 · 两条断言原来错在哪、现在量什么

`team_inbox_new` 的判据（A1，`notify-and-inbox`「One settle adds one to the pending count, never two」）是：
一条 auto 行若 `agent:` 就等于该收件箱文件自己的席位，它是**记录**、不算该席位的未读流量。于是
`docs/team/inbox/dev.md` 里一批 `[auto] agent:dev` 行，`team digest`/`team inbox` 对 dev 的未读数恒为 0，
而两条断言还在断言「三条合并事件 → 未读 1」。它们量的是记录行，量的地方已经不计数了 —— 断言本身没错得
离谱，是**量具选错了面**：

| 用例 | 原来量什么 | 现在量什么 | 合并语义还在不在 |
|---|---|---|---|
| `merge: line-counting readers count a merged line once` | `team inbox dev` 的未读（记录行 → 恒 0） | PM 的**指针行** `docs/team/inbox/pm.md`（`agent:dev` ≠ pm，是流量）：三条同键事件 = 1 条未读；`--ack` 之后再一条同键事件仍并进那一行 → 仍 0 | 在：`×4 first= last=` 在记录行与指针行**两处**同时断言，且两个文件各只有 1 行 |
| `detail: detail reading does not acknowledge` | 同一份记录文件的未读（同上，0 == 0 的空断言） | 同一个文件里加一条 `[manual]` 流量行（`team notify dev …`），未读=1；`--detail` 跑完必须仍是 1 | 不涉及合并；这条守的是「读面不许变成写面」 |

红侧到绿侧的现场（同一个夹具、同一批用例）：

```
# HEAD（b754b929）· bash skills/teamsmith/tests/bg-ledger.sh --select merge,detail
  ✗ merge: line-counting readers count a merged line once :: before=0 after=0 :: - …×4 first=… last=… :: MERGE-READERS four
  ✗ detail: detail reading does not acknowledge :: before=0 after=0
bg-ledger：20 passed, 2 failed

# 本分支 · 同一条命令
  ✓ merge: line-counting readers count a merged line once :: before=1 after=0 :: pm=- 2026-10-22T12:18:09.971Z [auto] agent:dev · P230 · knock=skipped:no-pane · see=docs/team/inbox/dev.md · ×4 first=2026-10-22T12:18:09.971Z last=2026-10-22T12:18:10.835Z || dev=- … · ×4 first=2026-10-22T12:18:09.971Z last=2026-10-22T12:18:10.835Z :: MERGE-READERS four
  ✓ detail: detail reading does not acknowledge :: before=1 after=1 :: - 2026-10-22T12:18:15Z [manual] agent:pm · READONLY manual notice
bg-ledger：22 passed, 0 failed
```

原来绿的 20 条一条没变（22 = 20 + 这 2 条），这就是任务书说的「其余不变」。

## 2 · 红侧（defect-fix 的翻转证据）

两条都必须是「改坏实现 → 只有对应用例红 → 还原后绿」，不是「反正它红了」：

| 破坏（scratch 副本，不碰真树） | 期望红的用例 | 实测 |
|---|---|---|
| ⑲（新）指针腿不再合并：`team_inbox_write_with_lock pm …` 换成无条件 `printf … >>` | `merge: line-counting readers count a merged line once` | `✓ flip 前提 merge-off：破坏已打上（cmd-agents.sh）` / `✓ flip flip-merge-off：红在「merge: line-counting readers count a merged line once」` / `✓ …同一用例在 pristine 树上 PASS（红 → 绿对照成立）` |
| ⑭（既有）`--detail` 变成写面（追加 `team_inbox_ack_set`） | `detail: detail reading does not acknowledge` | `✓ flip 前提 detail-acks：破坏已打上（cmd-status.sh）` / `✓ flip flip-detail-acks：红在「detail: detail reading does not acknowledge」` / `✓ …同一用例在 pristine 树上 PASS（红 → 绿对照成立）` |

⑲ 只改**指针腿**，不是「把合并全局关掉」：全局关掉会让 `merge: a run of same-key notifications is one line…`
先红，而 harness 在首个失败用例就退出，根本走不到要钉的那一条（P251 的 ⑮ 注释里记过同一件事）。指针腿正是
新断言量的那条流量 —— 三个事件各写一条指针行，PM 的待办就从 1 变成 3，用例立刻红。

`--select flip` 里其余 17 条红侧照旧逐条对得上（`221 ✓ / 1 ✗` 那一轮全部红侧都 `✓`，唯一一条 `✗` 见 §5）。

## 3 · 承接缺口：`merge`/`detail` 为什么一直不在 §13c 里

是 P236 的缺陷现场）—— 那四个组在被折进来时**已经存在**。`merge`/`detail`/`wake` 属于 P251

三组」）。A1 改判据之后它们静静地红了两个多月，门禁与 V96 都看不见 —— 这是承接缺口，不是回归。

## 5 · 顺手发现并处置：`flip-wording` 是一条恒红的死红侧

全量八组第一次跑出来是 `221 ✓ / 1 ✗`，那条 ✗ 是 `flip flip-wording：破坏后夹具仍然全绿（这条性质没有被守门）`。
根因：它翻转工具文本、等 `wording: the retired duty wording is gone from every registered text` 变红，而**那条用例
已经被 P264（4cd5827e「drop the text-class assertions」，独立复验 V39 PASS）连同整批 text-class 断言一起删掉了**。
用例没了，这条破坏就再没有人应答；`wording` 组今天的 pristine 基线只剩一条行为用例
（`✓ wording: the merged completion wake-up still names both ids and team_bg_wait`，见全量日志的 flip-green 段）。
也就是说 2026-10-15 起，每次跑 flip 组都会在同一个位置红一次 —— 一条恒红的守卫既守不住任何东西，又会盖住
真红的那一条。

处置：**退休**这一块（连带它那条 `M1` 破坏与前提检查），换成新的 ⑲（§2）。这是净零：进一条活的、出一条死的。
**没有**把被删的措辞断言加回来 —— 那是 P264 已裁定并独立复验过的删除，不属于本任务；如果 PM 想要重新守

处置后的读数就是 §4 的全量：`220 ✓ / 0 ✗`（比退休前少 1 条 ✓、少那条 ✗）。
