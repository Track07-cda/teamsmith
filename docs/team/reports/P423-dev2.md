## 答案（先给结论）

四件必须成立的事**都成立**，而且有真机证据：一条 45 秒后的提醒在一个隔离项目里真的把 PM 叫醒了。

1. **到期检查**：两种巡检形态各自有约 10 秒一次的轻量节拍，独立于完整巡检；完整巡检周期不变。
   真机：`state/reminders.log` 06:46:45 `admit n=1 overdue=0 … queue=1`。
2. **投递**：一批（≤8 条）冻结成一条完整消息，先写 intent 再调用 Pi；只有 Pi 自己那条
   `message_start` 才算送达。真机：06:46:47 `intent-sent batch=bat-…-1 generation=1`，
   06:48:58 `observed batch=bat-…-1 standby=auto-off generation=1`；PM 的会话文件里出现
   `custom_message / customType=team-reminder`，正文逐字、`details` 带批次 id 与 nonce。
3. **待命联动**：待命期间照常入队与投递；只有真回执才退出待命，且只退一次（代次校验）。
   真机：06:45:51 `standby on`（代次 1）→ 入队/冻结时仍 `on` → 06:48:58 观察后 `standby: off`，
   审计 `remind-observed … standby auto-off (bound generation 1)`，`right=spent / rightSpentBy=wake`。
4. **重启恢复**：`queued` 在新进程里照样被冻结送出；`intent` 超过 60 秒变 `unknown` 且不重发；
   `observed`/`resolved` 不再入队。夹具 F 段逐条钉住；真机也真实发生了「忙回合压过 60 秒 →
   unknown → 迟到的观察把它补成 observed」这一形状（见下）。

## 边界与没做的事（如实）

- **没做**：PM 侧模型工具 `team_remind`（3.3）、停着的 PM 的 prompt-free 恢复拉起（4.2）、
  可配置上限（活跃条数/正文字节/创建速率，2.2）。这些都在同一 change 的后续任务里；本片只到叫醒为止。
- **投递失败的「重试上限」读法**：批次只发一次（ceiling = 1）。`sendMessage` 抛错或返回都不算回执，
  所以状态是 `unknown` 而不是「重试 N 次」——这是设计 §2/§3 的显式选择（宁可让人确认，也不盲目重发）；
  解开它的唯一动作是 `team remind resolve <batch> --ack-unknown`。
- **`unknown` 会挡住下一批**（直到被观察或被确认），这是「一次只允许一批在飞」的直接后果，夹具 E 段钉住。
- **真机里观察到的边界**（不是缺陷，是设计里写明的）：PM 忙时 follow-up 会等这一轮没有工具调用才落地，
  60 秒窗口可能先把它判成 `unknown`；迟到的回执仍能把它补成 `observed` 并退待命一次。
  真机就是这样走的（06:47:49 unknown → 06:48:58 observed）。
- **没跑全量 smoke**（任务书要求不跑，选了 17 段）；`openspec validate --strict` 在这棵树上**红**
  （20 项，全是 `Requirement text is very long` 这类既有告警级别的问题，main 上同样红），`--all` 绿。
- **PM 侧工具面没验证过**：本片没有注入模型工具，`team remind` 仍是 CLI 唯一入口；面板形态的 10 秒
  tick 只在 bundle 里过了构建与静态检查（§28/§27 未选段），没有起真控制台观测它的节拍。
- **`ledger-ban` 在 main 上就是红的**：本分支 `hits=15`（用主检出的 names 文件），全部落在
  `docs/team/**` 里 PM 已有的任务书/复验记录（P415/P417/P418/P420），我一个字节都没改它们；
  main 上是 `hits=18`。这不是本分支引入的。
