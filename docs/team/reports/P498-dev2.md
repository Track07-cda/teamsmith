## 建议与待审决定

**只在新项目第一次初始化时读 Pi 已保存的默认模型。** `team init`、`team bootstrap` 和 `team bootstrap --print` 用同一处模型选择。缺任务映射就写入 `routine`（执行）、`analysis`（方案分析）、`verify`（独立验收），缺 PM 模型就用同一 Pi 默认。只建立两项现有项目设置；以后 Pi 的个人默认变了，已建项目的两项值不变。PM 和验收人可以用相同模型；验收仍由不同于实施者的人负责。D268 已定产品方向，不需要再问用户选哪些类别。

交正式提案审阅的边界：只采用**非交互、无扩展执行时已经生效**的 Pi 设置；未经信任的项目设置不参与，不能自动批准。查到的 Pi 1.6.0 CLI 没有一个跨安装方式、只输出这项结果且保证不碰模型运行环境的入口；建议只读其公开设置文件中的必要字段，复用现有 JS 运行时，既不引入 Pi SDK 依赖也不复制 Pi 的选模过程。下面是明确的候选行为；本轮无实现授权。旧版 Pi 的差异只需验证读值边界，不改产品的 Pi 版本门槛。

## 用户实际怎么用

以下示例是候选行为；每个初始化示例从一个独立的新项目开始。假设该项目能读到 Pi 已保存的 `vendor/default:high`：

| 命令 | 项目保存的结果 |
|---|---|
| `team init` | PM 和三种任务均为 `vendor/default:high`。只初始化项目文件，不开工作树或窗口。 |
| `team bootstrap --print`，然后 `team bootstrap` | 预览显示同样的四项值，不写文件、不改窗口；正式运行按当时读值初始化，再做原有的准备工作。预览不是锁定；要固定预览值，可把完整映射和 PM 模型一并传给正式命令。 |
| `team init --pm-model 'openai/gpt-6.2-sol'` | 仅 PM 换为显式模型；三种任务仍用 `vendor/default:high`。 |
| `team bootstrap --task-models 'maintenance=vendor/light audit=vendor/strong:high'` | 只创建 `maintenance`、`audit`，不补三种预置类型；PM 仍用 `vendor/default:high`。 |
| `team init --task-models 'maintenance=vendor/light audit=vendor/strong:high' --pm-model 'vendor/pm:high'` | 两值按原样保存，不读取 Pi 设置。 |

初始化之后可直接 `team task T1 --title '补齐导入校验' --agent dev --category routine`；改一个任务类型的模型用 `team config set-task-model routine 'vendor/other:low'`。`--task-models` 一直是**整份映射**，不新增按类别合并的旗标，不因 `team init` 有了预置类别就让 `team task` 推测任务类型。

- **无已保存默认或 Pi 不可用：** 只要仍缺一项，就在创建文件前退出，预览也给同样的原因；保存 Pi 默认，或只补目前缺的显式参数。两个显式值齐全时，模型选取不依赖 Pi 即可通过；这不代表没装 Pi 也能派单。Pi 可执行文件沿用 `TEAM_PI_BIN` / `PATH` 判断，只做可用路径检查，不调用它查模型。
- **明确给错值：** 先验显式输入，失败只点名出错参数和合法形状，不回退到 Pi；预览、正式运行一致。沿用现有写入校验，不把 `provider/model` 形状合法说成模型已可用。读取 Pi 设置失败也不猜；不把 JSON 原文或解析异常原文带到输出。
- **已有合法配置：** 两入口均不读 Pi，不补类别，不改变保存的模型。正常 `init` 仍可刷新 `AGENTS.md`，已有配置的 `bootstrap` 不刷新该段，仍按原流程补必要的准备文件；相异的显式值仍拒绝并指向配置修改。显式 `init --force` 保留原有整份重渲染语义，模型只取其现有合法值或本次显式值，不从 Pi 取。已有但无法使用的现行配置不按新项目自动补；指向修复现有配置，保留原有明确重渲染路径。
- **有旧模型键：** 保留现有拒绝（包括 `init --force`、`bootstrap --print`），仍只指向 `team up` 的机械迁移或显式 `team config upgrade-models`；在新项目的缺值提示中移除升级说明。

候选文案，任务类型同值时可合写：

```text
已保存模型：PM、执行、方案分析、独立验收均使用 vendor/default:high。
```

```text
Pi 未保存默认模型。请在 Pi 保存默认模型，或同时指定 --pm-model 和 --task-models。
```

若只缺任务模型，最后半句改为「或指定 --task-models」；无法找到 Pi 改为「未找到 Pi。请安装 Pi，或指定……」。不要求再次输入已给过的参数。

## 源码路径与 Pi 证据

**Teamsmith 当前的共同接点。** `scripts/team:77–93` 先定位/载入项目，再走 `scripts/lib/cmd-project.sh:216–254` 的 `team_init_model_policy_resolve`：当前是显式输入优先、已有合法值其次，其余拒绝。`init` 在 `cmd-project.sh:319–350` 先拒绝退休键，再解析模型、处理重入冲突；`:391–412` 才渲染配置并经 `team_config_set_in_file` 写 `TEAM_TASK_MODELS`、`TEAM_PM_MODEL`。`bootstrap` 在 `cmd-bootstrap.sh:186–228` 做相同前置检查，但新项目 `--print` 跳过解析（连显式值也未在这里校验）；正式运行在 `:307–310` 把解析后的两值交回 `init` 再加载。建议复用此解析和写入，把新项目 `--print` 的例外替换掉；正式 `bootstrap` 在改名、安装、文件写入之前解析，向 `init` 传同一次解析的完整值，不再读一次 Pi。判断首次运行要同时尊重现有入口的配置来源：`init` 指向主检出的 `.pi/team/config.sh`，`bootstrap` 用 `team_load_config` 解析的 `TEAM_CONFIG`，后者还支持显式 `--config`；不能把已有选定配置当作空白，也不借此改配置发现或写入目标。不要把 `TEAM_PI_SETTINGS_FILE` 当 Pi 的设置来源，它是 `common.sh:6533–6558` 的插件探测路径，不是 Pi 的 `PI_CODING_AGENT_DIR`。

**配置是派单的输入，Pi 只参与首次取值。** `cmd-docs.sh:4–36` 的 `team task` 先用 `team_task_policy_model` 检查合法且已配置的 `--category`，再写到任务书。`cmd-agents.sh:1154–1198` 的 `team_dispatch_select_identity` 先识别同一记录（任务、任务书、类别、分支和工作树），匹配时复用模型与 SID；新派单才从项目配置按类别查找，`--model` 不豁免类别必有映射。PM 另走 `common.sh:3204` 的 `team_pm_model_resolve` 和 `:3369` 的 `team_pm_pi_args`。两条启动路径都把单独的 provider 和含思考档后缀的 model 交给 Pi；不用改 `dispatch`、`resume`、`up` 或独立验收规则。

**本机 1.6.0；可用接口与取舍。** 这个非交互 shell 的 `PATH` 上没有 `pi`；本机安装目录的 `dist/bundle/cli.js --version` 返回 `1.6.0`。仓库 `README.md:106` 写的是 Pi ≥ 0.76.0、此前验证过 0.85.1，不是本机版本。按 Pi 1.6.0 的 `dist/index.js`，npm SDK 确实公开 `getAgentDir`、`SettingsManager` 和 `ProjectTrustStore`。可在确认信任后从 SDK 仅取 `getDefaultProvider()`、`getDefaultModel()`、`getModelThinkingLevel(provider, id)`、`getDefaultThinkingLevel()`；`SettingsManager.create` 的 `projectTrusted` 缺省为 **true**，不会替调用方判断，且原生读文件会用锁，`ProjectTrustStore.get` 会尝试创建目录和锁（`dist/core/{settings-manager,trust-manager}.js`）。不能假设自定义/独立 Pi 可执行文件附近就能导入该 SDK，旧版 0.76.0 的 `SettingsManager.create` 也没有这个信任选项。Pi CLI 的 `--list-models` 是目录搜索且会先建立运行环境，`pi config` 是资源编辑界面；RPC 的会话状态是实际会话的选中模型，不是已保存的默认。均不适合为初始化启动。裸 `pi --help` 在 1.6.0 也会先建运行环境以收集扩展旗标（`dist/main.js:577–794`），本轮未调用。

**仅取 Pi 的公开设置字段。** 用已有 `team_js_runner` 启动一次无常驻的 JSON 读取助手；全显式值或已有配置不调用它；如该运行时不可用，缺项时给配置显式值的同一条退路，不因此要求新装依赖。读取 `PI_CODING_AGENT_DIR/settings.json`（Pi 支持 `~` 展开，未设置时是 `~/.pi/agent/settings.json`），以及可信时目标项目根的 `.pi/settings.json`；不从执行命令的子目录或恢复会话所在目录猜项目。项目文件按键覆盖用户文件（`defaultProvider`、`defaultModel` 分别覆盖，不把缺失 provider 猜成某厂商）。思考档顺序：合并两文件后精确键 `modelThinkingLevels[provider/modelId]`、`defaultThinkingLevel`、Pi 内置 `medium`。内置值在本机及 0.85.1/0.76.0 源码一致；把选定档也保存为 `:level`，否则后改 Pi 思考档会影响未带后缀的新启动。显式值原样保存，用户故意不写后缀时仍由 Pi 决定该显式模型的思考档。遇到不能表示、无效或缺失的 provider/model 不猜，Pi 自己负责实际启动时按模型能力调整思考档；不打开 `auth.json`、`models.json`、模型注册表或会话文件，不输出其它设置。

**信任和自动选模的边界。** Pi 1.6.0 的非交互顺序是显式批准/拒绝、可作答的扩展、`<agent-dir>/trust.json` 中规范化目录及最近的父目录、最后是用户级 `defaultProjectTrust`（`always` 加载，`ask`/`never` 不加载）。初始化不是 Pi 会话，不接受一次性批准参数、不运行 `project_trust` 扩展、不运行信任提示、不写信任文件；只取已有的最近目录决定，找不到时仅用户级 `always` 允许读项目文件。已拒绝优先于 `always`，项目自身不能授权，未同意时只看用户设置。0.76.0 源码不具当前信任接口；用同一个保守口径，不承诺复刻老版本自动加载项目设置。如果 Pi 之后用命令行 `--model`、`--models`/`enabledModels` 的范围、会话恢复、扩展或凭据可用性改变启动结果，跟 Teamsmith 应读取的**已保存值**是两件事。1.6.0 的 `dist/main.js:721–755` 和 `dist/core/model-resolver.js:382–431` 表明：新会话可能优先取范围内第一项；未找到/未配置保存模型的认证时，可能从可用模型再选。初始化绝不代做这些判断，也不把首个可用模型当默认。
