## 判据设计依据（为什么是「内容」而不是别的）

1. **回执（按提交主题/`Agent:` trailer 找合并提交）在本仓库不可用**：PM 的 squash 提交主题不长这样。
   实测：`git log --oneline --grep='^P232[: ]' main`、`--grep='^P235[: ]'` 都是空；`P242` 的合并提交主题是
   `test(gate): the class-A fixtures follow the new routing contract`，一个字都没点任务号。选回执等于要求 PM
   改合并习惯，且旧记录（回执缺失）还得回落内容 —— 不如直接判内容。
2. **不用 3 路合并（`git merge-tree --write-tree`）当判据**：实测（git 2.53.0）对 `P240/P241/P242` 干净地给出
   「合并结果 = main 的树」（= 已合并），但对 `P232/P235/P238/V27/V28/V29` 全部冲突或给出不同的树 ——
   因为「PM 解过冲突 + 后来者又动过同一文件」在本仓库是常态。3 路合并把已合并的分支判成未合并就是假阳，
   所以它只用来做反向核对，不作为判据。
3. **内容判据的定义**（`team_branch_content_merge_state`）：
   - `base = merge-base(main, 分支)`；`changed = git diff --name-only --no-renames base 分支`（分支这次交付的东西）；
   - `still = git diff --name-only --no-renames 分支 main -- :(literal)<changed 里的每条路径>`（main 现在还不是
     分支那一版的路径，限制在 changed 集合内）；两条命令，逐路径逐字比较，没有行级启发式；
   - `still` 为空 → `merged`；`still` 与 `changed` 一样大 → `unmerged`；介于两者之间 → `partial`（点名最多 3 条
     缺的路径）；`changed` 为空 → `empty`（**绝不**当成 merged）。
   - `--no-renames` 是刻意的：改名的老路径必须留在 changed 集合里，逐路径比较才不漏。
4. **不能假阳**：只要它说 `merged`，就意味着分支相对于分叉点的每一处改动，main 现在都已经有了 —— 此时分支
   确实没有东西可并。唯一会误判成 `merged` 的形状是分支的净改动恰好等于 main 的现状（那本来也就无可交付）。
   反向的假阴（`partial`）是**故意**的：见下表，本仓库里合并较早、后来又被别人改过同一文件的分支都会落在这里，
   文案明说「解过冲突、或后来者又动过同一文件都长这样 —— 按内容核对」，交人看一眼，而不是猜。
5. **② 路线仍然要求分支的提交里有一份报告**（M9.6 的规则不变）：并入 + 报告才算交付。因此「squash 合并了但
   没提交报告」仍会拦住，只是文案不再是「未合并」。
6. **「已关单但分支未合并」的口径**（要求 2）：看板是权威 —— 任务一进 `done/closed/dropped`，就绪链根本不再问
   证据（`team_task_open_reason` 的第一条短路），不会因为「内容不在 main」新造一道 blocker。夹具里 `M5` 就是这条
   口径的守门：分支 `task/M5-closed` 的内容确实不在 main 上，它仍不是 blocker。
7. **作用面**：内容判据只在 change 就绪链上启用（`team_change_unfinished` → `team_task_open_reason` 传 1）。
   done 闸门（`team close` / `board set done` → `team_done_gate` → `team_done_evidence` 不传参数）保持原判据，
   这是要求 4 的字面要求；代价是「已合并但没复验记录」的任务仍要 PM 显式 close，这一点在新的 `change status`
   里会显示成 `已按 squash 合并（内容一致）`，不会再让人误以为代码没合并。

## 返修轮次 1（V30 F1：引号路径把「没落地」判成「已合并」）

### 缺陷与复现

`git diff --name-only` 默认（`core.quotePath=true`）把含**非 ASCII / 双引号 / 反斜杠**的路径 C 转义并加双引号
后再打印。改前的实现把这一串直接当字面 pathspec 用（`:(literal)$p`），于是这些路径**永远匹配不到** ——
`still` 为空 → 判成 `merged`（假阳）。同一个仓库、同一条改动（`task/W1-weird-unmerged`）的三种取法：

```
默认（core.quotePath=true）：        core.quotePath=false：              -z（NUL 分隔、逐字节原样）：
  "a b \344\270\255.txt"               a b 中.txt                          a b 中.txt
  "back\\slash.txt"                    "back\\slash.txt"                    back\slash.txt
  "q\"uote.txt"                        "q\"uote.txt"                        q"uote.txt
  "\344\270\255\346\226\207.txt"        中文.txt                            中文.txt
```

判据层（直接调 `team_branch_content_merge_state <分支> main`，同一份夹具、改前/改后两棵树）：

```
改前（交付 tip b9b242ee 的代码）：
  task/W1-weird-unmerged     merged    分支改过的 5 条路径，main 现在的内容就是分支那一版   ← 内容一条都没进 main
  task/W2-weird-half         merged    分支改过的 4 条路径，main 现在的内容就是分支那一版   ← 实际只进了 2 条
  task/W3-weird-merged       merged    分支改过的 5 条路径，main 现在的内容就是分支那一版

改后（返修轮次 1，tip da483799）：
  task/W1-weird-unmerged     unmerged  分支改过的 5 条路径没有一条在 main 上是分支那一版（分支 tip fa48bd1 · main 现状 19d2142）
  task/W2-weird-half         partial   分支改过的 4 条路径里 2 条已是分支那一版，还差 2 条：back\二.txt、纯 空格.txt（…）
  task/W3-weird-merged       merged    分支改过的 5 条路径，main 现在的内容就是分支那一版
```

### 修法（为什么是 `-z` + 数组）

- 两处 `git diff` 都换成 `git diff --name-only -z --no-renames`（NUL 分隔、逐字节原样），用
  `while IFS= read -r -d '' p; do …; done < <(…)` 读进 bash 数组；`changed` 集合与 pathspec 都从数组走，
  绝不再把命令替换的文本拼成 pathspec。
- **不用 `git -c core.quotePath=false`**（任务书要求评一句）：实测它只放开非 ASCII，含 `"` 或 `\` 的路径
  **照样**被引号包住（上面第二列里仍有两行带引号）—— 这两类路径仍会假阳；而 `-z` 是 git 自己给管道场景的
  「逐字节原样」契约，不依赖调用方/环境（仓库或用户配置把 `core.quotePath` 设回 true、或经 `GIT_CONFIG_*`
  注入都会让「设 flag」的方案失效）。判据不该依赖环境。
- 顺手指同一族：delta 的 `touched by` 列（三点差）也是同一串命令面，同样改成 `-z` + `tr '\0' '\n'`。
- 只给**显示**加了一层防护：列的路径里的控制字符（换行/制表/回车）转义成 `\n`/`\t`/`\r`，
  免得毁掉「一行一条 blocker」的结构；比较/匹配仍用原始字节，空格、双引号、反斜杠、非 ASCII 都原样显示
  （能直接复制回命令行）。

### 三态对照（奇特路径名，每条都过）

夹具（§12e 的 `12e-weird-paths`）在真 git 上造分支，路径各有：非 ASCII（`中文.txt`）、空格（`纯 空格.txt`）、
双引号（`q"uote.txt`）、反斜杠（`back\slash.txt`）、换行（`nl\nname.txt` 是真换行字节）；三条分支分别落在三种状态：

| 形状 | 路径 | 改前 | 改后 |
|---|---|---|---|
| 一条都没进 main（`task/W1-weird-unmerged`，5 条全是奇特名字） | 非 ASCII / 空格+非 ASCII / `"` / `\` / 换行 | `merged`（假阳） | `unmerged` 5/5，change 不再报 ready |
| 一半进了 main（`task/W2-weird-half`） | 前四条里进了 `中文二.txt`、`q"二.txt` | `merged`（假阳） | `partial` 2/4，点名 `back\二.txt`、`纯 空格.txt` |

## Decisions and deviations

- **选了「内容判定」而不是「合并回执」**：依据见上一节第 1 条（真仓库的 squash 提交不点任务号，回执造不出来）。
- **② 路线在内容合并之外仍要求「分支的提交里有一份报告」**（M9.6 不变）：这是偏离了「只要内容在 main 就算
  完成」的最松读法的一处；理由是报告是交付物、这条要求原本就在，且去掉它等于顺手放宽 done 的语义。
  后果写在红侧 ④：`M4` 那种形状仍被拦，但文案说清「已合并、缺的是报告」。
- **done 闸门保持旧判据**（要求 4 的字面要求）。若 PM 想让 `team close`/`board set done` 也认 squash，那是
  一次独立的口径决定（判据函数已经在那里，只差传参），本任务没有替 PM 做这个决定。
- **顺手修了 `touched by` 的两点差**（同一段输出、同一族的 squash 盲区）：改成三点差后，已合并的分支不再
  「看起来没碰过任何 delta 文件」。这不是要求 1–5 点名的项，但它在同一个命令、同一屏里，且旧行为是错的。
- **改了一条预算表记录**（§12e 的实测带）：夹具真花的钱要按 P70 表的纪律报上去。第一轮 3.00→7.00s（squash 夹具），
  返修轮次 1 再加奇特路径夹具后 7.00→9.00s；budget 始终是 60（floor），容器列保留历史值并注明未重测。
- **返修轮次 1 的两处取舍**：① 用 `-z` + 数组而不是 `git -c core.quotePath=false`（后者实测救不了含 `"`/`\`
  的路径，且依赖环境）；② 只给**显示**转义控制字符（换行/制表/回车），路径本身的空格/引号/反斜杠/非 ASCII 原样打印，
  判定永远用原始字节 —— 既保住「一行一条 blocker」的结构，也不把路径变成难以复制的 C 串。
- **没写 spec**：任务书 `anchor: none (infra)`。核对过
  `openspec/specs/board-and-status/spec.md` 的 readiness / 归档两条 requirement：它只说「每个映射任务都结束」
  与「两个消费者同一判据」，没有钉死「并入」怎么判，本次改动不与之矛盾，所以不发 delta。

## 未做项与风险

- **`partial` 是假阴，不是判决**：合并较早、后来又被别人改过同一文件（或 PM 解过冲突）的分支会停在
  `内容部分一致`，不会自己翻成 `merged`。真数据见上表（`P232/P235/P238/V27/V28/V29`）。这是「不假阳」的代价，
  文案已经明说该按内容核对。若 PM 想要更少的假阴，下一步只能是合并回执（需要 PM 的合并提交带上可解析的任务号），
  不是再猜内容。
- **没统一 `team_branch_squash_merged`**（digest 的 `[4] 待收尾` 与 roster 的「领先」列用的启发式：分支 tip 的
  tree 出现在 main 最近 200 个提交里）。它与本次判据同族但面不同（不是 `change status`），本任务没动它；
  真仓库里 `P232` 这类老分支在那里仍会显示「领先 N」。
- **没有在全量门禁里验证**（见上面的 Notes）：本改动落到的段是 §12e，消费面批次覆盖了 12f/12i/12j/4b/24/20/22/11i/0e；
  没跑的 121 个段键在选段输出里点名列出了。
- **`--paths` 选集偏大**：改 `common.sh`/`cmd-status.sh` 会选中 65 个段（这两个文件是共享面）。本次按任务书
  验收口径跑的是 `--select`；PM 复验时如果想要「改动 → 选段」的完整口径，那是 P243 那条线（路由/产品侧路径
  的选段登记），不在本任务里。
- **路径带换行时人读输出的形状**：判定逐字节精确（夹具里有这条路径，`unmerged 5/5` 把它算进去了），但若它
  恰好落在 `partial` 的前三条点名里，消息里的换行会被转义成可见的 `\n`（否则一条 blocker 会被拆成两行）。
  没有把路径整体 C 转义的选项：那正是 F1 的病。
- **同族但未改的其它路径输出点**：`team_committed_report*` 用 `git ls-tree -r --name-only` 取报告文件名，
  同样受引号影响；但它的输入是 `docs/team/reports/<任务 ID>-*.md`（ID 与 agent 名是看板/配置里的 ASCII 名），
  与分支内容无关，本次不动（若以后允许非 ASCII 的任务 ID，这两处要一起改）。判据那一处（本条任务的靶子）
  已全部走 `-z`。
