## 结论（先看这里）

**它是真竞态，不是判据写错，也不是「机器忙」。驱动的红侧与「多半绿」是同一个窗口的两头。**

门禁运行会给自己在 `<lock>.runs/<pid>.run` 里登记一条，删它的是 EXIT trap（`cleanup`）。旧树里这两件事
隔着 **711 行**：

```
:678  登记写出（gate_lock_register_run）        ← 登记从这一刻起可见
      …  临时根创建、运行指纹（git status）、段落守卫、tmux 隔离、假 pi 准备 …
:1393 trap cleanup EXIT 装好                     ← 从这一刻起才有人删
```

TERM/INT 落进这段窗口（19 世纪式的前导，本机实测 200ms～数秒），进程按默认动作退出、EXIT trap 还没装 ——
那条登记就**再没有主人删**。于是判据（等 `.runs/` 变空）等满 300 秒（1500×0.2s）才红。

判据本身还有第二处毛病，它把同一个 bug 变成噪声：它等的是**一段固定的 300 秒**，而不是一个确定的状态。
登记的主人是谁、什么时候死，是可以在进程表上确定看出来的（`wait` 返回 = 登记它的进程已被回收），
所以「再等一会儿看」既不是证据也不是容差 —— 它把一条一秒就能判定的红拖成五分钟。

一个提交收口两处（`11a81632`）：

1. **登记与它的删除从同一刻起算**：登记**之前**先武装一个只删自己那条的 EXIT trap
   （`_smoke_lock_drop_run_record`，`:638`），`cleanup` 装好后调**同一个函数**接手（幂等）；
   「两处都试」的删除逻辑由两份合成一份。自检出口（`SMOKE_LOCK_SELFTEST_CHILD`）显式
   `SMOKE_LOCK_RECORD=0` —— §34b② 要读那条登记（它断言「顶层运行也在 `.runs/` 登记自己那条」），
   这与队列父进程已有的 `SMOKE_LOCK_KEEP_RECORD=1` 是同一个决定（`:708`）。
2. **⑫ 等一个确定的状态**：判据改成 `wait "$P281NL_JOB"` 返回之后的即时检查，容差 25×0.2s=5s（`:16892`）；
   原来是 1500×0.2s=300s。不加大 sleep，不放宽判据（仍然是「`.runs/` 里一条都不剩」）。

`gate-lock.sh` **没动**：登记与删除的格式、写权、pid 复用判据一个字没改，改的只是「谁在什么时候负责删」。

## 二、竞态方向：受控探针（同一现场，只改「什么时候发 TERM」）

这条把「机器忙不忙」这个自由量拿掉了：同一段夹具（内层 `smoke.sh --select 0c`，0c 被注入成永不返回）、
同一个被打的进程（登记里那条 pid，也就是选段副本）、同一个等待方式。唯一变量是发信号的时刻：

| 变体 | 发信号的时刻 | 修前（`11a81632^`） | 修后（`11a81632`） |
|---|---|---|---|
| `early` | 登记**一出现**就 TERM（5ms 轮询；不给「轮询间隔」这个自由量） | **5/5 留下**（`left=1`） | 5/5 消失（`left=0`） |
| `late` | 等内层运行开出第一段（`trap cleanup EXIT` 已装好）再 TERM | 5/5 消失（`left=0`） | 5/5 消失（`left=0`） |

修前 `early` 的一次读数（原始一行）：

```
k=1 MODE=early detect=1584ms kill=0 waitrc=143 left=1 alive=no rec=3601575.run
```

`waitrc=143` = 被打的进程确实按 TERM 死了；`alive=no` = 它已经被回收；`left=1` = 登记还在 —— 也就是说
「登记随它退出消失」这件事在那一瞬间**确实不成立**，判据没有说谎，是产品那一瞬间真的漏了。

同一次 `early` 的内层日志只到父进程的选段头（副本自己一行都没来得及打），`late` 的内层日志已经到
`== #1 0 · 临时仓库`：**两种变体的差别正好是「副本有没有走过那段前导」**，这就是窗口本身。

## 三、判据方向（任务书 1.2）：它等的条件，与能不能等到一个确定时点

- 它断言的东西：内层运行自己登记的那条 `.runs/<pid>.run`，在它退出之后**不存在**。
- 旧判据等的条件：**300 秒内 `.runs/` 变空**。上限前 1.5 秒处还红过一次 `detect`（见上表），其余全靠
  「等」；它没有名字、没有身份、也没有「谁负责」——所以只能靠时间猜。
- 确定性的时点有两个，都读进程表就能判：
  1. `wait "$P281NL_JOB"` 返回 = 内层运行（以及它起的副本）已经被回收；
  2. 加上本次修复，那条登记在**主进程退出之前**一定被它的 EXIT trap 删掉 —— 于是 ①之后它就是确定消失。
- 所以新判据是「①之后立即检查，容差 5s（只覆盖 rm 与 ls 之间的文件系统抖动）」，不是「再等一会儿看」。
  300s 那个数原来的作用只是把一条已经确定了的红拖成五分钟，把形状藏起来（这点在红侧读数上很直观：
  同一棵树，改前红要 337s，改后红只 31s）。
