## 结论（先看这里）

**那 5 秒盖的是等待者自己的前导，不是持有者的寿命。** `flock --close -x "$P281_LOCK" sleep 5` 只做一件事：
保证「等待者从启动到第一次取锁」这段路上锁一直被别人持有。实测这段路 1.6s、到 exit 2 是 2.7s，而窗口给了
5.0s（起点在 0.4s 之后）——**前导慢 70% 就够把它撞穿**：等待者自己拿到锁、rc=0，本节两条断言假红。V79 §5.2
在 loadavg 26.9（32 核，已超过门禁自己给计时断言的 0.75×核 前提）时撞到的就是这两条。

**换成了确定性条件**（`2fc84763`，只动 §34b⑨ 这一处）：

- **就绪** = `flock` 的子进程开始执行 —— `--close` 下锁 fd 不进子进程，它只在**拿到锁之后**才跑，所以它一跑
  就等于「锁已被持有」（同时替掉了原来那句 `sleep 0.4` 的猜）；
- **放行** = `p281_waiter` 返回（`wait` 返回）之后本段写一个放行文件，持有者才退出。

等待者自己的 1s 上限照旧决定它 exit 2 —— 持有者不再参与任何计时，前导多慢都不影响判定。两处循环的上限
（30s 就绪 / 120s 放行）只用来防死等：耗尽时 `bad` 一行点名「没等到持有者拿到 <锁>」。

**证据（三条，都是跑出来的）**

1. 同一个**确定性替身**（把等待者晚启动 5s；替身化的正是被负载推移的那个量 —— 到达取锁点的时刻）：
   修前树 `✓123 ✗2`，两条红与 V79 §5.2 逐字相同；修后 `✓125 ✗0`。红绿两侧只有树不同。
2. **红侧**（都在最终 tip 上跑）：① 持有者不公布就绪 → `✗ 34b⑨ 没等到持有者拿到 …（30s 上限）→ 下面三条
   读数无效（这是「挂住」，不是「慢」）`；② 持有者拿到锁就退出 → 行为判据照样红（`期望 [2]，实际 [0]` +
   `找不到 [排队超限]`）。还原后绿。
3. **稳定性**：`--select 34b` 连跑五遍全绿（顺序执行、各自私有 `TMPDIR` 与私有锁），五次段尾见 §5。

**净零**：一条墙钟判据换成一条确定性判据，没有新增门禁段、没有新增夹具、没有加大任何秒数、没有删断言或
放宽判据。唯一的加法是 §3 那句 `bad` —— 任务书要的正是「上界耗尽时报没等到 X」，它替掉的是原来「等满
5 秒」那条隐含判据。

## 一、那 5 秒到底在等什么（先读代码，再量）

`§34b⑨` 的这一小节问的是一件事：**等待者会不会排队**。现场是一个真的 `flock --close` 持有者（它进程里
没有等待者的祖辈，登记里点的是另一个活着的进程 `$P281_NOTANC`），等待者是**真入口**：`p281_waiter` 用
`TEAM_SMOKE_LOCK_WAIT=1` 跑 `smoke.sh --select 0b`（`smoke.sh:16707`）。

等待者那一侧（`smoke.sh:507–566`）：取锁失败 → 打印「另一套全量 smoke 正在跑」（`:545`）→ `elapsed >= cap`
就打印「排队超限」并 `exit 2`（`:559`）→ 否则 `sleep 1` 再来一轮。`cap=1`，所以它必然在**第一次取锁失败
之后的第二个取锁点**退出。

实测（三遍、空闲，loadavg 3.2；探针每 5ms 看一次等待者的日志，`/var/tmp/p340-dev2/probe`）：

```
k=1 rc=2 arrive_at_lock=1615ms total=2682ms queue_line=1 limit_line=1
k=2 rc=2 arrive_at_lock=1728ms total=2786ms queue_line=1 limit_line=1
k=3 rc=2 arrive_at_lock=1636ms total=2698ms queue_line=1 limit_line=1
```

也就是：**窗口要盖住的是「等待者的前导」**（启动 bash、source 库、运行指纹那一套），不是子进程回收、
不是文件删除、也不是心跳写入 —— 这三样在这条判据里根本不存在。所以它等的过程**有可观测的完成条件**：
`wait` 返回（等待者已经被回收）。旧代码等的不是它，而是「反正它 5 秒内该走到」这个假设。

窗口的算术（修前）：持有者在 t≈0 拿锁、写记录、`sleep 0.4`，窗口到 t≈5.0s 关闭；等待者 t≈0.4s 起跑、
t≈2.0s 第一次取锁、t≈3.1s 退出。余量 1.9s ≈ 整段 2.7s 的 70%。V79 §5.2 的那两条红就是这个余量被吃掉的形状。

## 八、边界与没做的

- **只跑了 `--select 34b`**（任务书这样要求；全套门禁明写不要跑）。`34` / `34c` / `34d` 这次没重跑：改动只落在

## 九、净零怎么算的

拔掉：一条 5 秒窗口判据（`sleep 5`）＋一处 0.4 秒猜（`sleep 0.4`）。
换进：两处「等到一个事实」（就绪文件 / 放行文件）＋一处上界耗尽时的 `bad` 行。
没有新增门禁段、没有新增夹具文件、没有新增检查器、没有加秒数、没有删断言。判据强度：旧的是「等待者 5 秒
内该走到」；新的是「等待者活着的时候锁必须一直被持有，且它必须排队撞上限」——前者会随负载假红，后者与快慢无关。
