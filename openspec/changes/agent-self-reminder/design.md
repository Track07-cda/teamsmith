## Context

See `proposal.md`. P385 §9.1 and V111 §5.1 establish that Pi 1.4.0 `sendMessage` returns `undefined`, can defer or re-enter, and that an ID-bearing `message_start` is observed in both idle and busy-follow-up cases. It is not a durable session receipt, model-request receipt or completion receipt. A preceding extension handler can delay our handler after Pi emits the event. The present `team_watch_once` returns on Standby, and `team_pm_start` normally passes `@pm-prompt`; that prompt begins ordinary work. The present ordinary inbox journal and Outbox have different contracts and remain authoritative for their own messages.

## Goals / Non-Goals

The design decides the state authority, actual observation, concurrency, recovery and explicit limits needed to implement the settled MVP. It does not build a general scheduler, model autonomy into the transport, guarantee end-to-end exactly-once, change Pi internals, extend `/team` with a tool, or promise service while Pulse is stopped. An unprovable Standby ordering is a visible conservative exception to automatic exit, not an assertion that the newer generation was exited.

## Decisions

### 1. One snapshot is the authority, including Standby

The project resolves its physical main root and its one configured project-state root using the existing identity rules. A project's default is `<main>/.pi/team/state`; a legitimate `TEAM_STATE_DIR` override remains supported. All cooperating processes must use the **same canonical real path** for that project, not their `TMPDIR`. Pin the effective override in a project-local, atomically created state-root locator under `<main>/.pi/team/` before the new authority can be used; compare a caller's resolved state root to the pinned value and fail visibly on mismatch rather than create a second authority. An isolated fixture uses its own project root and locator; a foreign project root/override is rejected. The locator records path and project identity, not reminder data. An absent locator is initialized under the fixed project-local locator lock; an override change requires an explicit quiesced migration, never silent selection by whichever later process happens to start. Production launchers pass the verified state root to Pulse and Pi. This is necessary because today's state-dir environment override can differ between unrelated processes.

Under the canonical state root, `reminders/state.json` is the **only** Reminder delivery/resend authority. It also carries the authoritative Standby generation and reason, so observation, automatic off, consumed right and audit commit in *one* snapshot. It is versioned (`version: 1`, project UUID and canonical identity, next reminder/batch/queue sequence and retention high-water). A reminder contains stable `rem-<project UUID>-<sequence>` ID, owner `pm`, creator/source (`cli` or verified `pm-tool`; CLI use is not proof of a human caller), optional task reference and key, creation time, original normalized time request, UTC due instant, complete UTF-8 message, durable phase and transition/audit fields. A batch contains a unique ID, frozen ordered members and source per member, queued times, pre-send intent, bound Standby generation or `off`, target Pi session/process generation, correlation nonce, right state, observation and auto-off result. Every allocated ID is never reused; the project UUID prevents same-named projects from matching.

All production readers and writers of Standby move through the shared state API: `team_standby_on/off`, `team_in_standby`, reason/status/panel, patrol and death handling, CLI/tool add/cancel, Pulse admission/recovery and watcher intent/observation. Panel actions already call CLI. On first upgrade, acquire the same lock, import a legacy `state/standby` marker exactly once as a new on generation with its reason, or off if absent, then atomically publish the snapshot before retiring the marker. Readers use the snapshot, not a marker cache. A torn/invalid snapshot, unsupported version, missing identity or failed import blocks mutation and is diagnosed; it is never silently replaced by an empty store. Upgrade requires quiescing old Pulse/PM/CLI writers: an old binary that still writes the legacy marker cannot participate in this protocol. No reinitialization is required; the human-controlled upgrade/restart procedure is in the migration plan.

Each state transaction acquires the permanent regular file `<canonical-state>/reminders/authority.lock` with the OS `flock` utility, reads and validates the current snapshot, performs a bounded mutation, writes a same-directory unique temporary file, `fsync`s it, atomically renames it over the snapshot and `fsync`s the directory before reporting success. The lock file is never unlinked or renamed. An atomic creation/lock at `<main>/.pi/team/reminder-locator.lock` serializes locator establishment first; acquire locator before authority, never in the reverse order. Bash invokes `flock -x -w <bounded-wait> <lock> <transaction-helper> ...`; Node invokes the **same** `flock` command and same JS transaction helper via `spawn`, passing request data on stdin, not shell interpolation. The helper is the complete read/modify/write transaction; no hand-rolled Node `mkdir` lock is assumed interoperable with Bash. The `flock` parent and child keep the locked open-file description until the transaction exits; a killed owner releases it when the last inherited descriptor closes. Never use `--close`, remove the lock file, or run Pi, wait for a model, wait for a callback, or do a patrol while holding it. An idle synchronous Pi callback can therefore acquire the lock without deadlock. Lock timeout, missing `flock`, unsupported locking, write/fsync error and corruption are explicit errors, never unprotected fallback. The local scratch proof in the P387 report tests the proposed Bash/Node `flock` shape and owner death, not the eventual production implementation or all filesystems.

The JS runtime is already required; `flock` is an additional OS utility for this shared transaction, not a scheduler dependency. Existing `replies.mjs` and gate locking already use it, but projects on systems lacking it previously could use Standby: they now receive a visible error on Standby mutation as well as Reminder mutation until it is installed. This is a deliberate compatibility cost of preserving both immediate Standby and crash-safe cross-language ordering; no-reminder behavior is unchanged where the dependency is present. Do not silently downgrade to unlocked writes. Doctor gives the remedy. If the platform cannot provide this lock, the feature cannot honestly claim this contract.

### 2. API, limits and lifecycle

`team remind add --after <duration> --message <text>` or `--at <instant>`, `list`, `show <id>`, `cancel <id>`, and `resolve <batch-id> --ack-unknown` invoke the same state helper as `team_remind` actions `add/list/show/cancel`. Tool input contains no project, owner, sender, state path or arbitrary recipient; CLI derives the project from its verified runtime context, while the tool additionally requires the verified PM session on **each** call. `show` displays the batch ID and all members. `resolve` is an explicit CLI acknowledgment for a human/operator who has inspected the **whole** unknown batch; it atomically burns its single automatic-off right, closes all its unknown members and returns their IDs without resending. It does not assert that delivery did or did not happen. A new reminder, if wanted after investigation, receives a new ID. Listing exposes full text, source and status; history/unknown is distinguishable from work completed.

Exactly one of `at`/`after` is required. `at` is a strictly valid RFC 3339 date-time with `Z` or numeric offset; normalize it to UTC and reject missing zone, invalid date or past time. `after` is a positive integer plus `s`, `m` or `h`, computed **once inside the locked create transaction**. Both forms must be at least 30 seconds in the future at first creation; zero, overflow and shorter intervals are rejected with an explanation. Equal-key concurrent requests are checked before recomputing a relative deadline: while the key is active, an identical normalized request (same original time form/value, full message and optional task) returns the original ID and fixed due; a different request returns key conflict. A key remains reserved for scheduled, queued, intent and unknown records; observing or cancelling releases it. Reuse after release creates a new ID, so retrying a previously terminal create with the same key is **not** globally idempotent; callers can `show` the original ID. This is an explicit bounded-scope trade-off, not an exactly-once claim.

Only two new configuration knobs: `TEAM_REMIND_MAX_ACTIVE=100` (includes unresolved intent/unknown) and `TEAM_REMIND_MAX_BYTES=16384` UTF-8 bytes per message, positive integers with validation. Reject invalid Unicode, NUL, empty text or oversize explicitly; never truncate text on storage, display or delivery. A fixed rolling limit of 20 successful creates per 60 seconds per project, a 30-second minimum delay, at most 8 reminders per batch, and at most one batch submission per 5 seconds bound bursts without a quota framework. Idempotent key hits do not consume the creation limit; atomic timestamps survive restart. If wall time moves backwards, do not free the rate window until the recorded window has actually expired. The exact refusal names the reason and next eligible time. Limits do not authorize evicting active or uncertain records.

Durable phases: `scheduled` (not yet admitted), `queued` (Pulse committed a queue sequence and actual enqueue time), `intent` (one whole batch frozen before the call), `observed` (correlated Pi event durably committed), `unknown` (intent exists but observation is not provable), `cancelled`, and `resolved` (explicitly acknowledged unknown). `due` is a clock-derived view of scheduled, not an enqueue record; `held` is a displayed reason attached to queued/unknown, not a second queue. Sort admission by `(due, reminder sequence)` and assign monotone queue order in one transaction; dispatch queued items in that order. A repeated scan never creates another queue entry. Record the current Pulse instance's start instant; mark an item overdue if its due predates that start or its admission lags due by more than 30 seconds. Normal sub-30-second polling delay is not misleadingly labeled overdue. `cancel` serialized before intent makes scheduled/queued cancelled and repeat cancellation returns `already-cancelled`; after intent it returns `in-flight/unknown: cannot guarantee withdrawal`, and after observation returns `already-observed`. Missing/pruned IDs are reported distinctly. No cancellation aborts Pi or claims to retract a follow-up.

The delivery transaction freezes up to eight current queued IDs and their full text into **one** Pi custom message. It writes a single batch intent containing every member before invoking Pi; none can remain independently sendable after that commit. The intent includes a fresh correlation nonce, bound generation, verified target and timestamp. Only one batch is outstanding until observed or explicitly acknowledged; thereafter the next batch respects the 5-second spacing. The sending helper releases the lock before `pi.sendMessage({customType, content, details, display:true}, {triggerTurn:true, deliverAs:'followUp'})`; both content and details contain the batch/Reminder IDs, and content includes each full message, due, actual enqueue time, delivery-attempt time, source/task if present and whether it was overdue when admitted. `details` is not model-visible. No shell execution or typing into the editor is involved. The project and current state are rechecked by the PM rather than assumed unchanged.

Pi's return, synchronous catch, `before_agent_start` and an unrelated `agent_start` are not a delivery receipt. After an intent, process death, asynchronous error, restart, or 60 seconds without observation yields `unknown`; no automatic resend follows. While Pi is busy, this deadline describes uncertainty, not proof of failure, and a valid late follow-up can still arrive. A late valid observation can strengthen unknown to observed while the batch right remains unspent. An explicit unknown acknowledgment burns that right; a later event is recorded if retained but cannot reopen it or clear a newer Standby. An inability to prove who/what the event belongs to is visible as identity-unknown and cannot consume a right. A crash before intent is provably safe to admit/send again; after intent, absence of an event is never proof of non-delivery. A crash after snapshot rename but before the caller learns success is resolved by reading the snapshot, not repeating a stale transaction.

Keep all active/unknown records and all unspent batch rights indefinitely, counted against the active bound; reaching it rejects new creates and shows how to inspect/acknowledge unknowns. Retain terminal reminders/batches for at most the newest 1,000 terminal outcomes or 30 days, whichever removes them first, and bound the separate audit entries to the newest 1,000 or 30 days; compact in the same locked snapshot transaction without dropping evidence required by any active/unknown batch. Keep the project UUID, monotonically allocated sequence high-water, cumulative pruned count and retention boundary. Lookup checks active and retained records first; an absent issued ID at or below high-water is `history-pruned`, never a new or resendable ID. An unmatched/late event after pruning is ignored and diagnosed, never synthesized into a new queued reminder. Active old items are not evicted by advancing the terminal boundary; no second journal, ordinary `.deliver` floor, spool line or cache may independently authorize a Reminder resend. Ordinary inbox journaling and its floor stay unchanged.

### 3. Correlated wake and Standby generation

`standby on` increments a never-reused generation in the snapshot, even when already on; `off` records the manual transition. They wait only for a short local state transaction, never a Pi turn. At intent, bind the current generation or `off` in that same snapshot. The observation is Pi's public `message_start` for a `role: custom` message carrying the exact batch ID/nonce and member IDs matching a durable intent in the **verified current PM process and session**. For idle, this message enters the new run; for busy, the ID-bearing follow-up enters a later turn of the existing run. An unrelated run or a deferred action that has not reached that event is not a Reminder wake. The event is a positive run-entry observation only: no assertion about session fsync, a model request, model success or work completion.

The observer commits a single locked snapshot containing `observed`, event identity, consumed batch right, Standby result, and audit with batch ID plus every Reminder ID/source. If the bound generation is still the current on generation, it switches it off in that **same** atomic snapshot and records `auto-off`; ordinary patrol resumes by its existing rules. If Standby was already manually off, it records `already-off`, never inventing an automatic off. If the bound value is `off` or an older generation and a newer on generation now exists, it records `generation-ambiguous/preserved` and does not clear it. Repeat or late callbacks cannot spend the batch right again; all members share that one right, including after restart.

| Interleaving | Proven result |
|---|---|
| G1 on → intent binds G1 → observed while G1 is current | Commit observed + off G1 + one audit atomically. Normal success is not unknown. |
| G1 → intent G1 → Pi emits message event → another handler delays ours → manual off/on G2 → our handler | G2 differs from G1; preserve G2, record observed and ambiguous. Never sample G2 as the bound generation. |
| G1 → off/on G2 → intent binds G2 → observed while G2 current | Off G2 once: G2 definitely preceded intent and hence the wake. |
| G1 → intent G1 → off/on G2 → Pi emits message event → our handler | The handler sees the same facts as the delayed-handler row; the public event has no independently trustworthy cross-process event-order token. Preserve G2 and explicitly report ambiguity, although in this particular hidden ordering the wake followed G2. |
| Batch A+B observed and off G1 → manual on G2 → duplicate/late member event or restart | Right already spent; G2 stays on, no second off. |

The fourth row is the unavoidable conservative boundary under these public observations: a bound pre-send generation avoids deleting a later human decision but cannot prove a G2 entered between intent and the actual event was earlier than that event. Do not report it as an automatic exit or general D204 success. This is narrower than making every successful wake unknown; a reviewer must judge the disclosed boundary against D204 before Apply. No timestamp on message creation, callback-time generation, `ctx.isIdle()`, or API return can prove the missing order.

One snapshot makes observation/off/audit atomic to concurrent readers. If the process dies before that commit, intent survives and becomes unknown; after the commit, the same snapshot contains both off and the audit, so replay is a no-op. An error after rename/fsync uncertainty is reported and recovery rereads the snapshot: either the atomic result is present or it is not; never invent an audit. A newer generation always wins. Unknown identity, manual off/on, duplicate events, compaction and process restart do not create a new right.

### 4. Pulse and Reminder-only recovery

Both existing Pulse execution shapes own one lightweight 10-second timer that reads the bounded state snapshot and commits due IDs. This is not another daemon and never runs the full report/board scan or calls a model. Console's existing Node panel uses its timer and asynchronous child management; headless changes its existing Pulse loop to own the same lightweight tick while its ordinary `team watch --once` is one managed child. There is at most one full patrol and one Reminder recovery decision in flight per Pulse. Child status/reaping, timer cleanup on shutdown and a missed-tick recheck are explicit; shutdown kills/reaps only its own child. Due admission continues during a long patrol. If a due batch needs recovery while patrol/recovery is running, set one coalesced pending-recheck bit; when that operation ends, run one **Reminder-only** recheck immediately, not a second full patrol or ordinary nudge. Recompute from the authority after restart; no hint/index is trusted as the only source. Even if the PM is stopped or slow to start, normal conditions (Pulse alive, clock and storage healthy, lock available and OS scheduling responsive) target durable `queued` within 30 seconds of due. This is not a hard real-time guarantee or a promise about Pi/model start. No Reminder produces no extra model turn and no extra full patrol.

A separate, narrow `reminder-recovery` decision runs only when the authority has an eligible queued, not cancelled/intent item. It calls the same factored PM state, project identity, `starting`, continuity, window ownership, capacity, restart-attempt and successful-restart quota checks as normal patrol; it cannot claim success when any guard refuses. `starting` means wait, never respawn again. A running verified PM receives no ordinary nudge for this queue. When PM is absent and all existing guards pass, use the existing guarded spawn/continuity code in a **prompt-free Pi mode**: `pi` with the usual validated resume arguments and PM extensions but **without** `@pm-prompt` or any replacement initial user/model prompt. Start the watcher, then let it obtain and send the queued Reminder through the direct path. During this recovery, suppress replay/nudges of ordinary pending digest/inbox work until the correlated Reminder wake and successful generation-checked off; no pending backlog is included in the startup message. If the wake never arrives, leave Standby on, report queued/intent/unknown and do not send a generic startup prompt. Explicitly directed ordinary Outbox traffic retains its existing independent authorization and drain/`--now` behavior, and is not reclassified as a Reminder or ordinary patrol backlog. If necessary, separate that traffic from the suppressed backlog within the existing watcher, not by globally disabling Outbox. External human input or independently directed notifications are not claimed to be stopped by this reminder-only mechanism.

The P387 scratch probe actually resumed a prior session in real interactive Pi 1.4.0 in a private tmux server with no startup prompt, then a timer extension emitted a correlated custom message and the controlled provider received its complete text; the seed and resumed session IDs matched. This proves the public handoff shape locally, not PM identity/guards, real project's extensions, Standby or real-model autonomy. Custom PM adapters without the Pi watcher/observation contract remain held with a visible unsupported diagnostic; they must not be started with the ordinary prompt merely to simulate success. Once observed and Standby is provably off, ordinary work follows existing rules; if a newer generation is preserved, its normal Standby suppression remains in force.

### 5. Tool injection and diagnostics

Add a separate `team-remind.ts` in the PM's existing explicit `team_pm_pi_args`; do not inject it into workers or add a tool to `/team`. At `session_start`, project/session transitions and reload, verify physical root, current tmux session and PM pane, process/session generation and project configuration. Do not infer authorization solely from cwd, caller-supplied env or a forged owner. Valid PM registers `team_remind` with `exposure: direct`; invalid context never registers, or re-registers the same name with `exposure: hidden` and removes it from active tools if it was previously registered. Pi has no tool-unregister API. Every execute call re-verifies the same identity and fails before state access if stale or mismatched. Discovered/global copies loaded in an ordinary Pi or worker must likewise be hidden/refused.

Publish a small, freshness-bounded local capability evidence record containing physical project, PM seat, PID plus process start identity/launch nonce, session ID, extension version, state-root identity, timestamp and reported registration/exposure or explicit load error; refresh on session lifecycle and remove only one's own record on shutdown. `team doctor` correlates that record with existing PM process/launch proof: `not running`; `running but no/freshness-expired/mismatched evidence` (unknown, not proof of missing tool); `explicit load failure`; or `extension reported registered/active at <time>`. An explicit load failure must be backed by a current launch's publicly reported loader error naming the extension, or by the extension's own bootstrap error record. If the extension never executes and no attributable loader error is available, absence of its record is only unknown. It cannot query another Pi process's `getAllTools`, prove current model declaration after a loadout, or assert actual tool use. Custom adapters report capability unknown/unsupported. No new TUI visualization.

## Risks / Trade-offs

- [Concurrent Standby generation between intent and event] → Preserve newer generation and expose the ambiguity; automatic exit of that actual wake cannot be proven in that case. This boundary is a proposal-review decision, not an implemented guarantee.
- [Additional `flock` dependency] → Fail visibly and diagnose; never turn a lock failure into an unlocked write. A system lacking it loses automated Standby mutation until repaired, including without Reminders.
- [Uncertain send] → No blind resend; active unknowns can exhaust the configurable bound until explicitly inspected and acknowledged. This is preferable to hidden duplicates.
- [Storage/lock/fsync failure or old mixed writers] → Fail closed, retain evidence, require repair/quiesced migration. Atomic rename alone is not a power-loss durability claim.
- [User/global extensions or independent human messages] → The prompt-free handoff prevents this feature's generic startup work, not arbitrary external behavior in Pi. Real integration tests must exercise the supported extension set.

## Migration Plan

After proposal acceptance and separate authorization, quiesce old PM/Pulse and other project writers; back up the existing runtime state, validate `flock`/JS and the intended canonical state root, upgrade all writers, migrate the legacy Standby marker under the lock, then start the new Pulse/PM according to existing operations. No project re-init or automatic restart is performed by this proposal. Before rollback, quiesce the new writers and explicitly inspect/resolve outstanding intents and export the snapshot; a rollback helper recreates the legacy Standby marker from the authoritative current generation/reason and preserves the Reminder snapshot out of the old code's path. Old binaries cannot safely interpret or deliver outstanding Reminders; rollback suspends them and does not auto-replay. Verify marker, backup and stopped processes before resuming old code. Real deployment, rollback and any real-model calls require their separate authorization.
