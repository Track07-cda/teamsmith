## MODIFIED Requirements

### Requirement: Installed team instructions separate shared rules from role procedures without losing required duties

The generated AGENTS managed section SHALL be a short shared constitution and reading order for PM and workers, rather than a full PM operations runbook. The PM startup prompt SHALL retain the instructions needed to start, inspect pending work and make authorized dispatch/verification decisions without first loading every reference. The worker dispatch prompt SHALL remain self-contained on its assignment identity, worktree/branch, brief and ownership scope, security and cross-project boundaries, legal turn endings, evidence, report and applicable settled-delivery behavior. The daily skill SHALL retain its useful command/reference index; detailed procedures SHALL live in the existing skill references. The generated PROTOCOL summary SHALL point to those homes rather than become another detailed rule system.

This organization SHALL preserve every obligation and surface requirement already specified by dispatch, writing-discipline, key-replies, watchdog, verification, agent-adapters, boundary and this capability. A required short statement on AGENTS, the PM prompt, worker prompt or a reference MUST NOT become a bare link. In particular, role-specific organization is not permission to drop the specified writing duties, the marker-captured reply duty owned by `key-replies`, three-state ending/background contract, independent verification, category/recorded-model recovery, authorization or disk handover. The product SHALL NOT introduce a separate rule registry or prose-quality guard to enforce this organization. Rule preservation SHALL be judged by rule-by-rule reading and independent substantive review, not a keyword total, size budget, runtime benchmark or AI reviewer's score; size measurements SHALL be evidence only. This requirement does not change any dispatch, publication, lifecycle, model selection, capacity or gate-scope behavior.

Immediately after the role table, the default shared section SHALL give PMs of every model one short rule for proceeding only with work the user has already authorized, without asking again. It SHALL name checking facts, splitting and delegating work, making small reversible choices, coordinating corrections, arranging independent review and closing out authorized work. It SHALL direct the PM to stop at the proposal when the user only requested a proposal: agreement on the goal and scope does not authorize implementation. When a decision belongs to the user, the rule SHALL direct the PM to advance unaffected work first, then bring a recommendation and its concrete impact. The rule MUST NOT grant authority for new product trade-offs, scope changes, or unauthorized production operations, merges, pushes or releases.

The PM startup prompt and the daily skill’s PM loop SHALL point to the shared rule instead of restating it. The startup prompt and the daily skill’s adoption rule SHALL present the four existing separately recorded steps and their per-command preview and authorization as applying to Teamsmith tool-source upgrades, not as a routine PM workflow. Required local approval statements and the independent reviewer’s duties SHALL remain in place. The new shared text SHALL use the existing new-project generation and explicit existing-project refresh paths; the guidance MUST NOT imply automatic refresh, relocation of local rules, or that refresh writes only AGENTS.

The generated shared AGENTS section SHALL be the single complete rule for the PM’s standby decision. For projects that use the new default, the PM MAY run `team standby on --reason "…"` without asking again only when there is no work to advance, no task or verification is running, and no result is expected to return automatically. Project-specific standby rules take precedence; if the project reserves entry for the user, the PM SHALL leave it to them. Waiting only for a human decision may qualify under those conditions; an empty board or a turn ending alone does not. The guidance SHALL leave manual `team standby off` to a human, state that standby suppresses ordinary Pulse wake-ups, and preserve the existing exception for an actual correlated scheduled Reminder wake and its provably bound current standby state. It SHALL NOT introduce a new automatic state change.

In the PM startup checklist, standby guidance SHALL only say to start Pulse if Pulse is down and the PM is not on standby. The later PM paragraph and the generated PROTOCOL summary SHALL point to the shared standby rule; the daily skill and reference guidance SHALL NOT grant conflicting standby authority. The PM’s existing legal turn endings and instructions to return on background completion SHALL remain. The new default applies to new projects set up with the revised instructions or existing projects that explicitly adopt them. Changing the tool source or restarting Pulse alone SHALL NOT be presented as replacing an existing project’s instructions or a running session’s context.

#### Scenario: Each role can enter through the shipped instructions

- **WHEN** a reviewer reads the generated shared AGENTS section, PM startup prompt, worker dispatch prompt, daily skill index, generated PROTOCOL summary and their referenced procedures
- **THEN** the shared section gives the roles, boundaries and reading order; the PM has its startup commands and decision boundaries; the worker has its assignment and delivery essentials; and the command index resolves detailed procedures to existing references
- **AND** each statement another capability requires on a named surface is still stated there, even where that creates a short intentional duplicate

#### Scenario: Removing a required local statement is not accepted as slimming

- **GIVEN** a candidate diff that replaces a required local writing, publication or background-ending statement with only a reference link
- **WHEN** the rule-coverage read and independent substantive review compare the affected surface with its existing capability requirement
- **THEN** they identify the missing local statement as a preservation failure, irrespective of a smaller byte count or a green structural/behavioral gate
- **AND** the accepted remedy retains the required local statement, or returns the proposed obligation change for separately scoped delta review; it is not accepted under instruction organization alone

#### Scenario: Worker variants retain their applicable contracts

- **WHEN** local and remote worker prompts are rendered on the built-in Pi path and on custom adapter templates with and without the background-lane placeholder
- **THEN** each retains assignment/safety/evidence/report essentials and the three legal ending states, and delivery describes the actual local or PM-directed remote route rather than requiring a remote push or PR in local mode
- **AND** lane-tool instructions appear only on the paths that supply them, retaining the suspend default, normal completion harvest, bounded inline-wait exception and on-disk recovery evidence required by dispatch

#### Scenario: The default instruction distinguishes PM work from a user decision

- **WHEN** a reviewer reads the role section diff in the shipped AGENTS template
- **THEN** one brief rule after the role table assigns fact-checking, task breakdown, delegation, small reversible choices, corrections, independent review arrangements and closeout to the PM without asking again, only for work the user has already authorized
- **AND** the rule says that when the user asks only for a proposal the PM stops at the proposal, even if the goal and scope are agreed, and does not proceed to implementation
- **AND** the rule tells the PM to advance unaffected work before bringing a recommendation and its concrete impact, reserves new product trade-offs and scope changes for the user, and preserves authorization for production operations, merges, pushes and releases, with no model qualifier

#### Scenario: Startup and daily instructions keep authorization without prescribing upgrade steps for routine work

- **WHEN** a reviewer compares the PM startup prompt and the two changed passages in the daily skill to their prior text and the existing tool-source upgrade instructions
- **THEN** the startup prompt and daily PM loop point to the shared rule rather than copying it, and the two upgrade passages limit the same four separately recorded steps to tool-source upgrades and retain preview and authorization per command, including for configuration and the first fresh launch that reads it
- **AND** the startup prompt retains the warning that linked skills can read a changed shared source without an installer, the local shared-state approval statements remain explicit, and independent review is still assigned to a non-implementer

#### Scenario: The new rule does not change installation or refresh

- **WHEN** a reviewer reads the final source diff for the change introducing the proceed-within-authorization rule and compares its adoption description to the existing explicit-init refresh requirement
- **THEN** the diff changes only the three instruction sources, not the generation or loading paths; new projects use existing setup and existing project AGENTS files receive the rule only on an explicit refresh, with rules outside the managed markers preserved
- **AND** the description does not promise auto-refresh, automatic relocation of local rules inside the markers, AGENTS-only writes, or automatic updates to running sessions

#### Scenario: Standby entry has one default rule and does not bypass project policy

- **WHEN** a non-author reads the final AGENTS template, PM startup prompt, daily skill, PROTOCOL template, affected reference and README passages, and the ordinary Pulse message sent to a running PM
- **THEN** the shared text clearly permits PM entry with a reason and no further approval under the adopted default when there is no work to advance and no task, verification or automatic result outstanding, but defers to the user where project rules reserve the decision
- **AND** the text permits a wait only on a human decision under the same conditions, does not treat an empty board or a finished turn as sufficient, and distinguishes waiting for background completion from entering standby
- **AND** the other passages do not grant competing authority; the startup checklist says to start Pulse only if it is down and the PM is not on standby, and the human exit, ordinary Pulse suppression and existing actual Reminder exception are unchanged
- **AND** the ordinary Pulse message keeps its existing prefix, pending summary, digest instruction and language, dropping the standby command and wake-up promise with no replacement suffix
- **AND** the final diff changes only the named instruction sources and that one message string, not generation, loading, or runtime behavior such as counts, delivery, queueing, deduplication, recovery or standby/Reminder handling; the adoption description does not promise unattended project, state or session changes
