# seat-interrupt-entry · design

合同文本在 `specs/boundary/spec.md` 的两条 ADDED 里；本文件写**为什么这么判**、被否掉的备选、以及明说的边界。
数字全部来自本 worktree 的只读实测（读 `tmux capture-pane`、`stat`、`state/*.env`、既成实现），不写盘、不发信号。

## 0 三条事实基础（整套做法由它们决定）

1. **投递只在回合边界生效**（机制缺口，账本 D188）：`team say` 写给席位的消息要等它的回合结束才进上下文，
   所以一个 18/16 小时的单回合里，PM 的两条消息（含已复现的根因）一条也读不到。缺口因此不是「消息不通」，
   而是**没有一条能结束那个回合的正式入口**。
2. **回合在跑 ≠ 它在落盘**：2026-10-15T23:32:39Z 实测 `dev`，窗口显示 `Elapsed 53m 5s` + `⠙ Working`，而它那次
   会话的会话文件 `stat` 是 2112882 字节、mtime 22:39:31Z（3188 秒之前），20 秒后再采仍是同一字节数。反过来说，
   **「多久没有落盘」是今天就能读出来的一个数**，而且它正好对上 D188 的症状（长时间没有提交、没有改动工作树
   文件）。同一个读数也说明为什么它只能当**提示而不是判据**：我自己的会话文件在一个回合中途才写一次——写盘
   节奏由 Pi 决定，不由我们决定。
3. **同一会话 id 跨进程死亡继续追加**：`dev` 那次会话的文件是 03:36 创建的，而派单记录
   `state/dev.env` 是 `started=2026-10-15T22:38:58Z`、`mode=continued`、同一个 `sid=`，启动时 `sid_bytes=2103032`
   之后长到 2112882。所以「杀掉进程 → `resume` 回到同一会话」不是设想，是这台机器上今天已经发生过的路径。

## 1 与 `long-job-suspend` 的关系（任务书要求写清）

两者管的**对象不同**，机制不重叠：

| | 长**作业**（`background-jobs`，已归档） | 长**回合**（本变更） |
|---|---|---|
| 是什么 | 席位用 `team_bg_run` 起的 detached 作业 | 席位正在跑、还没结束的这一个回合 |
| 账本 | `state/bg.log`（`start` / `wait` 两类行） | 回合没有账本行 |
| 叫醒 | 完成时叫醒席位（挂起是第三种合法回合结束状态） | 没有叫醒，也没有「结束」的入口 |
| 本变更做什么 | **什么都不做**：不读 `state/bg`、不碰车道记录、不改 `[auto·suspended]` 标签 | 加一条结束回合的入口 + 一次审计 |

一个直接的后果写在 §9(b)：被打断的席位那条车道上在跑的作业**不受影响**（它们是 detached 的），本变更**刻意
不**在信号路径里再实现一遍「哪些作业在跑」的判据——`long-job-suspend` 已经把续跑后的第一件事定成「先查
`state/bg.log` / `team bg list` 再继续」，重复一遍判定只会多一套可能判错的读数。

## 2 机制：为什么是「按 pid 的 SIGTERM → 有界 → SIGKILL」，然后由 `resume` 回同一会话

**选中**：把该席位**自己那个 agent 进程**（pid 由它的窗口证明，见 §3）`SIGTERM`，有界 5 秒后仍活着才
`SIGKILL`；窗口留给 `resume` 去替换。这与 `reap` 用的是同一套信号纪律与同一个 5 秒有界上界。

**为什么信号对象必须是那个 pid，而不是一个 pane 上的按键**：

- 契约要的是一件事：**那个回合结束了**。`kill` 到具体 pid 表达的就是这件事，且它是 `boundary` 已经固化过的
  形状（「信号只发给记录过的 pid」+ 发信号前复验），静态 lint（`signal-lint.pl`）也认它。
- 既有路径里 `dispatch`/`resume`/`teardown` 也会**替换窗口**、从而结束那个回合（`dispatch` 会打一行「旧回合会被
  打断」），但它们的**目的**是别的：不问你为什么、也不留打断记录。本变更不改它们的语义（design §9），差别的
  那一半正是本入口存在的理由——理由、审计、以及把窗口与磁盘状态留下。
- 调度器的 harness 在 agent 返回后 `exec bash`（`cmd-agents.sh` 的窗口包装），所以进程退出后**窗口还在**、
  里面是一个 shell；存活判据 `team_agent_alive_in_pane` 因此判「不是活着的席位」，`resume` 就能照它既有的
  路径替换窗口、用同一个 `--session-id` 重新进入同一会话（§0.3 的实测）。

**被否掉的备选**：

- **`tmux send-keys C-c`（往 TUI 敲一个中断键）**：它是对**一个 pane** 的动作，不是对一个 pid 的动作——落在
  `boundary#Signals go to a recorded pid…` 的另一侧；而且它把「回合真的结束了」这件事交给 Pi 的键位语义（工具
  看不到它是否生效，也无法在发信号前复验对象）。一个「看起来温和」的动作如果**不能证明回合结束了**，反而比
  一个能证明的动作更危险：PM 会以为席位空了，然后投递仍然排在一个没结束的回合后面。
- **`tmux kill-window` 整个窗口**：带走现场（窗口尾屏是事后诊断的唯一载体），而且它是一次**破坏性 tmux 调用**
  （要过 `boundary#A destructive tmux call is decided by the object it targets…` 的目标判定与调用日志）。我们要
  的只是「回合结束」，不是「窗口消失」；窗口消失还会把 `resume` 的替换路径变成新建路径（收益为零）。
- **打断后自动 `resume`（或 `--resume` 一把梭）**：两个动作的前提不同——打断的前提是「对象是那个被证明的席位
  进程」，续跑的前提是 `dispatch` 那一整套（会话身份守卫 `team_guard_resume_session`、叠任务守卫、分支/工作树
  状态、容量）。合起来只有两种坏结果：把第二个动作的失败藏进第一个动作的成功里，或者**先杀了再拒绝续跑**。
  命令打印那条路线（`team resume --agent <seat>`），两步各自可观测——PM 也可能想先看一眼现场、或者换一套说法
  再派。
- **工具自动判断「卡住了」（按无落盘时长自动打断或自动提示成红）**：无落盘 ≠ 卡住（§0.2 的反例）。判断权在 PM；
  工具只提供动作与证据（任务书的边界，也是 `watchdog` 一路的口径：读数不替人做决定）。

## 3 对象证明链：名册 → 记录里的窗口 → pane → pid → 身份与启动时刻

`team interrupt` 的入口参数是**席位名**，所以「对象是证明过的」必须写成一条链，而不是一次搜索：

1. 席位名必须在本项目名册里（`team_agents`），否则拒绝并点名名册；
2. 窗口取**该席位自己派单记录**里的 `window=`（默认即席位名）——这是今天 `resume`/`teardown` 已经在用的同一个
   字段；
3. pid 取那个 pane 里的 agent 进程（前台进程，或那个本项目 agent 可执行文件的直接子进程——`P217` 的既有形状：
   `bash <agent>` 时 pane pid 自己就在跑它）；
4. 该 pid 再按**普查用的同一套身份判据**读一次（`team_orphan_*`：进程自己的 `environ` 里 `TEAM_MAIN_ROOT` 属于
   本项目、`TEAM_ROOT` 等于派单记录里那个工作树、命令行命中本项目配置的 agent 可执行文件）；
5. 计划态打印 pid；执行态**发信号前**把 (3)(4) 连同**进程启动时刻**再读一遍，一致才发。

**为什么不按名字/模式找进程**：`boundary#Scripts select processes by recorded pid, and the lint keeps it that way`
与三次信号事故（按模式、按谓词、`pkill -f`）已经把这条路堵死。这里唯一的「名字」是**名册里的席位名**，它映射
到的是**本项目自己的记录与窗口**，进程仍然由身份与启动时刻证明——没有任何一步是「在进程表里找长得像的」。

**为什么拒绝集合这样切**（每条都给出路，PM 不必猜）：

| 目标状态 | 决定 | 出路 |
|---|---|---|
| 进程不在（回合早就结束了） | 拒绝 | `team resume --agent <seat>` |
| 窗口没了、进程还活着（孤儿） | 拒绝 | `team reap --orphans` |
| 名字不在名册 | 拒绝 | 名册（`team add-agent … --register`） |
| 另一个项目的席位进程 | 拒绝、**零点名** | 跨项目一律不做（`boundary#Actions stay inside the project…`） |
| 调用者自己或它的祖先 | 拒绝 | `reap` 的同一个判据（`/proc/<pid>/stat` 的 ppid 链） |
| 存活判据给不出结论（自己那个 tmux server 查询不到） | 拒绝 | 不猜（与普查的「未判定」同一方向） |

## 4 判据的两侧：新鲜窗口与审计里的证据

**新鲜窗口（默认 3600 秒）**：证据 = 该席位**自己的**最新磁盘活动：

- 它那次会话的**会话文件**（派单记录里的 `sid=` 解析出来的那份，`team_session_file` 的既有解析），mtime；
- 它工作树里 **git 报为改动**的文件（与审计里的未提交计数**同一次** `git status --porcelain -z` 读出来的路径）
  的 mtime，取最新的那个。

比窗口更新 → **拒绝**（不发信号、不写任何东西），拒绝里点名**读的是哪个文件、多大岁数、窗口多少**；`--force`
才越过它，而越权会写进那一行审计（`guard=forced`）。窗口用 `TEAM_INTERRUPT_FRESH_SEC` 可调，非数字退回默认值。

**为什么默认是 3600 秒而不是 60 秒**：两侧代价不对称。假阳（拒绝一次本该发生的打断）的代价是 PM 多打一个
`--force` 与一行越权审计；假阴（打断一个正在写的席位）的代价是它那些没提交的活。所以窗口按「宁可拒绝」定：
D188 的形状（16/18 小时无落盘）离 1 小时很远，而一个正在跑长门禁的席位通常在写工作树或写会话。

**为什么不把窗口登记成契约键**（`cmd-config.sh` 的 schema + `config.sh.tmpl` + `references/config.md` + 面板
`zh/en` 标签四面）：`references/config.md` 里出现的 `` `TEAM_*` `` 必须同时在 schema 里（`config-cli.sh` 的
completeness 走查是**双向**的），而 `TEAM_REAP_GRACE_SEC` 已经立了先例：**契约只要求「有界」，不要求一个可配
键**，所以它留在实现里、把默认值写进命令页。本变更照抄这个先例：**不新增契约键、不动面板数据面与重建产物**。
（门禁需要改窗口时用同一个环境变量，夹具与慢机器都用得上。）

**为什么 `--force` 不越过别的拒绝**：身份、存活、跨项目、名册、自身这五条不是「判断」而是「事实」；它们错了就是
打错了对象（`reap` 的拒绝集合与理由同源）。`--force` 的语义因此窄到一句话：**我看见了它在写盘，仍然要打断它。**

## 5 审计行：一次打断一行，字段逐个可核

`state/interrupt.log` 每次**授权的**打断恰好一行：

```
<ISO 时间戳> actor=<运行目录解析出的 actor> seat=<席位> pid=<pid> session_last=<会话最后落盘时间|-> \
uncommitted=<n> guard=<clear|forced> reason=<一句话> signal=<SIGTERM|SIGTERM→SIGKILL> outcome=<gone|failed|still-alive>
```

- **与 `reap` 的差异**：`reap` 的主体是**一个信号**，所以每个信号一行（SIGTERM 一行、SIGKILL 再一行）；本次的
  主体是**一次打断**，事后要回答的是「这次打断是否必要」，所以完成态只留一行，并在 `signal=` 里记实际发过的
  序列、在 `outcome=` 里记结果。
- **`session_last` 与 `uncommitted` 是发信号之前读的那一份**（任务书要的正是「打断前」的读数）：它们是事后判断
  「这次打断是否必要」的两个数。会话文件不存在时写 `-`（缺证据不编造，与普查的字段口径一致）。
- **被拒绝的打断不写审计行**：拒绝是读数（stdout 一行 + 退出码），不是动作。`reap` 的计划态同样不写它的审计
  文件——「没有动作就没有证据」是这一族的一致口径。
- **actor 从运行时目录解析**（`team_sender_resolve` 的既有规则）：解析不出来就**拒绝**，什么都不写、什么都不发
  ——审计的第一件事是「谁」，而身份不许猜（`notify` 的发送者纪律同源）。

## 6 理由投递：写进它自己的阅读顺序

发信号**之前**，理由写进两个地方：

- **该席位的线程**（`docs/team/threads/<seat>.md`）：席位被 `resume` 起来后读的东西是**提示词里那三步**（AGENTS.md
  → 它自己的 thread → 任务书），thread 正好在第二步。条目里写：谁、什么时候、为什么、以及**它该先做什么**。
- **该席位的收件箱**（`docs/team/inbox/<seat>.md`）：同一件事的**持久**通知行（收件箱这一面已经在
  `notify-and-inbox` 的合同里，本变更不新增标签类，只写一行）。

顺序是先写理由、再发信号，理由是**写不进去就拒绝**（不发信号）——否则就会出现「杀了它，但它续跑起来不知道为什么」
这一种坏结果。

**明说的边界**：工具能保证的是理由**落在**席位阅读顺序会读到的位置（thread 在第二步，且这是提示词渲染出来的
一行事实），**不能**保证一个活着的模型真的照做——没有任何门禁能验这件事。这与 writing-discipline 的立场同族：
措辞与阅读由读的人拿住，门禁只拿它能判的东西。

## 7 能力落点与任务切分

| 内容 | 落点 | 理由 |
|---|---|---|
| 入口、计划态、对象证明链、复验、信号、审计行、拒绝集合、读命令不打断 | `boundary`（ADDED ①） | 该能力是「谁能发信号、发给谁、留什么证据」的家（`reap` 就在里面）；写别处就是第二套说法 |
| 理由必填与投递面、新鲜窗口与 `--force`、工作树逐字节幸存 | `boundary`（ADDED ②） | 同一个动作的前提与副作用，放在同一个能力里，拒绝的理由与对象证明同源 |

**一个能力 = 一个 apply 任务**：`deltas:` 的单写者守卫按「同一 capability 的同一个 delta 文件」判，两个 apply
任务落在同一份 `specs/boundary/spec.md` 上就要 `--force`，所以本变更的 apply 切成**一个**任务：入口/判据/审计/
理由 + 夹具 + 门禁段接线 + 命令页与文档。它能被一个工作块做完的依据是**机器已经都在**（`reap` 的信号/复验/审计
形状、`team_orphan_*` 的身份判据、pane 侧的 pid 解析、`team_inbox_append`/thread 写入器、续跑守卫），新的只有
「读证据 → 判 → 记 → 发」这一段接线；夹具形态与 `tests/seat-visibility.sh` 的 reap 组同族。
独立 verify 由**没有写过本 change 的席位**做（写的人不验自己的活）。

**写集串行（要写进 apply 任务书）**：apply 要动 `tests/smoke.sh` 与 `tests/section-*.tsv`——此刻
`gate-lock-hygiene`（未归档）也在动同一批文件；apply 交付前 `git merge main`，冲突按两侧保留，语义冲突停下报 PM，
**不许**为了让门禁绿而删掉任一侧的段。

## 8 已知边界（明说，不当保证）

- **同一个回合里反复跑命令但从不落盘的席位**：新鲜窗口拦不住（证据是旧的）——这正是 D188 的形状，也是我们要的
  方向；代价是它同样不会拦住「在跑长门禁、刚好没写盘」的席位，那种情况由 PM 用 `--force` + 一句话理由越过。
- **只对一个 pid 发信号**：不整组、不按父子、不按名字（`boundary#Scripts select processes by recorded pid…` 与
  `signal-lint.pl` 只认 pid 精确形态，`reap` 同源）。一个回合里被 agent 起的**工具子进程**是否随它退出，是那个 CLI
  自己的关闭行为，本入口不保证也不检查：它的职责是「那个回合结束了」，不是「这台机器上没有别的残留」。夹具因此
  断言的只是**我们发过的那个对象**（恰好一个 pid）与它确实退出。
- **窗口留着、不是遗体**：调度器的 harness 在 agent 返回后 `exec bash`（`cmd-agents.sh` 的窗口包装），而本入口只对
  agent 的 pid 发信号、不碰那个 shell——所以打断后该窗口里是一个**活着的 shell**（`pane_dead=0`），`resume` 按它既有
  的「窗口已存在 → 替换」路径处理它，`dispatch#A dead pane is never a live seat…` 那套遗体证据**不**适用于这次停止。
  这次停止的权威记录是 `state/interrupt.log` 那一行（§5）。
- **被打断席位的后台作业不受影响**（detached）：作业继续跑、叫醒落进一个已经死掉的会话；续跑后按
  `long-job-suspend` 的纪律先查 `state/bg.log` / `team bg list` 再继续。本变更**不**为此在信号路径里再读一遍
  车道（§1）。
- **死因分类不认这次停止**：`watchdog` 的死因读取器是一个闭集词表（`quota|balance|rate_limit|window|auth|normal|
  unknown`），本变更不改它，所以这次停止在名册/巡检里大概率显示 `unknown`——它不给错的原因，而「为什么」由
  `state/interrupt.log` 那一行回答。改名册/巡检/面板的显示是另一件事（另一个能力、另一个变更）。
- **打断是进程级的**：TUI 里那一轮的回答与工具结果丢了（会话文件按它**已经写下**的部分保留），未提交的工作树
  文件逐字节还在。任务书的红侧 ② 就是这条：**打断不改工作树**。
- **一个席位一次**：不做批量（`--all` 之类）。批量打断是「一次决策作用于多个对象」，与「每一次打断都要一句话
  理由」的审计形状冲突；真需要时由 PM 逐条决定。

## 9 Non-Goals

- 不改 `resume`/`dispatch`/`reap`/`teardown` 的任何语义（只打印一条已经存在的路线）。
- 不做自动判断「卡住了」的启发式，不自动打断、不自动续跑。
- 不动 `ps`/`status`/`digest`/面板的数据面与既有行（读数面一行不改）。
- 不动别的项目的任何东西；跨项目一律拒绝、零点名。
- 不新增契约键、不动面板重建产物、不改死因词表。
- 不顺手改 `team bg` 车道、不重复 `long-job-suspend` 的机制。
